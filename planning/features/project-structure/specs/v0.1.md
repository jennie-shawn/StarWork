# StarWork 当前项目结构重整 SPEC

## 背景

当前 StarWork 项目已经从早期探索进入产品化阶段。旧结构里有三个历史产物：

1. `matters/`：用于记录事项推进过程。
2. 根目录 `参考资料/`：用于存放临时参考材料。
3. 根目录 `输出/`：用于存放草稿和确认成果。

这些目录在早期很有用，但现在会带来新的问题：

- 产品事实源已经收敛到 `product/`，但过程材料仍散落在 `matters/`。
- 功能 SPEC 平铺在 `product/docs/`、`product/core/`、`product/cli/`、`product/skills/`，缺少按功能点聚合的档案。
- 支线功能会同时涉及 Core、CLI、Skill、Docs、测试和验收，单独看任何一个目录都看不清完整上下文。
- `AGENTS.md` 仍然要求优先读取 `matters/registry.md`，已经不符合新的产品管理方式。

本 SPEC 目标是规划一次项目资料架构重整：

> 未来 StarWork 的产品事实、功能规划、讨论沉淀、参考资料、验收材料，都收敛到 `product/` 下；`matters/`、根目录 `参考资料/`、根目录 `输出/` 关闭，不再作为长期工作区。

## 设计原则

### 1. `product/` 是唯一产品事实源

StarWork 是一个产品项目，不再把“产品怎么推进出来”长期放在根目录事项工作区。

所有能影响产品判断、版本计划、能力边界、CLI、Skill、Core、Pack、文档、验收的材料，最终都进入 `product/`。

### 2. 实现目录和规划目录分开

实现目录负责“东西在哪里运行”：

- `product/core/`
- `product/cli/`
- `product/skills/`
- `product/kit-skills/`
- `product/packs/`
- `product/adapters/`
- `product/schemas/`

规划目录负责“为什么这么做、怎么验收、历史怎么演变”：

- `product/planning/`

不要把讨论过程、版本 SPEC、功能参考资料塞进实现目录。

### 3. 支线功能按功能点归档

知识库、多智能体、项目中心、init、doctor/upgrade 等都是独立功能。每个功能都应该有自己的档案入口。

不再让一个功能的资料散落在：

```text
product/docs/
product/cli/
product/skills/
matters/
输出/
参考资料/
```

### 4. SPEC 按版本管理

功能 SPEC 不应一直覆盖同一个文件，导致看不出历史变化。

每个功能的 SPEC 应进入：

```text
product/planning/features/<feature>/specs/
```

并按版本保存：

```text
v0.1.md
v0.2.md
v0.3.md
```

`index.md` 说明当前生效版本。

### 5. 过程材料不再按事项归档，而是按功能归档

过去：

```text
matters/<matter>/drafts/
matters/<matter>/notes.md
matters/<matter>/progress.md
```

未来：

```text
product/planning/features/<feature>/discussions/
product/planning/features/<feature>/references/
product/planning/features/<feature>/acceptance/
```

也就是说，不再问“这是哪个事项的材料”，而是问“这是哪个功能的材料”。

### 6. 根目录保持干净

根目录只保留项目运行和协作必要入口。

根目录不再新增：

- `matters/`
- `参考资料/`
- `输出/`
- `scripts/`
- 泛化临时目录

## 根目录职责

### `AGENTS.md`

根目录 Agent 协作规则。它回答：

- 这个项目是什么。
- Agent 进入项目后先读什么。
- 哪些目录是只读主库资源。
- 产品事实源在哪里。
- 新材料如何路由。

重整后，`AGENTS.md` 不应再把 `matters/` 作为默认工作区。

### `CLAUDE.md`

Claude Code 适配入口。它应继续指向 `AGENTS.md`，不单独维护一套冲突规则。

### `.starwork/`

StarWork 运行状态层。

只放机制状态，不放产品事实：

- workspace 配置
- skill 配置
- handoff 本地队列
- 运行状态

### `_系统/`

当前项目的协作和状态层。

保留：

- `_系统/上下文/`
- `_系统/任务/`
- `_系统/协作/`
- `_系统/主库同步/`
- `_系统/跨项目/` 或后续迁移到 `.starwork/handoff/` 的兼容状态

注意：`_系统/` 仍是项目运行和协作层，不承担产品资料归档职责。

### `identity/`、`lessons/`

主库快照，只读参考。

项目本地新增的可复用经验，如确实有跨项目价值，应通过主库回写流程处理，不直接随手改这些目录。

### `matters/`

迁移完成后关闭。

关闭含义：

- 不再新建 matter。
- 不再维护 `matters/registry.md` 作为当前事项注册表。
- 有价值内容迁入 `product/planning/features/` 或 `product/planning/archive/`。
- 原目录可以整体进入 `product/archive/matters/`，或迁移确认后删除。

### `参考资料/`

迁移完成后关闭。

处理规则：

- 与某个功能相关的参考资料，迁入 `product/planning/features/<feature>/references/`。
- 与整体产品方向相关的参考资料，迁入 `product/planning/references/`，如果后续需要该目录。
- 无长期价值的临时说明进入 `product/archive/` 或删除。

### `输出/`

迁移完成后关闭。

处理规则：

- 草稿类内容，迁入对应功能的 `discussions/` 或 `drafts/`。
- 验收报告，迁入对应功能的 `acceptance/`。
- 正式文档，迁入 `product/docs/`。
- 示例产物，迁入 `product/examples/` 或对应功能 `examples/`。

## `product/` 目标结构

### `product/core/`

Core 协议和能力定义。

放：

- 工作台协议。
- Kit 结构。
- Capability 定义。
- Profile。
- Preset。
- Runtime layer。
- Core 层 SPEC。

不放：

- 功能讨论过程。
- 用户阅读型 HTML。
- 功能验收报告。
- 临时参考资料。

### `product/cli/`

CLI 实现和命令级正式规格。

放：

- CLI 源码。
- CLI 测试。
- 命令 SPEC。
- 命令实现相关 README。

不放：

- 功能全貌规划。
- 与 CLI 无关的 Skill 讨论。
- 功能验收过程材料。

### `product/skills/`

系统级 StarWork Skill。

放：

- 默认可安装的 StarWork 系统 Skill。
- `starworkInit`
- `starworkDoctor`
- `starworkKnowledge`
- `starworkMultiagent`

边界：

- 系统级 skill 可以通过全量安装命令安装。
- Hub Kit 自带 skill、Project Kit 自带 skill 不放这里。

### `product/kit-skills/`

Kit 自带 Skill。

放：

- `starworkSpawn`
- `starworkAudit`
- `neat-freak`
- 其他随特定 Kit 分发、但不应默认系统级安装的 Skill。

边界：

- 这类 skill 不进入全量系统安装命令。
- 它们由 init、spawn、upgrade 或 Kit 分发机制放入工作台。

### `product/packs/`

Pack 定义。

放：

- Pack manifest。
- language files。
- rules。
- seed。
- Pack 自己定义的业务目录和工作流。

不放：

- Kit 底层协议。
- 系统级 Skill。
- 功能规划资料。

### `product/adapters/`

Agent 适配层。

放：

- Codex、Claude Code、Cursor、Trae 等适配规则。
- 适配模板。

### `product/schemas/`

结构化 schema。

放：

- Pack schema。
- Blueprint schema。
- Workspace state schema。
- CLI 输入输出 JSON schema。

### `product/examples/`

正式示例。

放：

- 示例工作台。
- 示例 blueprint。
- 示例配置。
- 用户文档中会引用的样例。

不放：

- 发布包。
- 临时测试输出。

### `product/releases/`

发布产物。

当前已有 `.gitignore` 应避免 release zip 或生成物反复干扰 git。

建议职责：

- 本地打包验证输出。
- 不作为产品事实源。
- 默认不提交大型构建产物。

### `product/docs/`

正式阅读文档。

放：

- 面向用户或 Agent 的指南。
- HTML 阅读稿。
- 对外说明。
- 当前路线图阅读版。
- 文档中心索引。

不放：

- 每个功能的全部历史 SPEC。
- 功能讨论过程。
- 大量参考资料。

`product/docs/` 可以链接到 `product/planning/features/`，但不承担功能档案职责。

## 新增 `product/planning/`

`product/planning/` 是产品规划事实源，承接过去 `matters/` 的长期价值，但按产品结构重组。

建议结构：

```text
product/planning/
├── README.md
├── roadmap/
│   ├── README.md
│   ├── current.md
│   └── history/
├── decisions/
│   ├── README.md
│   └── index.md
├── features/
│   ├── README.md
│   ├── knowledge-base/
│   ├── multiagent/
│   ├── project-center/
│   ├── project-init/
│   ├── doctor-upgrade/
│   ├── spawn/
│   ├── skill-distribution/
│   └── rules-memory/
└── archive/
    ├── README.md
    └── matters/
```

### `product/planning/README.md`

规划区总入口。

说明：

- 什么材料进入 planning。
- planning 和 docs、core、cli、skills 的边界。
- 如何创建一个功能档案。
- 当前活跃功能列表。

### `product/planning/roadmap/`

路线图和里程碑。

建议从 `product/docs/roadmap.md` 拆分：

- `product/planning/roadmap/current.md`：当前内部里程碑事实源。
- `product/docs/roadmap.md`：对内/对外可读版本。
- `product/docs/roadmap.html`：HTML 阅读版。

也可以先不拆，等文档规模变大后再迁移。

### `product/planning/decisions/`

跨功能产品决策。

例如：

- Project Kit 不包含通用业务目录。
- Matter 机制关闭，未来按功能档案归档。
- Kit Skill 和系统 Skill 分开管理。
- Knowledge 是能力，不是基础目录。

单功能内部决策仍放在该功能自己的 `decisions.md`。

### `product/planning/features/`

按功能点归档的核心目录。

每个功能一个文件夹。

标准结构：

```text
product/planning/features/<feature>/
├── README.md
├── specs/
│   ├── index.md
│   ├── v0.1.md
│   └── v0.2.md
├── cli.md
├── skill.md
├── core.md
├── docs.md
├── acceptance/
│   ├── README.md
│   └── YYYY-MM-DD-acceptance.md
├── decisions.md
├── references/
├── discussions/
├── examples/
└── archive/
```

#### `README.md`

功能总览。

必须包含：

- 功能是什么。
- 当前状态。
- 当前生效 SPEC。
- 相关实现位置。
- 相关 CLI。
- 相关 Skill。
- 待定问题。

#### `specs/`

版本化 SPEC。

规则：

- `v0.1.md`、`v0.2.md` 保存历史版本。
- `index.md` 指向当前生效版本。
- 大边界变化开新版本。
- 小措辞修正可改当前版本，但要在文件内记录变更。

#### `cli.md`

该功能涉及的 CLI 设计。

例如知识库：

```text
starwork knowledge init
starwork knowledge status --json
starwork knowledge check
starwork knowledge apply --blueprint
```

#### `skill.md`

该功能对应 Skill 的工作流设计。

例如：

- skill 何时触发。
- 怎么采访用户。
- 如何调用 CLI。
- 哪些动作必须让 CLI 执行。
- 哪些动作由 Agent 判断。

#### `core.md`

该功能涉及的 Core 能力或 Kit 调整。

例如：

- 是否新增 capability。
- 是否影响 Project Kit。
- 是否影响 Hub / Project Center。
- 是否影响 profile / preset。

#### `docs.md`

该功能需要哪些用户文档和 Agent 文档。

#### `acceptance/`

验收材料。

放：

- 验收标准。
- 验收报告。
- 复验报告。

#### `decisions.md`

功能内部关键决策。

只记录已经确定的判断，不记录完整讨论过程。

#### `references/`

参考材料。

可以放：

- 外部链接摘录。
- 竞品调研。
- 技术参考。
- 用户反馈原文整理。

#### `discussions/`

重要讨论产物。

放：

- 方案对比。
- 未定问题分析。
- 用户访谈整理。
- 旧 matter 迁移来的有价值讨论。

#### `examples/`

示例。

放：

- 示例目录结构。
- 示例 blueprint。
- 示例输出。
- 示例知识页。

#### `archive/`

功能内部废弃材料。

## 迁移规则

### 从 `matters/` 迁移

建议映射：

| 旧路径 | 新位置 |
|---|---|
| `matters/2026-05-09-starwork-core-v0.1-build/` | `product/planning/features/core-kit-pack-boundary/discussions/` 或 `product/planning/archive/matters/` |
| `matters/2026-05-09-starwork-project-bootstrap/` | `product/planning/features/rules-memory/discussions/` |
| `matters/2026-05-11-starwork-cli-v0.1-design/` | `product/planning/features/project-init/discussions/`、`doctor-upgrade/`、`spawn/` |
| `matters/2026-05-19-starwork-public-alpha-test/` | `product/planning/features/alpha-test/discussions/` |
| `matters/registry.md` | `product/planning/archive/matters/registry.md` |

迁移时不要机械搬完就算。

每个 matter 应分三类处理：

1. 已定稿结论：提炼进 `specs/` 或 `decisions.md`。
2. 有价值讨论：进入 `discussions/`。
3. 仅历史留痕：进入 `product/planning/archive/matters/`。

### 从根目录 `参考资料/` 迁移

当前只有 `参考资料/README.md`。

建议：

- 如果只是模板说明，归档。
- 如果未来有真实参考资料，按功能迁入 `features/<feature>/references/`。

### 从根目录 `输出/` 迁移

当前只有 README。

建议：

- `输出/草稿/README.md` 归档或删除。
- `输出/确认成果/README.md` 归档或删除。
- 后续不再使用根目录输出。

### 从 `product/docs/` 迁移

不是所有 `docs` 都要迁走。

迁移判断：

| 文档类型 | 保留在 `product/docs/` | 迁到 `product/planning/features/` |
|---|---|---|
| 用户阅读文档 | 是 | 否 |
| HTML 阅读稿 | 是 | 否 |
| 安装指南 | 是 | 否 |
| Roadmap 阅读版 | 是 | 可在 planning 保留内部事实源 |
| M2.x 功能 SPEC | 否，逐步迁移 | 是 |
| 功能备忘 | 否，逐步迁移 | 是 |
| 验收报告 | 否 | 是 |

例如：

```text
product/docs/m2.11-knowledge-capability-spec.md
→ product/planning/features/knowledge-base/specs/v0.1.md
```

`product/docs/README.md` 应只索引正式阅读文档，同时链接到 planning 入口。

## AGENTS.md 路由规则调整

根 `AGENTS.md` 应更新为新的项目路由。

### 进入项目后先读

建议改为：

```text
1. _系统/上下文/current-projects.md
2. _系统/上下文/decisions.md
3. _系统/上下文/product-principles.md
4. _系统/任务/current-work.md
5. product/planning/README.md
6. product/planning/features/README.md
```

`matters/registry.md` 不再作为必读入口。

如果迁移期间 `product/planning/README.md` 还不存在，则临时保留旧入口，但应标注 deprecated。

### 总路由规则

建议写入 `AGENTS.md`：

```markdown
## 产品资料路由

StarWork 产品事实源统一进入 `product/`。

- 产品实现进入 `product/core/`、`product/cli/`、`product/skills/`、`product/kit-skills/`、`product/packs/`、`product/adapters/`、`product/schemas/`。
- 正式用户文档和 HTML 阅读稿进入 `product/docs/`。
- 功能规划、版本 SPEC、讨论沉淀、参考资料、验收材料进入 `product/planning/features/<feature>/`。
- 跨功能产品决策进入 `product/planning/decisions/`。
```


## 迁移实施计划

### Phase 0：冻结旧入口

- 在 `matters/README.md` 标记 deprecated。
- 在根 `参考资料/README.md` 标记 deprecated。
- 在根 `输出/README.md` 标记 deprecated。
- AGENTS 先增加“旧目录不再新增内容”的规则。

### Phase 1：建立 planning 骨架

创建：

```text
product/planning/
product/planning/features/
product/planning/decisions/
product/planning/roadmap/
product/planning/inbox/
product/planning/archive/
```

并写入 README。

### Phase 2：建立首批功能档案

优先：

```text
knowledge-base/
core-kit-pack-boundary/
project-init/
doctor-upgrade/
spawn/
skill-distribution/
multiagent/
project-center/
rules-memory/
alpha-test/
```

### Phase 3：迁移高价值 SPEC

先迁移：

- `product/docs/m2.11-knowledge-capability-spec.md`
- `product/docs/m2.10-core-kit-pack-boundary-cleanup-spec.md`
- `product/docs/m2.8-workspace-naming-optimization-spec.md`
- `product/docs/m2.7-init-github-issues-optimization-spec.md`
- `product/docs/m2.6-alpha-core-flows-optimization-spec.md`

迁移后 `product/docs/` 保留跳转说明，或更新 `docs/README.md` 指向新位置。

### Phase 4：吸收 matters

逐个处理 matter：

1. 先读 `README.md`、`notes.md`、`progress.md`、`drafts/`。
2. 提炼结论到对应 feature 的 `specs/` 或 `decisions.md`。
3. 重要讨论放 `discussions/`。
4. 原始历史归档到 `product/planning/archive/matters/`。
5. 更新根 AGENTS，移除 `matters/registry.md` 必读。

### Phase 5：清理根目录

确认迁移后：

- 删除或归档根 `matters/`。
- 删除或归档根 `参考资料/`。
- 删除或归档根 `输出/`。
- 确认根目录只保留必要入口。

### Phase 6：更新文档中心

- 更新 `product/docs/README.md`。
- 更新 `product/docs/index.html`。
- 添加 planning 入口说明。
- 确保用户阅读文档和产品规划档案边界清楚。

## 验收标准

1. 根 `AGENTS.md` 不再把 `matters/` 作为默认推进工作区。
2. 新功能规划有明确入口：`product/planning/features/<feature>/`。
3. 功能 SPEC 按版本存放在 `specs/`。
4. `product/docs/` 不再继续平铺新增 M2.x 功能 SPEC。
5. `matters/`、根 `参考资料/`、根 `输出/` 标记关闭，且不再新增内容。
6. 至少完成一个试点功能档案，例如 `knowledge-base/`。
7. 开发 Agent 能根据 AGENTS 路由判断：
   - 写实现去哪里。
   - 写 SPEC 去哪里。
   - 写参考资料去哪里。
   - 写验收报告去哪里。
8. 历史材料没有直接丢失；要么提炼进功能档案，要么进入 archive。

## 建议先做的试点

建议用知识库功能作为第一个试点：

```text
product/planning/features/knowledge-base/
├── README.md
├── specs/
│   ├── index.md
│   └── v0.1.md
├── cli.md
├── skill.md

├── decisions.md
```
