## 2. 重新判断

`ISSUE-016` 的根因不是用户不懂某几个词，而是初始化一开始就把用户带进“配置流程”，却没有先完成产品认知。

新用户第一次接触 StarWork 时，脑子里的顺序通常是：

1. 这是什么产品？
2. 它能帮我做什么？
3. 为什么我现在要初始化？
4. 接下来它会带我做哪几步？
5. 会不会改坏我的项目？
6. 我每一步该怎么选？

上一版规划从“安全感”和“选项解释”切入是必要的，但还不够。新手体验必须先把 StarWork 讲清楚，再讲接下来要做什么，最后才进入 CLI 预览和写入。

## 3. 一句话目标

让第一次使用 StarWork 的用户先理解“StarWork 是什么、能做什么、接下来会发生什么”，再在有安全感的情况下完成初始化。

## 4. 新手第一屏

`starworkInit` 的第一屏必须回答三个问题：

1. StarWork 是什么。
2. StarWork 能帮用户做什么。
3. 这次初始化接下来会做什么。

推荐口径：

```text
StarWork 是一个给 AI 协作准备的项目工作台。

它不会替你写业务代码，也不是另一个笔记软件；它做的是把项目里的规则、任务、交接、资料和 AI 使用方式整理清楚，让 Codex、Claude Code、Cursor 这类 AI 工具每次进项目时都知道：
- 这个项目是什么；
- 现在正在做什么；
- 哪些文件能改，哪些不能改；
- 重要资料和交接记录在哪里。

接下来我会分三步带你完成：
1. 先确认这个工作台要服务什么项目；
2. 再预览 StarWork 准备写入哪些协作文件；
3. 你确认没问题后，我再正式写入并做一次健康检查。

整个过程中，我会先预览，不会直接改你的业务代码或覆盖已有规则文件。
```

要求：

- 先讲产品，不先问配置。
- 先讲“能做什么”，不先讲目录名。
- 先讲“接下来三步”，让用户知道流程长度。
- 最后再补安全承诺。

## 5. 产品认知模型

### 5.1 StarWork 是什么

用户语言：

```text
StarWork 是 AI 项目的工作台底座。
```

可展开解释：

- 它给项目补一套“AI 进项目前要读的说明”。
- 它把当前任务、项目状态、协作记录和交接信息放到固定位置。
- 它让不同 AI 工具、不同 Agent、不同会话尽量用同一套项目事实。

不要这样说：

- “StarWork 是 Core 协议。”
- “StarWork 会初始化 baseline / profile / capability / preset。”
- “StarWork 会安装 Pack 和 adapter profile。”

### 5.2 StarWork 能做什么

小白用户只需要先知道五个能力：

| 能力 | 用户语言 |
| --- | --- |
| 项目说明 | 让 AI 知道这个项目是什么、目标是什么。 |
| 当前任务 | 让 AI 知道现在正在推进什么，不用每次重新解释。 |
| 协作规则 | 告诉 AI 哪些文件能改、哪些需要先问。 |
| 交接记录 | 不同会话或不同 Agent 接手时能看懂上下文。 |
| 健康检查 | 初始化后检查关键文件是否齐全。 |

进阶能力只在后面轻描淡写：

```text
后续需要时，StarWork 还可以继续加知识库、多 Agent 分工和不同 AI 工具适配；第一次不用一次全开。
```

### 5.3 初始化是在做什么

用户语言：

```text
初始化就是把一个普通项目目录整理成 StarWork 工作台。
```

具体来说：

- 新建或确认一个项目目录。
- 写入 StarWork 自己需要的协作文件。
- 如果项目已有 AI 规则文件，先生成待整合草稿，不直接覆盖。
- 最后运行健康检查，确认 AI 能找到入口。

## 6. 推荐体验流程

### 6.1 总流程

新手初始化分为七步：

1. 讲清楚 StarWork 是什么、能做什么。
2. 告诉用户接下来会做哪几步。
3. 判断使用场景：新建工作台，还是接入已有项目。
4. 确认工作台服务对象：一个具体项目，还是多个项目的管理中心。
5. 确认语言、路径和推荐结构。
6. 先预览将要写入的内容，不写入。
7. 用户确认后正式写入，再运行健康检查。

这七步里，前两步是认知引导，不能省略。

### 6.2 Step 1：讲产品

触发条件：

- 用户说“初始化 StarWork”。
- 用户说“把这个项目接入 StarWork”。
- 用户说“创建工作台”。
- 用户在非 StarWork 目录里尝试 MultiAgent / Knowledge 等能力，需要先接入。

Skill 首次回复必须包含：

- 产品定义。
- 核心功能。
- 接下来流程。
- 安全承诺。

示例：

```text
可以，我先简单说清楚 StarWork 在做什么。

StarWork 是给 AI 协作准备的项目工作台。它会把项目说明、当前任务、协作规则、交接记录和健康检查入口放到固定位置，让 AI 每次进入项目时不用从零猜上下文。

这次我会带你做三件事：
1. 确认这个工作台服务哪个项目；
2. 预览 StarWork 准备补哪些协作文件；
3. 你确认后再正式写入，并做一次检查。

我会先预览，不会直接改你的业务代码，也不会直接覆盖已有 AI 规则文件。
```

### 6.3 Step 2：告诉用户下一步要做什么

讲完产品后，不要立刻抛命令。先给用户一个清晰的下一步：

```text
第一步，我需要判断你是哪种情况：

1. 你已经有一个项目，想把它接入 StarWork；
2. 你只是想试用，准备从零创建一个新工作台。

如果你现在就在真实项目目录里，我建议选 1。
```

这里的关键是让用户知道“为什么现在问这个问题”。

### 6.4 Step 3：新建还是接入已有项目

显示口径：

```text
你现在是要接入已有项目，还是新建一个空工作台试用？
```

选项解释：

| 选项 | 适合谁 | 接下来会做什么 | 默认推荐 |
| --- | --- | --- | --- |
| 接入已有项目 | 已经有代码、文档、资料或真实项目目录 | 保留现有内容，只补 StarWork 协作文件；已有 AI 规则先生成待整合草稿 | 当前目录非空时推荐 |
| 新建空工作台 | 只是试用，或还没有项目文件 | 创建一个新目录和最小工作台骨架 | 试用时推荐 |

### 6.5 Step 4：一个项目还是项目中心

显示口径：

```text
这个工作台是服务一个具体项目，还是用来管理多个项目？
```

解释：

| 选项 | 内部类型 | 用户理解 |
| --- | --- | --- |
| 一个具体项目 | `project` | 比如一个产品、一个客户交付、一个研究项目。 |
| 多个项目的管理中心 | `hub` | 像总控台，用来登记和管理多个项目。 |

默认：

- 新用户默认 `project`。
- 只有用户明确说要“管理多个项目 / 项目中心 / 总控台”时才走 `hub`。

### 6.6 Step 5：语言、路径、结构

这一步仍然每次只问一个问题。

语言：

```text
这个工作台的目录和说明文字，你想用中文还是英文？如果不确定，我建议先用中文。
```

路径：

```text
我需要确认工作台写在哪里。
目标路径是：
`/absolute/path`

确认后我先做预览，不会立刻写入。
```

结构：

```text
第一次使用建议先用推荐结构。
推荐结构会准备最少必要的项目说明、当前任务、协作规则和交接记录；以后可以再定制。

你想先用推荐结构，还是现在就定制目录？
```

不要把“标准结构 / 标准文件”作为主表达。统一说“推荐结构”。

### 6.7 Step 6：预览

预览前先告诉用户正在做什么：

```text
我现在先生成一份写入预览。预览只告诉你 StarWork 打算创建或更新哪些文件，不会真的写入。
```

Skill 执行：

```bash
starwork init --type project --pack general --language <zh|en> --target <path> --dry-run
```

已有非空项目或已有 AI 规则文件时：

```bash
starwork init --type project --pack general --language <zh|en> --target <path> --agent-docs draft --dry-run
```

预览复述必须使用四组：

```text
这是预览，还没有写入文件。

会创建：
- ...

会更新：
- ...

不会改动：
- 你的业务代码
- 已有非空 AI 规则文件

需要你确认：
- 目标路径是否正确
- 是否接受这些 StarWork 协作文件
```

### 6.8 Step 7：确认写入与检查

用户确认后：

```bash
starwork init ... --yes
starwork doctor --target <path>
```

完成回复必须解释结果，而不是只说命令成功：

```text
StarWork 工作台已经创建好了。

这次写入的是项目协作文件，不是业务代码。
健康检查也通过了，说明 AI 后续能找到项目说明、当前任务和协作规则。

下一步你可以用 Codex / Claude Code / Cursor 打开这个目录，让 AI 先读项目规则。
```

如果有待整合草稿：

```text
还有一步没有自动完成：你的项目已经有 AI 规则文件，所以 StarWork 只生成了待整合草稿，没有直接覆盖原文件。
接下来我会帮你对比现有规则和 StarWork 建议，再由你确认是否合并。
```

## 7. 信息层级

### 7.1 第一层：必须讲

- StarWork 是 AI 协作项目工作台。
- 它能整理项目说明、当前任务、协作规则、交接记录。
- 接下来先确认场景，再预览，再写入，再检查。
- 不默认改业务代码，不直接覆盖已有 AI 规则文件。

### 7.2 第二层：按需讲

- 推荐结构 vs 定制结构。
- 项目工作台 vs 项目中心。
- AI 工具适配。
- 知识库。

### 7.3 第三层：不要主动讲

- Core / Profile / Capability / Preset / Kit / Pack 的内部边界。
- adapter profile、host_native_dirs、capabilities。
- pending_merge 作为内部状态名。
- blueprint schema。

## 8. 术语口径

| 内部术语 | 用户语言 |
| --- | --- |
| StarWork Core | StarWork 工作台规则 |
| dry-run | 预览，不写入 |
| `--yes` | 确认写入 |
| 入口文件 | AI 读项目规则的说明文件 |
| pending_merge | 待整合草稿 |
| Pack | 附加工作能力 |
| Adapter | AI 工具适配 |
| Project workspace | 项目工作台 |
| Hub workspace | 项目中心 |
| Standard structure | 推荐结构 |
| Blueprint | 定制方案 |

首次出现内部文件名时可以保留文件名，但必须配一句解释：

```text
`AGENTS.md` 是 AI 进入项目时优先读取的规则说明。
```

## 9. CLI 要求

CLI 不承担完整产品介绍，但必须在 help / dry-run 中承接同一套用户语言。

### 9.1 `starwork init --help`

必须说明：

```text
starwork init 会把一个目录整理成 StarWork 工作台，让 AI 能找到项目说明、当前任务、协作规则和交接记录。
```

参数解释：

```text
--dry-run
  预览将要写入的文件，不做真实改动。

--yes
  确认执行，会真实写入 StarWork 工作台文件。

--agent-docs draft
  已有 AI 规则文件时，先生成待整合草稿，不覆盖原文件。
```

### 9.2 dry-run 输出

dry-run 必须先显示：

```text
这是预览，不会写入文件。
```

然后按四组展示：

```text
会创建：
- ...

会更新：
- ...

不会改动：
- ...

需要你确认：
- ...
```

已有项目时必须明确：

```text
检测到这是已有项目。
StarWork 会保留现有文件，先生成待整合草稿，不直接覆盖已有 AI 规则文件。
```

### 9.3 JSON 输出

建议新增面向 Skill 的用户摘要：

```json
{
  "user_summary": {
    "product_purpose": "把项目整理成 AI 协作工作台",
    "mode": "preview_no_write",
    "target_kind": "existing_project",
    "will_create": [],
    "will_update": [],
    "will_not_touch": [],
    "needs_confirmation": []
  }
}
```

如本轮不实现 `user_summary`，Skill 必须仍按同等结构复述 CLI actions。

## 10. Skill 要求

### 10.1 开场必须是产品介绍

`starworkInit` 不得一上来问配置。必须先讲：

- StarWork 是什么。
- 能做什么。
- 接下来要做什么。
- 安全边界。

### 10.2 引导要有路标

每进入下一步，Skill 需要告诉用户“现在为什么问这个”。

示例：

```text
现在先确认你是哪种项目情况，因为新建工作台和接入已有项目的安全策略不一样。
```

### 10.3 每次只问一个问题

不允许一次性问完类型、语言、路径、结构、知识库、宿主。

### 10.4 默认不要主动开进阶能力

默认不主动开启：

- 知识库。
- MultiAgent。
- 所有宿主适配。
- 定制 blueprint。

但可以在初始化完成后提示：

```text
工作台建好后，如果你需要，我再帮你开启知识库、多 Agent 分工或适配具体 AI 工具。
```

### 10.5 已有项目必须强调保留

已有项目场景中，Skill 必须明确：

- 保留业务代码。
- 保留已有 AI 规则文件。
- StarWork 先生成待整合草稿。
- 用户确认后才合并。

## 11. Init-family Skill 统一体验标准

本 SPEC 不只约束 `starworkInit`。凡是负责“从无到有启用某种 StarWork 能力”的 Skill，都属于 Init-family Skill，需要复用同一套新手体验顺序。

### 11.1 判定标准

一个 Skill 只要满足任一条件，就算有 Init 属性：

- 会创建一个新的工作台、项目、能力结构或协作层。
- 会把普通目录、旧工作区或项目中心里的想法转成 StarWork 可管理对象。
- 会启用用户此前没有使用的 StarWork 能力。
- 会在用户确认后写入 StarWork 机制文件、规则入口、蓝图或状态记录。

不纳入第一批的 Skill：

- 只做日常维护，不负责启用能力的 Skill。
- 只做巡检报告，且不会引导用户创建或升级的 Skill。
- 已经在能力启用之后才安装到项目内的业务 Skill。

### 11.2 第一批需要同步优化的 Skill

| Skill | Init 属性 | 第一屏必须讲清楚 |
| --- | --- | --- |
| `starworkInit` | 创建或接入 StarWork 工作台 | StarWork 是什么、能做什么、初始化接下来三步。 |
| `starworkKnowledge` | 启用项目知识库能力 | 知识库是什么、和参考资料/草稿有什么区别、开启后 AI 会如何使用它。 |
| `starworkMultiagent` | 初始化 Agent Lanes 或创建 Agent 团队 | 多 Agent 分工是什么、能解决什么协作问题、接下来会先设计职责再创建/绑定会话。 |
| `starworkDoctor` upgrade flow | 把旧目录或历史工作区无损升级为 StarWork 工作台 | 诊断是什么、升级是什么、不会移动/删除旧文件，接下来先看事实再做蓝图。 |
| `starworkSpawn` | 从项目中心创建新的项目工作台 | Spawn 是什么、为什么从项目中心创建、接下来会先设计项目再预览生成。 |

暂不纳入第一批：

- `starworkAudit`：主要是巡检和修复建议，不是默认初始化入口；如果后续 repair flow 做成常规创建/修复入口，再纳入。
- `starworkKnowledgeProject`：知识库启用后的项目内维护 Skill，不负责开启能力。
- `neat-freak`：会话收束，不属于 StarWork init 体验。

如果后续新增独立 `adapt` Skill 或其它能力启用 Skill，也必须套用本节标准。

### 11.3 通用开场结构

所有 Init-family Skill 的第一屏都按四段组织：

1. 这个能力是什么。
2. 它能帮用户做什么。
3. 接下来会分哪几步完成。
4. 安全边界是什么。

模板：

```text
先简单说清楚这一步在做什么。

<能力名> 是 <用户语言的一句话定义>。
它能帮你：
- <能力 1>
- <能力 2>
- <能力 3>

接下来我会分 <N> 步带你完成：
1. <先确认什么>
2. <再预览什么>
3. <用户确认后写入什么>
4. <最后如何检查>

整个过程中，我会先预览，不会在你确认前改动关键文件。
```

禁止开场：

- 直接输出 CLI 命令。
- 直接问配置参数。
- 直接说内部对象名，例如 `blueprint`、`pending_merge`、`adapter profile`、`capability manifest`，除非已经先用人话解释。

### 11.4 各 Skill 详细使用流程

#### starworkKnowledge

适用场景：

- 用户说“开启知识库”“初始化知识库”“让 AI 记住项目知识”。
- 用户问“这个项目的长期知识放哪里”。
- 用户已有 `知识/`、`knowledge/`、`资料库/` 等目录，想纳入 StarWork 管理。

第一屏必须先讲：

```text
项目知识库是让 AI 长期记住项目稳定理解的地方。

它不是原始资料文件夹，也不是草稿区。原始材料仍放在参考资料区，临时想法仍放在草稿区；知识库只沉淀会反复用到、已经比较稳定的判断，比如客户背景、产品规则、术语解释、长期策略和复盘结论。

接下来我会分三步带你开启：
1. 先检查当前项目是否已经有知识库；
2. 再预览 StarWork 准备创建哪些知识库文件；
3. 你确认后再正式开启，并做一次结构检查。

我不会把旧资料整包搬进知识库，也不会在你确认前改动原始资料。
```

引导流程：

1. 先确认目标目录是 StarWork 工作台。
   - 如果用户没有给路径，先问目标项目目录。
   - 不要默认扫描主目录或过大的上级目录。
2. 运行 `starwork knowledge status --json`。
   - 如果已开启，告诉用户“知识库已经存在”，转入维护流程，不重复 init。
   - 如果未开启，进入开启说明。
3. 用人话确认知识库边界。
   - 说清楚“知识库放稳定理解，参考资料放原始材料，输出区放草稿和成果”。
   - 如果用户只是想存一堆资料，建议先放参考资料区，不急着开启知识库。
4. 运行 `starwork knowledge init --dry-run`。
   - 向用户复述会创建哪些目录和文件。
   - 明确这是预览，不写入。
5. 用户确认后运行 `starwork knowledge init --yes`。
6. 运行 `starwork knowledge check`。
7. 完成后告诉用户下一步怎么用。

预览复述格式：

```text
这是知识库开启预览，还没有写入文件。

会创建：
- 知识库索引
- 知识卡片目录
- 综合判断目录
- 来源记录目录

不会改动：
- 参考资料区里的原始材料
- 当前草稿和成果文件

需要你确认：
- 是否现在开启项目知识库
- 是否保持原始资料仍在参考资料区
```

完成反馈：

```text
项目知识库已经开启。

以后稳定的项目理解可以沉淀到知识库；原始资料仍放参考资料区，临时草稿仍放输出或工作区。接下来如果你给我一份资料，我会先判断它适合做来源、知识卡片，还是综合判断，不会直接整包塞进知识库。
```

必须避免：

- 一开始就说 `starwork knowledge init --dry-run`。
- 把知识库讲成“资料夹”。
- 默认把历史资料整包搬进知识库。
- 用户只是想保存原始资料时，强行建议开启知识库。
- 开启成功后让用户安装全局 `starworkKnowledgeProject`。

开发验收点：

- Skill 文案中有“知识库不是原始资料文件夹，也不是草稿区”。
- Skill 文案中有开启三步：检查状态、预览、确认后开启并检查。
- Skill 明确先 `status --json`，再 `init --dry-run`，再 `init --yes`，最后 `check`。
- Skill 明确旧资料不默认搬迁。

#### starworkMultiagent

适用场景：

- 用户说“初始化多 Agent”“创建 Agent 团队”“分产品/开发/验收几个智能体”。
- 用户说“把当前会话登记为某个常用智能体”。
- 用户说“让开发 Agent 开始做事”“查看另一个 lane 进度”。

第一屏必须按用户意图区分：

创建团队 / 初始化协作层时：

```text
多 Agent 分工是让一个项目里的不同 AI 会话承担稳定职责。

它适合产品规划、开发、验收、资料整理这类需要并行推进或长期交接的项目。StarWork 会先记录每个 Agent 的职责和可写范围，再为需要的 Agent 创建或绑定会话。

接下来我会分四步带你完成：
1. 先确认当前目录已经是健康的 StarWork 工作台；
2. 再和你确认需要哪些职责；
3. 预览要新增的 lane 和写入范围；
4. 你确认后再创建或绑定 Agent 会话。

注意：只创建职责位不等于 Agent 团队已经能工作。只有 lane 存在并绑定到可工作的会话后，才能说这个 Agent 已创建并绑定。
```

绑定当前会话时：

```text
我可以把当前会话登记成一个稳定职责位。这样以后 StarWork 就知道这个会话负责什么、能改哪些范围、交接记录在哪里。

接下来我会先确认职责和写入范围，再预览 lane 记录，确认后把当前会话绑定进去。
```

引导流程：创建 Agent 团队

1. 先运行 `starwork doctor --target <path> --json`。
   - 不是 StarWork 工作台时，停止 MultiAgent 写入，转 `starworkInit`。
   - 有 AI 入口待整合草稿时，停止创建团队，转 `starworkInit` 整合入口。
2. 读取现有 lane 状态。
   - `agent-lanes.md`
   - `.starwork/agent-lanes/state.json`
   - `shared.md`
3. 向用户复述建议职责，不直接写。
   - 每个职责包含：lane id、职责名、写入范围、为什么需要它。
   - 默认不要创建过多 Agent；小项目建议 2-3 个。
4. 对缺失 lane 执行 dry-run。
   - `starwork multiagent init --dry-run`，如协作层未初始化。
   - `starwork multiagent add ... --dry-run`。
5. 复述预览：
   - 会新增哪些职责位。
   - 每个职责位能写哪里。
   - 哪些只是登记，还没有会话。
6. 用户确认后执行 `--yes`。
7. 对需要独立 Codex 会话的 lane：
   - `starwork multiagent message launch <lane> --json`
   - 读取 `message` 和 `session_name`
   - 调用 `create_thread`
   - 调用 `set_thread_title(threadId, session_name)`
   - 成功后 `starwork multiagent bind ... --yes`
8. 输出完成状态：
   - 哪些 Agent 已创建并绑定。
   - 哪些只有 lane，未绑定会话。
   - 哪些需要用户手动操作。

预览复述格式：

```text
这是多 Agent 协作层预览，还没有创建或绑定会话。

计划新增：
- 产品规划 Agent：负责需求澄清、SPEC 和验收标准；可写 product/planning/**
- 开发 Agent：负责 CLI / Skill 实现；可写 product/cli/**, product/skills/**

不会做：
- 不会自动扩大写入范围
- 不会在未确认前创建会话
- 不会把只有 lane 的职责说成已经可工作

需要你确认：
- 这些职责是否准确
- 每个 Agent 的可写范围是否合适
```

完成反馈：

```text
多 Agent 团队创建结果：

已创建并绑定：
- 产品规划 Agent -> codex:...

只登记了职责、尚未绑定会话：
- 验收 Agent：原因是当前会话缺少创建线程工具

接下来可做：
- 给开发 Agent 发送任务
- 查看某个 Agent 的进度
- 继续绑定未完成的 Agent
```

必须避免：

- 一上来就执行 `multiagent init/add/launch`。
- 只创建 lane 就说 Agent 团队已创建。
- 在 StarWork 工作台未完成初始化或 AI 入口仍是待整合草稿时继续创建团队。
- 自己从 purpose 或 Launch Message 拼会话名；标题必须用 CLI 返回的 `session_name`。
- 把 CLI `launch` 当成 Codex 创建会话主流程。

开发验收点：

- Skill 创建团队流程前有产品解释和四步路标。
- Skill 明确 lane-only 与“已创建并绑定 Agent”的区别。
- Skill 文案包含 `doctor` 前置检查和 pending merge 阻断。
- Skill 文案明确用 `create_thread` / `set_thread_title` / `bind` 完成 Codex 创建绑定。

#### starworkDoctor upgrade flow

适用场景：

- 用户说“看看这个旧目录能不能接入 StarWork”。
- 用户说“升级这个旧工作区”“整理成 StarWork 工作台”。
- doctor 发现目录不是标准 StarWork，但有资料、成果、任务或规则痕迹。

第一屏必须讲：

```text
我会先把这个目录当作“历史工作区候选”来诊断。

诊断不是挑错，也不会改文件；它会看这个目录里有没有项目说明、成果、资料、当前任务和 AI 规则这些线索，判断它能不能无损整理成 StarWork 工作台。

接下来我会分三步：
1. 先只读扫描目录，给出人话结论；
2. 再列出哪些角色我能确认、哪些需要你确认；
3. 只有你明确要升级时，我才生成升级蓝图并先预览。
```

引导流程：

1. 确认目标目录。
   - 没有路径就问。
   - 不默认扫描主目录。
2. 运行 `starwork doctor --target <path> --json --inventory-depth all`。
3. 第一轮结果必须分三组说：
   - 我看到的事实。
   - 我推测的角色。
   - 需要你确认的地方。
4. 如果用户只想诊断，停在诊断建议，不生成 blueprint。
5. 如果用户明确要升级：
   - 先确认目录角色，如正式成果区、资料区、草稿区、当前任务入口。
   - 最多一次问 3 个会影响 blueprint 的问题。
6. 生成 upgrade blueprint 和规则文件。
7. 执行 `starwork upgrade --blueprint ... --dry-run`。
8. 复述预览：
   - 会补哪些 StarWork 文件。
   - 会保留哪些旧目录。
   - 不会移动、删除或覆盖哪些内容。
9. 用户确认后才执行 `starwork upgrade --yes`。
10. 执行 `starwork doctor --target <path>`。

诊断复述格式：

```text
我先给人话结论：
这个目录还不是标准 StarWork 工作台，但已经有可接入信号，适合走无损升级路线。

我看到的事实：
- 有资料目录
- 有最终成果目录
- 缺少 StarWork 工作台身份证

我推测的角色：
- “交付物/”可能是正式成果区，置信度高
- “素材/”可能是参考资料区，置信度中

需要你确认：
- “交付物/”是否只放最终确认版本？
```

升级预览复述格式：

```text
这是升级预览，还没有写入。

会补齐：
- StarWork 工作台身份证
- AI 规则入口
- 当前任务入口

会保留：
- 旧资料目录
- 旧成果目录

不会做：
- 不移动旧文件
- 不删除旧目录
- 不覆盖已有规则
```

必须避免：

- 开场说“你的工作区不合格”。
- 把 doctor 结果直接等同最终判断。
- 用户未确认语义就生成或执行 upgrade blueprint。
- 直接执行 `upgrade --yes`。
- 把低置信度目录角色说成事实。

开发验收点：

- Skill 第一屏出现“诊断不是挑错，也不会改文件”。
- 诊断输出按事实 / 推测 / 需要确认分组。
- upgrade flow 明确先 dry-run，确认后 yes，再 doctor。
- 文案明确不移动、不删除、不覆盖旧文件。

#### starworkSpawn

适用场景：

- 用户在项目中心里说“创建一个新项目工作台”。
- 用户已有项目中心，想从中开一个新项目。
- 用户描述一个新项目想法，需要转成项目工作台。

第一屏必须讲：

```text
从项目中心创建项目工作台，是把一个新项目登记到项目中心，并生成这个项目自己的 StarWork 工作台。

它适合你已经有一个项目中心，现在要从里面开一个新项目。StarWork 会先设计这个项目的目录、规则和初始文件，再预览要创建的内容。

接下来我会分三步：
1. 先确认新项目是什么、要交付什么；
2. 再设计项目工作台结构；
3. 你确认后用 spawn 预览并创建。
```

引导流程：

1. 确认当前或指定目录是项目中心。
   - 如果不是项目中心，转 `starworkInit` 或 `starworkDoctor`。
2. 解释为什么从项目中心创建：
   - 项目中心负责登记多个项目。
   - 新项目工作台负责具体项目的日常协作。
3. 采访新项目，但每次只问一组：
   - 项目名称和目标。
   - 最终交付物是什么。
   - 日常资料、草稿、成果大致怎么分。
   - 是否需要特殊规则。
4. 先给用户一版人话方案，不直接生成文件：
   - 项目名称。
   - 工作台路径建议。
   - 推荐结构。
   - 需要的规则。
5. 用户确认后，才生成 spawn blueprint 包。
6. 执行 `starwork spawn --blueprint ... --dry-run`。
7. 复述预览。
8. 用户确认后执行 `starwork spawn --blueprint ... --yes`。
9. 执行 `starwork doctor --target <project-path>`。

方案复述格式：

```text
我建议这样创建这个项目工作台：

项目目标：
- ...

工作台会包含：
- 项目说明和当前任务入口
- 资料区
- 草稿区
- 确认成果区
- 项目专属 AI 规则

暂不做：
- 不把这个一次性目录偏好做成 Pack
- 不创建空的可选目录
- 不写入项目中心，直到你确认
```

预览复述格式：

```text
这是从项目中心创建新项目的预览，还没有写入。

会创建：
- 新项目工作台目录
- 项目规则
- 初始任务入口

会更新：
- 项目中心的项目登记

不会改动：
- 其他项目工作台
- 项目中心已有规则
```

必须避免：

- 一开始就讲 `spawn blueprint`。
- 把一次性目录偏好直接建议成 Pack。
- 未确认 hub 和 target 路径就执行写入。
- 只生成 blueprint 就说项目已创建。
- 创建空的 `handoff.md` 或 `seed/` 可选文件。

开发验收点：

- Skill 第一屏讲清项目中心和项目工作台的关系。
- Skill 先输出人话方案，再生成 blueprint。
- Skill 明确 dry-run / yes / doctor 顺序。
- Skill 明确不把一次性定制误判成 Pack。

### 11.5 横向验收标准

每个 Init-family Skill 的验收都要检查：

- 第一屏是否先讲“这是什么能力”。
- 第一屏是否讲“能帮用户做什么”。
- 第一屏是否讲“接下来会做哪几步”。
- 是否先预览再写入。
- 是否避免用内部词作为主表达。
- 是否在用户确认前不执行 `--yes`。
- 是否把关键风险翻译成人话。

## 12. 文档要求

A 测安装指南 / 新手文档需要一个“第一次使用 StarWork”章节，顺序如下：

1. StarWork 是什么。
2. 它能帮你做什么。
3. 第一次初始化会做哪几步。
4. 它默认不会改什么。
5. 三种推荐路径。

推荐路径：

| 场景 | 推荐 |
| --- | --- |
| 只是试用 | 新建空工作台 + 推荐结构 + 先预览 |
| 已有真实项目 | 接入已有项目 + 推荐结构 + 待整合草稿 + 先预览 |
| 已有成熟工作流 | 接入已有项目 + 先预览 + 再定制结构 |

默认不会改：

- 不默认改业务代码。
- 不直接覆盖已有非空 AI 规则文件。
- 不在用户确认前正式写入。
- 不要求第一次就开启知识库、多 Agent 或所有 AI 工具适配。

## 14. 验收标准

### 14.1 产品认知

- `starworkInit` 第一屏能让新用户知道 StarWork 是 AI 协作项目工作台。
- 第一屏说明 StarWork 能整理项目说明、当前任务、协作规则和交接记录。
- 第一屏说明接下来会先确认场景、再预览、再写入、再检查。

### 14.2 流程引导

- 每一步都告诉用户为什么现在问这个问题。
- 每次只问一个主要问题。
- 默认推荐明确。
- 不要求用户先理解 CLI 参数。

### 14.3 安全感

- 初始化开始前说明不会默认改业务代码。
- 所有真实写入前都有预览。
- 已有项目不直接覆盖已有非空 AI 规则文件。
- 用户未确认绝对路径前不会执行 `--yes`。

### 14.4 CLI

- `starwork init --help` 有产品一句话。
- dry-run 明确“这是预览，不会写入文件”。
- dry-run 输出包含“会创建 / 会更新 / 不会改动 / 需要你确认”。
- 已有项目 dry-run 明确保留现有文件和 AI 规则。

### 14.5 Init-family Skill

- `starworkKnowledge` 第一屏讲清知识库不是资料夹，而是长期稳定理解层。
- `starworkMultiagent` 第一屏讲清多 Agent 分工是什么，以及不是只创建 lane。
- `starworkDoctor` upgrade flow 第一屏讲清诊断是只读、升级是用户确认后的无损补齐。
- `starworkSpawn` 第一屏讲清从项目中心创建项目工作台的含义和流程。
- 上述 Skill 都不得一上来直接输出 CLI 命令或内部 schema 名。

### 14.6 文档

- A 测指南或新手文档有“第一次使用 StarWork”章节。
- 文档顺序是产品介绍、能力说明、初始化流程、安全边界、推荐路径。
- GitHub Issue #4 回填处理结果和文档入口。

## 15. 不做范围

- 不重设计 StarWork Core 目录协议。
- 不改变 `starwork init` 的基础参数模型。
- 不在本轮加入交互式 TUI。
- 不强制首次初始化开启知识库。
- 不强制首次初始化创建 MultiAgent 团队。
- 不为所有宿主默认生成适配入口。
