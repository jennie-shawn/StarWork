## 2. 背景

当前有两个未关闭的 P1 问题都指向 `starwork doctor` 的可信度：

1. preserve-names Hub 已在 `workspace.upgrade.core_role_mapping` 中声明 `skills/` 是 Skill 角色目录，但 `doctor` 仍按 `language: zh` 默认检查 `技能/registry.json`，导致 false warning。
2. Hub Kit 缺少 `starworkSpawn` / `starworkAudit` 时，如果 `.starwork/skills.json` 为空，`doctor` 仍可能报告健康，因为它只检查“已经声明的 Skill”，没有检查“该 Kit 必须具备的 Skill”。

这两个问题表面上一个是路径，一个是 Skill 缺失；产品根因相同：`doctor` 没有把 StarWork 工作台的真实事实源串起来。它应该先理解这个工作台实际采用的角色路径和 Kit 能力，再做健康判断。

## 3. 一句话目标

让 `starwork doctor` 在 Hub 工作台中按真实角色路径检查 Skill registry，并能发现 Hub Kit 必需 Skills 缺失，给出安全、可执行但不自动写入的修复指引。

## 4. 产品原则

### 4.1 真实路径优先于语言默认路径

如果工作台通过 preserve-names upgrade 保留了历史路径，`doctor` 必须尊重 `.starwork/workspace.json` 中的 `upgrade.core_role_mapping`。

路径优先级：

1. `workspace.upgrade.core_role_mapping` 中对应 role 的路径。
2. workspace / kit state 中已经记录的正式路径。
3. 当前 workspace type + language 的默认路径。

不能因为 `language: zh` 就强行把 Hub Skill registry 推导到 `技能/registry.json`。

### 4.2 Required Skills 不能只依赖 manifest

`.starwork/skills.json` 是当前安装状态记录，不是 required skills 的唯一来源。

`doctor` 必须能从 `workspace_type`、`kit`、Pack 和 Capability 推导“这个工作台应该具备哪些 Skill”。即使 `.starwork/skills.json` 是空数组，也要检查 Hub Kit 应有的 `starworkSpawn` 和 `starworkAudit`。

### 4.3 Doctor 只诊断，不静默修复

本版不增加自动修复。`doctor` 只能输出：

- 缺少什么；
- 应该在哪些路径出现；
- 为什么需要；
- 推荐用户下一步运行什么安全流程。

不得静默复制 Skill、改 registry、改 symlink 或改 host mount。

### 4.4 Kit-bundled Skills 不是全局系统 Skill

`starworkSpawn` / `starworkAudit` 属于 Hub Kit 自带 Skill，应存在于 Hub 工作台及其宿主挂载路径中。不要把它们加入全局系统 Skill 安装清单，也不要在 repair hint 中提示用户全局安装。

## 5. ISSUE-018 修复要求：preserve-names Hub registry 路径

### 5.1 现象

复现场景：

```json
{
  "workspace_type": "hub",
  "kit": "hub",
  "language": "zh",
  "upgrade": {
    "strategy": "preserve-names",
    "core_role_mapping": [
      { "role": "skills", "path": "skills/", "confidence": "high" }
    ]
  }
}
```

实际存在：

```text
skills/registry.json
```

当前错误表现：

```text
项目中心缺少托管 Skill 注册表。
path: 技能/registry.json
```

### 5.2 应有行为

`doctor` 应检查：

```text
skills/registry.json
```

并在 JSON 输出中暴露它采用的实际路径：

```json
{
  "skills": {
    "registry": {
      "exists": true,
      "path": "skills/registry.json",
      "path_source": "upgrade.core_role_mapping",
      "role": "skills",
      "count": 0
    }
  }
}
```

字段名可以按现有代码风格微调，但必须机器可读，并能看出“为什么选了这个路径”。

### 5.3 路径解析边界

建议新增或收敛一个内部 helper，供 doctor 和后续 required skill 检查复用：

```text
resolveWorkspaceRolePath(state, role, fallbackPath)
```

行为：

- 输入 role，例如 `skills`、`project_registry`。
- 先查 `state.upgrade.core_role_mapping[]`。
- mapping path 必须继续使用现有安全相对路径校验。
- 返回 `{ path, source, role }` 一类结构，而不是只返回字符串。
- 找不到 mapping 时再回退到现有 Hub path 默认逻辑。

不要求本版把所有路径都迁到该 helper，但 Hub Skill registry 和 required skill source path 必须使用同一套解析结果。

### 5.4 非目标

- 不改变 preserve-names upgrade blueprint 的 schema。
- 不迁移用户目录。
- 不在 `skills/registry.json` 缺失时自动创建。

## 6. ISSUE-019 修复要求：required Kit Skills 检查

### 6.1 Required Skills 来源

本版 required skills 至少覆盖 Hub Kit：

```text
workspace_type: hub
kit: hub
required skills:
  - starworkSpawn
  - starworkAudit
```

事实源优先使用 CLI 内已有的 `KIT_BUNDLED_SKILLS` 信息，避免另写一份名单导致漂移。

后续 Pack / Capability required skills 可扩展，但本版验收不要求完整实现 Pack / Capability 推导。

### 6.2 检查维度

每个 required skill 至少检查：

| 维度 | 检查对象 | 缺失等级 |
|---|---|---|
| source | Hub 正式 Skill 源目录，例如 `skills/starworkSpawn/SKILL.md` | warn，strict fail |
| manifest | `.starwork/skills.json` 是否登记该 Skill | warn，strict fail |
| host mounts | `.agents/skills/<id>/SKILL.md`、`.claude/skills/<id>/SKILL.md` 等应有挂载 | warn，strict fail |
| frontmatter | `SKILL.md` 是否含基础 `name` / `description` | warn，strict fail |

说明：

- 如果当前代码还没有通用 frontmatter parser，可先做最小可验证检查：`SKILL.md` 存在，且文件头部包含 `name:` 和 `description:`。
- symlink 是否真实指向 source 可以作为增强项；本版至少要判断目标路径存在。
- source 路径要尊重 5.3 的角色路径解析。preserve-names Hub 应检查 `skills/<id>/SKILL.md`，不是 `技能/<id>/SKILL.md`。

### 6.3 JSON 输出

`doctor --json` 必须增加机器可读结果。建议结构：

```json
{
  "skills": {
    "required": [
      {
        "id": "starworkSpawn",
        "required_by": "kit:hub",
        "status": "missing_mount",
        "source": {
          "path": "skills/starworkSpawn",
          "status": "ok"
        },
        "manifest": {
          "path": ".starwork/skills.json",
          "status": "missing"
        },
        "mounts": [
          {
            "agent": "codex",
            "path": ".agents/skills/starworkSpawn",
            "status": "missing"
          },
          {
            "agent": "claude",
            "path": ".claude/skills/starworkSpawn",
            "status": "missing"
          }
        ],
        "repair_hint": "这是 Hub Kit 自带 Skill。请重新运行受控的 StarWork Hub Kit 安装/同步流程，或按文档补齐 Hub 工作台内的 Kit Skill；不要把该 Skill 安装为全局系统 Skill。"
      }
    ]
  }
}
```

状态枚举建议：

| status | 含义 |
|---|---|
| `ok` | source、manifest、mount 和基础 frontmatter 均满足 |
| `missing_source` | Hub 工作台正式 Skill 源缺失 |
| `missing_manifest` | source 存在但 `.starwork/skills.json` 未登记 |
| `missing_mount` | 宿主挂载缺失 |
| `invalid_frontmatter` | `SKILL.md` 基础元信息缺失 |
| `partial` | 多个非致命问题并存，开发实现若不方便细分可使用 |

### 6.4 非 JSON 输出

普通输出要让小白用户知道“这不是全局安装问题”，推荐口径：

```text
提醒：项目中心缺少 Hub 自带 Skill：starworkSpawn
- 应在项目中心内存在：skills/starworkSpawn
- 应挂载给 Codex：.agents/skills/starworkSpawn
- 应挂载给 Claude Code：.claude/skills/starworkSpawn
建议：重新运行 StarWork 的 Hub Kit 安装/同步流程，或按文档补齐项目中心内的 Kit Skill。不要把它安装成全局系统 Skill。
```

具体命令如果当前 CLI 没有安全 repair 入口，不要编造命令。

### 6.5 strict 语义

本版产品口径：

- 普通 `starwork doctor`：required skill 缺失记为 `warn`，`ok` 仍可为 true，只要没有 fail。
- `starwork doctor --strict`：required skill 缺失导致 `strict_ok: false`，进程退出码为 1。

理由：缺少 Hub Kit Skill 会影响 Agent 工作流，但不一定代表工作台基础结构损坏；普通检查给用户修复建议，严格检查用于发布、A 测和 CI 场景。

## 7. 开发建议

建议按以下顺序实现：

1. 抽出或收敛 Hub role path resolver，先修 `skills/registry.json` 的路径来源。
2. 给 `skills.registry` JSON 增加 `path_source` 或等价字段。
3. 增加 `collectRequiredSkills(state)`，首版只返回 Hub Kit 的 `KIT_BUNDLED_SKILLS.hub`。
4. 增加 `checkRequiredSkillInstallations(result, workspaceRoot, state, manifest)`。
5. 让 required skill 检查复用 role path resolver 和 existing manifest parse 结果，避免重复读文件和路径漂移。
6. 调整 `finishDoctor` / strict 汇总逻辑，使 required skill warning 在 strict 下失败。
7. 补齐测试和一次 preserve-names Hub smoke。

不要把 18 和 19 分成两个互相不了解的 patch；19 的路径判断必须继承 18 的修复结果。

## 8. 验收场景

### 8.1 Preserve-names Hub registry path

构造 Hub：

- `workspace_type: hub`
- `kit: hub`
- `language: zh`
- `upgrade.strategy: preserve-names`
- `upgrade.core_role_mapping` 包含 `{ role: "skills", path: "skills/" }`
- 文件存在：`skills/registry.json`
- 文件不存在：`技能/registry.json`

期望：

- `doctor --json` 的 `skills.registry.path` 是 `skills/registry.json`。
- 不输出“项目中心缺少托管 Skill 注册表”。
- 退出码为 0。

### 8.2 标准中文 Hub registry path

构造普通中文 Hub：

- 无 preserve-names mapping。
- 文件存在：`技能/registry.json`。

期望：

- `doctor --json` 仍检查 `技能/registry.json`。
- 不破坏现有中文 Hub。

### 8.3 Hub required skills missing with empty manifest

构造 Hub：

- `.starwork/skills.json` 存在但 `skills: []`。
- 缺少 `starworkSpawn` 或 `starworkAudit` source / mounts。

期望：

- `doctor --json` 包含 `skills.required[]`。
- `starworkSpawn` / `starworkAudit` 至少一个状态不是 `ok`。
- 非 JSON 输出明确说明缺少 Hub 自带 Skill。
- 普通 doctor 输出 warning。
- `--strict` 输出 `strict_ok: false` 且退出码为 1。

### 8.4 Hub required skills complete

构造 Hub：

- `starworkSpawn` / `starworkAudit` source 存在。
- `.starwork/skills.json` 登记二者。
- `.agents/skills/*` 和 `.claude/skills/*` mount 存在。
- `SKILL.md` 有基础 frontmatter。

期望：

- `skills.required[].status` 均为 `ok`。
- 普通和 strict doctor 均通过。

### 8.5 Preserve-names Hub required skills

构造 preserve-names Hub：

- role mapping 指向 `skills/`。
- `skills/starworkSpawn` / `skills/starworkAudit` 存在。
- 不存在 `技能/starworkSpawn` / `技能/starworkAudit`。

期望：

- doctor 不检查 `技能/<skill>`。
- required skill source path 使用 `skills/<skill>`。
