# StarWork Host Adapter 总 SPEC

## 1. 状态

- 日期：2026-06-02
- 状态：draft
- 所属功能：Host Adapters
- 相关模块：Core、CLI、Skills、Adapters、MultiAgent、Knowledge、Upgrade
- 相关命令：`starwork adapt`、`starwork doctor`、`starwork init`、`starwork multiagent`、`starwork knowledge`
- 相关宿主：Codex、Claude Code、Cursor、Trae

参考来源：

- Trae Skills 官方文档：`https://docs.trae.cn/ide/skills`
- Cursor Agent Skills 官方文档：`https://cursor.com/cn/docs/skills`

## 2. 一句话定义

StarWork Host Adapter 是 StarWork 面向不同 AI 宿主的通用适配层。

它把 StarWork 工作台协议翻译成某个宿主能正确读取、正确行动、正确保存上下文的方式。

```text
StarWork Core 定义工作台应该如何协作
Host Adapter 定义某个 AI 工具如何进入并遵守这套协作方式
```

## 3. 为什么需要全局 Adapter

此前 `starwork adapt` 的定位偏窄：为 Claude、Cursor、Trae 等宿主生成一个规则入口文件，让它们知道要读 `AGENTS.md`。

但现在 StarWork 已经不只是初始化目录：

- `doctor` 要判断当前工作台对当前宿主是否可用。
- `skills` 要考虑系统级 Skill、Kit Skill、Capability Skill 的安装和识别方式。
- `multiagent` 要处理 session id、会话命名、读取、继续、跨会话指令。
- `knowledge` 要确保宿主知道知识库是长期理解层，不是参考资料或草稿目录。
- `upgrade` 要从用户原有规则文档里提炼有效内容，并转成适合目标宿主的入口。

所以 adapter 不能只属于 MultiAgent，也不能只是 `CLAUDE.md` / Cursor rules 生成器。它应该是 StarWork 的全局宿主适配层。

## 4. 产品边界

### 4.1 Adapter 负责什么

Host Adapter 负责回答：

- 这个宿主从哪里读项目规则？
- 这个宿主能否识别 StarWork Skill？怎么安装或挂载？
- 这个宿主能否获得当前会话 ID？
- 这个宿主能否改名、读取、继续、创建或指挥其他会话？
- 这个宿主的记忆、transcript、summary、history 是否可读？是否可靠？
- 这个宿主有哪些私有状态文件绝不能改？
- 当宿主不支持自动操作时，StarWork 应该如何降级成人工步骤？

### 4.2 Adapter 不负责什么

Host Adapter 不负责：

- 不重新定义 Core 目录结构。
- 不为每个宿主复制一套完整规则。
- 不绕过宿主权限、登录或安全机制。
- 不直接改写宿主私有数据库、加密存储或 transcript。
- 不承诺所有宿主都具备 Codex 的后台多会话能力。
- 不把宿主 history 当成 StarWork 正式事实源。

## 5. 与 StarWork 各层的关系

| StarWork 层 | Adapter 的作用 |
| --- | --- |
| Core | Core 定义通用工作台协议；Adapter 不改 Core，只说明宿主如何读取和执行 Core。 |
| Kit | Kit 生成基础规则入口；Adapter 决定是否还要生成宿主专属入口文件。 |
| Pack | Pack 定义场景工作流；Adapter 确保宿主能读到 Pack 规则和场景边界。 |
| CLI | CLI 调用 adapter 做探测、生成入口、输出能力降级说明。 |
| Skills | Skill 按 adapter 能力选择自动执行、半自动执行或人工交付包。 |
| MultiAgent | MultiAgent 使用 adapter 的 session 能力，但不拥有整个 adapter 层。 |
| Knowledge | Knowledge 使用 adapter 的规则入口和 memory 边界，避免宿主把知识库当普通资料夹。 |
| Upgrade | Upgrade 使用 adapter 规则提炼能力，把旧规则转成目标宿主能读懂的入口。 |

## 6. Adapter 能力域

Host Adapter 分为六个能力域。

### 6.1 Rules

规则入口能力。

| 能力 | 含义 |
| --- | --- |
| `rules.entry_file` | 宿主优先读取的规则文件，例如 `AGENTS.md`、`CLAUDE.md`、Cursor rules。 |
| `rules.can_generate_entry` | CLI 是否能生成宿主入口。 |
| `rules.can_update_entry` | CLI 是否能安全更新宿主入口。 |
| `rules.supports_project_scope` | 宿主规则是否能绑定到当前项目。 |
| `rules.supports_nested_rules` | 宿主是否支持目录级规则。 |

### 6.2 Skills

Skill 识别、存放目录和分发能力。

这里必须区分三类目录：

| 类型 | 含义 |
| --- | --- |
| 全局系统 Skill 目录 | Agent 宿主自己的全局 Skill 安装位置，例如通过 `npx skills add` 安装到用户环境。StarWork 只提示安装，不复制到项目。 |
| StarWork 项目挂载目录 | StarWork 在项目内维护的 Skill 挂载入口，例如 `.agents/skills/`、`.claude/skills/`。 |
| 宿主原生发现目录 | 某个宿主自己会读取的项目级规则或 Skill 目录，例如 Cursor rules、Trae rules。某些宿主没有原生 Skill 发现目录，只能靠规则入口引导。 |

| 能力 | 含义 |
| --- | --- |
| `skills.system_install` | 是否支持系统级 Skill 安装。 |
| `skills.project_mount` | 是否支持项目内 Skill 挂载。 |
| `skills.primary_project_dir` | 当前宿主推荐优先写入的项目级 Skill 目录。 |
| `skills.project_mount_dirs` | StarWork 应把项目内 Skill 放到哪些目录。 |
| `skills.host_native_dirs` | 宿主原生会发现哪些目录；没有则为空数组。 |
| `skills.global_dirs` | 宿主全局 Skill 目录；StarWork 只提示，不默认写入。 |
| `skills.conflict_priority` | 多个目录同名 Skill 冲突时的优先级。 |
| `skills.discovery` | 宿主是否会自动发现项目 Skill。 |
| `skills.trigger_style` | 用户或 Agent 如何触发 Skill。 |
| `skills.adapter_rule_required` | 是否必须通过宿主规则入口告诉 Agent 去读项目 Skill manifest。 |

当前初始判断：

| Host | 推荐项目 Skill 目录 | 其他可发现目录 | 说明 |
| --- | --- | --- | --- |
| Codex | `.agents/skills/` | `.agents/skills/` | Codex / Codex-compatible Agent 优先使用通用 StarWork 项目 Skill 入口。 |
| Claude Code | `.claude/skills/`，可同时保留 `.agents/skills/` | `.claude/skills/` | Claude Code 需要独立入口；通用 `.agents/skills/` 可作为跨宿主备用挂载。 |
| Cursor | `.cursor/skills/` | `.agents/skills/`、`.claude/skills/`、`.codex/skills/` | Cursor 官方支持项目级 `.cursor/skills/` 和 `.agents/skills/`，并兼容 Claude / Codex skill 目录。 |
| Trae | `.trae/skills/` | `.agents/skills/` | Trae 官方支持项目级 `.trae/skills/` 和 `.agents/skills/`；同名时 `.trae/skills/` 优先。 |

规则：

- `.starwork/skills.json` 永远是项目实际可用 Skill 清单。
- 宿主目录只负责让对应 Agent 看见或使用 Skill，不替代 `.starwork/skills.json`。
- adapter 不决定“应该安装哪些 Skill”；它只决定目标宿主需要哪些入口目录和规则引导。
- 对于支持原生 Skill 目录的宿主，adapter 仍必须通过规则入口提示 Agent 读取 `.starwork/skills.json`，因为宿主目录不记录 StarWork 的来源、所有权和分发原因。

### 6.3 Sessions

会话管理能力。

| 能力 | 含义 |
| --- | --- |
| `sessions.detect_current` | 是否能识别当前会话 ID。 |
| `sessions.rename` | 是否能改名。 |
| `sessions.list` | 是否能列出历史会话。 |
| `sessions.read` | 是否能读取会话内容或摘要。 |
| `sessions.continue` | 是否能继续历史会话。 |
| `sessions.send_message` | 是否能向非当前会话发送消息。 |
| `sessions.create` | 是否能创建新会话。 |
| `sessions.pin` | 是否能置顶。 |
| `sessions.archive` | 是否能归档。 |

### 6.4 Memory

宿主记忆和 transcript 能力。

| 能力 | 含义 |
| --- | --- |
| `memory.transcript_read` | 是否能安全只读 transcript。 |
| `memory.transcript_write` | 是否允许写 transcript。默认应为 `unsupported`。 |
| `memory.summary_visible` | 宿主摘要是否对用户可见。 |
| `memory.project_memory` | 是否有项目级 memory，例如 `CLAUDE.md` 或宿主 memory 目录。 |
| `memory.export` | 是否有官方导出能力。 |

### 6.5 Commands

宿主命令或 API 能力。

| 能力 | 含义 |
| --- | --- |
| `commands.cli_available` | 是否存在宿主 CLI。 |
| `commands.api_available` | 是否有公开或稳定 API。 |
| `commands.requires_auth` | 是否需要登录或授权。 |
| `commands.can_probe` | StarWork 是否能安全探测能力。 |

### 6.6 Safety

安全边界能力。

| 能力 | 含义 |
| --- | --- |
| `safety.private_paths_readonly` | 哪些宿主路径最多只读。 |
| `safety.never_write_paths` | 哪些路径绝不能写。 |
| `safety.destructive_commands` | 哪些宿主命令不可由 StarWork 自动执行。 |
| `safety.degradation_required` | 哪些能力必须降级为人工操作。 |

## 7. 能力等级

每个 adapter 能力必须使用统一等级：

| 等级 | 含义 |
| --- | --- |
| `supported` | 可稳定自动执行。 |
| `partial` | 有入口，但不完整、不稳定或依赖环境。 |
| `manual` | StarWork 只能生成操作提示或可复制内容，由用户手工执行。 |
| `unsupported` | 当前不支持，或不建议依赖。 |
| `unknown` | 尚未调研清楚。 |

规则：

- `partial` 不能被解释成已完成。
- `manual` 不能被伪装成自动执行。
- `unsupported` 不应出现在默认流程里，除非是清楚的解释。
- `unknown` 必须进入待确认问题，不得写进正式承诺。

## 8. 当前宿主能力判断

### 8.1 Codex

定位：当前 MultiAgent 自动编排能力最完整的宿主。

| 能力域 | 判断 |
| --- | --- |
| Rules | `AGENTS.md` 原生友好。 |
| Skills | 支持系统级 Skill 和项目 Skill。 |
| Sessions | 可读取、创建、继续、发送跨会话消息；pin / archive 视具体接口稳定性而定。 |
| Memory | thread 可读，前端刷新不一定及时。 |
| Commands | Codex app-server 可作为 adapter 增强入口。 |
| Safety | 不直接改写 Codex 私有状态。 |

### 8.2 Claude Code

定位：transcript / resume 型宿主，适合做第一个非 Codex adapter 样板。

| 能力域 | 判断 |
| --- | --- |
| Rules | `CLAUDE.md` 是强规则入口，适合承载 StarWork 入口说明。 |
| Skills | 可通过规则入口引导 Skill 使用；具体系统级 Skill 机制需按环境判断。 |
| Sessions | `$CLAUDE_CODE_SESSION_ID` 稳定；`claude --resume <id>` 可继续；不能向非当前会话后台发送 follow-up。 |
| Memory | transcript JSONL 可安全只读；compact 不透明，不能替代 worklog。 |
| Commands | `claude` CLI 可探测，可启动命名会话，可 resume。 |
| Safety | 不写 transcript，不执行 `claude project purge`。 |

### 8.3 Cursor

定位：轻量自动化宿主，适合做 capability probe + 降级执行。

| 能力域 | 判断 |
| --- | --- |
| Rules | Cursor rules 可作为入口。 |
| Skills | 官方支持项目级 `.cursor/skills/` 和 `.agents/skills/`，并兼容 `.claude/skills/`、`.codex/skills/`；StarWork 仍需通过规则入口引导 `.starwork/skills.json`。 |
| Sessions | 可获得部分 chat id / transcript 线索；当前 IDE 会话 ID 无稳定官方直出。 |
| Memory | transcript 可作为调试观察，不应成为正式事实源。 |
| Commands | `cursor agent` 有 create / resume / ls 线索，但认证和 UI 一致性需验证。 |
| Safety | 不直接改写 Cursor 私有数据库。 |

### 8.4 Trae

定位：观察型宿主，当前主要支持项目协作层和人工交付。

| 能力域 | 判断 |
| --- | --- |
| Rules | Trae rules 可作为入口。 |
| Skills | 官方支持项目级 `.trae/skills/` 和 `.agents/skills/`；同名时 `.trae/skills/` 优先，StarWork 仍需通过规则入口引导 `.starwork/skills.json`。 |
| Sessions | 可从 `state.vscdb` 读 session 元数据；不能读完整消息或发送消息。 |
| Memory | 自动摘要和加密数据库不能替代 StarWork worklog。 |
| Commands | `trae-cn` 主要是 IDE 启动器，不提供 chat/session 管理命令。 |
| Safety | 不读取或改写加密 `database.db`；不依赖 snapshot v2。 |

## 9. CLI 影响

### 9.1 `starwork adapt`

当前 `adapt` 应从“生成入口文件”升级为“宿主适配管理命令”。

产品口径：

- `starwork adapt` 主要给 Skill、开发者和高级排查使用。
- 普通用户不需要先理解或手动执行 `adapt`。
- `starworkInit`、`starworkDoctor`、`starworkMultiagent`、`starworkKnowledge` 应在各自流程中包装 adapter 能力；旧 `starworkUpgrade` Skill 的职责由 `starworkDoctor` 承接。
- 对用户展示时，说“正在适配 Cursor / Trae / Claude Code”，不要说“正在写 adapter profile”。

建议后续子能力：

```bash
starwork adapt <host>
starwork adapt <host> --check
starwork adapt <host> --capabilities --json
starwork adapt all
```

v0.1 仍保持兼容：继续生成 `CLAUDE.md`、Cursor rules、Trae rules。

增强方向：

- 写入 `.starwork/workspace.json` 的 adapter profile。
- 输出每个 host 的支持 / 降级能力。
- 不再只说“已生成规则文件”，而是说明宿主能自动做到什么、哪些需要人工。

### 9.2 `starwork doctor`

`doctor` 应增加宿主视角检查：

```bash
starwork doctor --host claude-code
starwork doctor --host cursor
starwork doctor --host trae
```

检查内容：

- 宿主规则入口是否存在。
- 规则入口是否指向 `AGENTS.md`。
- 宿主能力是否与 `.starwork/workspace.json` 记录一致。
- 是否存在危险私有路径写入风险。

### 9.3 `starwork init`

`init` 不应默认问一堆宿主问题。

建议方式：

- 初始化工作台时生成通用 `AGENTS.md`。
- 如果通过 `starworkInit` Skill 触发，用户明确说“我要给 Claude Code / Cursor / Trae 用”时，Skill 负责包装 adapter 流程并生成宿主入口。
- 如果用户直接使用 CLI 且未传 `--adapter`，只做轻量提示：可以继续让 Agent 帮他适配常用 AI 工具。
- 高级用户仍可通过 `starwork init --adapter <host>` 或后续 `starwork adapt <host>` 显式执行。

### 9.4 `starwork multiagent`

`multiagent` 应调用 adapter 的 session 能力，不再把 Codex 能力当成默认能力。

影响：

- `status --host` 应按 host profile 输出。
- `read <lane>` 只在 host 支持读取时自动执行。
- `instruct <lane>` 在不支持后台发送时生成 handoff message。
- `launch <lane>` 在不支持后台创建时生成启动命令或人工步骤。
- 需要新增或规划 `continue <lane>` 和 `handoff <lane>`。

### 9.5 `starwork knowledge`

`knowledge` 应使用 adapter 规则入口解释知识库边界：

- 知识库是长期理解层。
- 参考资料是人类输入。
- 输出是项目成果。
- 宿主 memory / summary 不能替代 StarWork 知识库。

### 9.6 `starwork upgrade`

升级历史模板时，adapter 应参与规则提炼：

- 识别原有 `CLAUDE.md`、Cursor rules、Trae rules。
- 提炼有效规则，不保留混乱或过期内容。
- 写入目标宿主入口，但不覆盖用户原文件。
- 原始宿主规则作为证据保留到升级工作区。

## 10. Skill 影响

### 10.1 `starworkMultiagent`

需要按 host 分支解释：

- Codex：可自动 read / launch / instruct。
- Claude Code：可读 transcript、可 resume，但不能后台发消息。
- Cursor：部分自动化，失败时给人工交付包。
- Trae：主要是人工交付和元数据观察。

流程改造：

- 开始前读取 adapter state；没有 state 时，先探测当前宿主痕迹。
- 对 Codex lane，可以继续使用自动跨会话能力。
- 对 Claude Code lane，优先提供 resume / transcript 摘要能力。
- 对 Cursor / Trae lane，默认生成 handoff message，不说“已自动发送”。
- 生成的跨会话指令要包含目标 lane、任务内容、上下文和完成后回报方式。

### 10.2 `starworkInit`

需要在用户明确提到宿主时，提示：

- 可以先初始化通用 StarWork 工作台。
- Skill 内部再调用 adapter 生成对应宿主入口。
- 不要把宿主入口当作新的工作台结构。

流程改造：

- 如果用户说“给 Cursor / Trae / Claude Code 用”，init Skill 应完成初始化加宿主适配，而不是只给用户一条命令。
- 如果用户没说宿主，最多问一个轻量问题；用户不确定时跳过宿主适配。
- 写入宿主入口前，展示会新增或修改哪些文件，例如 `.cursor/skills/`、`.trae/skills/`、`CLAUDE.md`。
- 完成后调用 `doctor --host` 做检查。

### 10.3 `starworkDoctor`

需要在诊断中区分：

- StarWork 工作台结构是否健康。
- 宿主适配入口是否健康。
- 宿主历史规则是否值得提炼。

流程改造：

- 先做 StarWork 基础诊断，再做宿主诊断。
- 自动探测 `CLAUDE.md`、`.cursor/skills/`、`.trae/skills/`、`.agents/skills/` 等痕迹。
- 如果用户没指定宿主，先列出疑似使用过的宿主，让用户选择是否深入。
- 将 `doctor --host --json` 转译为人话报告，不直接展示内部字段。
- 对可修复问题，先给修复计划，再由用户确认执行。

### 10.4 `starworkKnowledge`

需要知道：

- 宿主 transcript / memory 不是知识库。
- Claude Code transcript 可以作为资料来源，但需要用户确认后吸收。
- Cursor / Trae 的内部历史不应直接吞入知识库。

流程改造：

- 开启 knowledge 后，检查已启用宿主的规则入口是否说明知识库边界。
- 对 Cursor / Trae / Claude Code，Skill 应通过 adapter 更新入口说明，而不是要求用户手动改规则文件。
- 如果用户想从宿主历史中提炼知识，只能作为候选资料，不能直接导入。

### 10.5 `starworkUpgrade`

需要在旧模板升级时包装 adapter 能力：

- 识别旧 `AGENTS.md`、`CLAUDE.md`、Cursor rules、Trae rules。
- 提炼有效内容，不原样复制混乱规则。
- 生成目标宿主入口的升级 blueprint。
- 执行升级后调用 `doctor --host` 验收。

### 10.6 `starworkAudit` / `starworkRepair`

Hub 下的 audit / repair 需要包装 adapter 能力：

- 批量扫描卫星项目启用或疑似启用的宿主。
- 汇总每个项目的宿主入口和 Skill 目录健康状态。
- Repair 只修 StarWork 可控文件，不碰宿主私有数据库和 transcript。

## 11. 文件与数据模型建议

### 11.1 Adapter Profile

建议在 `.starwork/workspace.json` 或未来 `.starwork/adapters.json` 记录：

```json
{
  "version": 1,
  "adapters": {
    "codex": {
      "enabled": true,
      "rules_entry": "AGENTS.md",
      "capabilities": {
        "sessions.detect_current": "partial",
        "sessions.send_message": "supported"
      }
    },
    "claude-code": {
      "enabled": true,
      "rules_entry": "CLAUDE.md",
      "capabilities": {
```

### 11.2 Adapter Module

实现层建议按宿主拆分：

```text
product/adapters/
```

## 12. 实现阶段

### Phase 1：Adapter Contract 和 Capability Profile

目标：

- 输出正式 adapter contract。
- 为 Codex、Claude Code、Cursor、Trae 建立 profile。
- 更新 `starwork adapt --capabilities` 设计。
- 更新 `starworkMultiagent` skill 认知。

验收：

- 文档中不再把 adapter 说成 MultiAgent 子能力。
- 每个 host 都有清楚的 supported / partial / manual / unsupported 能力表。
- Skill 不会承诺宿主不支持的自动操作。

### Phase 2：Skill 包装流程改造

目标：

- 让 `starworkInit`、`starworkDoctor`、`starworkMultiagent`、`starworkKnowledge`、`starworkAudit` 都能包装 adapter 能力；repair blueprint 由 `starworkAudit` 设计、`starwork repair` CLI 执行。
- 普通用户不需要直接学习 `starwork adapt`。
- Skill 能根据宿主能力自动选择“直接执行、生成预览、请求确认、人工交付”。

验收：

- 用户在 init skill 中选择 Cursor / Trae / Claude Code 后，Skill 会完成 adapter 流程。
- Doctor skill 能把宿主问题和 StarWork 结构问题分开说明。
- MultiAgent skill 不会对 Cursor / Trae 承诺自动跨会话派活。
- Knowledge / Upgrade skill 能更新或生成宿主入口规则，但不直接暴露内部 profile 字段。

### Phase 3：`starwork adapt` 升级

目标：

- `adapt` 继续生成规则入口。
- 新增 host capability 输出。
- 写入 adapter profile。
- `doctor --host` 可读取 adapter profile。

验收：

- `starwork adapt claude-code --capabilities --json` 可输出 Claude Code 能力。
- `starwork adapt cursor --capabilities --json` 不承诺 Codex 式后台派活。
- `starwork adapt trae --capabilities --json` 清楚说明人工交付边界。

### Phase 4：Claude Code 样板 Adapter

目标：

- 自动读取 `$CLAUDE_CODE_SESSION_ID`。
- 支持 Claude Code session binding。
- 支持 transcript 只读观察。
- 支持 `continue <lane>` 输出或执行 `claude --resume <id>`。
- 支持 release 时 StarWork 侧 transcript 归档。

验收：

- Claude Code 用户可绑定当前会话为 lane。
- `status --host` 能看到 Claude Code session 元数据。
- `read <lane>` 不倾倒完整 transcript，只输出可控摘要。
- 不写入 Claude Code 私有状态，不执行 `project purge`。

### Phase 5：Cursor / Trae 降级 Adapter

目标：

- Cursor 支持 capability probe、手动 binding、可选 resume 实验。
- Trae 支持 capability probe、手动 binding、元数据观察。
- 两者不支持自动交付时生成 handoff message。

验收：

- Cursor / Trae 用户不会看到虚假的“已发送 / 已创建”。
- `instruct` 在不可自动发送时输出人工交付包。
- `status --host` 能用人话解释当前宿主限制。

### Phase 6：课程和 A 测文档

目标：

- 把 Codex、Claude Code、Cursor、Trae 的差异写进 A 测指南。
- 课程里强调 StarWork MultiAgent 是“项目协作协议 + 宿主增强”，不是所有宿主都能自动调度。

验收：

- 用户知道 Codex 最适合自动编排。
- 用户知道 Claude Code 适合 resume / transcript。
- 用户知道 Cursor 是部分自动化。
- 用户知道 Trae 当前主要是人工交付和元数据观察。

## 13. 待确认问题

## 14. 当前产品判断

下一步不应直接做 Cursor / Trae / Claude Code 的零散适配，而应先做 Host Adapter Contract。

第一批实现建议：

1. Adapter capability profile。
2. `starwork adapt --capabilities`。
3. `starworkMultiagent` 按 host 降级的 skill 认知。
4. Claude Code transcript / resume 样板。

这样 StarWork 才不会把 Codex 的强能力误当成所有宿主的共同能力。
