# StarWork Host Adapter v0.1 落地开发 SPEC

## 1. 状态

- 日期：2026-06-02
- 状态：ready-for-development
- 所属功能：Host Adapters
- 前置文档：[StarWork Host Adapter 总 SPEC](v0.1.md)
- 开发目标：先搭建通用 adapter 架子，再按宿主逐个适配
- 第一批宿主：Codex、Claude Code、Cursor、Trae

参考来源：

- Trae Skills 官方文档：`https://docs.trae.cn/ide/skills`
- Cursor Agent Skills 官方文档：`https://cursor.com/cn/docs/skills`

## 2. 开发目标

本 SPEC 要解决的问题：

1. Adapter 成为 StarWork 全局能力，不再只是 `starwork adapt` 的规则文件生成器。
2. CLI 和 Skill 能根据宿主能力做正确降级，不把 Codex 的能力误当成所有宿主都支持。
3. 先建立稳定的 adapter contract、profile、状态文件和 CLI 输出，再逐个实现宿主适配。
4. 每个阶段都有明确验收标准，方便开发 lane 分段提交、产品 lane 分段验收。

## 3. 非目标

v0.1 不做：

- 不重写 Core / Kit / Pack 结构。
- 不把宿主私有 history / transcript 变成 StarWork 正式事实源。
- 不直接改写 Cursor、Trae、Claude Code、Codex 的私有数据库或 transcript。
- 不承诺 Cursor / Trae / Claude Code 支持 Codex 式后台跨会话指令。
- 不实现复杂插件安装器。
- 不实现跨宿主统一 UI。
- 不实现自动调度、定时任务、文件锁或并发冲突仲裁。

## 4. 总体架构

Host Adapter v0.1 分成四层：

```text
product/adapters/                 # 产品内置宿主适配定义
  contract.md                      # adapter contract
  <host>/profile.json              # 宿主能力表
  <host>/rules.md                  # 宿主规则入口模板说明
  <host>/safety.md                 # 宿主安全边界

product/cli/src/cli.js             # CLI 执行层，v0.1 可继续单文件实现
  adapter registry                 # 读取 / 内置 host profile
  adapt command                    # 生成入口、输出能力、写入状态
  doctor host checks               # 宿主适配健康检查
  multiagent host routing          # 按 host 能力降级

.starwork/adapters.json            # 工作台内 adapter 状态
.starwork/workspace.json           # 保留 v0.1 adapters 摘要字段，兼容旧逻辑
```

原则：

- `product/adapters/` 是产品事实源，说明每个宿主能力和安全边界。
- `.starwork/adapters.json` 是具体工作台的运行状态，不写业务内容。
- `.starwork/workspace.json.adapters` 保留摘要，不再承载全部 adapter 细节。
- CLI 可以先集中实现，但概念和配置必须按 adapter contract 分层。

## 5. 数据模型

### 5.1 Host Profile

每个宿主一个 profile，建议位置：

```text
product/adapters/<host>/profile.json
```

最小结构：

```json
{
  "schema": "starwork.adapter.profile.v0.1",
  "host": "claude-code",
  "label": "Claude Code",
  "rules": {
    "entry_file": "CLAUDE.md",
    "can_generate_entry": "supported",
    "can_update_entry": "partial",
    "supports_project_scope": "supported",
    "supports_nested_rules": "unknown"
  },
  "skills": {
    "system_install": "manual",
    "project_mount": "manual",
    "primary_project_dir": ".claude/skills/",
    "project_mount_dirs": [
      ".agents/skills/",
      ".claude/skills/"
    ],
    "host_native_dirs": [
      ".claude/skills/"
    ],
    "global_dirs": [
      "~/.claude/skills/"
    ],
    "conflict_priority": [
      ".claude/skills/",
      ".agents/skills/"
    ],
    "discovery": "manual",
    "trigger_style": "rules-guided",
    "adapter_rule_required": true
  },
  "sessions": {
    "detect_current": "supported",
    "rename": "partial",
    "list": "partial",
    "read": "supported",
    "continue": "supported",
    "send_message": "manual",
    "create": "partial",
    "pin": "unsupported",
    "archive": "unsupported"
  },
  "memory": {
    "transcript_read": "supported",
    "transcript_write": "unsupported",
    "summary_visible": "unsupported",
    "project_memory": "supported",
    "export": "partial"
  },
  "commands": {
    "cli_available": "partial",
    "api_available": "unsupported",
    "requires_auth": "partial",
    "can_probe": "supported"
  },
  "safety": {
    "private_paths_readonly": [
      "~/.claude/projects/**",
      "~/.claude/sessions/**"
    ],
    "never_write_paths": [
      "~/.claude/projects/**/*.jsonl",
      "~/.claude.json"
    ],
    "destructive_commands": [
      "claude project purge"
    ],
    "degradation_required": [
      "sessions.send_message",
      "sessions.pin",
      "sessions.archive"
    ]
  }
}
```

能力等级只允许：

```text
supported | partial | manual | unsupported | unknown
```

Skill 目录字段规则：

- `skills.project_mount_dirs` 是 StarWork 在项目内写入、复制或软链 Skill 的目标目录。
- `skills.primary_project_dir` 是当前宿主最推荐的项目级 Skill 目录。
- `skills.host_native_dirs` 是宿主可能自动发现的项目级 Skill 目录；如果宿主没有稳定发现机制，则写空数组。
- `skills.global_dirs` 是宿主全局 Skill 目录；StarWork 只提示用户，不默认写入。
- `skills.conflict_priority` 记录多个目录出现同名 Skill 时的优先级。
- `skills.adapter_rule_required=true` 表示必须通过宿主规则入口告诉 Agent 读取 `.starwork/skills.json` 和对应 Skill 目录。
- `.starwork/skills.json` 是项目实际可用 Skill 清单，不能被任何宿主目录替代。

### 5.2 Workspace Adapter State

新增：

```text
.starwork/adapters.json
```

结构：

```json
{
  "schema": "starwork.adapters.state.v0.1",
  "updated_at": "2026-06-02T00:00:00.000Z",
  "adapters": {
    "claude-code": {
      "enabled": true,
      "rules_entry": "CLAUDE.md",
      "profile_version": "0.1",
      "installed_by": "starwork adapt claude-code",
      "installed_at": "2026-06-02T00:00:00.000Z",
      "capabilities": {
        "sessions.detect_current": "supported",
        "sessions.continue": "supported",
        "sessions.send_message": "manual",
        "memory.transcript_read": "supported"
      },
      "last_probe": {
        "status": "pass",
        "observed_at": "2026-06-02T00:00:00.000Z",
        "facts": [],
        "warnings": []
      },
      "generated_entries": [
        "CLAUDE.md"
      ]
    }
  }
}
```

兼容策略：

- `.starwork/workspace.json.adapters` 继续保留简略安装记录，例如 `{ "claude-code": { "installed_at": "..." } }`。
- 新逻辑优先读 `.starwork/adapters.json`。
- 如果只有旧 `workspace.json.adapters`，`doctor --host` 应提示“旧 adapter 记录，可通过 `starwork adapt <host> --capabilities` 刷新”。

## 6. Host Profile 初始矩阵

### 6.0 官方 Skill 规范约束

Cursor 和 Trae 都已经支持项目级 Skill，但目录和优先级不同，adapter 不能再只按 `.agents/skills/` 一种入口处理。

Cursor 官方规范要点：

- 项目级目录包括 `.cursor/skills/` 和 `.agents/skills/`。
- Cursor 还兼容 `.claude/skills/`、`.codex/skills/` 以及对应全局目录。
- Skill 文件夹必须包含 `SKILL.md`。
- `SKILL.md` frontmatter 必须包含 `name` 和 `description`。
- `name` 只能使用小写字母、数字和连字符，并且必须与父文件夹名一致。
- 可选字段包括 `paths`、`disable-model-invocation`、`metadata`。
- 可选资源目录包括 `scripts/`、`references/`、`assets/`。
- Cursor 支持递归发现；嵌套目录下的 Skill 可按子目录作用域生效。

Trae 官方规范要点：

- 项目级目录包括 `.trae/skills/`。
- 全局目录为 macOS / Linux 的 `~/.trae-cn/skills`，Windows 的 `%userprofile%/.trae-cn/skills`。
- Trae 也支持 `.agents/skills/`。
- `.trae/skills/` 与 `.agents/skills/` 存在同名 Skill 时，`.trae/skills/` 优先。
- 被禁用的项目 Skill 记录在 `.trae/skill-config.json`。
- Skill 文件夹必须包含 `SKILL.md`，并通过 frontmatter 提供 `name` 和 `description`。

StarWork 的处理原则：

- Cursor 优先写 `.cursor/skills/`，可同步 `.agents/skills/` 作为跨宿主入口。
- Trae 优先写 `.trae/skills/`，可同步 `.agents/skills/` 作为跨宿主入口。
- `.starwork/skills.json` 仍是 StarWork 的项目 Skill 事实清单；宿主目录只负责让宿主看见 Skill。
- `doctor --host` 必须检查宿主目录之间的同名冲突、Skill frontmatter 合法性，以及 `.starwork/skills.json` 与实际目录是否一致。

### 6.1 Codex

- rules：`AGENTS.md`
- skills.primary_project_dir：`.agents/skills/`
- skills.project_mount_dirs：`.agents/skills/`
- skills.host_native_dirs：`.agents/skills/`
- skills.global_dirs：`~/.agents/skills/`
- skills.discovery：`supported` 或 `partial`，按实际 Codex / Agent 环境确认；若无法确认先标 `partial`
- sessions.read：`supported`
- sessions.send_message：`supported`
- sessions.create：`supported`
- sessions.continue：`supported`
- sessions.pin / archive：按当前实现可先标 `partial` 或 `unsupported`
- memory.transcript_read：`partial`
- safety：不写 Codex 私有状态

Codex 是 MultiAgent 自动编排样板，但不应反向定义所有宿主的默认能力。

- skills.primary_project_dir：`.claude/skills/`

- skills.project_mount_dirs：`.cursor/skills/`，必要时同时写 `.agents/skills/` 作为开放标准兼容入口

- sessions.send_message：`partial`
- sessions.create：`partial`

## 7. CLI 落地设计

### 7.1 `starwork adapt`

保留现有用法：

```bash
starwork adapt claude
starwork adapt cursor
starwork adapt trae
starwork adapt all
```

新增或明确：

```bash
starwork adapt <host> --capabilities
starwork adapt <host> --capabilities --json
starwork adapt <host> --check
starwork adapt <host> --dry-run
starwork adapt <host> --target <path> --yes
```

host 别名：

| 输入 | 标准 host |
| --- | --- |
| `codex` | `codex` |
| `claude` | `claude-code` |
| `claude-code` | `claude-code` |
| `cursor` | `cursor` |
| `trae` | `trae` |
| `all` | 全部 |

行为：

1. 先执行现有 doctor 阻塞检查。
2. 读取目标 workspace language 和 role paths。
3. 加载 host profile。
4. 生成或检查宿主规则入口。
5. 检查并按需创建该 host 需要的 Skill 挂载目录。
6. 如果已有 `.starwork/skills.json`，检查其中的 mount target 是否覆盖当前 host 的 `skills.project_mount_dirs`。
7. 写入 `.starwork/adapters.json`。
8. 同步 `.starwork/workspace.json.adapters` 摘要。
9. 输出人话说明：这个宿主能自动做什么，哪些需要人工。

冲突规则：

- 如果宿主入口文件不存在，直接创建。
- 如果宿主入口文件已存在且含 StarWork 管理标记，可安全更新。
- 如果宿主入口文件已存在但不是 StarWork 管理文件，不覆盖，生成旁路文件并提示用户合并。

建议管理标记：

```md
<!-- STARWORK:ADAPTER_ENTRY v0.1 host=claude-code -->
```

验收要点：

- 现有 `starwork adapt claude/cursor/trae` 流程不破坏。
- `--capabilities --json` 不写文件。
- `--dry-run` 不写 `.starwork/adapters.json`。
- 有用户自写 `CLAUDE.md` 时不覆盖。
- `adapt claude-code --dry-run` 能展示将检查或创建 `.claude/skills/`。
- `adapt cursor --dry-run` 能展示将检查或创建 `.cursor/skills/`，并通过 Cursor rules 引导读取 `.starwork/skills.json`。
- `adapt trae --dry-run` 能展示将检查或创建 `.trae/skills/`，并通过 Trae rules 引导读取 `.starwork/skills.json`。

### 7.2 `starwork doctor --host`

新增：

```bash
starwork doctor --host claude-code
starwork doctor --host cursor
starwork doctor --host trae
starwork doctor --host all
starwork doctor --host claude-code --json
```

检查项：

- StarWork 工作台基础健康。
- `.starwork/adapters.json` 是否存在。
- host 是否已启用。
- 宿主入口文件是否存在。
- 宿主入口文件是否指向 `AGENTS.md`。
- 宿主入口文件是否包含当前项目状态和当前工作入口。
- host profile 声明的 `skills.project_mount_dirs` 是否存在。
- `.starwork/skills.json` 中的 mount targets 是否覆盖当前 host 所需目录。
- 宿主原生 Skill 目录和通用 `.agents/skills/` 中是否存在同名 Skill 冲突。
- 规则入口是否明确提示读取 `.starwork/skills.json`，避免宿主原生目录绕过 StarWork 的来源和分发记录。
- host profile 中的危险路径是否被 StarWork 写入过。
- 当前能力状态是否会误导用户，例如 Trae 标成 `send_message=supported`。

输出原则：

- 不要求所有宿主都启用。
- 未启用 host 时输出 info，不作为 fail。
- 已启用 host 且入口缺失，输出 warning 或 fail。
- 已启用 host 但 Skill 挂载目录缺失，输出 warning。
- 已启用 host 但 `.starwork/skills.json` 缺失，输出 info 或 warning；不要当成 Core 结构错误。
- 安全风险，例如准备写私有数据库，必须 fail。

### 7.3 `starwork init`

v0.1 不新增复杂交互。

调整：

- init 完成后，如果用户传入 `--adapter <host>`，执行对应 `adapt`。
- 如果通过 `starworkInit` Skill 触发，Skill 负责询问宿主并包装 adapter 流程。
- 如果用户直接使用 CLI 且未传 `--adapter`，只给轻量提示，不强迫用户理解 adapter。

```text
如果你主要使用 Claude Code / Cursor / Trae，可以让 Agent 继续帮你适配这个工具。
高级用户也可以运行 starwork adapt <host>。
```

建议暂不加入交互问题，避免 init 过重。

### 7.4 `starwork multiagent`

MultiAgent 调用 adapter session 能力。

需要调整：

- session id 支持 `codex:`、`claude-code:`、`cursor:`、`trae:`。
- `bind` 在未传 `--session` 时，可按当前宿主尝试自动识别：
  - Codex：当前已有逻辑。
  - Claude Code：读 `$CLAUDE_CODE_SESSION_ID`。
  - Cursor：暂不自动识别，除非 probe 能确认。
  - Trae：暂不自动识别，除非 probe 能确认。
- `status --host` 按 host 分支：
  - Codex：读 thread。
  - Claude Code：读 session metadata / transcript metadata。
  - Cursor：读 capability probe 结果。
  - Trae：读 capability probe 结果。
- `read <lane>`：
  - Codex：读 thread。
  - Claude Code：读 transcript 摘要。
  - Cursor：v0.1 可返回 partial / manual，后续实现 transcript 摘要。
  - Trae：返回 unsupported，并提示用 worklog。
- `instruct <lane>`：
  - Codex：自动发送。
  - Claude Code / Cursor / Trae：不能自动发送时生成 handoff message。
- `launch <lane>`：
  - Codex：自动创建 thread。
  - Claude Code：生成启动命令。
  - Cursor：可实验性生成 / 执行 create-chat，但默认先 manual / partial。
  - Trae：生成人工步骤。

新增建议：

```bash
starwork multiagent continue <lane>
starwork multiagent handoff <lane> --message "<text>"
```

`continue`：

- Claude Code：输出或执行 `claude --resume <session-id>`。
- Cursor：输出或执行 `cursor agent --resume <chatId>`，前提是 capability 可用。
- Trae：输出 UI 操作步骤。
- Codex：可用现有 read / instruct 能力，不急于新增。

`handoff`：

- 生成 StarWork 格式化消息。
- 写入 shared context。
- 不声称已送达。
- 用于低自动化宿主的人工交付。

### 7.5 `starwork knowledge`

Adapter 对 knowledge 的影响：

- `knowledge init` 成功后，如果已启用 host adapter，应提醒该宿主规则入口也会引导知识库边界。
- `knowledge check --host <host>` 可作为后续增强，检查宿主入口是否说明：
  - 知识库是长期理解层。
  - 不要把参考资料、草稿、输出混入知识库。
  - 宿主 transcript / summary 不是知识库。
- Claude Code transcript 可以作为候选资料来源，但必须用户确认后吸收。
- Cursor / Trae 内部 history 不直接作为知识库来源。

v0.1 实现建议：

- 先更新 adapter 规则入口模板，加入 knowledge 边界。
- 暂不做自动 transcript 吸收。

### 7.6 `starwork upgrade`

Adapter 对 upgrade 的影响：

- starworkDoctor / upgrade blueprint 应识别旧宿主规则文件：
  - `CLAUDE.md`
  - `.cursor/rules/**`
  - `.trae/rules/**`
  - 旧 `AGENTS.md`
- 规则提炼后写入新 adapter 入口。
- 不覆盖用户原规则，原文件应保留或复制到升级证据区。
- 如果旧规则混乱，skill 应总结“可保留规则”和“废弃规则”，不要原样塞回新入口。

v0.1 实现建议：

- 先在 spec 和 skill 中明确规则。
- CLI upgrade 暂不自动重写复杂规则，继续按 blueprint 执行。

### 7.7 `starwork audit / repair`

Adapter 对 hub 管理的影响：

- Hub audit 检查项目时，可汇总每个项目启用的 adapter。
- Repair 只修 StarWork adapter state 或规则入口缺失，不修宿主私有状态。
- Hub 不应替卫星项目直接读取宿主 transcript，除非用户显式授权。

## 8. Skill 落地设计

### 8.0 产品判断

`starwork adapt` 是底层工具命令，不是主要面向普通用户的入口。

对用户来说，更自然的入口应该是：

- “帮我初始化 StarWork 工作台” -> `starworkInit`
- “帮我检查这个工作台有没有问题” -> `starworkDoctor`
- “帮我管理多个 Agent Lane” -> `starworkMultiagent`
- “帮我开启知识库” -> `starworkKnowledge`
- “帮我从旧模板升级” -> `starworkDoctor`

这些 Skill 在流程里调用 adapter 能力，必要时才向用户展示底层命令。用户不需要先理解 `adapter profile`、`host_native_dirs`、`capabilities` 这些概念。

Skill 的统一流程原则：

1. 先识别用户当前主要使用的宿主：Codex、Claude Code、Cursor、Trae，或不确定。
2. 如果用户不确定，不强迫选择；先按 StarWork 通用入口生成，后续可补宿主适配。
3. Skill 内部可调用 `starwork adapt <host> --capabilities --json` 获取能力，但不要把原始 JSON 直接甩给用户。
4. Skill 内部可调用 `starwork adapt <host> --dry-run` 生成执行预览，再用人话解释会改哪些文件。
5. 真正写入文件前，Skill 应让用户确认，除非用户已经明确要求“直接执行”。
6. 写入后，Skill 应调用 `starwork doctor --host <host>` 做二次检查。
7. 对不支持自动能力的宿主，Skill 必须输出人工交付步骤，不能说“已完成自动派发”。

底层命令与 Skill 的关系：

| CLI 能力 | 谁主要使用 | 用户是否需要直接感知 |
| --- | --- | --- |
| `starwork adapt --capabilities --json` | Skill / 开发者 | 默认不展示，只转译为人话。 |
| `starwork adapt --dry-run` | Skill / 开发者 | 可展示摘要，不展示内部字段。 |
| `starwork adapt <host> --yes` | Skill 在用户确认后调用 | 用户只需知道“正在适配 Cursor / Trae / Claude Code”。 |
| `starwork doctor --host <host>` | Skill / 用户排查 | 可展示人话诊断结果。 |
| `starwork multiagent ...` | Skill / 高级用户 | Skill 应解释当前宿主能自动做什么。 |

### 8.1 Skill 目录认知

默认解释：

| Host | 项目 Skill 入口 | Skill 话术要求 |
| --- | --- | --- |
| Codex | `.agents/skills/` | 可提示读取通用 StarWork 项目 Skill 入口。 |
| Claude Code | `.claude/skills/`，必要时参考 `.agents/skills/` | 优先提示 Claude Code 使用 `.claude/skills/`；不要只说 `.agents/skills/`。 |
| Cursor | `.cursor/skills/`，可同步 `.agents/skills/` | Cursor 官方支持自动发现项目级 Skill；rules 仍要引导 Agent 读 `.starwork/skills.json`。 |
| Trae | `.trae/skills/`，可同步 `.agents/skills/` | Trae 官方支持自动发现项目级 Skill；同名时 `.trae/skills/` 优先，rules 仍要引导 Agent 读 `.starwork/skills.json`。 |

`.starwork/skills.json` 是项目 Skill 事实清单；宿主目录是入口，不是事实源。

### 8.2 `starworkInit`

`starworkInit` 是 adapter 最常见的包装入口。

触发场景：

- 用户说“帮我初始化 StarWork”。
- 用户说“我要给 Cursor / Trae / Claude Code 用”。
- 用户说“帮我建立一个适合某个 AI 工具使用的工作区”。

改造后的流程：

1. 先完成原有工作台类型判断：项目工作台 / 项目中心。
2. 询问或识别主要使用环境：
   - 如果用户已经明确说 Cursor / Trae / Claude Code / Codex，直接采用。
   - 如果用户没说，只问一个轻量问题：“你主要准备用哪个 AI 工具打开这个工作台？”
   - 如果用户选择“暂不确定”，跳过 adapter，仅生成通用 StarWork 工作台。
3. 初始化工作台主体结构。
4. 如果已选择宿主，Skill 调用 `starwork adapt <host> --dry-run`。
5. Skill 用人话解释将补充哪些入口：
   - Cursor：`.cursor/skills/` 和 `.cursor/rules/starwork.mdc`
   - Trae：`.trae/skills/` 和 `.trae/rules/starwork.md`
   - Claude Code：`.claude/skills/` 和 `CLAUDE.md`
   - Codex：确认 `AGENTS.md` 和 `.agents/skills/`
6. 用户确认后，Skill 调用 `starwork adapt <host> --yes`。
7. Skill 调用 `starwork doctor --host <host>`，确认宿主入口可用。
8. 输出最终说明：用户接下来应该用哪个 AI 工具打开、它会读哪些规则和 Skill。

`starworkInit` 不能做的事：

- 不把宿主选择混同为工作台类型。
- 不默认给所有宿主都生成入口。
- 不要求普通用户理解 adapter。
- 不直接推荐用户手动执行 `starwork adapt`，除非用户是开发者或要求命令。

验收：

- 用户说“我要给 Cursor 用”，Skill 会完成 init + cursor adapter 流程，而不是只提示一条命令。
- 用户说“我不确定用什么工具”，Skill 不阻塞 init。
- Skill 输出只说“Cursor 入口”“Trae 入口”“Claude Code 入口”，不直接解释 `host profile`。
- Skill 完成后必须告诉用户改了哪些文件、下一步用哪个工具打开、如何验证是否生效。

### 8.3 `starworkDoctor`

`starworkDoctor` 是 adapter 的诊断入口。

触发场景：

- 用户说“帮我检查这个 StarWork 项目”。
- 用户说“为什么 Cursor / Trae / Claude Code 看不到 skill？”
- 用户说“这个工作台在某个 AI 工具里不好用”。

改造后的流程：

1. 先运行普通 `starwork doctor`，判断 StarWork 工作台基础结构是否健康。
2. 探测宿主痕迹：
   - `AGENTS.md` / `.agents/skills/` -> Codex / 通用 Agent
   - `CLAUDE.md` / `.claude/skills/` -> Claude Code
   - `.cursor/rules/` / `.cursor/skills/` -> Cursor
   - `.trae/rules/` / `.trae/skills/` / `.trae/skill-config.json` -> Trae
3. 如果用户未指定宿主，Skill 用人话列出“看起来这个工作台可能给哪些工具用过”，让用户选择是否深入检查。
4. 对选定宿主调用 `starwork doctor --host <host> --json`。
5. Skill 把 JSON 转成诊断报告：
   - 工作台结构问题
   - 宿主入口问题
   - Skill 目录问题
   - 同名 Skill 冲突
   - 宿主能力限制
6. 对可修复问题，Skill 先输出修复计划；需要写文件时再调用 `starwork adapt <host> --yes` 或后续 repair。
7. 对不可自动修复问题，输出人工步骤。

特别规则：

- 不能把宿主适配问题说成 Core 坏了。
- 不能把 Cursor / Trae 不支持后台跨会话派活说成 StarWork 故障。
- 不能把 `.starwork/skills.json` 缺失直接判成严重错误；要看项目是否已启用 Skill 管理。
- 对 Trae，如果 `.trae/skill-config.json` 禁用了 StarWork 声明启用的 Skill，应提示“这个 Skill 可能被 Trae 关掉了”。

验收：

- Cursor 项目缺 `.cursor/skills/` 时，Doctor Skill 会指出“Cursor 看不到项目 Skill 入口”，而不是输出内部字段。
- Trae 项目存在 `.trae/skills/foo` 和 `.agents/skills/foo` 同名时，Doctor Skill 会提示优先级冲突。
- Doctor Skill 能清楚区分“项目结构问题”和“宿主适配问题”。

### 8.4 `starworkMultiagent`

必须新增 host 分支：

| Host | Skill 话术 |
| --- | --- |
| Codex | 可以自动读取、发送、创建会话，但仍以 StarWork worklog 为准。 |
| Claude Code | 可以绑定当前会话、读取 transcript、resume；不能后台发消息给非当前会话。 |
| Cursor | 部分自动化，失败时生成可复制交付消息。 |
| Trae | 主要是项目协作记录和人工交付。 |

`instruct` 结果解释：

- Codex 自动发送成功：可以说已送达。
- `started_unverified`：不能说完成。
- Manual handoff：只能说已生成交付消息，等待用户手动发送。

改造后的流程：

1. 开始前读取当前工作台 adapter state。
2. 如果没有 adapter state，Skill 根据当前宿主痕迹和用户说法判断：
   - 当前在 Codex：可直接使用 Codex 会话能力。
   - 当前在 Claude Code：先引导或自动执行 Claude Code adapter。
   - 当前在 Cursor / Trae：先确认宿主支持边界，再进入人工交付优先流程。
3. 创建 lane 时，根据宿主能力决定：
   - Codex：可以创建 thread。
   - Claude Code：生成或执行 resume / launch 命令。
   - Cursor：默认生成人工启动步骤，能力可用时再执行。
   - Trae：默认生成人工启动步骤。
4. 发送跨会话指令时，根据能力决定：
   - Codex：可以 `send_message_to_thread`。
   - Claude Code / Cursor / Trae：默认生成格式化 handoff message。
5. 读取 lane 状态时，根据能力决定：
   - Codex：读 thread。
   - Claude Code：读 transcript 摘要。
   - Cursor：如果无稳定读取能力，读取 StarWork worklog / handoff。
   - Trae：读取 StarWork worklog / handoff，不读加密数据库。

验收：

- Skill 不会对 Cursor / Trae 说“已自动发送给另一个会话”。
- Skill 会把“可自动完成”和“需要人工复制”的步骤分开。
- Skill 生成的 handoff message 明确包含目标 lane、任务、上下文和完成后回报方式。

### 8.5 `starworkKnowledge`

`starworkKnowledge` 应通过 adapter 确保不同宿主都理解知识库边界。

触发场景：

- 用户说“帮我开启知识库”。
- 用户说“让 Cursor / Trae / Claude Code 也能正确使用知识库”。
- 用户说“把以前的资料整理成 StarWork 知识库”。

改造后的流程：

1. 先检查 StarWork knowledge capability 是否已启用。
2. 如果未启用，走 knowledge init 流程。
3. 探测或询问用户主要宿主。
4. 对已启用宿主，检查规则入口是否说明：
   - 知识库是长期理解层。
   - 参考资料是输入材料。
   - 工作区 / 输出是过程和成果。
   - 宿主 transcript / memory 不是 StarWork 知识库。
5. 如果规则入口缺少知识库说明，Skill 调用 adapter 更新入口。
6. 如果用户想从 Claude Code transcript 中提炼知识，Skill 只能作为候选资料处理，需要用户确认。
7. 对 Cursor / Trae，除非有稳定官方导出能力，不建议直接吸收内部历史。

验收：

- Skill 不会把宿主 memory / transcript 说成知识库。
- 开启 knowledge 后，Cursor / Trae / Claude Code 的入口规则都能读到 knowledge 边界。
- 需要写宿主入口时，Skill 会说明改了哪个入口文件。

### 8.6 `starworkDoctor` upgrade flow

独立 `starworkUpgrade` 系统 Skill 已取消；旧模板用户迁移时最容易接触 adapter 的入口是 `starworkDoctor` 的 upgrade blueprint 流程。

触发场景：

- 用户已有旧项目，想升级到 StarWork。
- 用户已有 `CLAUDE.md`、Cursor rules、Trae rules 或其他 Agent 规则文件。
- 用户想保留原有 AI 使用习惯。

改造后的流程：

1. 调用 doctor / runtime scan 获取目录、规则文件和宿主痕迹。
2. 读取旧规则文件，但不直接原样搬进新规则。
3. Skill 将旧规则分三类：
   - 可保留：项目事实、工作边界、用户偏好。
   - 需要改写：旧目录路径、旧术语、旧工作流。
   - 应废弃：过期命令、冲突规则、污染业务目录的临时指令。
4. 根据目标宿主生成 adapter 入口计划。
5. 将提炼结果写入 upgrade blueprint。
6. 用户确认 blueprint 后，由 `starwork upgrade` / repair 执行。
7. 执行后调用 `doctor --host` 做验收。

验收：

- 旧 `CLAUDE.md` / Cursor rules / Trae rules 的有效内容会被提炼，不会丢失。
- 升级后的入口不出现 StarWork 内部占位符。
- 旧规则原文保留在升级证据区，不直接污染新 AGENTS / host rules。

### 8.7 `starworkAudit` / `starwork repair`

当前没有独立 `starworkRepair` Skill；Hub 下的 `starworkAudit` 和 `starwork repair` CLI 应包装 adapter 能力，而不是要求用户逐个项目运行命令。

改造后的流程：

1. Hub Skill 读取 `projects/registry.json`。
2. 针对每个卫星项目运行基础健康检查。
3. 探测每个卫星项目启用或疑似启用的宿主。
4. 对每个宿主调用 `doctor --host <host> --json`。
5. 汇总为 Hub 视角报告：
   - 哪些项目适配了 Cursor。
   - 哪些项目适配了 Trae。
   - 哪些项目只有通用入口。
   - 哪些项目存在 Skill 冲突。
6. Repair 只修 StarWork 可控文件：规则入口、adapter state、Skill mount dirs。
7. Repair 不读写宿主私有数据库，不碰 transcript。

验收：

- Hub audit 能看到项目级 adapter 健康状态。
- Hub repair 不会跨项目误改业务文档。
- 修复计划会明确列出每个项目将修改哪些 StarWork 文件。

### 8.8 用户视角补充验收

从用户角度，adapter 能力必须满足下面这些体验条件，否则即使底层命令可用，也不算完整。

#### 适配成功后，用户要知道发生了什么

每个 Skill 包装完成 adapter 后，必须输出三件事：

1. 已为哪个工具适配：例如 Cursor、Trae、Claude Code。
2. 改动了哪些 StarWork 可控文件：例如 `.cursor/skills/`、`.trae/rules/starwork.md`、`CLAUDE.md`。
3. 用户接下来怎么验证：例如重新打开 Cursor / Trae，或运行一次 `starwork doctor --host <host>`。

不能只输出“适配完成”。

#### 多宿主并存必须可行

同一个 StarWork 工作台可以同时适配多个宿主。

规则：

- 不默认给所有宿主生成入口。
- 用户选择第二个宿主时，不删除第一个宿主的入口。
- `.starwork/adapters.json` 必须支持多个 host 同时 `enabled=true`。
- `doctor --host all` 应按宿主分别报告，不把 Cursor 的限制说成 Trae 的问题。
- 同名 Skill 冲突要按宿主优先级解释，不能直接删除任意一侧。

#### 用户不选宿主也必须能用

如果用户不确定自己会用哪个 AI 工具：

- init 仍然生成通用 StarWork 工作台。
- `AGENTS.md` 和 `.starwork/workspace.json` 仍是基础入口。
- 后续随时可以通过 Skill 补做宿主适配。
- Doctor 不应因为没有 adapter state 就报错。

#### 失败后要能恢复

adapter 写入必须尽量原子化：

- 先 dry-run，再确认写入。
- 入口文件已有用户内容时不覆盖。
- 只有写入成功后才更新 `.starwork/adapters.json`。
- 如果中途失败，Doctor 应能提示哪些文件已生成、哪些状态未写入。
- StarWork 管理的入口文件应带管理标记，方便后续安全更新。

#### 宿主刷新问题要讲人话

Cursor / Trae 写入 Skill 目录后，宿主 UI 是否立即发现仍需实测。

v0.1 用户提示必须保守：

- 如果宿主没有立即看到 Skill，先提示用户重启窗口或刷新项目。
- 不说“Cursor / Trae 一定会立刻识别”。
- A 测指南要记录是否需要重启、重新打开项目或触发一次聊天。

验收：

- `starworkKnowledge` Skill 中明确：宿主 transcript / memory 不是 StarWork 知识库。
- `starworkDoctor` Skill 中明确：旧宿主规则要提炼后迁移，不原样复制。
- `starworkAudit` Skill 中明确：只修 StarWork 可控文件，不碰宿主私有状态。
- 所有 Skill 面向用户的话术避免 `adapter profile`、`host_native_dirs`、`capabilities` 等内部词。

### Phase 3：`starwork adapt --capabilities`

目标：

- `starwork adapt <host> --capabilities` 输出人类可读能力表。
- `starwork adapt <host> --capabilities --json` 输出结构化 profile。
- `all` 支持汇总所有 host。
- 不写文件。

验收：

- `starwork adapt claude-code --capabilities --json` 可输出 `claude-code` profile。
- `starwork adapt cursor --capabilities` 明确说明 partial / manual 能力。
- `starwork adapt trae --capabilities` 明确说明 Trae 不能自动发送跨会话指令。
- `--capabilities --json` 输出中包含每个 host 的 Skill 目录策略。
- `--capabilities --dry-run` 与无 `--dry-run` 行为一致：都不写文件。
- 旧 `starwork adapt claude/cursor/trae --dry-run` 仍可用。

### Phase 4：Workspace Adapter State

目标：

- 新增 `.starwork/adapters.json` 写入逻辑。
- `starwork adapt <host>` 生成规则入口后写入 adapter state。
- `.starwork/workspace.json.adapters` 保留摘要兼容。

验收：

- 对健康工作台执行 `starwork adapt claude-code --yes` 后生成或更新 `.starwork/adapters.json`。
- `adapters.json` 包含 schema、host、rules_entry、capabilities、generated_entries。
- `adapters.json` 支持多个 host 同时启用，不会因为新增 Cursor 而删除 Claude Code 记录。
- `adapters.json` 记录对应 host 的 Skill mount dirs 摘要或可从 profile 追溯。
- `--dry-run` 不写 `adapters.json`。
- `adapt claude-code --yes` 至少保证 `.claude/skills/` 存在。
- `adapt cursor --yes` 至少保证 `.cursor/skills/` 存在，并让规则入口说明如何读取 `.starwork/skills.json`。
- `adapt trae --yes` 至少保证 `.trae/skills/` 存在，并让规则入口说明如何读取 `.starwork/skills.json`。
- 如果入口文件已有用户内容，不覆盖，生成旁路文件或提示。
- 如果写入中途失败，不应写入“已启用”的 adapter state；doctor 能提示残留文件和未完成状态。
- 旧测试全部通过。

### Phase 5：`doctor --host`

目标：

- `doctor` 支持 `--host <host|all>`。
- 检查 adapter state、规则入口和能力误标。
- 输出区分 Core 健康和 Host Adapter 健康。

验收：

- 未启用 host 时输出 info，不作为 fail。
- 启用 host 但入口文件缺失时 warning / fail，取决于严重度。
- Trae 若被记录为 `sessions.send_message=supported`，doctor 应 fail 或 high warning。
- `doctor --host` 检查 host 所需 Skill mount dirs 是否存在。
- `doctor --host` 检查规则入口是否引导 `.starwork/skills.json`。
- `doctor --host` 对 Cursor / Trae 同名 Skill 冲突给出 warning，尤其 Trae 中 `.trae/skills/` 会优先于 `.agents/skills/`。
- `doctor --host cursor` 检查 `.cursor/skills/*/SKILL.md` 的 `name` 是否与父文件夹一致，且只包含小写字母、数字和连字符。
- `doctor --host trae` 检查 `.trae/skill-config.json` 中是否禁用了 `.starwork/skills.json` 仍声明启用的 Skill。
- `doctor --host claude-code --json` 输出 host-specific checks。
- `doctor --host all` 对多个 host 分别报告，不把某个宿主的限制当成全局错误。
- 旧 doctor 测试不受影响。

### Phase 6：Claude Code 样板 Adapter

目标：

- 支持从环境变量识别 Claude Code session。
- 支持 `multiagent bind` 绑定 `claude-code:<id>`。
- 支持 `multiagent status --host` 读取 Claude Code session / transcript 元数据。
- 支持 `multiagent read <lane>` 输出 Claude Code transcript 摘要。
- 支持 `multiagent continue <lane>` 输出或执行 `claude --resume <id>`。

验收：

- 在有 `CLAUDE_CODE_SESSION_ID` 环境变量时，bind 可自动建议或使用 `claude-code:<id>`。
- 无环境变量时，提示用户手动传 `--session claude-code:<id>`。
- `read <lane>` 不输出完整 transcript，只输出可控摘要或最近 N 条。
- 不写任何 `~/.claude/**` 文件。
- 不执行 `claude project purge`。
- 测试用 fixture transcript 覆盖新版 `.jsonl` 和旧版目录两种格式。

### Phase 7：MultiAgent Handoff 降级

目标：

- 对不支持后台发送的 host，`instruct` 不报假成功。
- 新增或模拟 `handoff` 能力，生成可复制 StarWork MultiAgent Instruction。

验收：

- 对 `claude-code:<id>` 执行 `instruct` 时，若无后台发送能力，返回 `manual_handoff_required`。
- 对 `cursor:<id>` 能力不可用时，返回 `manual_handoff_required`。
- 对 `trae:<id>` 默认返回 `manual_handoff_required`。
- handoff message 写入 shared context，但 delivery 不标记为 completed。
- Skill 解释中明确“已生成交付消息，不等于已送达”。

### Phase 8：Cursor 轻量 Probe

目标：

- 支持 Cursor capability probe。
- 支持手动 binding。
- 支持可选 transcript / CLI 状态观察。

验收：

- `adapt cursor --capabilities --json` 输出 partial 能力。
- `status --host` 对 cursor lane 不承诺完整 read。
- 如果 `cursor` CLI 不存在，输出清楚 warning。
- 不写 Cursor 私有数据库。

### Phase 9：Trae 观察型 Probe

目标：

- 支持 Trae capability probe。
- 支持手动 binding。
- 可选只读元数据观察。

验收：

- `adapt trae --capabilities --json` 输出 manual / unsupported 边界。
- `status --host` 清楚说明无法读取完整聊天内容。
- 不读取或改写加密 `database.db`。
- 不承诺自动 launch / instruct。

### Phase 10：Knowledge / Upgrade / Skills 文档和 Skill 同步

目标：

- 更新 `starworkMultiagent`、`starworkInit`、`starworkDoctor`、`starworkKnowledge`。
- 更新用户文档和 A 测指南。
- 更新 CLI 能力注册表。

验收：

- Skill 不再把 adapter 当成 MultiAgent 子能力。
- Skill 对不同宿主有不同话术。
- 文档中明确 Codex、Claude Code、Cursor、Trae 的差异。
- A 测指南包含“如何测试 adapter 能力”的步骤。
- A 测指南包含 Cursor / Trae 写入 Skill 后是否需要重启、刷新窗口或重新打开项目的记录项。

## 11. 发布和迁移

迁移策略：

- 现有工作台不要求立刻生成 `.starwork/adapters.json`。
- 用户通过 StarWork Skill 完成宿主适配，或高级用户直接运行 `starwork adapt <host>` 后，才写入新 adapter state。
- 旧 `workspace.json.adapters` 继续可读。
- 公开文档中说明：adapter 是增强层，不是 Core 必需层。

版本建议：

- 该功能足够大，建议发布时递增到下一个 alpha。
- 发布说明中重点写：
  - adapter 现在是 StarWork 全局能力。
  - Codex / Claude Code / Cursor / Trae 的能力不同。
  - Cursor / Trae 不承诺自动跨会话派活。

## 12. 风险和防护

| 风险 | 防护 |
| --- | --- |
| 把 Codex 能力误推广到所有宿主 | profile 等级强制区分 supported / partial / manual / unsupported。 |
| 自动写坏宿主私有状态 | safety.never_write_paths + 测试保护。 |
| init 交互变重 | adapter 不默认进入 init 主流程，只做可选参数和后续 adapt。 |
| Skill 说法过度承诺 | 更新 skill，manual handoff 不说已送达。 |
| transcript 输出过长 | `read` 默认摘要，必须支持限制条数。 |
| adapter state 和 workspace state 漂移 | doctor --host 检查并提示刷新。 |

## 13. 开发 lane 执行建议

建议开发 lane 不要一次性实现所有阶段。

推荐提交切分：

1. `feat(adapters): add host profiles`
2. `feat(cli): expose adapter capabilities`
3. `feat(cli): persist workspace adapter state`
4. `feat(doctor): add host adapter checks`
5. `feat(multiagent): support claude-code session observations`
6. `feat(multiagent): add manual handoff fallback`
7. `docs(skills): align host adapter guidance`

每个提交都必须保持：

- `npm test` 通过。
- `git diff --check` 通过。
- 不改写无关 Core / Pack 结构。
