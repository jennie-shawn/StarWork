# MultiAgent v0.7 Codex Skill 直调标准工具 SPEC

## 1. 状态

- 日期：2026-06-08
- 状态：ready-for-development
- 所属功能：MultiAgent / `starworkMultiagent` Skill / Codex Host Tools
- 关联问题：
  - `product/planning/issues/ISSUE-017.md`
  - `product/planning/issues/ISSUE-008.md`
  - `product/planning/issues/ISSUE-011.md`
- 取代关系：
  - 本 SPEC 取代 v0.6 中关于 Codex launch / instruct / read / rename / pin / archive 的根本修复方向。
  - v0.6 中短标题修复仍可作为 ISSUE-015 的实现依据。
- 影响模块：`starworkMultiagent` Skill、`starwork multiagent` CLI 的消息模板 / 状态记录辅助命令、`.starwork/agent-lanes/state.json`、`_系统/协作/agent-lanes.md`、`_系统/协作/shared.md`

## 2. 背景

ISSUE-017 已经证明：

1. StarWork 当前 `multiagent launch` 通过 standalone `codex app-server thread/start` 创建的 thread，不等于 Codex App 标准会话控制工具创建的 conversation。
2. 当前 Codex App 标准 `create_thread` 创建的新会话，可继续被 `send_message_to_thread` 投递。
3. `create_thread`、`send_message_to_thread`、`read_thread`、`set_thread_title` 等工具只能在 Codex App 当前 Agent turn 中使用，普通 Node CLI 进程不能直接调用。

产品判断：

```text
Codex 场景不需要让 CLI 参与 host action 编排。
starworkMultiagent Skill 应按用户场景直接调用 Codex App 标准工具。
CLI 只保留 StarWork 文件状态、消息模板和校验辅助。
```

## 3. 一句话目标

`starworkMultiagent` 在 Codex App 中直接按场景调用 Codex 标准会话控制工具；不通过 CLI `launch` / `instruct` 或 CLI host-action 中转。CLI 不执行、不编排 Codex host tools，只负责 StarWork 协作状态和消息模板。

## 4. 产品原则

### 4.1 Skill 是 Codex 会话控制执行者

Codex App 标准工具的执行主体是当前 Agent / `starworkMultiagent` Skill。

Skill 必须直接调用：

| 场景 | Codex 标准工具 |
| --- | --- |
| 创建 lane 会话 | `create_thread` |
| 向 lane 会话发送指令 | `send_message_to_thread` |
| 读取 lane 会话状态 | `read_thread` |
| 搜索 / 确认历史会话 | `list_threads` |
| 设置会话标题 | `set_thread_title` |
| 置顶会话 | `set_thread_pinned` |
| 归档 / 取消归档会话 | `set_thread_archived` |

Skill 不得要求 CLI 生成 `host_action_required` 再执行。

### 4.2 CLI 只做 StarWork 状态与模板辅助

CLI 可以继续负责：

- 初始化 Agent Lanes 文件：`multiagent init`
- 新增 / 更新 lane：`multiagent add`
- 绑定真实 session：`multiagent bind`
- 释放绑定：`multiagent release`
- 登记共享输出：`multiagent share`
- 输出只读状态：`multiagent status`
- 生成标准 Launch / Instruction message 模板
- 记录已投递的 cross-lane request

CLI 不得负责：

- 创建 Codex thread。
- 向 Codex thread 投递消息。
- 读取 Codex thread。
- 改 Codex thread 标题。
- pin / archive Codex thread。
- 调用 standalone `codex app-server` 作为正常 Codex 路径。

### 4.3 不使用 host_action / completion 架构

v0.7 不采用：

```text
CLI -> host_action_required -> Skill -> CLI completion
```

而采用：

```text
Skill 读上下文
  -> 必要时调用 CLI 准备 / 更新 StarWork 文件状态
  -> Skill 直接调用 Codex 标准工具
  -> Skill 调用 CLI 记录 StarWork 状态
  -> Skill 向用户汇报真实结果
```

这里的 CLI 调用是文件状态记录，不是 host tool execution broker。

## 5. Skill 场景流程

### 5.1 创建 Agent 团队 / launch lane

用户意图：

```text
帮我创建产品、开发、验收三个智能体
创建 development Agent
launch 这个 lane
```

Skill 流程：

1. 读取项目上下文和 Agent Lanes。
2. 如协作层不存在或 lane 缺失，用 CLI 创建 / 更新 StarWork 文件状态：

```bash
starwork multiagent init --target <path> --yes
starwork multiagent add <lane> --purpose "<purpose>" --write "<scope>" --target <path> --yes
```

3. 生成 Launch Message。可以通过 CLI 新增模板辅助命令获取：

```bash
starwork multiagent message launch <lane> --target <path> --json
```

返回：

```json
{
  "schema": "starwork.agent_lanes.message.v0.1",
  "type": "launch",
  "lane": "development",
  "session_name": "功能开发 Agent",
  "message": "<!-- STARWORK:MULTIAGENT_MESSAGE v1 -->..."
}
```

4. Skill 直接调用 Codex App `create_thread`：

```text
create_thread(prompt = message, target = 当前项目 local 环境)
```

5. 如果需要命名，Skill 直接调用：

```text
set_thread_title(threadId, session_name)
```

6. 如果用户要求置顶，Skill 直接调用：

```text
set_thread_pinned(threadId, true)
```

7. Skill 用 CLI 记录 StarWork binding，不带 `--session-name` / `--pin`，避免 CLI 再碰宿主：

```bash
starwork multiagent bind <lane> \
  --session codex:<threadId> \
  --target <path> \
  --yes
```

8. CLI 写入 state 时记录：

```json
{
  "session_origin": "codex_create_thread_tool",
  "session_surface": "codex_app_host_tool",
  "created_by": "starworkMultiagent skill",
  "host_tools": {
    "create_thread": "used",
    "set_thread_title": "used_or_not_requested",
    "set_thread_pinned": "used_or_not_requested"
  }
}
```

成功口径：

- 只有 `create_thread` 返回 threadId 且 `bind` 成功后，才能说 Agent 已创建并绑定。
- 如果 `create_thread` 不可见或失败，不能说已创建；输出手动创建说明和 Launch Message。

### 5.2 向 lane 发送指令 / instruct

用户意图：

```text
让开发 Agent 开始实现这个 SPEC
通知产品规划 Agent 复验
```

Skill 流程：

1. 读取目标 lane session。
2. 若目标 lane 未绑定，先询问用户要 bind 还是 launch。
3. 生成 Instruction Message。可以通过 CLI 新增模板辅助命令获取：

```bash
starwork multiagent message instruct <to-lane> \
  --from <from-lane> \
  --message "<text>" \
  --target <path> \
  --json
```

4. Skill 直接调用：

```text
send_message_to_thread(threadId = <target thread id>, prompt = message)
```

5. 投递成功后，Skill 用 CLI 记录 request：

```bash
starwork multiagent request record \
  --from <from-lane> \
  --to <to-lane> \
  --message "<text>" \
  --host-delivery delivered \
  --delivery-tool send_message_to_thread \
  --target <path> \
  --yes
```

成功口径：

- 可以说“已投递 / 已发送到目标会话”。
- 不得说“目标任务已完成”。
- 目标完成仍需通过目标 lane worklog、shared outputs、回传消息或 `read_thread` 观察。

失败 / 工具不可见口径：

- 输出 `manual_handoff_required`。
- 展示完整 `STARWORK:MULTIAGENT_MESSAGE`。
- 不得调用 CLI app-server 低层投递作为替代。

### 5.3 查看 lane 状态 / read status

用户意图：

```text
看看开发 Agent 做到哪了
读一下产品规划 Agent 最近几轮
```

Skill 流程：

1. CLI 读取 lane binding：

```bash
starwork multiagent status --target <path> --json
```

2. 对 Codex session，Skill 直接调用：

```text
read_thread(threadId, turnLimit = <n>)
```

3. Skill 汇总：

- thread 状态。
- 最近 turn 摘要。
- 是否有 in-progress / interrupted / failed。
- StarWork worklog / shared outputs 是否有正式记录。

注意：

- `read_thread` 是宿主观察，不替代 lane worklog。
- 不再使用 CLI `multiagent read --host` 的 app-server 路径作为 Codex 正常观察。

### 5.4 绑定当前会话 / bind current session

用户意图：

```text
把当前会话绑定为产品规划 Agent
以后这个会话就是 development Agent
```

Skill 流程：

1. 如果当前上下文能获得当前 threadId，直接使用。
2. 如果不能自动获得，询问用户提供当前 Codex thread id。
3. 如用户要求改名，Skill 直接调用：

```text
set_thread_title(threadId, "<职责名> Agent")
```

4. Skill 调用 CLI 记录 binding：

```bash
starwork multiagent bind <lane> --session codex:<threadId> --target <path> --yes
```

5. 如用户要求置顶，Skill 直接调用：

```text
set_thread_pinned(threadId, true)
```

### 5.5 归档 / 释放 lane

用户意图：

```text
这个 Agent 先归档
这个 lane 不用了
释放当前绑定
```

Skill 流程：

1. 如需归档 Codex thread，Skill 直接调用：

```text
set_thread_archived(threadId, true)
```

2. 如需释放 StarWork binding，CLI 记录：

```bash
starwork multiagent release <lane> --target <path> --yes
```

3. Skill 提醒用户：释放前应确认 lane worklog 已写清当前状态和下一步。

## 6. CLI 辅助变更

### 6.1 新增 message 模板命令

新增：

```bash
starwork multiagent message launch <lane> --target <path> --json
starwork multiagent message instruct <lane> --from <from-lane> --message "<text>" --target <path> --json
```

职责：

- 只生成标准 `STARWORK:MULTIAGENT_MESSAGE`。
- 不调用任何 host。
- 不写 shared / state，除非命令名明确为 record。
- 供 Skill 复用协议模板，避免 Skill 手写消息格式。

### 6.2 新增 request record 命令

新增：

```bash
starwork multiagent request record \
  --from <lane> \
  --to <lane> \
  --message "<text>" \
  --host-delivery <delivered|manual_handoff_required|failed> \
  --delivery-tool <tool-name> \
  --target <path> \
  --yes
```

职责：

- 写入 `_系统/协作/shared.md` Cross-Lane Requests。
- 写入 `.starwork/agent-lanes/state.json` requests。
- 不调用任何 host。

### 6.3 bind 必须支持纯记录模式

`multiagent bind` 在没有 `--session-name`、`--pin`、`--archive` 等宿主增强参数时，只能写 StarWork state / registry，不得调用 Codex host。

如用户传入宿主增强参数：

- CLI 不直接调用 Codex host。
- CLI 应提示：在 Codex App / `starworkMultiagent` Skill 中执行对应工具。
- 或者要求 Skill 先执行工具，再用 bind 记录结果。

## 7. 禁止事项

`starworkMultiagent` 和 CLI 都不得在 Codex 正常路径中使用：

```text
codex app-server --listen stdio://
thread/start
turn/start
thread/resume
thread/name/set
thread/read
thread/list
host_action_required
host-action complete
```

不得通过以下方式绕过标准工具：

- shell 调 Codex 私有 socket。
- 读取 Codex 私有数据库。
- 用 app-server proxy 模拟 Desktop App host tools。
- 把 `codex:<thread-id>` 当作自动投递能力证明。

## 8. 多宿主边界

本 SPEC 只处理 Codex。

Cursor、Trae、Claude Code 等宿主的兼容策略暂不在本 SPEC 中展开。后续单独讨论：

- 哪些宿主有等价的标准会话工具。
- 哪些宿主只能手动 handoff。
- Skill 如何按宿主选择执行器。
- CLI 如何只维护 StarWork 状态，不碰宿主私有实现。

在多宿主 SPEC 出来前：

- Codex 使用本 SPEC。
- Cursor / Trae 继续按现有人工或只读 transcript 路径处理。
- 不为了统一多宿主而降低 Codex 标准工具路径。

## 9. 开发任务

### Phase 1：修改 `starworkMultiagent` Skill

- Codex launch 场景：Skill 直接调用 `create_thread`。
- Codex instruct 场景：Skill 直接调用 `send_message_to_thread`。
- Codex read 场景：Skill 直接调用 `read_thread`。
- Codex rename / pin / archive 场景：Skill 直接调用对应标准工具。
- Skill 不再调用 `starwork multiagent launch` 来创建 Codex thread。
- Skill 不再调用 `starwork multiagent instruct` 来执行 Codex 自动投递。
- Skill 不再等待 CLI 返回 `host_action_required`。
- 工具不可见时输出 manual handoff。

### Phase 2：补 CLI 模板与记录命令

- 增加 `multiagent message launch`。
- 增加 `multiagent message instruct`。
- 增加 `multiagent request record`。
- 确保这些命令不调用 host。

### Phase 3：冻结旧 Codex app-server 正常路径

- `multiagent launch` 不再作为 Codex 自动创建的推荐入口；在 Codex 下应提示使用 `starworkMultiagent` Skill。
- `multiagent instruct` 不再尝试 Codex 自动投递；在 Codex 下应提示 Skill 直接调用工具或输出 handoff message。
- app-server helper 只能保留为 legacy diagnostic，不作为默认路径。

### Phase 4：Skill 冗余与旧逻辑清理

修改后的 `starworkMultiagent` Skill 必须清理旧逻辑。不得残留以下内容：

- 把“创建 Agent 团队”映射为 `starwork multiagent launch --lanes ...` 的主流程。
- 把“向 lane 发送指令”映射为 `starwork multiagent instruct <lane>` 的自动投递主流程。
- 说明 “Skill 不维护宿主能力矩阵，凡是依赖宿主能力的动作都调用 CLI” 作为 Codex 场景原则。
- 解释 `delivered`、`manual_handoff_required` 等 CLI host delivery 状态为 Codex 自动投递主判断。
- 要求检查 `launch_status` / `rename_status` / `binding_status` 来判断 Codex thread 是否创建成功。
- 建议用 `multiagent read --host` 或 `status --host` 作为 Codex 正常会话读取主路径。
- 任何 `host_action_required` / `host-action complete` 的中转流程。
- 任何 `codex app-server`、`thread/start`、`turn/start`、`thread/resume`、`thread/name/set`、`thread/read`、`thread/list` 的正常路径描述。

允许保留：

- `multiagent init/add/bind/release/share/status` 作为 StarWork 文件状态命令。
- `manual_handoff_required` 作为工具不可见或失败时的用户 fallback 结果。
- 非 Codex 宿主的人工 handoff / 只读 transcript 说明，但不得影响 Codex 标准工具路径。

### Phase 5：测试与验收

- Skill 文档测试：Codex launch 指向 `create_thread`。
- Skill 文档测试：Codex instruct 指向 `send_message_to_thread`。
- Skill 文档测试：Codex read 指向 `read_thread`。
- Skill 文档测试：不再出现 `multiagent launch --lanes` 作为 Codex 创建主流程。
- Skill 文档测试：不再出现 `multiagent instruct` 作为 Codex 自动投递主流程。
- CLI 测试：message 命令只输出模板，不写 host。
- CLI 测试：request record 写 shared / state。
- CLI 测试：bind 纯记录模式不调用 fake codex app-server。
- 真实验收：Skill 通过 `create_thread` 创建 lane，再通过 `send_message_to_thread` 成功投递后续消息。

## 10. 验收标准

### 10.1 行为验收

- 用户通过 `starworkMultiagent` 创建 Codex Agent 时，实际调用 `create_thread`。
- 创建出的 Agent 会话可继续被 `send_message_to_thread` 投递。
- `starworkMultiagent` 投递 Codex 指令时，实际调用 `send_message_to_thread`。
- `starworkMultiagent` 读取 Codex lane 时，实际调用 `read_thread`。
- `starworkMultiagent` 改名 / pin / archive 时，实际调用对应标准工具。
- 工具不可见时，用户得到清晰的手动交付消息，不会看到“已通知 / 已创建”的误报。

### 10.2 Skill 清理验收

修改后的 `product/skills/starworkMultiagent/SKILL.md` 必须通过旧逻辑扫描：

- 不得再把 `starwork multiagent launch --lanes` 写作 Codex 创建 Agent 团队主流程。
- 不得再把 `starwork multiagent instruct` 写作 Codex 自动投递主流程。
- 不得再要求 Codex 场景“凡是依赖宿主能力的动作都调用 StarWork CLI，并根据 CLI 返回状态解释下一步”。
- 不得再用 `launch_status` / `binding_status` 作为 Codex 标准工具创建会话的成功判断。
- 不得再把 `multiagent read --host` / `status --host` 作为 Codex 正常读取主路径。
- 不得出现 `host_action_required`、`host-action complete` 作为 Codex 正常执行链路。
- 不得出现 app-server 低层方法作为正常路径：`thread/start`、`turn/start`、`thread/resume`、`thread/name/set`。
- 如保留 `manual_handoff_required`，必须只作为工具不可见 / 工具失败 fallback。

### 10.3 CLI 验收

- CLI 不再在 Codex 正常路径中启动 standalone `codex app-server`。
- `multiagent message launch` 和 `multiagent message instruct` 只生成消息模板，不写 host。
- `multiagent request record` 只记录 shared / state，不写 host。
- `multiagent bind` 纯记录模式不调用 fake codex app-server。
- 如果用户直接终端运行旧 `multiagent launch` / `multiagent instruct`，CLI 不得误报 Codex 自动创建或自动投递成功，应提示使用 `starworkMultiagent` Skill 或走 handoff。
