## 2. 背景

真实测试中，用户要求创建 MultiAgent 团队后出现三个问题：

1. 在非 StarWork 项目中生成了 `AGENTS.starwork-new.md`，但主入口 `AGENTS.md` 没有引用它。
2. 用户说“创建 Agent 团队”，实际只创建了 lane，没有创建和绑定独立会话。
3. 创建会话后，没有自动改成对应 Agent 名称。

复盘后确认，`AGENTS.starwork-new.md` 的根因不是 MultiAgent 不会合并规则文件，而是 MultiAgent 绕过了 `starworkInit` 的标准接入流程。

正确边界：

```text
starworkInit 管工作台接入
starworkMultiagent 管团队协作
```

MultiAgent 不应该在一个普通目录里半自动补 StarWork 入口文件。普通目录需要先通过 `starworkInit` 安全接入 StarWork，再进入团队创建流程。

## 3. 一句话目标

让用户说“帮我创建一个 Agent 团队”时，StarWork 能交付一个真正可工作的团队；如果当前目录还不是 StarWork 工作台，必须先进入标准初始化 / 接入流程，而不是生成无人读取的副本文件。

## 4. 产品边界

### 4.1 `starworkInit` 负责

- 判断当前目录是不是 StarWork 工作台。
- 将非 StarWork 项目安全接入 StarWork。
- 处理已有 `AGENTS.md`、`README.md`、宿主规则入口和 adapter sidecar。
- 执行 `starwork init` / `starwork adapt` / `starwork doctor` 的标准验证链路。
- 保证后续 Agent 会读取正确入口。

### 4.2 `starworkMultiagent` 负责

- 在已接入 StarWork 的工作台里创建 MultiAgent 协作层。
- 设计 lane、职责和写入范围。
- 绑定当前会话到主 lane。
- 在支持的宿主中创建并绑定其他 lane 会话。
- 发送 Launch Message 和跨会话指令。
- 用 `status` / `read` 复核团队是否真的可工作。

### 4.3 MultiAgent 不负责

- 不直接合并用户已有 `AGENTS.md`。
- 不生成无人引用的 `AGENTS.starwork-new.md`。
- 不绕过 `starworkInit` 创建 `.starwork/`、README 或规则入口。
- 不把“创建 lane”说成“创建团队完成”。
- 不承诺 Cursor / Trae / Claude Code 拥有 Codex 式后台自动创建和派活能力。

## 5. 用户语义重新定义

### 5.1 初始化协作层

用户表达：

```text
初始化 multiagent
创建协作层
先建几个职责位
```

解释为：

```text
只创建 Agent Lanes 协作文件和 lane，不一定创建独立宿主会话。
```

允许结果：

- lane 可以是 `unbound`。
- 输出必须说明这只是“职责位”，不是完整团队。

### 5.2 登记当前会话

用户表达：

```text
把当前会话设为产品规划 Agent
这个会话负责开发
```

解释为：

```text
创建或复用一个 lane，并把当前会话绑定到该 lane。
```

允许结果：

- 只绑定当前会话。
- 不自动创建其他 lane 会话。

### 5.3 创建 Agent 团队

用户表达：

```text
帮我创建一个 Agent 团队
创建产品规划、开发、调研三个智能体
搭一套多智能体团队
```

解释为：

```text
创建多个 lane，并尽可能创建和绑定对应宿主会话，让每个成员都能开始工作。
```

成功结果：

- 每个团队成员都有 lane。
- 在 Codex 中，每个非当前 lane 都应有独立 thread。
- 每个新 thread 都收到 Launch Message。
- 每个新 thread 都写回 lane binding。
- 每个新 thread 都尽量改名为对应 Agent 名称。
- 最后输出团队状态，不留未解释的 `unbound`。

如果做不到：

- 必须明确说“团队创建未完成”。
- 必须列出哪些 lane 仍未绑定。
- 必须给出下一步，例如手动交付、重试 launch、或先完成 init。

## 6. 标准流程

### 6.1 前置检查

`starworkMultiagent` 每次执行写入或团队创建前，先检查目标目录：

```bash
starwork doctor --target <path> --json
```

最低要求：

- 能识别 `.starwork/workspace.json`。
- 能识别当前语言的协作路径。
- 能确认主规则入口可读。

如果不是 StarWork 工作台：

1. 停止 MultiAgent 创建流程。
2. 告诉用户需要先接入 StarWork。
3. 转入 `starworkInit` Skill，由它采访用户、判断工作台类型、选择 Pack、处理已有规则入口，并生成 dry-run 方案。
4. 用户确认 `starworkInit` 方案后，才由 `starworkInit` 执行对应 CLI。

只有 doctor 通过后，才继续 MultiAgent。

### 6.2 团队创建流程

输入：

- 团队成员列表。
- 每个成员的 lane id。
- 每个成员的职责。
- 每个成员的可写范围。
- 当前会话应绑定到哪个 lane。
- 当前宿主，默认为当前可用宿主；Codex 支持自动 launch，其他宿主默认降级。

流程：

```text
1. doctor 检查目标是否为 StarWork 工作台
2. 必要时 multiagent init
3. 为每个成员 multiagent add
4. bind 当前会话到主 lane
5. 对其他 lane 执行 multiagent launch
6. 每个 launch 使用对应 Agent 名称作为 session name
7. 执行 multiagent status --host
8. 用人话总结团队是否真的创建完成
```

跨会话指令只负责把消息送到目标 lane。发送方不应默认等待目标 lane 完成全部任务；目标完成情况通过后续 `read`、worklog 或回传指令确认。

跨会话指令必须使用宿主提供的标准投递能力。Codex 场景应接入 `send_message_to_thread` 或明确等价的稳定 API；不得再用 `thread/resume` + `turn/start` 模拟后台发送。其他宿主如果没有标准后台投递 API，则该宿主不支持自动 `instruct`，只能输出人工 handoff。

### 6.3 团队创建完成定义

只有满足以下条件，才能说“团队已创建完成”：

- 所有目标 lane 均已存在。
- 当前会话已绑定到指定主 lane。
- Codex 自动创建的 lane 已有 `codex:<thread-id>` binding。
- Launch Message 已发送并验证完成，或以保守状态说明需要复核。
- 每个新会话都有清晰的 Agent 显示名称，或有明确 warning。

以下情况不能说完成：

- 只创建了 lane，但大部分 lane 仍是 `unbound`。
- launch 失败但仍写入 binding。
- `started_unverified` 被解释成已完成。
- 非 Codex 宿主只生成了 handoff message，却说成已自动创建会话。
- 跨会话指令只是投递成功，却被解释成目标任务已经完成。

## 7. CLI 调整建议

### 7.1 短期：修现有命令行为

#### `multiagent launch`

当前能力保留，但需要增强：

- 支持批量 launch 时为每个 lane 自动生成 session name。
- 默认 session name 来自 lane display name / purpose，而不是统一名称。
- JSON 输出必须包含：
  - lane
  - session id
  - session name
  - rename status
  - launch status
  - binding status

示例：

```json
{
  "lane": "development",
  "thread_id": "019...",
  "session": "codex:019...",
  "session_name": "开发 Agent",
  "rename_status": "ok",
  "launch_status": "completed",
  "binding_status": "bound"
}
```

#### `multiagent status`

需要更清楚暴露团队状态：

- 哪些 lane 已绑定。
- 哪些 lane 未绑定。
- 哪些 lane 只是职责位。
- 哪些 lane 有宿主会话但命名失败。

### 7.2 中期：新增团队级命令

建议新增：

```bash
starwork multiagent team create
```

或：

```bash
starwork multiagent setup --team
```

该命令封装组合流程，减少 Skill 串命令出错。

推荐能力：

- 接收团队 blueprint。
- dry-run 展示 lane、写入范围、宿主会话、会话名称。
- 执行后逐 lane 输出成功 / 失败 / 需要人工处理。
- 原子性要求：失败的 lane 不应污染成功 lane；但不能把失败 lane 伪装成完成。

v0.3 不强制实现该命令，但需要在开发评估中确认是否进入下一版。

## 8. Skill 调整

### 8.1 修复已安装 Skill 版本漂移

当前发现：

- 产品源 `product/skills/starworkMultiagent/SKILL.md` 已包含 `launch / instruct / handoff / continue`。
- 实际安装路径中的 `starworkmultiagent/SKILL.md` 仍是旧版，只包含 `init / bind / release / inspect / share`。

必须处理：

- 发布包内 Skill 为最新版。
- 全局安装后的 Skill 为最新版。
- 项目内 `.agents/skills/starworkmultiagent/` 如存在，也应能被升级或提示过期。

验收：

```text
实际加载的 starworkMultiagent description 必须包含 launch 和 cross-session instructions。
```

### 8.2 `starworkMultiagent` 新增前置分支

在任何团队创建前：

```text
如果目标不是 StarWork 工作台：
  不执行 multiagent init/add/launch
  转入 starworkInit Skill 接入流程
```

Skill 对用户说法：

```text
这个目录还不是 StarWork 工作台。我要先帮你把它安全接入 StarWork，确认 Agent 会读到正确规则后，再创建多智能体团队。
```

禁止说法：

```text
我先补一个 AGENTS.starwork-new.md
```

### 8.3 团队创建不再停在 lane-only

当用户说“创建团队”时，Skill 必须继续执行到以下任一结果：

- 团队创建完成。
- 团队创建部分完成，并列出未完成 lane。
- 因宿主能力或用户确认缺失而阻塞。

不能以“是否继续创建独立会话？”作为最终答复，除非用户之前只要求“先设计 lane”。

### 8.4 会话命名默认开启

团队创建场景中，`--session-name` 不再是可选增强，而是默认行为。

命名格式：

```text
<职责名> Agent
```

示例：

```text
产品规划 Agent
开发 Agent
功能调研 Agent
```

命名要求：

- `<职责名>` 优先使用 lane 的可读职责名 / display name；不要直接使用难懂的 lane id，除非没有更好的职责名。
- 中文工作台使用中文职责名，例如 `产品规划`、`功能开发`；英文工作台使用英文职责名，例如 `Planning`、`Development`。
- 不要默认加入项目名或目录名；项目归属由 StarWork lane binding、workspace 路径和状态输出表达。
- 不要把 thread id、UUID、日期、状态词、`lane`、`session` 等内部词放进用户可见会话名。
- 名称必须能让用户在宿主会话列表里一眼分清“这是哪个职责的 Agent”。
- 多个会话批量创建时，每个会话名必须不同，不得共用一个笼统名称。
- 如果宿主不支持自动改名，StarWork 仍要在 JSON / 状态输出里给出建议会话名，并提示用户手动改名。

如果宿主不支持自动命名：

- 不阻塞绑定。
- 输出 warning。
- 给用户手工命名建议。

## 9. `ISSUE-005` 修复口径

原问题标题：

```text
MultiAgent 在非 StarWork 项目初始化时生成 AGENTS 副本而非合并入口
```

修复后口径应调整为：

```text
MultiAgent 不应在非 StarWork 项目中绕过 starworkInit 做局部初始化
```

验收重点不再是让 MultiAgent 学会合并 `AGENTS.md`，而是：

- MultiAgent 遇到非 StarWork 项目时停止。
- 引导进入 `starworkInit` 标准流程。
- `AGENTS.md` 合并 / sidecar / 引用策略由 `starworkInit` 和 adapter 负责。
- MultiAgent 不再直接制造 `AGENTS.starwork-new.md`。

## 10. 验收计划

### 10.1 非 StarWork 项目接入

准备一个已有 `AGENTS.md` 的普通项目。

执行用户意图：

```text
帮我创建一个产品规划、开发、功能调研的 Agent 团队
```

预期：

- Skill 先判断不是 StarWork 工作台。
- Skill 进入 `starworkInit` Skill 接入流程，而不是直接运行 `starwork init` CLI。
- 未经 `starworkInit`，不得执行 `multiagent init/add/launch`。
- 不生成无人引用的 `AGENTS.starwork-new.md`。

### 10.2 Codex 团队创建

在健康 StarWork 工作台中执行团队创建。

预期：

- 创建目标 lane。
- 当前会话绑定到主 lane。
- 其他 lane 通过 Codex launch 创建独立 thread。
- 所有自动创建的 thread 写回 binding。
- `multiagent status --json` 不应留下未解释的 `unbound`。

### 10.3 会话命名

批量创建三个 lane：

```text
product-planning
development
feature-research
```

预期：

- 三个新会话分别使用对应 Agent 名称。
- 命名失败时输出 warning。
- binding 不因命名失败回滚。

### 10.4 非 Codex 降级

Cursor / Trae / Claude Code 场景中创建团队。

预期：

- 不承诺自动后台创建和派活。
- 输出人工交付或 continue 指引。
- 状态中清楚区分 `bound`、`unbound`、`manual_handoff_required`。

### 10.5 回归测试

需要补充或确认：

- 已有 `AGENTS.md` 的普通项目不会被 MultiAgent 局部初始化污染。
- `launch --lanes` 支持逐 lane session name。
- 团队创建后状态 JSON 能表达每个 lane 的绑定和命名结果。
- Skill 文案不会把 lane-only 结果说成团队完成。

## 12. 决策结论

本次不把 `AGENTS.starwork-new.md` 问题归为 MultiAgent 的规则合并能力缺失。

正式决策：

```text
Init 管入口，MultiAgent 管协作。
```

MultiAgent 团队创建必须建立在 StarWork 工作台已经正确接入的前提上。任何非 StarWork 项目的接入、规则入口保护、sidecar 和 doctor 验证，都应该回到 `starworkInit` 标准流程。
