## 背景

当前 `starworkMultiagent` Skill 已经承担多类职责：MultiAgent 主入口路由、AI 团队创建、当前会话 ID 校验、Codex / Claude Code 宿主工具边界、跨 lane 投递保证、Workflow Builder / Runner、消息模板、lane workspace 与正式输出晋升等。

product-lead 与 product-multiagent 复核后确认：

- stable `product/skills/starworkMultiagent/SKILL.md` 约 528 行。
- next `product/skills-next/starworkMultiagent/SKILL.md` 约 656 行。
- 当前本地安装 next Skill 约 640 行。

分段读取本身不必然导致错误，但已经带来四类产品风险：

1. Agent 可能未读完或漏读后半段关键规则。
2. 长文档稀释 hard safety rules 的注意力。
3. stable 与 next 共享规则重复维护后容易漂移。
4. 低频 workflow / host / onboarding 流程让普通 MultiAgent 任务付出不必要 token 成本。

v0.13 的目标是把 `starworkMultiagent/SKILL.md` 从“完整操作手册”改为“短主入口 + 硬安全规则索引 + reference loading table”。

## 产品目标

主 Skill 必须默认加载所有不可犯错的硬规则；低频流程和长模板按场景放入 `references/`，由主 Skill 明确指示在对应场景触发时读取。

目标效果：

- 主 Skill 更短、更不容易漏读。
- 当前会话 ID、真实投递、CLI 账本边界和成功口径仍常驻主文件。
- stable / next 共享 hard rules 有测试防漂移。
- workflow 仍只属于 next，不混入 stable 主流程。
- references 缺失时能明确识别安装不完整，并停止高风险动作。

## 非目标

本版不做：

- 不新增 MultiAgent 用户功能。
- 不改变 v0.8 / v0.10 / v0.11 / v0.12 的产品语义。
- 不新增独立 `starworkWorkflow` Skill。
- 不改变 CLI 命令行为。
- 不调整 workflow definition / packet schema。
- 不实现后台 daemon、文件 watcher、调度器或自动 loop runtime。
- 不实现完整 `starwork skills install --agent codex --global` 安装入口。

## 主 Skill 必须保留的硬规则

以下规则不能只放入 reference。主 Skill 可压缩表达，但必须保留等价语义。

### 当前会话 ID 必须确认

主 Skill 必须保留：

- 任何会话控制或跨会话操作前，必须确认当前会话 ID。
- `<codex_delegation>` 中的 `source_thread_id` 优先作为当前来源会话 ID。
- 不得用历史 worklog、旧 binding、相似标题或最近更新时间推断当前会话。
- 如果 current session id 不明，停止绑定、改名、置顶、归档、释放和以当前会话为来源的投递记录。
- 发送前必须检查目标 lane session 不等于当前会话；否则默认阻断自我投递。

### 跨 lane / Agent / session 必须真实投递

主 Skill 必须保留：

- 目标是另一个 lane / Agent / session 的步骤是必须投递步骤。
- 必须投递步骤不能用当前回复说明替代。
- 合法结果只有真实自动投递成功、明确人工转交、明确阻塞。
- 未投递成功不得说“已通知”“已完成交接”或“目标任务已完成”。

### 工具不可见时先工具发现

主 Skill 必须保留：

- `send_message_to_thread` 或宿主标准工具不可见时，先使用工具发现能力查找。
- 发现失败或调用失败时，进入 `manual_handoff_required`。
- manual handoff 必须展示完整可复制 `STARWORK:MULTIAGENT_MESSAGE`，并明确“尚未自动送达”。

### 投递成功后才能 request record delivered

主 Skill 必须保留状态写入顺序：

```text
确认目标 lane / session / current session
  -> 组装 message
  -> 调用宿主标准线程工具成功
  -> 再执行 starwork multiagent request record delivered...
```

未真实投递成功不得记录：

```text
delivered_via_codex_thread_tool
delivered_via_claude_code_session_tool
```

### CLI 只做 StarWork 项目事实源

主 Skill 必须保留 v0.8 边界：

- CLI 是项目事实源账本，不是宿主会话动作执行者。
- Codex App 正常路径中，创建、投递、读取、命名、置顶、归档由 Skill 调用宿主标准工具。
- CLI 只用于 `doctor`、`multiagent status`、`multiagent init`、`multiagent add`、`multiagent bind`、`multiagent release`、`multiagent share`、`multiagent request record` 等项目内事实源读写。
- 不得恢复 `starwork multiagent instruct`、`starwork multiagent launch`、`multiagent message instruct`、`multiagent message launch` 作为 Codex 正常路径。

### 成功口径必须分层

主 Skill 必须保留：

- Agent 已创建 / 会话已绑定不等于任务已开始或完成。
- 消息已送达不等于目标任务已完成。
- workflow 当前节点消息已送达只代表消息送达和 request 已记录。
- 目标任务完成必须来自目标 lane 回传、worklog、shared output 或明确会话观察。

### 前置保护摘要

主 Skill 必须保留：

- 先确认目标目录是 StarWork 工作台。
- `rules_entry_status: pending_merge` 时转 `starworkInit`，不继续 multiagent 写入。
- `multiagent.compatibility.status` 不是 `current` 时，先走 v0.10 升级预览，不进行写入类 MultiAgent 操作。

## stable / next 差异

### stable

stable 主 Skill 和 stable references 不应包含 workflow builder / runner 的可执行步骤。

允许出现：

- “workflow 是 next 内测能力。”
- “stable 不引导普通用户测试 workflow。”
- “如果用户询问 workflow，请说明需要 next 或等待正式发布。”

不允许出现：

- Builder 第一屏。
- Runner 启动步骤。
- compact packet 字段表。
- full packet 触发条件。
- workflow instance 生成规则。

### next

next 必须包含：

- `workflow-builder.md`
- `workflow-runner.md`
- `workflow-packet-budget.md`

next 主 Skill 必须保留：

- frontmatter `starwork_channel: next`
- frontmatter `starwork_multiagent` 或后续等价版本标识
- CLI / Skill 同源检查提醒
- 普通 latest 用户不测试 workflow 的提醒
- workflow builder / runner 的 reference 路由

### 共享 hard rules

以下语义必须在 stable 与 next 保持一致：

- 当前会话 ID 确认。
- 工具不可见先工具发现。
- 未投递成功不得记录 delivered。
- CLI 只做项目事实源。
- 成功口径不等于目标完成。
- v0.8 禁止项。

## 风险与缓解

### hard safety rules 被拆散

缓解：hard rules 只允许压缩，不允许完全迁出主 Skill；主 Skill 保留不可违反的短规则，reference 承载细节和示例。

### references 变成新的大文件

缓解：单个 reference 建议不超过 5,000 中文字符，一个 reference 只服务一个场景。新增场景先判断是否已有 reference，不能继续往 `delivery-guarantee.md` 塞无关内容。

### stable / next 漂移

缓解：共享 reference 同名同结构，增加 shared-rule diff test。每次改投递保证、当前会话 ID、CLI 边界时必须同时检查 stable / next。

### references 未随安装复制

缓解：主 Skill 明确 references 缺失时停止高风险动作；安装文档要求完整目录安装；next A 测仍限制 `@next` 和同源安装。

## 关闭标准

v0.13 可关闭的条件：

1. stable / next 主 Skill 行数达到目标或满足硬上限。
2. 主 Skill 保留所有 hard safety rules。
3. 长流程已迁入 references，并能按场景读取。
4. stable / next references 结构与差异符合本 SPEC。
5. 安装文档说明 references 必须完整安装。
6. 文本扫描、路径检查、目标回归测试和 `npm test` 均通过。
