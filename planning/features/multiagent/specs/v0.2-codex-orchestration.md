# StarWork MultiAgent v0.2 Codex 多会话编排 SPEC

## 1. 状态

- 日期：2026-06-01
- 状态：implemented
- 所属功能：MultiAgent / Agent Lanes
- 目标宿主：Codex Desktop / Codex App Server
- 相关 CLI：`starwork multiagent`
- 相关 Skill：`starworkMultiagent`
- 事实源：StarWork 项目内 `_系统/协作/` 和 `.starwork/agent-lanes/`

## 1.1 重要修订说明

本 SPEC 记录的是 v0.2 阶段的探索和实现口径，其中关于 `multiagent instruct` 使用 `thread/resume` + `turn/start` 发送跨会话指令的设计已经被 `ISSUE-008` 废止。

后续实现必须遵守：

- Codex 自动跨会话发送必须使用 Codex 标准线程投递能力，例如 `send_message_to_thread` 或明确等价的稳定宿主 API。
- 不再把 `thread/resume` + `turn/start` 作为 StarWork `instruct` 的标准实现。
- `resume` / `continue` 只表示恢复会话继续工作，不能包装成后台发送。
- 其他宿主没有标准后台投递 API 时，不支持自动 `instruct`，只能走人工 handoff。

## 2. 背景

Codex 新增或暴露了更多 thread 级能力。经过本地测试，以下链路已经验证可用：

```text
thread/read
thread/resume
turn/start
thread/list
```

测试结论：

- `thread/read` 可以读取指定 thread 的元信息和 turns。
- 未加载的历史 thread 直接 `turn/start` 会返回 `thread not found`。
- 正确发送链路是先 `thread/resume`，再 `turn/start`。
- 如果 `turn/start` 后过早关闭 app-server 连接，目标 turn 可能变成 `interrupted`。
- 等待 `turn/completed` 后再关闭连接，目标 turn 可以正常完成并被 `thread/read` 读到。
- Codex 前端界面可能不会立即刷新新 turn，用户重启 Codex 后才看到变化。这应视为 Codex 宿主 UI 的刷新缺陷，StarWork 不能依赖前端可见性作为发送成功标准。

因此，MultiAgent v0.2 的重点不是“继续旧会话”，而是：

> 让一个会话可以创建、观察、指挥其他 lane 会话，并在 StarWork 项目内留下可审计记录。

## 3. 产品定位

一句话定义：

```text
Codex 多会话编排 = 一个 StarWork lane 可以向另一个 lane 的 Codex thread 发送结构化指令，并观察其执行状态。
```

它解决的用户场景：

- 产品规划 lane 完成 SPEC 后，向开发 lane 发送开发指令。
- 开发 lane 完成实现后，向产品规划 lane 发送验收请求。
- 主控会话批量创建多个 lane 会话，让它们按职责待命。
- 用户或主控 lane 查看其他 lane 当前是否空闲、是否收到指令、最近回复了什么。

## 4. 非目标

v0.2 不做：

- 不实现 `release --archive-session`。
- 不做自动任务调度。
- 不做多会话自动合并代码。
- 不做文件锁或并发冲突仲裁。
- 不把 Codex 的 host 状态变成 Core 必选字段。
- 不依赖 Codex 前端是否实时刷新。
- 不直接修改 Codex 私有数据库或 JSONL 历史文件。

## 5. 核心概念

| 概念 | 定义 |
| --- | --- |
| Lane | StarWork 中的稳定职责位，例如 `product-planning`、`development`、`review`。 |
| Codex Thread | Codex 宿主里的会话实例。 |
| Binding | 某个 lane 当前绑定的 Codex thread。 |
| Host Observation | 通过 Codex app-server 读取到的 thread 状态。它只是观察结果，不是 StarWork 事实源。 |
| Cross-session Instruction | 一个 lane 给另一个 lane 发送的结构化跨会话指令。 |
| Launch Message | `multiagent launch` 创建 lane thread 后发送的初始化消息。 |

## 6. 设计原则

1. StarWork 事实源优先：所有跨会话请求必须写入项目内记录，不能只存在于 Codex thread。
2. Codex host 能力是增强层：失败不能破坏 lane registry 和 shared context。
3. 发送必须可审计：谁发给谁、为什么发、关联什么文件、是否送达，都要记录。
4. 消息必须格式化：StarWork 自动发送的 launch / instruct 消息要和人类手写消息明显区分。
5. 不抢宿主 UI 职责：Codex 前端是否刷新，只能作为体验问题，不能作为协议成功条件。
6. 先 Codex，后适配：Cursor / Trae 后续按同一 Host Adapter 能力层降级实现。

## 7. 新增 CLI 能力

### 7.1 `starwork multiagent status --host`

用途：查看 StarWork lane 状态和 Codex host 状态是否一致。

示例：

```bash
starwork multiagent status --host --target .
starwork multiagent status --host --json --target .
```

输出必须区分两层：

```text
StarWork state:
- lane 是否存在
- lane 绑定的 session id
- worklog 路径
- write_scope

Codex host observation:
- thread 是否能读取
- thread 当前状态：notLoaded / idle / active / systemError
- thread 标题
- cwd
- turn 数量
- 最近更新时间
```

重要语义：

- `notLoaded` 表示 thread 存在于历史中，但没有被当前 app-server 加载。
- `idle` 表示 thread 已加载且空闲。
- `active` 表示 thread 正在执行。
- `status --host` 不应自动 `resume` 所有 thread，除非用户显式传入 `--load`。

JSON 建议：

```json
{
  "lanes": [
    {
      "lane": "development",
      "starwork": {
        "bound": true,
        "session": "codex:019e..."
      },
      "host": {
        "adapter": "codex",
        "readable": true,
        "status": "notLoaded",
        "name": "StarWork 开发 Agent",
        "cwd": "/path/to/project",
        "turn_count": 3,
        "ui_visibility": "not_guaranteed"
      }
    }
  ]
}
```

### 7.2 `starwork multiagent bind --pin`

用途：绑定 lane 到 Codex thread，并可选将该 thread 置顶。

示例：

```bash
starwork multiagent bind development \
  --session codex:019e... \
  --session-name "StarWork 开发 Agent" \
  --pin \
  --target . \
  --yes
```

行为：

1. 先写入 StarWork lane binding。
2. 再 best-effort 同步 Codex thread 标题。
3. 再 best-effort pin Codex thread。
4. 标题同步或 pin 失败时，只输出 warning，不回滚 StarWork binding。

待确认点：

- Codex app-server 的 pin 能力需要在实现时确认具体 JSON-RPC 方法。若当前版本无稳定 pin 接口，`--pin` 应显示为 unsupported warning。

### 7.3 `starwork multiagent read <lane>`

用途：读取某个 lane 绑定的 Codex thread 的最近状态。

示例：

```bash
starwork multiagent read development --target .
starwork multiagent read development --turns 5 --json --target .
```

行为：

- 从 lane binding 解析 Codex thread id。
- 调用 `thread/read`。
- 默认 `includeTurns: false`，只读元信息。
- 用户传 `--turns` 或 `--include-turns` 时，调用 `includeTurns: true`，并只展示最近 N 个 turns。

输出必须提示：

```text
这是 Codex host observation。正式交接仍以 lane worklog 和 shared outputs 为准。
```

不得：

- 不自动把 host 内容写入 StarWork 正式文档。
- 不把完整历史默认打印出来。
- 不默认 resume 目标 thread。

### 7.4 `starwork multiagent instruct <to-lane>`

用途：向另一个 lane 发送跨会话指令。

示例：

```bash
starwork multiagent instruct development \
  --from product-planning \
  --message "请根据 product/planning/features/multiagent/specs/v0.2-codex-orchestration.md 开始实现。" \
  --target . \
  --yes
```

行为分两步：

1. 项目内留痕  
   在当前语言镜像对应的协作共享索引中登记请求。

2. Codex host 发送  
   如果目标 lane 绑定了 Codex thread：
   - `thread/resume`
   - `turn/start`
   - 等待 `turn/completed` 或超时
   - `thread/read` 校验最近 turn

发送失败时：

- 项目内请求记录仍保留。
- 标记 delivery 为 `failed` 或 `pending_host_delivery`。
- 输出失败原因。

完成后建议：

- 目标 lane 完成后，应更新自己的 worklog。
- 如有正式输出，应登记到 `shared.md` 的 `Shared Outputs`。
- 如需回传验收请求，可反向使用 `multiagent instruct`。

### 7.5 `starwork multiagent launch`

用途：为一个或多个 lane 创建 Codex thread，并发送格式化初始化消息。

示例：

```bash
starwork multiagent launch development \
  --session-name "StarWork 开发 Agent" \
  --pin \
  --target . \
  --yes
```

批量示例：

```bash
starwork multiagent launch \
  --lanes product-planning,development,review \
  --pin \
  --target . \
  --yes
```

行为：

1. 确认 lane 已存在；不存在时，除非用户提供 blueprint，否则不自动创建。
2. 调用 Codex `thread/start` 创建 thread。
3. 使用格式化 Launch Message 发送初始化内容。
4. 将新 thread 绑定到 lane。
5. 可选同步 session name。
6. 可选 pin。
7. 在 `.starwork/agent-lanes/state.json` 记录 host metadata。

后续可扩展：

```bash
starwork multiagent launch --blueprint <file>
```

blueprint 可同时定义 lane、write_scope、session_name、launch_message。

## 8. Codex App Server 调用约定

### 8.1 初始化

所有 app-server 调用先发送：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "initialize",
  "params": {
    "clientInfo": {
      "name": "starwork",
      "version": "<package-version>"
    },
    "capabilities": null
  }
}
```

### 8.2 读取 thread

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "thread/read",
  "params": {
    "threadId": "<thread-id>",
    "includeTurns": true
  }
}
```

### 8.3 加载 thread

```json
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "thread/resume",
  "params": {
    "threadId": "<thread-id>",
    "excludeTurns": true
  }
}
```

### 8.4 发送消息

```json
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "turn/start",
  "params": {
    "threadId": "<thread-id>",
    "input": [
      {
        "type": "text",
        "text": "<formatted-message>"
      }
    ]
  }
}
```

### 8.5 等待完成

实现必须监听：

```text
turn/started
turn/completed
thread/status/changed
```

发送类命令默认等待到：

- `turn/completed`
- 或超时
- 或 `turn` 进入失败状态

不得在 `turn/start` 刚返回后立刻断开 app-server，否则可能导致目标 turn 变成 `interrupted`。

## 9. 格式化消息协议

StarWork 自动发送到其他 Codex thread 的消息，必须使用明确外壳，和人类手写消息区分。

### 9.1 总原则

- 必须声明这是 StarWork MultiAgent 系统消息。
- 必须声明消息类型：`launch` 或 `instruction`。
- 必须声明 from / to lane。
- 必须提供清楚的消息内容、任务边界和完成后回报方式。
- 必须避免伪装成人类自然留言。

### 9.2 Launch Message 格式

`multiagent launch` 发送的初始化消息必须使用：

```md
<!-- STARWORK:MULTIAGENT_MESSAGE v1 -->

# StarWork MultiAgent Launch

message_type: launch
from_lane: <launcher-lane-or-user>
to_lane: <lane-id>
workspace: <absolute-or-project-relative-path>
created_at: <ISO-8601>

## 你的职责

<lane purpose>

## 你可以主动修改的范围

<write_scope>

## 你启动后必须先读取

1. AGENTS.md
2. <collaboration_root>/agent-lanes.md
3. <collaboration_root>/lanes/<lane-id>/worklog.md
4. <collaboration_root>/shared.md

## 当前要求

请先完成初始化阅读，确认你已经理解自己的 lane 职责和写入边界。
除非后续收到明确指令，否则不要主动修改项目文件。

## 回报方式

完成初始化后，在本会话回复一句：

已进入 <lane-id> lane，等待下一步指令。

<!-- /STARWORK:MULTIAGENT_MESSAGE -->
```

### 9.3 Cross-session Instruction 格式

`multiagent instruct` 发送的跨会话指令必须使用：

```md
<!-- STARWORK:MULTIAGENT_MESSAGE v1 -->

# StarWork MultiAgent Instruction

message_type: instruction
request_id: <REQ-YYYYMMDD-HHMMSS-lane>
from_lane: <from-lane>
to_lane: <to-lane>
created_at: <ISO-8601>
recorded_in: <collaboration_root>/shared.md

## 消息内容

<用自然语言写清楚这条指令的背景、要完成的任务、相关文件或参考依据。>

## 边界

- 只在你的 write_scope 内主动修改。
- 如需修改 write_scope 之外的文件，先在 <collaboration_root>/shared.md 记录请求或在回复中说明需要授权。
- 不要修改与本任务无关的文件。

## 完成后请回报

1. 更新你的 lane worklog。
2. 如有正式输出，登记到 <collaboration_root>/shared.md 的 Shared Outputs。
3. 如需验收，向 <from-lane> 发送回传指令或在回复中明确说明。

<!-- /STARWORK:MULTIAGENT_MESSAGE -->
```

### 9.4 为什么必须格式化

格式化消息有三个作用：

- 让目标 Agent 明确知道这是 StarWork 系统协作消息，不是普通用户聊天。
- 方便后续 `thread/read` 从历史里识别 StarWork 指令。
- 方便课程和用户理解：这是 lane 之间的工作交接，不是随口喊另一个 AI。

## 11. Shared Context 记录规则

`multiagent instruct` 必须写入当前语言镜像对应的 `shared.md` 的 `Cross-Lane Requests`。

协作路径不能写死中文路径，必须根据工作台语言 profile 决定：

| language | collaboration_root | shared context |
| --- | --- | --- |
| `zh` | `_系统/协作` | `_系统/协作/shared.md` |
| `en` | `_system/collaboration` | `_system/collaboration/shared.md` |

所有格式化消息里的 `<collaboration_root>`、`recorded_in`、worklog 路径和 Shared Outputs 提示，都必须使用当前工作台语言镜像下的实际路径。

建议表格字段升级为：

```md
| id | from | to | request | status | host_delivery | link | updated |
|---|---|---|---|---|---|---|---|
```

状态：

| 状态 | 含义 |
| --- | --- |
| `recorded` | 已记录，但未尝试发送宿主消息。 |
| `sent` | 已发送到目标 Codex thread。 |
| `completed` | 目标 Codex turn 已完成。 |
| `failed` | 宿主发送失败。 |
| `needs_manual_delivery` | 目标 lane 没有可用 thread，需要人工转达。 |

## 12. Skill 调整

`starworkMultiagent` 需要新增意图：

| 用户说法 | Skill 解释 | CLI |
| --- | --- | --- |
| “让开发 lane 开始开发” | 向 development 发送跨会话指令 | `multiagent instruct development` |
| “看看开发 lane 做到哪了” | 读取 development host 状态 | `multiagent read development` 或 `status --host` |
| “帮我创建产品、开发、验收三个智能体” | 为多个 lane launch Codex threads | `multiagent launch --lanes ...` |
| “把这个 lane 固定起来” | 绑定并置顶 Codex thread | `multiagent bind --pin` |

Skill 生成 instruct 消息时必须采访或推断：

- from lane
- to lane
- 消息内容
- 写入边界
- 完成后如何回报

## 13. 用户体验说明

需要在文档中明确：

- Codex 前端可能不会立即显示跨会话新增消息。
- `thread/read` 能读到不代表前端已刷新。
- 发送成功的判断标准是 app-server 的 `turn/completed` 和 `thread/read` 结果。
- 如果前端没有变化，可尝试重新打开或重启 Codex。
- StarWork 会在项目内记录请求和 delivery state，因此不会只依赖前端显示。

## 14. 验收标准

### 14.1 `status --host`

- 能列出已有 lane。
- 能读取 Codex thread 的 name、cwd、status、turn count。
- 对 `notLoaded` 给出人话解释。
- JSON 输出区分 `starwork` 和 `host`。

### 14.2 `bind --pin`

- StarWork binding 成功后，即使 pin 失败也不回滚。
- pin 不支持时输出清楚 warning。
- `--dry-run` 不写任何文件、不调用 host mutation。

### 14.3 `read`

- 能读取目标 lane 绑定 thread。
- 默认不输出完整 turns。
- `--turns N` 只输出最近 N 个 turns。
- 不自动污染项目事实源。

### 14.4 `instruct`

- 会先写入 `shared.md` 请求记录。
- 目标 thread 未加载时，会先 `thread/resume`。
- 发送后等待 `turn/completed` 或超时。
- 成功后能用 `thread/read` 读到格式化 instruction message。
- 发送失败时，项目内记录仍保留，并标记失败。

### 14.5 `launch`

- 能为单个 lane 创建 Codex thread。
- 能发送格式化 Launch Message。
- 能绑定新 thread 到 lane。
- 能批量 launch 已有 lanes。
- Launch Message 明显区别于人类消息。

### 14.6 回归

- 现有 `multiagent init/add/bind/release/status/share` 行为不被破坏。
- `npm test` 通过。
- app-server 不可用时，CLI 降级为清楚的 warning，不破坏 StarWork 文件。

## 15. 分阶段实现计划

### Phase 0：实现前确认

目标：开发前先确认 Codex app-server 能力、现有 multiagent 状态文件和中英文路径映射，避免直接进入大改。

实现内容：

- 复核当前 `multiagent init/add/bind/release/status/share` 的现有行为和测试。
- 确认 Codex app-server 方法：
  - `thread/read`
  - `thread/list`
  - `thread/resume`
  - `turn/start`
  - `thread/name/set`
  - pin 相关方法是否存在。
- 明确 zh/en 协作路径解析函数：
  - `zh`：`_系统/协作`
  - `en`：`_system/collaboration`
- 明确 `.starwork/agent-lanes/state.json` 是否已有旧实现或冲突路径。

验收标准：

- 输出一份简短实现确认记录，写入对应 lane worklog 或开发记录。
- 能用测试脚本证明 `thread/read`、`thread/resume`、`turn/start` 的最小闭环可用。
- 开发者明确 pin 能力是可实现还是 v0.2 先降级 warning。
- 没有修改现有 CLI 行为。

### Phase 1：Codex Host Adapter 基础层

目标：先把 Codex app-server 调用封装成可测试的内部工具，不直接暴露新 CLI。

实现内容：

- 新增或整理 Codex host adapter 函数：
  - `readCodexThread(threadId, options)`
  - `listCodexThreads(options)`
  - `resumeCodexThread(threadId)`
  - `startCodexTurn(threadId, formattedMessage, options)`
  - `waitForCodexTurnCompleted(turnId, timeout)`
  - `setCodexThreadName(threadId, name)` 复用现有能力。
- app-server 调用必须统一处理：
  - initialize
  - JSON-RPC response 解析
  - notification 监听
  - timeout
  - stderr warning 收集
  - app-server 不可用降级。
- `startCodexTurn` 不得发完即断；必须等待 completed、失败或超时。

验收标准：

- 有单元测试覆盖：
  - 成功读取 thread。
  - 未加载 thread 直接 start 失败时，调用方能得到清楚错误。
  - resume 后 start 成功。
  - 等待 completed 后再关闭连接。
  - timeout 返回可解释状态。
- mock app-server 测试中能模拟 `thread/status/changed`、`turn/started`、`turn/completed`。
- 真实 app-server 不可用时不会破坏任何 StarWork 文件。
- `npm test` 通过。

### Phase 2：Agent Lanes 状态层与路径兼容

目标：建立 `.starwork/agent-lanes/state.json`，并把中英文协作路径解析纳入 multiagent 公共逻辑。

实现内容：

- 新增 `.starwork/agent-lanes/state.json` 读写逻辑。
- 将 host metadata、delivery state 写入 state.json。
- 保持当前 `agent-lanes.md` 的 `current_session` 兼容字段。
- 实现 language profile 下的协作路径解析：
  - `collaboration_root`
  - `agent_lanes_path`
  - `shared_context_path`
  - `lane_worklog_path`
  - `lane_workspace_path`
- 所有新增命令不得硬编码 `_系统/协作/`。

验收标准：

- 中文项目生成和读取 `_系统/协作/shared.md`。
- 英文项目生成和读取 `_system/collaboration/shared.md`。
- state.json 不存在时能自动初始化。
- state.json 损坏时给出清楚错误，不静默覆盖。
- `agent-lanes.md` 与 state.json 不一致时，CLI 输出 warning。
- 现有 `multiagent status --json` 不因 state.json 新增而破坏。

### Phase 3：`status --host` 与 `read <lane>`

目标：先完成只读能力，让用户能观察 Codex thread 状态。

实现内容：

- `multiagent status --host`
  - 显示每个 lane 的 StarWork binding。
  - 显示 Codex host observation。
  - 不默认 resume thread。
- `multiagent status --host --load`
  - 可选 resume 已绑定 thread 后再观察。
- `multiagent read <lane>`
  - 默认只读 thread 元信息。
  - `--turns N` 输出最近 N 个 turns。
  - `--json` 输出结构化结果。
- 输出中解释 `notLoaded / idle / active`。

验收标准：

- 未绑定 lane 显示 `unbound`，不报错。
- 绑定但 thread 不存在时显示 host unreadable。
- 绑定且 thread 存在时可读出 name、cwd、status、turn count。
- `status --host` 默认不会把 `notLoaded` 变成 `idle`。
- `status --host --load` 可以通过 resume 将可加载 thread 观察为 `idle`。
- `read <lane> --turns 2` 只展示最近 2 个 turns。
- `read` 不写入项目文件。

### Phase 4：`bind --pin`

目标：在现有 bind 基础上增加 Codex thread 置顶增强，但不让 pin 影响 binding 主流程。

实现内容：

- `multiagent bind <lane> --pin`
- 如果 Codex pin 方法可用：
  - binding 成功后 best-effort pin。
  - state.json 记录 `pinned: true` 或实际状态。
- 如果 Codex pin 方法不可用：
  - 输出 unsupported warning。
  - 不回滚 binding。
  - state.json 记录 pin unsupported 或 unknown。

验收标准：

- `--dry-run --pin` 不调用 host mutation。
- binding 成功、pin 成功时，状态输出包含 pinned 信息。
- binding 成功、pin 失败时，CLI exit code 仍表示主流程成功，并输出 warning。
- 非 Codex session 使用 `--pin` 时降级为 unsupported warning。
- 现有 `bind --session-name` 测试继续通过。

### Phase 5：格式化消息生成器

目标：先实现 StarWork MultiAgent 自动消息格式，不急着发送。

实现内容：

- 实现 Launch Message 生成器。
- 实现 Cross-session Instruction Message 生成器。
- 格式必须包含：
  - `<!-- STARWORK:MULTIAGENT_MESSAGE v1 -->`
  - message type
  - from / to lane
  - created_at
  - `<collaboration_root>` 解析后的真实路径
  - `## 消息内容`
  - 边界
  - 完成后回报方式
- 提供 brief 模式，但不得去掉 marker。

验收标准：

- 中文项目消息中使用 `_系统/协作`。
- 英文项目消息中使用 `_system/collaboration`。
- Instruction Message 不再出现独立的 `## 背景`、`## 请完成的任务`、`## 相关文件`。
- 消息 marker 可以被正则识别。
- 生成器有快照测试或等价断言测试。

### Phase 6：`instruct <to-lane>`

目标：完成跨会话指令主链路。

实现内容：

- `multiagent instruct <to-lane> --from <lane> --message <text>`
- 先写入当前语言镜像的 `shared.md` Cross-Lane Requests。
- 再向目标 lane 绑定的 Codex thread 发送格式化 Instruction Message。
- 发送链路：
  - `thread/read` 确认存在。
  - `thread/resume` 加载。
  - `turn/start` 发送。
  - 等待 `turn/completed` 或超时。
  - `thread/read` 校验最新 turn。
- 将 host delivery 写入 state.json。
- 目标 lane 未绑定或 host 不可用时，shared.md 记录保留，并标记 `needs_manual_delivery` 或 `failed`。

验收标准：

- `--dry-run` 显示将写入 shared.md 的请求和将发送的格式化消息，不写文件、不发 host。
- 目标 lane 不存在时拒绝。
- 目标 lane 未绑定时，shared.md 可记录请求，但 host delivery 标记为 `needs_manual_delivery`。
- 成功发送后：
  - shared.md 有请求记录。
  - state.json 有 delivery 记录。
  - `thread/read` 能读到格式化 Instruction Message。
  - delivery 状态为 `completed`。
- 发送超时时，状态为 `failed` 或 `timeout`，且不删除 shared.md 请求。
- 不会因 Codex 前端未刷新而误判失败。

### Phase 7：`launch <lane>` 与批量 `launch --lanes`

目标：为已有 lane 创建 Codex thread，并发送格式化 Launch Message。

实现内容：

- `multiagent launch <lane>`
- `multiagent launch --lanes a,b,c`
- 创建 Codex thread。
- 发送格式化 Launch Message。
- 绑定新 thread 到 lane。
- 可选 `--session-name`。
- 可选 `--pin`，按 Phase 4 规则降级。
- 写入 state.json。
- 批量 launch 时，一个 lane 失败不应吞掉其他 lane 的结果；最终输出逐 lane 成功/失败。

验收标准：

- 单 lane launch 能创建 thread、发送 Launch Message、绑定 lane。
- 批量 launch 能为多个已有 lane 创建和绑定 thread。
- lane 不存在时不自动创建，除非用户提供后续 blueprint 能力。
- Launch Message 能被 `thread/read` 读到，并含 StarWork marker。
- 中文/英文项目路径正确。
- 批量结果 JSON 能表达每个 lane 的状态。
- app-server 不可用时不修改 agent-lanes.md binding。

### Phase 8：Skill 与文档更新

实现内容：

### Phase 9：端到端验收

目标：验证产品规划 lane 与开发 lane 的真实闭环。

验收场景：

1. 创建或使用已有两个 lane：
   - `product-planning`
   - `development`
2. `launch development` 创建开发 lane Codex thread。
3. 产品规划 lane 使用 `instruct development` 发送开发指令。
4. `read development --turns 2` 能读到开发 lane 收到指令。
5. 开发 lane 完成后，反向 instruct 产品规划 lane 验收。
6. 产品规划 lane 通过 `read` 或前端确认收到验收请求。

验收标准：

- 全流程不需要手工复制消息。
- StarWork 项目内 `shared.md` 和 state.json 能还原请求流转。
- 即使 Codex 前端不刷新，CLI 仍能用 `thread/read` 证明消息存在。
- `npm test` 通过。
- 没有新增未解释的 `.starwork-new`、临时文件或业务文档污染。

## 17. 风险与开放问题

| 问题 | 判断 |
| --- | --- |
| Codex 前端不刷新 | 视为宿主缺陷，StarWork 不依赖前端刷新。 |
| `turn/start` 连接过早关闭会 interrupted | 发送命令必须等待 `turn/completed` 或进入明确异步模式。 |
| pin API 未确认 | 实现时确认；不可用则降级 warning。 |
| Host 状态与 StarWork 状态不一致 | `status --host` 负责暴露差异，不自动修复。 |
| 格式化消息太长 | launch 和 instruct 可提供 brief 模式，但必须保留 StarWork message marker。 |
| 中英文镜像路径不一致 | 所有协作路径必须从 language profile 或 workspace state 解析，不得硬编码 `_系统/协作/`。 |
| Cursor / Trae 不支持同等能力 | 后续通过 Host Adapter 能力矩阵降级，不反向削弱 Codex 样板体验。 |

## 18. 与后续阶段关系

v0.2 先做 Codex 完整样板。

后续阶段：

- Cursor 适配：按 host adapter contract 支持 read / instruct 的可用子集。
- Trae 适配：主要支持状态读取和人工恢复提示。
- 课程文档：基于 Codex 样板体验，再解释 Cursor / Trae 的降级路径。
