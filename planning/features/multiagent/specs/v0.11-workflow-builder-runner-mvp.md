# MultiAgent v0.11 Workflow Builder / Runner MVP SPEC

## 1. 状态

- 日期：2026-06-16
- 状态：accepted
- 所属功能：MultiAgent / Workflow Builder / Workflow Runner / Next 测试版本
- 关联问题：`product/planning/issues/ISSUE-024.md`
- 关联前置：`product/planning/issues/ISSUE-022.md`、`product/planning/features/multiagent/specs/v0.10-upgrade-migration-compatibility.md`
- 原始草案：`_系统/协作/lanes/product-multiagent/workspace/drafts/2026-06-16-v0.11-workflow-builder-runner-mvp-spec.md`
- 晋升 lane：product-lead

## 2. 一句话目标

让 `starworkMultiagent` 支持第一版 workflow 能力：

```text
用户可以先设计一个多 Agent workflow
  -> 预览和保存 workflow definition 草案
  -> 明确确认后再启动 workflow
  -> Runner 生成 compact + reference packet
  -> 按 v0.8 标准线程工具投递或人工交接
  -> 记录真实 delivery status
```

v0.11 的核心不是后台自动化，而是把 workflow 从“靠 Agent 记忆的流程”变成“可设计、可预览、可确认、可逐节点交接的 Packet Runtime”。

## 3. 与 v0.10 的关系

v0.10 和 v0.11 必须分开：

| 版本 | 主题 | 解决问题 |
| --- | --- | --- |
| v0.10 | 升级 / 迁移兼容 | 旧 MultiAgent 工作区升级后不能被误判为空，写入前先兼容读取和迁移 |
| v0.11 | Workflow Builder / Runner MVP | 设计 workflow、保存 definition、启动 runner、生成 packet 并投递 |

开发顺序采用：

```text
先做 v0.10；如果同一轮 next 研发推进，则把 v0.10 作为 v0.11 Phase 0 前置验收。
```

理由：

- v0.11 会新增 workflow definition、草案路径、可能的 workflow instance / packet request 记录，会扩大 MultiAgent 文件结构和状态模型。
- 如果旧工作区升级兼容没先解决，workflow 写入很容易让旧用户的 lane、binding、request 进入新旧结构分裂。
- v0.11 的 Builder 可以只写 lane workspace 草案，风险较低；但 Runner 一旦开始记录 request / delivery，就必须依赖 v0.10 的兼容读取与写入阻断。

因此 v0.11 设置 Phase 0：

```text
Phase 0 = v0.10 ready-for-development SPEC 已实现并验收通过，或至少 development 在同一 next 分支先完成 v0.10 验收项。
```

v0.11 Runner 不得在 Phase 0 未通过时进入可写 / 可投递验收。

## 4. 目标用户问题

用户想做的是：

- “帮我设计一个产品开发循环。”
- “SPEC 写完后自动通知 development，development 完成后回到 product review。”
- “我想让多个 Agent 之间按固定流程传递任务。”
- “进入这个流程，但不要让 Agent 忘掉下一步该做什么。”

当前缺口：

- 只有 Agent-to-Agent message，没有 workflow definition。
- 只有运行讨论，没有构建入口。
- 只讲“完整 Packet”，容易造成消息过长。
- CLI / Skill next 版本可能错配，导致 CLI 已有 workflow 功能但 Skill 还是 latest。

## 5. 非目标

v0.11 MVP 不做：

- 不做后台 daemon。
- 不做文件 watcher。
- 不做定时轮询。
- 不做无限自动循环。
- 不做复杂 DAG 调度器。
- 不做跨项目 workflow 队列。
- 不新增独立 `starworkWorkflow` 全局 Skill。
- 不绕过 v0.8 标准线程工具边界。
- 不把投递成功说成目标任务完成。
- 不让普通用户用 `latest` 试 workflow。
- 不把未确认 draft 写入 `.starwork` workflow state。

## 6. 产品原则

### P1. Builder 和 Runner 必须分开

设计 workflow 不等于启动 workflow。

| 子模式 | 允许 | 禁止 |
| --- | --- | --- |
| Workflow Builder | 采访、设计、预览、校验、保存草案 | 创建 instance、投递消息、记录 delivery |
| Workflow Runner | 读取已确认 definition、生成 instance、生成 packet、投递或人工交接 | 重新设计 workflow、执行未确认 draft、跳过 gate |

### P2. 第一版不新增 `starworkWorkflow`

第一版由 `starworkMultiagent` 承担 workflow 构建和运行入口。

原因：

- workflow 的基础对象仍是 lane、cross-lane message、return contract 和 delivery status。
- `starworkMultiagent` 已经负责多 Agent 分工和交接。
- 新增 Skill 会扩大安装、路由和同源版本风险。

未来当 workflow schema、Pack workflow、Core workflow 稳定后，再评估拆出 `starworkWorkflow`。

### P3. Packet 默认 compact + reference

Runner 默认不复制完整 Workflow Definition。

默认 message 只传当前节点需要的最小字段，并引用：

- workflow definition path
- workflow version
- node id
- input paths
- return contract keys

### P4. Next 版本必须同源安装

workflow 是 next 功能，不能让普通用户通过 latest 测试，也不能接受 next CLI + latest/main Skill 的错配。

## 7. 意图路由

### 7.1 主入口 `starwork`

`starwork` 主入口应路由：

| 用户话语 | 路由 |
| --- | --- |
| “StarWork 怎么用” | `starwork` 主入口 |
| “创建几个 Agent / AI 岗位” | `starworkMultiagent` 团队设计 |
| “设计一个 workflow / 自动通知流程 / 产品开发循环” | `starworkMultiagent` Workflow Builder |
| “进入 / 启动 / 执行 workflow” | `starworkMultiagent` Workflow Runner |

### 7.2 含混意图追问

用户说：

```text
帮我做一个产品迭代循环。
```

Skill 必须追问：

```text
你是想先设计这个流程，还是现在就按已有流程开始执行？
```

不得在未确认时进入 Runner。

## 8. Workflow Builder

### 8.1 第一屏

Builder 第一屏必须说明：当前只是设计 workflow，不会触发任何 Agent。

建议话术：

```text
可以。我先帮你设计这个多 AI 协作流程。

这一步只会生成 workflow 草案，说明：
1. 哪些 AI 岗位参与；
2. 每一步什么时候触发；
3. 每一步要产出什么；
4. 哪些地方需要你或产品负责人确认；
5. 完成后下一步交给谁。

在你确认前，我不会通知任何 Agent，也不会启动真实流程。
```

### 8.2 采访问题

Builder 至少采访：

1. 目标：这个 workflow 要稳定解决什么问题。
2. 参与 lane：涉及哪些 AI 岗位，优先复用已有 lane。
3. 触发条件：什么事件启动流程，什么事件表示当前节点完成。
4. 每步输入：下一位 Agent 需要哪些材料才能开始。
5. 每步产出：当前节点必须留下什么结果。
6. Return contract：完成后必须回传哪些字段。
7. Gate / stop：哪些节点必须人审，哪些状态停止。
8. 写入边界：确认前只保存草案，不真实投递。

### 8.3 Definition 草案结构

Builder 生成 Workflow Definition 草案：

```yaml
workflow_id: product_iteration_loop
title: 产品迭代流程
status: draft
version: 0.1
owner_lane: product-lead
nodes:
  product_spec:
    lane: product-multiagent
    trigger: user_confirmed
    inputs:
      - issue_path
    outputs:
      - spec_path
      - acceptance_criteria
      - open_questions
    return:
      - spec_path
      - decision_needed
      - recommendation
    gate:
      type: owner_gate
      owner: product-lead
    next:
      accepted: development_implementation
      needs_revision: product_spec
      rejected: stop
  development_implementation:
    lane: development
    trigger: spec_accepted
    inputs:
      - spec_path
      - acceptance_criteria
    outputs:
      - changed_files
      - verification
      - risks
    return:
      - changed_files
      - verification
      - risks
      - review_request
    gate:
      type: product_review_gate
      owner: product-lead
    next:
      done: product_review
      blocked: human_gate
  product_review:
    lane: product-lead
    trigger: implementation_done
    inputs:
      - changed_files
      - verification
    outputs:
      - acceptance_result
      - issue_status
      - next_action
    return:
      - acceptance_result
      - issue_status
    next:
      passed: stop
      failed: development_implementation
```

### 8.4 预览表

保存前必须向用户展示预览：

| 步骤 | 负责 lane | 触发条件 | 输入 | 产出 | Return Contract | Gate / Stop |
| --- | --- | --- | --- | --- | --- | --- |
| SPEC 草案 | product-multiagent | 用户确认 | issue | spec, acceptance | spec_path, decision_needed | product-lead gate |
| 开发实现 | development | spec accepted | spec, acceptance | changed_files, verification | changed_files, verification, risks | product review gate |
| 产品复验 | product-lead | implementation done | changed_files, verification | acceptance_result | issue_status, next_action | passed stop / failed loop |

确认句：

```text
如果这个 workflow 设计没问题，我只会先保存草案，不会启动流程或通知任何 Agent。
```

### 8.5 草案保存路径

用户确认前只能保存为草案：

```text
_系统/协作/lanes/<builder-lane>/workspace/drafts/workflows/<workflow-id>.draft.md
```

例如：

```text
_系统/协作/lanes/product-multiagent/workspace/drafts/workflows/product-iteration-loop.draft.md
```

不得写：

- `product/`
- `.starwork/workflows/state.json`
- 目标 lane worklog
- shared request delivery status

## 9. Workflow Runner

### 9.1 启动条件

Runner 只在用户明确说以下语义时启动：

- 启动这个 workflow。
- 进入产品迭代流程。
- 按这个已确认 workflow 开始执行。

Runner 不得默认执行未确认 draft。

如果用户指定的是 draft，必须追问：

```text
这个 workflow 还只是草案。你要先确认它，再启动吗？
```

### 9.2 Runner 流程

Runner 执行：

1. 读取已确认 Workflow Definition。
2. 检查 v0.10 Phase 0 是否通过。
3. 检查目标 lane 是否存在。
4. 检查目标 lane current_session。
5. 检查目标 lane 不是当前会话，除非用户明确要求当前会话执行。
6. 生成 workflow instance id。
7. 生成当前节点 compact + reference packet。
8. 调用宿主标准线程工具投递，或输出 manual handoff。
9. 用 request record 记录真实 delivery status。

### 9.3 当前会话 ID 校验

发送前必须确认：

- 当前会话 id。
- 目标 lane session id。
- 两者不相同。

如果目标 lane 是当前会话：

- 默认不投递。
- 说明“目标岗位绑定的是当前会话，直接发送会形成自我交接”。
- 只有用户明确要求当前会话执行当前节点，才可进入本地执行模式，不调用 `send_message_to_thread`。

## 10. Packet 策略

### 10.1 默认 compact + reference

默认 instruction：

```text
<!-- STARWORK:MULTIAGENT_MESSAGE v1 -->

# StarWork Workflow Instruction

message_type: workflow_instruction
request_id: REQ-...
from_lane: product-lead
to_lane: development
created_at: 2026-06-16T00:00:00+08:00
recorded_in: _系统/协作/shared.md

packet_mode: compact
wf: product_iteration_loop
wf_i: WF-20260616-001
wf_def: _系统/协作/lanes/product-multiagent/workspace/drafts/workflows/product-iteration-loop.confirmed.md
wf_v: 0.1
node: development_implementation

inputs:
- spec: product/planning/features/multiagent/specs/v0.10-upgrade-migration-compatibility.md
- issue: product/planning/issues/ISSUE-022.md

do:
- implement_spec
- run_acceptance_checks
- update_worklog

return:
- changed_files
- verification
- risks
- review_request

gate:
- next_owner: product-lead
- do_not_continue_without_review: true

<!-- /STARWORK:MULTIAGENT_MESSAGE -->
```

### 10.2 Full packet 使用条件

仅允许：

- 目标 Agent 无法访问项目文件。
- manual handoff 必须完整自包含。
- 用户明确要求完整上下文。

### 10.3 长度预算

| message | 上限 |
| --- | --- |
| 默认 instruction | ≤ 2,000 中文字符 |
| 默认 response | ≤ 1,500 中文字符 |
| full packet | ≤ 4,000 中文字符 |

超出预算：

- 长内容写入文件。
- message 中只放路径引用。

## 11. Delivery status

Runner 投递成功只能说：

```text
workflow 当前节点消息已送达，并已记录 StarWork request。
```

不得说：

```text
目标 Agent 已完成。
workflow 已完成。
```

目标完成必须来自：

- 目标 lane 回传 message。
- 目标 lane worklog。
- shared output。
- thread read 观察到明确完成，但仍需区分“观察”与“正式事实源”。

## 12. v0.8 边界保持

Codex App 正常路径继续直接调用标准线程工具：

- `send_message_to_thread`
- `create_thread`
- `read_thread`
- `set_thread_title`
- `set_thread_pinned`
- `set_thread_archived`

不得恢复以下命令作为 Codex 正常路径：

- `starwork multiagent instruct`
- `starwork multiagent launch`
- `multiagent message instruct`
- `multiagent message launch`
- `multiagent read --host codex`
- `multiagent status --host codex`

CLI 只维护项目事实源：

- `multiagent status --target`
- `multiagent bind`
- `multiagent share`
- `multiagent request record`

## 13. Next 发布策略

### 13.1 普通用户

普通用户继续使用：

```bash
npm install -g @jennie-shawn/starwork@latest
```

普通用户不应通过 latest 测 workflow。

### 13.2 内测 / A 测用户

内测用户使用：

```bash
npm install -g @jennie-shawn/starwork@next
```

或：

```bash
npx @jennie-shawn/starwork@next --version
```

所有 workflow A 测文档必须写 `@next`。

### 13.3 Skill 安装错配风险

当前命令：

```bash
npx skills add jennie-shawn/StarWork -g -a codex -y
```

可能绕过 npm dist-tag，导致：

```text
CLI = next
Skill = latest / GitHub main
```

这会让用户安装了 next CLI，却仍被旧 `starworkMultiagent` Skill 引导，造成 workflow 行为缺失或边界错误。

### 13.4 最小可接受策略

v0.11 MVP 的最小策略：

1. A 测文档明确要求 CLI 使用 `@next`。
2. A 测文档不得继续建议用 `npx skills add jennie-shawn/StarWork` 安装 workflow next Skill，除非该命令能锁定 next 对应版本。
3. 内测阶段可要求从同一 next 分支 / 同一 npm 包手工安装 Skill。
4. `starworkMultiagent` next Skill 必须在文档或 frontmatter 中标注 channel / version。
5. `doctor` 或 `starworkMultiagent` 首屏必须提示：如果 CLI 是 next 但 Skill 无 workflow builder/runner 能力，则当前安装错配，需要重新安装 next Skill。
6. 如果无法自动检测 Skill channel，本轮 workflow 只能内部手工测试，不进入外部 A 测。

### 13.5 完整策略

正式策略应新增 StarWork 自己的 Skill 安装入口：

```bash
npx @jennie-shawn/starwork@next skills install --agent codex --global
```

要求：

- 从当前 npm 包内的 `skills/` 安装系统级 Skills。
- 安装 Skill 时记录 `starwork_version` 和 `channel`。
- `starwork doctor` 或 `starwork skills doctor` 能检查 CLI / Skill channel 是否一致。
- A 测指南只使用 StarWork CLI 自带安装入口安装 next Skill。

完整策略未实现前，不建议对普通外部用户开放 workflow next。

## 14. Phase 切分

### Phase 0：v0.10 前置验收

完成条件：

- v0.10 升级 / 迁移兼容实现通过验收。
- 旧 MultiAgent 工作区不会被新 status / doctor 判空。
- 写入类命令在未迁移旧结构时安全阻断。
- Skill 遇到旧结构时先引导迁移。

### Phase 1：Builder

完成：

- 意图区分。
- 采访流程。
- 预览表。
- 草案保存到 lane workspace。
- 不投递、不写 `.starwork` workflow state、不写 `product/`。

### Phase 2：Runner

完成：

- 读取已确认 definition。
- 生成 workflow instance id。
- 生成 compact + reference packet。
- 当前会话 ID 校验。
- 投递或 manual handoff。
- request record 真实 delivery status。

### Phase 3：Next 安装保护

完成：

- A 测文档使用 `@next`。
- CLI / Skill channel 错配至少有检查、说明或内测限制。
- 不让 latest 用户误用 workflow。

## 15. 验收标准

### 15.1 Builder / Runner 意图区分

测试场景：

- 用户说“帮我设计一个产品开发 workflow”。
- 用户说“启动产品开发 workflow”。
- 用户说“帮我做一个产品迭代循环”。

期望：

- 设计语义进入 Builder。
- 启动语义进入 Runner。
- 含混语义必须追问。
- 设计语义不得投递消息。

### 15.2 Builder 草案保存

Builder 确认保存后：

- 只写：

```text
_系统/协作/lanes/<builder-lane>/workspace/drafts/workflows/<workflow-id>.draft.md
```

- 不写 `product/`。
- 不写 `.starwork/workflows/state.json`。
- 不调用 `send_message_to_thread`。
- 不调用 `multiagent request record`。
- 不生成 delivery status。

### 15.3 Workflow Definition 预览表

预览必须包含：

- lane
- 触发条件
- 输入
- 产出
- return contract
- gate / stop

且必须有确认句：

```text
如果这个 workflow 设计没问题，我只会先保存草案，不会启动流程或通知任何 Agent。
```

### 15.4 Runner packet

Runner 默认生成：

- `packet_mode: compact`
- `wf`
- `wf_i`
- `wf_def`
- `wf_v`
- `node`
- `inputs`
- `do`
- `return`
- `gate`

默认不复制完整 Workflow Definition。

长度：

- instruction ≤ 2,000 中文字符。
- response ≤ 1,500 中文字符。
- full packet ≤ 4,000 中文字符。

full packet 只在明确条件下出现。

### 15.5 Delivery status

投递成功后：

- 可以说消息已送达。
- 可以说已记录 request。
- 不可以说目标任务已完成。

目标完成必须来自目标 lane 回传、worklog、shared output 或明确会话观察。

### 15.6 v0.8 禁止项扫描

`product/skills/starworkMultiagent/SKILL.md` 不得恢复以下正常路径：

```bash
rg -n "starwork multiagent instruct|starwork multiagent launch|multiagent message instruct|multiagent message launch|multiagent read --host codex|multiagent status --host codex|--session-name|--pin" product/skills/starworkMultiagent/SKILL.md
```

期望无命中，除非出现在明确禁止说明中；Skill 正常路径不得包含这些命令。

### 15.7 当前会话 ID 校验

发送前必须确认：

- 当前会话 ID。
- 目标 lane session ID。
- 目标 lane 不是当前会话。

如果目标 lane 是当前会话：

- 默认阻断投递。
- 提示用户这是自我交接。
- 用户明确要求当前会话执行时，进入本地执行模式，不调用 `send_message_to_thread`。

### 15.8 Next 发布保护

验收：

- A 测文档必须使用 `@next`。
- 普通用户文档不得用 `latest` 试 workflow。
- 不得继续无说明地使用 `npx skills add jennie-shawn/StarWork` 安装 workflow next Skill。
- CLI / Skill channel 错配必须有检查、警告或明确“仅内部手工测试”限制。

### 15.9 与 v0.10 的关系

如果采用 Phase 0：

- development 开始 v0.11 Runner 前必须先通过 v0.10 验收。
- v0.11 SPEC 必须标注 Phase 0 完成条件。
- product-lead 验收 v0.11 时先检查 v0.10 是否已完成。

如果 product-lead 决定完全先做 v0.10：

- v0.11 development 派发应等待 v0.10 accepted。
