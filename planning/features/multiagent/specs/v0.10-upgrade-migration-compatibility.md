- 日期：2026-06-15

- 关联问题：`product/planning/issues/ISSUE-022.md`

- 晋升 lane：product-lead

## 2. 背景

`ISSUE-022` 来自一个真实产品风险：MultiAgent 后续如果调整文件结构、目录名称、状态字段或协作记录格式，已有用户的工作台可能被新版误判为空、不可读或需要手工迁移。

当前 MultiAgent 已经形成多层事实源：

- 机器状态：`.starwork/agent-lanes/state.json`
- 人类可读 lane 注册：`_系统/协作/agent-lanes.md` 或 `_system/collaboration/agent-lanes.md`
- 跨 lane 请求和共享输出：`_系统/协作/shared.md` 或 `_system/collaboration/shared.md`
- lane worklog：`_系统/协作/lanes/<lane>/worklog.md`
- lane workspace：`_系统/协作/lanes/<lane>/workspace/`

这些内容一旦存在，就应被视为用户项目的协作历史。新版 StarWork 不能因为字段升级或路径演进，把已有 lane、binding、request、shared output 或 worklog 当作不存在。

## 3. 用户问题

用户真正担心的不是“有没有一个迁移命令”，而是：

- 升级后原来的 AI 岗位还在不在。
- 原来的会话绑定还能不能继续投递。
- 原来的交接请求、共享成果和工作记录会不会丢。
- 新版提示是否能解释风险，而不是直接报错或重复初始化。
- 自动修复会不会覆盖手写记录。

因此 v0.10 的目标不是重做 MultiAgent 文件结构，而是建立一条安全升级原则：

```text
先兼容读取，再预览迁移，最后确认写入。
```

## 4. 一句话目标

让新版 MultiAgent 在遇到旧结构时，能先读出已有团队和会话绑定；如果需要迁移，必须通过 `doctor` 和 dry-run 给出清晰预览，用户确认后才写入，并且不删除、不覆盖用户手写协作记录。

## 5. 非目标

本版不做：

- 不设计新的后台 daemon、自动调度器或 Loop Engineering 系统。
- 不迁移课程项目、旧 runtime spike 或历史 `matters/` 原始资料。
- 不把 `_系统/协作/` 和 `_system/collaboration/` 合并成单一路径；语言路径仍按当前工作台语言选择。
- 不强制所有旧工作台一次性升级到未来完整 workbench 结构。
- 不改 v0.8 边界：Codex App 宿主动作仍由 Skill 直接调用标准线程工具，CLI 只维护项目事实源。
- 不让 MultiAgent 绕过 `starworkInit` 的 `pending_merge` 安全边界。
- 不自动改写 `AGENTS.md`、`CLAUDE.md`、README 或宿主规则入口。

## 6. 结构版本模型

### 6.1 Canonical structure version

v0.10 以当前已落地结构作为第一个稳定结构版本：

```json
{
  "version": 1,
  "lanes": {},
  "requests": []
}
```

规范含义：

- `.starwork/agent-lanes/state.json.version = 1` 表示当前 MultiAgent 机器状态结构版本。
- 后续如果移动路径或改变字段语义，才递增为 `version = 2`、`version = 3`。
- v0.10 不要求立即把当前结构升到 version 2；它要求所有读写路径都尊重 version / legacy detection。

### 6.2 兼容状态

CLI 和 Skill 应统一使用这些兼容状态：

| status | 含义 | 默认行为 |
| --- | --- | --- |
| `current` | 已是当前支持的结构 | 可读，可写 |
| `legacy_readable` | 旧结构可读，能识别 lane / binding / request | 只读可继续，写入前建议迁移 |
| `migration_available` | 可自动生成安全迁移计划 | 允许 dry-run，确认后写入 |
| `migration_required_for_write` | 读可以兼容，写会造成新旧结构分裂 | 写入类 MultiAgent 命令阻断，先迁移 |
| `blocked_conflict` | 存在冲突或无法安全合并 | 不自动迁移，提示人工处理 |
| `unknown_partial` | 只能识别部分文件，无法确认完整语义 | 不写入，提示备份后人工确认 |

## 7. 旧结构识别

### 7.1 识别入口

`doctor`、`multiagent status --json` 和迁移 dry-run 都应通过同一套读取函数识别 MultiAgent 结构，避免不同命令给出不同判断。

识别顺序：

1. 读取 `.starwork/workspace.json`，确认目标是 StarWork 工作台。
2. 读取 `.starwork/agent-lanes/state.json`。
3. 读取当前语言协作入口：
   - 中文：`_系统/协作/agent-lanes.md`、`_系统/协作/shared.md`
   - 英文：`_system/collaboration/agent-lanes.md`、`_system/collaboration/shared.md`
4. 读取 lane worklog / workspace 路径是否存在。
5. 汇总机器状态和 Markdown 注册表，不因任一侧缺失就直接判空。

### 7.2 Legacy classes

至少支持以下旧结构 fixture：

| class | 判断条件 | 处理 |
| --- | --- | --- |
| `state_v1_current` | `state.json.version === 1` 且 Markdown 注册表可对应 | `current` |
| `state_unversioned` | `state.json` 有 `lanes` / `requests`，但没有 `version` | `legacy_readable` + `migration_available` |
| `markdown_only` | 无 `.starwork/agent-lanes/state.json`，但 `agent-lanes.md` 有 lane 表 | `legacy_readable` + `migration_available` |
| `state_only` | 有 state.json，但缺 `agent-lanes.md` 或 shared.md | `legacy_readable` + `migration_available` |
| `mixed_language_paths` | 同时存在 `_系统/协作/` 与 `_system/collaboration/` MultiAgent 记录 | `blocked_conflict`，除非 workspace language 明确且另一侧为空 |
| `conflicting_lane` | 同一 lane 在 state 和 Markdown 中 purpose / write_scope / session 冲突 | `blocked_conflict` |
| `malformed_state` | state.json 无法解析，但 Markdown 可读 | `unknown_partial`，不自动覆盖损坏 state |

### 7.3 不得误判为空

只要任一可信来源能读出 lane，就不得把 MultiAgent 团队显示为空。

示例：

- `state.json` 缺失但 `agent-lanes.md` 有 `development`、`product-planning`，`status` 必须显示这些 lane，并标记来源为 `markdown_legacy`。
- `agent-lanes.md` 缺失但 `state.json` 有 binding，`status` 必须显示 binding，并提示 Markdown 注册表缺失。
- `shared.md` 表格格式旧，但能识别 request id、from、to、status，`status` 不得丢弃这些 request。

## 8. 兼容读取策略

### 8.1 `multiagent status --json`

新版 status 应返回兼容信息：

```json
{
  "multiagent": {
    "compatibility": {
      "status": "legacy_readable",
      "structure_version": null,
      "target_structure_version": 1,
      "legacy_classes": ["state_unversioned"],
      "read_sources": [
        ".starwork/agent-lanes/state.json",
        "_系统/协作/agent-lanes.md",
        "_系统/协作/shared.md"
      ],
      "migration": {
        "required_for_write": true,
        "available": true,
        "dry_run_command": "starwork multiagent upgrade --target <path> --dry-run"
      }
    }
  }
}
```

要求：

- `lanes` 仍应包含从旧结构读出的 lane。
- `current_session`、`host`、`thread_id`、`session_id` 等旧字段应尽量归一化输出。
- 不得因为兼容状态不是 `current` 就隐藏 lane。
- 写入类命令可以因 `required_for_write` 阻断，但只读状态不能阻断。

### 8.2 Markdown source priority

当 state 和 Markdown 都存在且不冲突：

- lane purpose / write_scope 以 `agent-lanes.md` 为更接近用户可读事实的来源。
- binding / host session 以 `.starwork/agent-lanes/state.json` 为机器事实来源。
- request delivery status 以 `.starwork/agent-lanes/state.json.requests` 为机器事实来源，`shared.md` 作为人类可读索引。

当冲突时，不自动选择胜者，返回 `blocked_conflict`。

## 9. Dry-run 迁移预览

### 9.1 命令入口

建议新增 scoped 命令：

```bash
starwork multiagent upgrade --target <path> --dry-run
starwork multiagent upgrade --target <path> --yes
starwork multiagent upgrade --target <path> --json --dry-run
```

说明：

- 这是 MultiAgent 结构迁移，不是全项目升级。
- 顶层 `starwork upgrade` 未来可以委托到该命令，但 v0.10 不要求先设计完整顶层 upgrade。
- `--dry-run` 必须是默认建议入口；`--yes` 必须只执行上一轮可安全描述的迁移计划。

### 9.2 Dry-run 输出分组

dry-run 人类输出必须用用户语言分组：

```text
这是一次预览，不会写入文件。

已识别：
- 旧版 MultiAgent 状态文件：.starwork/agent-lanes/state.json
- AI 岗位注册表：_系统/协作/agent-lanes.md
- 交接记录：_系统/协作/shared.md

将会创建：
- 缺失的 lane worklog
- 缺失的 lane workspace 目录

将会更新：
- .starwork/agent-lanes/state.json：补充 version 和兼容迁移记录

将会保留：
- 现有 worklog 内容
- 现有 shared outputs 和 requests
- 现有 AGENTS.md / CLAUDE.md / README.md

不会做：
- 不删除旧文件
- 不覆盖用户手写记录
- 不创建或通知新的 AI 会话
```

### 9.3 Dry-run JSON

JSON 输出至少包含：

```json
{
  "status": "migration_available",
  "target_structure_version": 1,
  "safe_to_apply": true,
  "will_create": [],
  "will_update": [],
  "will_copy": [],
  "will_preserve": [],
  "will_not_touch": [],
  "conflicts": [],
  "warnings": [],
  "backup": {
    "will_create_backup": true,
    "path": ".starwork/backups/multiagent/<timestamp>/"
  }
}
```

要求：

- dry-run 不得写入 `.starwork` 或协作目录。
- 每个 `will_update` 项必须说明字段级原因，例如“补充 `version: 1`”。
- 如果存在冲突，`safe_to_apply` 必须为 `false`，且 `--yes` 必须失败。

## 10. 用户确认后写入

### 10.1 写入原则

`--yes` 只能执行 dry-run 中已经说明的安全动作。

允许动作：

- 创建缺失目录：lane `workspace/`、`worklog.md` 的空模板。
- 创建缺失机器状态文件：`.starwork/agent-lanes/state.json`。
- 为 unversioned state 补充 `version: 1`。
- 把 Markdown-only lane 转写到 state 的 `lanes` 字段。
- 把 state-only lane 补入 `agent-lanes.md`。
- 补齐 request record 的机器字段，但不得改变原 request id 和原状态含义。
- 创建备份目录并复制会被更新的旧文件。

禁止动作：

- 删除旧文件。
- 覆盖非空 worklog。
- 重写 `shared.md` 中用户手写的说明段落。
- 把无法解析的 state.json 直接覆盖成新 state。
- 因迁移创建新 Codex thread、发送消息、改名、置顶或归档。
- 绕过 `pending_merge` 改写 AI 入口文档。

### 10.2 Backup

任何会修改已有文件的迁移，都必须先复制旧文件到：

```text
.starwork/backups/multiagent/<YYYYMMDD-HHMMSS>/
```

备份至少包含：

- 原 `.starwork/agent-lanes/state.json`
- 原 `agent-lanes.md`
- 原 `shared.md`

如果某个文件不存在，不创建空备份副本，但在 migration report 中记录 `missing_before_migration`。

### 10.3 Migration report

`--yes` 成功后写入：

```text
.starwork/agent-lanes/migration-report-<timestamp>.json
```

内容至少包含：

- source version / target version。
- legacy classes。
- applied actions。
- backup path。
- skipped actions。
- conflicts resolved / unresolved。
- command timestamp。

## 11. Doctor 提示

### 11.1 JSON 字段

`starwork doctor --target <path> --json` 应新增或扩展：

```json
{
  "multiagent": {
    "status": "warn",
    "compatibility": {
      "status": "migration_required_for_write",
      "structure_version": null,
      "target_structure_version": 1,
      "legacy_classes": ["markdown_only"],
      "required_for_write": true,
      "dry_run_command": "starwork multiagent upgrade --target <path> --dry-run"
    }
  }
}
```

### 11.2 人类输出

人类输出必须说明：

- 已检测到旧版 MultiAgent 协作记录。
- 目前可以读取已有 AI 岗位。
- 写入新岗位、绑定会话或记录交接前，建议先预览迁移。
- 预览不会写入文件。

不得只输出内部字段，例如：

```text
schema mismatch
legacy_readable
```

## 12. Skill 行为

`starworkMultiagent` 遇到 legacy / migration 状态时：

1. 可以先读取并汇总已有 AI 岗位。
2. 不得直接执行 `multiagent init`、`add`、`bind`、`share` 或 `request record` 这类写入命令。
3. 必须用用户语言解释：

```text
我找到了这个项目里已有的多 AI 协作记录，但它看起来是旧版结构。

为了避免新旧记录分裂，我会先给你看一次升级预览。预览不会写入文件；确认后才会整理结构。
```

4. 调用或建议：

```bash
starwork multiagent upgrade --target <path> --dry-run
```

5. 用户确认后才可执行 `--yes`。
6. 迁移成功并重新 doctor 通过后，才继续创建岗位、绑定会话或发送交接消息。

如果是 `blocked_conflict` 或 `unknown_partial`：

- Skill 不得承诺自动修复。
- 应列出冲突来源，建议用户或 product-planning 人工判断。
- 可把冲突摘要写入 lane workspace，但不得改正式协作文件。

## 13. 失败与降级

### 13.1 JSON 损坏

如果 `.starwork/agent-lanes/state.json` 不能解析：

- `status` 不得崩溃。
- 如果 Markdown 可读，仍显示 Markdown 里的 lane。
- `doctor` 返回 `unknown_partial`。
- `upgrade --yes` 必须失败，提示先备份并人工处理损坏 state。

### 13.2 Markdown 表格不可解析

如果 `agent-lanes.md` 或 `shared.md` 有手写内容但表格不可解析：

- 不得覆盖整个 Markdown 文件。
- 可从 state 输出机器事实。
- `doctor` 给 warn。
- dry-run 只能建议人工修复 Markdown 表格或生成 sidecar 草稿，不得直接重写。

### 13.3 路径冲突

如果中文和英文协作路径同时存在且都有内容：

- 优先根据 `.starwork/workspace.json.language` 判断当前语言。
- 如果非当前语言路径也有 lane / request，返回 `blocked_conflict`。
- 不自动移动或合并两套路径。

### 13.4 Pending merge

如果 `doctor --host` 或 adapter state 显示 AI 入口文档 `pending_merge`：

- MultiAgent 迁移可以做只读识别和 dry-run。
- 写入迁移前必须提示：入口文档仍待整合。
- 不得借 MultiAgent 迁移写入 `AGENTS.md` / `CLAUDE.md` 或宿主 rules。

## 14. 验收标准

### 14.1 Fixture 覆盖

development lane 至少新增这些 fixture 或等价测试场景：

| fixture | 内容 | 期望 |
| --- | --- | --- |
| `multiagent-current-v1` | state version 1 + agent-lanes.md + shared.md | doctor 为 current，无迁移 warning |
| `multiagent-state-unversioned` | state 有 lanes / requests 但无 version | status 读出 lane / binding，doctor 提示 migration_available |
| `multiagent-markdown-only` | 只有 agent-lanes.md / shared.md | status 读出 lane，dry-run 计划创建 state.json |
| `multiagent-state-only` | 只有 state.json | status 读出 binding，dry-run 计划补 Markdown 注册 |
| `multiagent-conflicting-lane` | state 和 Markdown 同 lane session 冲突 | doctor 为 blocked_conflict，--yes 失败 |
| `multiagent-malformed-state` | state.json 损坏，Markdown 可读 | status 不崩溃，doctor 为 unknown_partial |

### 14.2 Status 兼容读取

对旧结构执行：

```bash
starwork multiagent status --target <fixture> --json
```

必须满足：

- 返回已有 lane，而不是空团队。
- 返回已有 `current_session` / host binding。
- 返回 `multiagent.compatibility.status`。
- 对 `migration_required_for_write` 给出 dry-run command。

### 14.3 Doctor 识别

对旧结构执行：

```bash
starwork doctor --target <fixture> --json
```

必须满足：

- JSON 中有 `multiagent.compatibility`。
- 人类输出不只暴露内部状态词。
- 普通 doctor 对 legacy 可读结构返回 warn 但不崩溃。
- `--strict` 下如果 `required_for_write` 为 true，应返回非零或 `strict_ok=false`。

### 14.4 Dry-run 不写入

对每个可迁移 fixture 执行：

```bash
starwork multiagent upgrade --target <fixture> --dry-run
starwork multiagent upgrade --target <fixture> --json --dry-run
```

必须满足：

- 文件树无变化。
- 输出包含 `will_create`、`will_update`、`will_preserve`、`will_not_touch`。
- JSON 包含 `safe_to_apply`。
- 冲突 fixture 的 `safe_to_apply=false`。

### 14.5 Confirmed migration 写入安全

对安全 fixture 执行：

```bash
starwork multiagent upgrade --target <fixture> --yes
```

必须满足：

- 修改前文件进入 `.starwork/backups/multiagent/<timestamp>/`。
- state 补齐 `version: 1` 或创建 state。
- 缺失 worklog / workspace 可创建，但非空 worklog 不被覆盖。
- `shared.md` 中原 request id、status 和手写说明不丢失。
- 写入 `.starwork/agent-lanes/migration-report-<timestamp>.json`。
- 再次执行 `doctor` 为 `current` 或无 migration warning。

### 14.6 写入阻断

当 compatibility 为 `migration_required_for_write` 时，以下命令必须阻断并提示先 dry-run 迁移：

```bash
starwork multiagent add <lane> --target <fixture> --yes
starwork multiagent bind <lane> --session codex:<id> --target <fixture> --yes
starwork multiagent share --target <fixture> --yes
starwork multiagent request record --target <fixture> --yes
```

只读命令不阻断：

```bash
starwork multiagent status --target <fixture> --json
starwork doctor --target <fixture> --json
```

### 14.7 Skill 行为验收

扫描 `product/skills/starworkMultiagent/SKILL.md` 或增加文本测试，必须覆盖：

- 遇到旧结构时先解释升级风险。
- 先给 `upgrade --dry-run` 预览。
- 确认前不写入。
- 迁移成功后才继续创建岗位 / 绑定 / 交接。
- 不把旧结构误说成“没有 AI 岗位”。

### 14.8 v0.8 / v0.9 边界回归

v0.10 完成后仍必须通过 v0.8 / v0.9 禁止项扫描：

```bash
rg -n "starwork multiagent instruct|starwork multiagent launch|multiagent message instruct|multiagent message launch|multiagent read --host codex|multiagent status --host codex|--session-name|--pin" product/skills/starworkMultiagent/SKILL.md
```

不得有命中。

### 14.9 建议验证命令

开发完成前至少运行：

```bash
node --check product/cli/src/cli.js
node --check product/cli/test/init.test.js
git -C product diff --check
node --test product/cli/test/init.test.js --test-name-pattern "multiagent|upgrade|migration|compatibility|doctor"
npm test
```

## 15. 禁止事项

- 不得把旧结构当空结构重新初始化。
- 不得在 dry-run 中写任何文件。
