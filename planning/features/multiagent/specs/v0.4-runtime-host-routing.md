# MultiAgent v0.4 运行时宿主能力路由 SPEC

## 1. 状态

- 日期：2026-06-03
- 状态：ready-for-development
- 所属功能：MultiAgent / Host Adapter / Skills
- 关联问题：
  - `product/planning/issues/ISSUE-008.md`
  - `product/planning/issues/ISSUE-011.md`
- 影响模块：`starwork multiagent` CLI、Host Adapter profile、`starworkMultiagent` Skill、`starwork adapt`、`starwork doctor --host`

## 2. 背景

此前讨论中出现过一个偏差：试图让 `adapt` 或 Skill 承担过多宿主兼容判断。

最新产品判断是：

```text
Skill：场景路由 + CLI 调用方式
CLI：运行时宿主能力判断 + 执行 / 降级
adapt：准备宿主环境 + 写入 adapter state
adapter profile：声明宿主能力基线
```

举例：

用户说“让开发 Agent 开始开发”时，`starworkMultiagent` Skill 不应该自己判断 Codex / Cursor / Claude Code / Trae 各自支不支持后台发消息。Skill 只应该调用：

```bash
starwork multiagent instruct development --from product-planning --message "<text>" --target <path> --json
```

然后由 CLI 判断：

- 目标 lane 绑定的是 Codex，且当前环境可调用 Codex 标准投递能力：发送并返回 `delivered`。
- 目标 lane 绑定的是 Cursor，但没有标准后台投递能力：返回 `manual_handoff_required`。
- 目标 lane 绑定的是 Claude Code / Trae，不能后台发送：返回 `manual_handoff_required`。
- 目标 lane 未绑定：返回 `unbound`。
- 宿主尚未适配：返回 `needs_adapt`。
- 宿主明确不支持：返回 `unsupported`。

## 3. 一句话目标

把 StarWork MultiAgent 的宿主差异判断收敛到 CLI 运行时，不让 Skill 维护宿主兼容性百科，也不让 `adapt` 承担业务命令的运行时判断。

## 4. 分层边界

| 层级 | 职责 | 不负责 |
| --- | --- | --- |
| Skill | 判断用户意图；选择 CLI 子命令；优先 dry-run；读取 JSON；用人话解释结果 | 不维护宿主能力矩阵；不判断某工具底层是否支持跨会话发送 |
| CLI | 读取 lane/session/adapters/profile；判断当前命令在目标宿主是否可执行；执行标准能力或降级；返回结构化状态 | 不静默安装全局工具；不伪装不支持能力 |
| adapt | 生成宿主规则入口；创建宿主 Skill 挂载目录；写 `.starwork/adapters.json`；让 doctor 可检查 | 不判断某次 `instruct` 是否应该发送；不替业务 Skill 做场景路由 |
| adapter profile | 声明宿主能力基线、Skill 目录、规则入口、安全降级 | 不代表当前机器一定可执行；最终以 CLI 运行时 probe 为准 |
| doctor --host | 检查 adapter state、入口、Skill 目录、危险能力声明 | 不执行业务命令 |

## 5. 运行时能力判断模型

CLI 每次执行依赖宿主能力的命令时，都必须走同一个判断链：

```text
用户命令
  ↓
解析目标 lane / session
  ↓
解析 host：codex / cursor / claude-code / trae / unknown
  ↓
读取 adapter profile 能力基线
  ↓
读取 .starwork/adapters.json 当前适配状态
  ↓
必要时进行轻量运行时 probe
  ↓
执行标准能力 or 返回降级状态
```

### 5.1 Host 来源

优先顺序：

1. 目标 lane 的 `current_session` 前缀，例如 `codex:<id>`、`cursor:<id>`。
2. `.starwork/agent-lanes/state.json` 中该 lane 的 host metadata。
3. `.starwork/adapters.json` 中已启用 host。
4. 当前运行环境的明确环境变量或 CLI 参数。

如果无法确定 host，返回：

```json
{
  "status": "needs_adapt",
  "reason": "Target lane host is unknown. Run starwork adapt <host> or bind the lane to a host session."
}
```

### 5.2 Profile 与运行时 probe 的关系

adapter profile 只表示基线能力，不表示当前机器一定能用。

例如：

- profile 写 `sessions.send_message: supported`，但当前环境没有可调用的标准 API，则本次命令必须降级。
- profile 写 `manual` / `unsupported`，CLI 不得尝试自动发送。
- profile 写 `partial`，CLI 必须 probe；probe 失败则降级。

### 5.3 同一宿主的会话级能力差异

CLI 不能只根据宿主名称判断能力。

真实测试中，Codex 不同会话可能暴露不同的工具清单：有的会话能发现 `send_message_to_thread`、`read_thread`、`create_thread` 等线程管理工具；有的会话只能发现子智能体工具，无法调用 Codex 标准线程投递能力。

这类情况必须视为运行时能力差异，而不是用户操作错误。

规则：

- `host=codex` 只表示目标会话属于 Codex，不表示当前发送方环境一定能自动投递。
- CLI 必须在每次 `instruct` 时 probe 当前可用的标准投递能力。
- probe 发现 `send_message_to_thread` 或明确等价稳定 API 可用时，才允许返回 `delivered`。
- probe 发现只有子智能体工具、低层 turn API 或无法确认标准投递能力时，必须返回 `manual_handoff_required` 或 `unsupported`。
- 禁止用子智能体工具、`thread/resume + turn/start` 或其他低层能力冒充既有会话标准投递。

## 6. `multiagent instruct` 运行时规范

### 6.1 Skill 调用

`starworkMultiagent` Skill 只负责路由和调用：

```bash
starwork multiagent instruct <to-lane> \
  --from <from-lane> \
  --message "<text>" \
  --target <path> \
  --json
```

Skill 不写：

- Codex 如何发送。
- Cursor 是否能后台发送。
- Claude Code transcript 在哪里。
- Trae 数据库是否可读。

Skill 只解释 CLI 返回状态。

### 6.2 CLI 返回状态

`multiagent instruct --json` 必须稳定返回：

```json
{
  "schema": "starwork.agent_lanes.instruct.v0.4",
  "request": {},
  "host": {
    "id": "codex",
    "session": "codex:..."
  },
  "host_delivery": {
    "status": "delivered",
    "mode": "host_standard_api",
    "message_path": "_系统/协作/shared.md",
    "manual_handoff": null,
    "warning": null
  }
}
```

允许状态：

| status | 含义 | Skill 应如何解释 |
| --- | --- | --- |
| `delivered` | 已通过宿主标准能力投递 | “消息已投递，不代表目标任务完成。” |
| `manual_handoff_required` | 宿主不支持自动后台投递，已生成手动交付消息 | “需要你手动复制给目标会话。” |
| `needs_adapt` | 目标宿主未适配或状态不足 | “需要先运行适配流程。” |
| `unbound` | 目标 lane 没有绑定宿主会话 | “需要先绑定或创建目标 Agent 会话。” |
| `unsupported` | 宿主明确不支持该能力，且没有自动降级动作 | “这个工具暂不支持该能力。” |
| `failed` | 标准能力尝试失败 | “发送失败，保留项目记录，可手动交付或重试。” |

### 6.3 Codex 发送要求

Codex 自动发送必须使用 Codex 标准跨线程投递能力，例如：

```text
send_message_to_thread
```

或 development lane 证明的明确等价稳定 API。

禁止：

```text
thread/resume + turn/start
```

原因：这不是 StarWork `instruct` 的产品语义，而是恢复目标会话后模拟新 turn；它会造成 UI 形态不一致，也可能引入 interrupted 风险。

### 6.4 Codex 可行性门槛

development lane 必须先验证 CLI 进程能否调用 Codex 标准投递能力。

如果能做到：

- `codex:<thread-id>` 目标返回 `delivered`。
- `host_delivery.mode` 为 `host_standard_api`。
- 不产生 `thread/resume` + `turn/start` 调用链。

如果 CLI 进程暂时无法调用 Codex 标准投递能力：

- 不允许退回 `thread/resume` + `turn/start`。
- 返回 `manual_handoff_required` 或 `unsupported`。
- JSON 中明确说明当前 CLI 环境无法访问 Codex 标准投递能力。
- 如果当前会话只暴露子智能体发送能力，也必须视为标准投递能力不可用；不得新建或复用子智能体来替代向既有 Codex thread 发送消息。

### 6.5 非 Codex 宿主

Cursor / Claude Code / Trae 的规则由 CLI 判断：

- profile 或 probe 表明有标准后台投递 API：可尝试自动发送。
- 没有标准后台投递 API：返回 `manual_handoff_required`。
- 只能 resume / continue：不能包装成 `instruct` 自动发送。

`resume` / `continue` 只属于：

```bash
starwork multiagent continue <lane>
```

不属于自动派活。

## 7. `adapt` 的正确定位

`adapt` 是准备工作，不是运行时裁判。

`starwork adapt <host>` 可以做：

- 写宿主规则入口。
- 创建宿主 Skill 挂载目录。
- 写 `.starwork/adapters.json`。
- 写 `.starwork/workspace.json.adapters` 摘要。
- 输出该宿主能力 profile。
- 让 `doctor --host` 能检查规则入口、Skill 目录、危险声明。

`adapt` 不做：

- 不判断某次 `multiagent instruct` 应该怎么发。
- 不替 `starworkMultiagent` Skill 决定业务流程。
- 不静默安装全局系统级 Skill。
- 不静默安装宿主 CLI。
- 不把 profile 中的 `partial` 描述成自动完成。

## 8. Skill / CLI / adapt 的配合流程

### 8.1 正常发送

```text
用户：让开发 Agent 开始开发
  ↓
starworkMultiagent Skill：识别为 instruct
  ↓
CLI：starwork multiagent instruct development --json
  ↓
CLI：判断目标 lane = codex:<id>
  ↓
CLI：检查 Codex 标准投递能力可用
  ↓
CLI：发送，返回 delivered
  ↓
Skill：告诉用户“已投递，等待对方回报”
```

### 8.2 Cursor 不支持自动发送

```text
用户：让 Cursor 里的开发 Agent 开始开发
  ↓
Skill：调用同一个 instruct 命令
  ↓
CLI：判断目标 lane = cursor:<id>
  ↓
CLI：profile/probe 显示无标准后台投递 API
  ↓
CLI：返回 manual_handoff_required + handoff message
  ↓
Skill：告诉用户“这个工具不能自动发送，请手动复制这段消息”
```

### 8.3 未适配

```text
用户：让开发 Agent 开始开发
  ↓
CLI：目标 session host unknown 或 adapter state 缺失
  ↓
CLI：返回 needs_adapt
  ↓
Skill：引导用户运行 starwork adapt <host> --dry-run
```

## 9. 开发任务

### Phase 1：统一 Host Capability Resolver

新增或整理 CLI 内部能力解析函数：

```text
resolveHostRuntimeCapability({ workspaceRoot, lane, command })
```

输出：

```json
{
  "host": "codex",
  "session": "codex:...",
  "profile_level": "supported",
  "adapter_enabled": true,
  "runtime_available": true,
  "action": "auto_send"
}
```

验收：

- `codex:<id>`、`cursor:<id>`、`claude-code:<id>`、`trae:<id>` 都能得到稳定判断。
- adapter state 缺失时返回 `needs_adapt`。
- profile 为 `manual` / `unsupported` 时不尝试自动能力。

### Phase 2：重写 `multiagent instruct` 路由

要求：

- `instruct` 不再直接调用 Codex app-server 低层发送链路。
- 先调用 Host Capability Resolver。
- 自动发送只走宿主标准投递能力。
- 不支持时生成 handoff message。

验收：

- Cursor / Claude Code / Trae 在无标准后台投递 API 时返回 `manual_handoff_required`。
- Codex 若标准投递能力可用，返回 `delivered`。
- Codex 若标准投递能力不可用，返回 `manual_handoff_required` 或 `unsupported`，不得 fallback 到 `thread/resume` + `turn/start`。

### Phase 3：校准 `starworkMultiagent` Skill

要求：

- Skill 删除宿主能力百科。
- Skill 保留 CLI 调用方式。
- Skill 按 CLI 状态解释：
  - `delivered`
  - `manual_handoff_required`
  - `needs_adapt`
  - `unbound`
  - `unsupported`
  - `failed`

验收：

- Skill 不出现 Codex / Cursor / Claude Code / Trae 的完整能力矩阵。
- Skill 不描述宿主私有路径、数据库、transcript 细节。
- Skill 不自己判断某宿主是否支持跨会话发送。

### Phase 4：校准 `adapt`

要求：

- 保持 `adapt` 是准备工作。
- `adapt --capabilities` 输出 profile。
- `adapt <host>` 写入口、目录和 state。
- 若未来安装项目内 host Skill，应作为适配准备计划，而不是业务运行时判断。

验收：

- `adapt` 不承诺某次 `instruct` 一定能自动发送。
- `doctor --host` 能检查 adapter state 与 Skill 目录。
- `multiagent instruct` 的运行时判断不依赖 Skill 文案。

### Phase 5：测试

至少新增 / 更新测试：

1. `instruct` 对 `cursor:<id>` 返回 `manual_handoff_required`。
2. `instruct` 对 `claude-code:<id>` 返回 `manual_handoff_required`，除非 profile/probe 明确支持标准投递。
3. `instruct` 对 `trae:<id>` 返回 `manual_handoff_required`。
4. `instruct` 对未绑定 lane 返回 `unbound`。
5. adapter state 缺失时返回 `needs_adapt`。
6. 默认 `instruct` 不产生 `thread/resume` + `turn/start` 调用链。
7. Skill 文案不包含宿主能力矩阵。
8. Codex profile 标记支持，但运行时 probe 找不到标准投递能力时，返回 `manual_handoff_required` 或 `unsupported`。
9. Codex 运行时只发现子智能体发送能力时，不返回 `delivered`，也不创建子智能体替代投递。

## 10. 验收标准

本 SPEC 完成的标准：

- 用户可以用同一条 `starwork multiagent instruct` 命令面对不同宿主。
- CLI 根据目标宿主返回正确状态。
- Skill 不需要知道宿主能力差异。
- `adapt` 仍是准备工作，不承担业务命令运行时判断。
- Codex 自动发送只使用标准投递能力；做不到就明确降级。
- Cursor / Claude Code / Trae 不支持自动发送时，用户得到可复制的 handoff message。

## 11. 非目标

本版本不做：

- 自动安装宿主 CLI。
- 静默安装全局系统级 Skill。
- 将 Cursor / Claude Code / Trae 强行做成 Codex 同等自动编排。
- 写入宿主私有数据库或 transcript。
- 使用非公开低层 turn API 伪装标准跨会话发送。
