## 2. product-lead 决策

product-lead 接受 product-multiagent 的核心判断：`ISSUE-027` 不是文案问题，而是 workflow runtime 缺少一等 run state、Step Router 和 self-delivery guard 的产品模型问题。v0.14 作为 P0 修复进入 development。

对草案 open questions 的拍板如下：

1. Confirmed Workflow Definition 第一版仍允许保存在 lane workspace 或 product planning 中；v0.14 不新增 `.starwork/workflows/definitions/`。CLI run state 必须记录 `workflow_definition_path`，runtime state 写入 `.starwork/workflows/runs/<run-id>.json`。
2. Fixture 使用具体 lane id，不使用模糊 `product`。建议测试 fixture 使用 `testing -> product-lead -> development -> product-lead`；若在临时测试工作台中无这些真实 lane，可创建等价 fixture lane，但 JSON 与文案必须展示明确 lane id。
3. `blocked_self_delivery` 和 `manual_confirmation_required` 必须写入 workflow event log。v0.14 最小范围不要求写 `multiagent request record`；如果 implementation 选择同步写 request record，只能写非 delivered 状态，绝不能写 `delivered_via_codex_thread_tool`。
4. v0.14 需要同步更新 next `starworkMultiagent` workflow runner reference、A 测指南和 MultiAgent 用户文档，明确 workflow next 是“由 AI 辅助推进的内测 workflow”，不是后台自动化或无监督流程引擎。
5. 完整 `starwork skills install --agent codex --global` 不是 v0.14 前置；本轮继续沿用 `@next` CLI + `skills-next --full-depth` 的 next 测试安装口径。

## 3. 背景

用户确认 `ISSUE-027` 是严重 P0：MultiAgent workflow 缺少专门管理机制，并出现测试 Agent 把 workflow 消息发给自己的问题。

典型异常链路：

```text
用户 -> testing agent：提交问题
期望：testing agent 记录 / 补全问题 -> product agent 做设计 -> development 实现 -> product review
异常：testing agent 把 workflow 消息发给 testing agent 自己
```

v0.11 已经接受 Workflow Builder / Runner MVP，解决了“如何设计 workflow、确认 definition、生成 compact packet 并投递”的第一版问题。v0.12 已经接受 workflow / delegation 投递保证，要求跨 lane 步骤必须真实投递，不能用当前回复说明替代。v0.13 已经接受 `starworkMultiagent` Skill 瘦身 / references 分层。

但 `ISSUE-027` 暴露出新的根因：Runner 仍缺少一等 workflow run state 和 step router。当前 self-delivery guard 只在“目标 lane 已经算出来之后”比较目标 session 与当前 session；它不能保证目标 lane 本身是从 workflow definition + run state 推导出来的，而不是当前 Agent 根据上下文、当前会话或最近活跃 lane 猜出来的。

因此 v0.14 不是 v0.11 的文案小修，而是 workflow runtime / run state 的最小补洞。

## 4. 一句话目标

让 workflow Runner 在每次推进前都有可检查的一等 run state，并由 Step Router 只根据 Workflow Definition + Workflow Run State 计算下一步目标 lane；如果目标 lane 或目标 session 指向当前 Agent 自己，默认结构化阻断，绝不伪装成跨 Agent delivered。

## 5. 非目标

v0.14 不做：

- 不做后台 daemon。
- 不做文件 watcher。
- 不做无监督自动循环。
- 不做复杂 DAG 调度器。
- 不做跨项目 workflow 队列。
- 不推翻 v0.11 compact + reference packet。
- 不推翻 v0.12 投递保证。
- 不新增独立 `starworkWorkflow` Skill。
- 不把 workflow next 开放成普通 latest 能力。
- 不承诺后台自动化或无监督自动流转。

## 6. 与 v0.11 / v0.12 / v0.13 的关系

| 版本 | 已解决 | v0.14 如何衔接 |
| --- | --- | --- |
| v0.11 | Builder / Runner MVP、confirmed definition、compact + reference packet | 保留 compact packet 和 Runner 入口，补 run state、step router 和 self-delivery guard |
| v0.12 | 必须真实投递、工具发现、未投递不得记 delivered | 保留投递保证，新增阻断状态不能写成 delivered |
| v0.13 | 短主 Skill + references 分层 | v0.14 主要落在 next `workflow-runner.md` / 新 workflow state reference / CLI 状态命令，不把 stable 主流程变长 |

v0.14 修正的是 runtime 缺口，而不是否定 v0.11。v0.11 的 compact + reference packet 仍是消息预算策略；v0.12 的真实投递仍是 delivery 事实边界；v0.14 增加的是“在生成 packet 和投递前，先由 run state 确定当前节点和下一目标”。

## 7. 核心产品判断

### 6.1 workflow 必须有一等管理对象

v0.14 后，Runner 不能只靠当前 prompt、当前 Agent 身份或 compact packet 推进流程。至少需要这些对象：

- Workflow Definition
- Workflow Run Instance
- current node / current step
- current actor lane
- next target lane
- run status
- event log
- blocked reason

### 6.2 Step Router 是唯一下一步来源

下一步目标 lane 只能来自：

```text
Workflow Definition + Workflow Run State + 当前节点 completion event
```

不得从以下信号推断：

- 当前用户正在和哪个 Agent 说话。
- 当前会话绑定哪个 lane。
- 最近哪个 Agent 活跃。
- compact packet 里缺失时由 Agent 自己猜。
- lane 名称与用户语义相似。

### 6.3 testing agent 是入口 actor，不是默认下一步目标

用户向 testing agent 提交问题，只说明：

```text
entry actor = testing
```

不说明：

```text
next target lane = testing
```

在 `testing_intake -> product_design -> development_implementation -> product_review` fixture 中，testing agent 完成 intake 后，下一步目标必须是 product lane。

### 6.4 Self-Delivery Guard 分两层

Runner 必须同时做：

1. lane guard：`from_lane == to_lane` 默认阻断。
2. session guard：`current_session_id == target_lane.current_session` 默认阻断。

任一命中，都不得调用宿主发送工具，不得记录 `delivered_via_codex_thread_tool`。

### 6.5 self step 必须显式建模

如果 workflow definition 明确允许当前节点由同一个 lane 自己处理，应显式标记：

```yaml
allow_self_step: true
```

这类步骤只能记录为：

```text
self_step_recorded
```

或等价状态。不得说“跨 Agent 消息已送达”，不得走 `send_message_to_thread` 模拟给自己发消息。

## 8. Workflow Definition 最小补充

v0.11 definition 可以继续存在于 confirmed definition 文件中，但 v0.14 要求节点至少能表达 route 关系和 self step 策略。

建议最小结构：

```yaml
workflow_id: issue_to_delivery
version: 0.2
status: confirmed
owner_lane: product-lead
entry:
  node: testing_intake
  actor_lane: testing
nodes:
  testing_intake:
    actor_lane: testing
    inputs:
      - user_report
    outputs:
      - issue_path
      - repro_notes
    return:
      - issue_path
      - severity
      - recommendation
    transitions:
      ready_for_design:
        target_node: product_design
        target_lane: product
    allow_self_step: false
  product_design:
    actor_lane: product
    inputs:
      - issue_path
      - repro_notes
    outputs:
      - spec_path
      - acceptance_criteria
    return:
      - spec_path
      - acceptance_criteria
      - decision_needed
    transitions:
      accepted:
        target_node: development_implementation
        target_lane: development
      needs_revision:
        target_node: product_design
        target_lane: product
        allow_self_step: true
  development_implementation:
    actor_lane: development
    inputs:
      - spec_path
      - acceptance_criteria
    outputs:
      - changed_files
      - verification
    return:
      - changed_files
      - verification
      - risks
    transitions:
      done:
        target_node: product_review
        target_lane: product
  product_review:
    actor_lane: product
    transitions:
      passed:
        target_node: stop
      failed:
        target_node: development_implementation
        target_lane: development
```

要求：

- 每个非终止 transition 必须有 `target_node`。
- 每个跨 lane transition 必须有 `target_lane`。
- `target_lane` 缺失时不能由 Agent 根据当前会话猜测，必须进入 `blocked_missing_route`。
- `allow_self_step` 默认 false。

## 10. 状态机

建议状态：

| 状态 | 含义 | 是否可投递 |
| --- | --- | --- |
| `planned` | run 已创建但未准备投递 | 否 |
| `ready` | 当前 step 和 next target 已由 Step Router 计算完成 | 可进入 preflight |
| `delivering` | 已通过 preflight，正在调用宿主发送工具 | 过程中 |
| `delivered` | 宿主工具真实投递成功，request 已记录 | 已完成当前投递 |
| `blocked_self_delivery` | lane guard 或 session guard 命中 | 否 |
| `manual_confirmation_required` | route 疑似自投递或用户需确认本地 self step | 否 |
| `blocked_missing_route` | definition / run state 无法确定下一目标 | 否 |
| `manual_handoff_required` | 宿主工具不可用或投递失败，需要人工转交 | 否 |
| `self_step_recorded` | definition 明确允许 self step，已记录为本地步骤 | 不跨 Agent |
| `completed` | workflow 达到 stop / passed 等终态 | 否 |
| `failed` | workflow 因错误或用户决定终止 | 否 |

关键边界：

- `blocked_self_delivery`、`manual_confirmation_required`、`self_step_recorded` 都不得写成 `delivered`。
- `delivering` 只有在 preflight 全部通过后才能进入。
- `delivered` 只有在宿主工具成功返回，且 request record 成功后才能进入。

## 11. Step Router 规则

Step Router 输入：

- Workflow Definition。
- Workflow Run State。
- 当前 completion event 或用户启动事件。
- 当前会话 ID。
- StarWork lane binding 状态。

Step Router 输出：

- `from_lane`
- `to_lane`
- `target_node`
- `target_session`
- `route_status`
- `blocked_reason`
- `packet_seed`

算法要求：

1. 读取 run state 的 `current_node` 和 `current_actor_lane`。
2. 读取当前节点在 definition 中的 `transitions`。
3. 根据 completion event 的 outcome 选择 transition。
4. 从 transition 读取 `target_node` 和 `target_lane`。
5. 如果 target 是 `stop`，更新 run 为 `completed`，不投递。
6. 如果 `target_lane` 缺失，进入 `blocked_missing_route`。
7. 读取 `target_lane.current_session`。
8. 执行 lane guard：`from_lane == to_lane` 时默认阻断。
9. 执行 session guard：`current_session_id == target_session` 时默认阻断。
10. 如果 definition / transition 明确 `allow_self_step: true`，不发送消息，记录 `self_step_recorded`。
11. 只有 route_status 为 `ready` 时，Runner 才能生成 compact + reference packet 并进入投递 preflight。

禁止：

- 不得从当前会话所属 lane 推导 `to_lane`。
- 不得因为用户正在跟 testing agent 说话，就把下一步发给 testing。
- 不得在 route 缺失时让 Agent “按理解选择一个 lane”。

| 字段 | 示例 |
| --- | --- |

| workflow id | `issue_to_delivery` |
| current step | `testing_intake` |

## 13. Self-Delivery Guard

### 12.1 lane guard

条件：

```text
from_lane == to_lane
```

默认结果：

```text
blocked_self_delivery
```

用户话术：

```text
我发现下一步目标会指向当前 Agent 自己，这可能是 workflow 配置或路由错误，已停止自动投递。
```

允许例外：

- definition 当前 transition 或 node 明确 `allow_self_step: true`。
- 用户确认这是本地 self step，不是跨 Agent handoff。

例外状态：

```text
self_step_recorded
```

### 12.2 session guard

条件：

```text
current_session_id == target_lane.current_session
```

默认结果：

```text
blocked_self_delivery
```

如果 lane 不同但 session 相同，说明 lane binding 可能错误或多个 lane 绑定到同一会话。Runner 必须阻断，并提示用户先修正 binding 或确认本地执行。

### 12.3 阻断时禁止动作

命中任一 guard 时：

- 不调用 `send_message_to_thread`。
- 不调用 Claude Code 对应发送工具。
- 不执行 `multiagent request record --host-delivery delivered_via_codex_thread_tool`。
- 不说“已投递到目标会话”。
- 必须写入 run event，记录阻断原因。

## 14. CLI / Skill 分工

### 13.1 产品判断

v0.14 应新增最小 `starwork multiagent workflow ...` CLI 子命令。

理由：

1. `multiagent request record` 只能记录一次请求投递事实，不能表达 workflow run 的 current node、next target、blocked reason 和 event log。
2. lane workspace 草案适合承载 definition draft，不适合做一等 runtime state。
3. 本次 P0 根因就是缺少可靠 run state 和 Step Router；如果继续只靠 Skill 文案和 workspace 文件，Agent 仍可能凭上下文猜路由。

### 13.2 最小 CLI 命令范围

建议 Phase 1 只新增四类能力：

```bash
starwork multiagent workflow start --definition <path> --entry-node <node> --actor-lane <lane> --target <path> --json --yes
starwork multiagent workflow status --run <run-id> --target <path> --json
starwork multiagent workflow route --run <run-id> --event <event-json-or-key> --target <path> --json
starwork multiagent workflow event record --run <run-id> --type <type> --status <status> --target <path> --json --yes
```

要求：

- `start` 创建 run state。
- `status` 只读展示 run state。
- `route` 只根据 definition + run state 计算下一步，不投递。
- `event record` 记录 delivered / blocked / self_step / completed 等事件。

### 13.3 CLI 负责

CLI 负责项目事实源：

- 持久化 run state。
- 读取 workflow definition。
- 基于 definition + run state 计算 route。
- 记录 event log。
- 输出机器可读 route preflight。
- 拒绝在缺失 target lane / target session / self-delivery guard 命中时返回可投递状态。

### 13.4 Skill 负责

Skill 负责宿主编排：

- 识别用户 workflow intent。
- 读取 reference。
- 调用 CLI `workflow status` / `workflow route`。
- 向用户展示投递前预览。
- 在 route_status 为 ready 时调用宿主标准线程工具。
- 投递成功后调用 `multiagent request record` 和 `workflow event record`。
- 阻断时输出用户话术，不调用发送工具。

### 13.5 与现有 request record 的关系

`workflow event record` 和 `multiagent request record` 不是互相替代：

- `workflow event record` 是 workflow run 内部状态和 event log。
- `multiagent request record` 是 StarWork cross-lane request / delivery 账本。

真实跨 lane 投递成功时，两者都应记录：

1. 宿主发送工具成功。
2. `multiagent request record --host-delivery delivered_via_codex_thread_tool ...`
3. `multiagent workflow event record --type step_delivered --status delivered ...`

阻断时只记录 workflow event，不记录 delivered request。

## 15. 存储位置建议

建议将 runtime state 写入 `.starwork`，因为它是项目内机器可读运行状态，不是 lane 草稿。

最小结构：

```text
.starwork/workflows/
  runs/
    <run-id>.json
  events/
    <run-id>.jsonl
```

也可以第一版只用：

```text
.starwork/workflows/runs/<run-id>.json
```

其中 `events` 数组内嵌在 run state 中。

Definition 的 confirmed 文件第一版仍可留在 lane workspace 或 product planning 中，但 run state 必须引用 `workflow_definition_path`。

## 16. Packet 与消息格式

v0.14 不改变 v0.11 compact + reference packet 预算，但 packet 必须新增或确认包含 run state 路由字段：

```yaml
packet_mode: compact
wf: issue_to_delivery
wf_i: WF-20260622-issue-to-delivery-001
wf_def: _系统/协作/lanes/product-lead/workspace/workflows/issue-to-delivery.confirmed.md
wf_v: "0.2"
node: product_design
from_lane: testing
to_lane: product
route_source: definition+run_state
route_event: ready_for_design
inputs:
  - product/planning/issues/ISSUE-027.md
do:
  - Produce product design SPEC
return:
  - spec_path
  - acceptance_criteria
gate:
  type: product_review_gate
```

如果 packet 中 `to_lane` 与 run state 不一致，Runner 必须以 run state 为准，并记录 `blocked_packet_route_mismatch` 或要求重建 packet。

## 17. 用户话术

### 16.1 正常投递前

```text
我准备推进这个 workflow 的下一步。当前 step 是 testing_intake，来源 lane 是 testing；根据 workflow definition 和 run state，下一步目标是 product_design，由 product lane 执行，目标会话是 codex:<id>。
```

### 16.2 自投递阻断

必须包含：

```text
我发现下一步目标会指向当前 Agent 自己，这可能是 workflow 配置或路由错误，已停止自动投递。
```

可以补充：

```text
我没有调用发送工具，也没有把这次记录为 delivered。请确认 workflow definition 的下一步目标 lane，或明确这是允许的 self step。
```

### 16.3 允许 self step

```text
这个节点在 workflow definition 中标记为允许 self step。我会把它记录为本地步骤 `self_step_recorded`，不会把它说成跨 Agent 消息已送达。
```

### 16.4 目标缺失

```text
我无法从 workflow definition 和 run state 确定下一步目标 lane。为了避免误投递，我已停止自动推进，并记录为 blocked_missing_route。
```

- `route_event = ready_for_design`
- `next_target_lane = product`
- 不能返回 testing 作为下一步目标。

### 18.3 Self-delivery 阻断 fixture

给定：

```text
from_lane == to_lane
```

或：

```text
current_session_id == target_lane.current_session
```

Runner 必须：

- 返回 `blocked_self_delivery` 或 `manual_confirmation_required`。
- 写 workflow event。
- 不调用发送工具。
- 不记录 `delivered_via_codex_thread_tool`。

### 18.4 阻断时禁止 delivered

测试必须验证阻断状态下：

- 没有调用 `send_message_to_thread`。
- 没有执行 `multiagent request record --host-delivery delivered_via_codex_thread_tool`。
- 用户输出不包含“已投递到目标会话”或“workflow 当前节点消息已送达”。

### 18.5 允许 self step fixture

给定 definition 显式标记：

```yaml
allow_self_step: true
```

Runner 必须：

- 不调用发送工具。
- 记录 `self_step_recorded` 或等价状态。
- 不说跨 Agent 消息已送达。

### 18.6 状态机验收

测试必须覆盖：

- `planned`
- `ready`
- `delivering`
- `delivered`
- `blocked_self_delivery`
- `manual_confirmation_required`
- `self_step_recorded`
- `completed`
- `failed`

并验证非法转换被拒绝，例如：

- `blocked_self_delivery -> delivered`
- `self_step_recorded -> delivered`
- 未经 `delivering` 直接 `delivered`

### 18.7 用户话术验收

发现自投递风险时，必须输出：

```text
我发现下一步目标会指向当前 Agent 自己，这可能是 workflow 配置或路由错误，已停止自动投递。
```

### 18.8 next 文档验收

v0.14 完成前，workflow next 文档只能说：

```text
由 AI 辅助推进的内测 workflow
```

不得承诺：

- 后台自动化。
- 无监督自动流转。
- 自动连续跑完整 workflow。

### 18.9 v0.8 / v0.12 边界不能回归

必须继续满足：

- Codex 正常路径仍用标准线程工具。
- 工具不可见时先工具发现，失败 manual handoff。
- 真实投递成功后才能记录 delivered。
- 消息送达不等于目标任务完成。
- 不恢复 `starwork multiagent instruct`、`starwork multiagent launch`、`multiagent message instruct`、`multiagent message launch` 作为 Codex 正常路径。

## 20. 最小可开发范围

建议立即开发的最小范围：

1. Workflow run state schema。
2. `.starwork/workflows/runs/<run-id>.json` 持久化。
3. `starwork multiagent workflow start/status/route/event record` 最小 CLI。

## 22. 已决策项
