## 背景

`ISSUE-025` 暴露了 MultiAgent workflow next 的关键断点：Agent 在一个本应自动投递到目标 lane 的 workflow / delegation 步骤中，没有调用 `send_message_to_thread`，而是在当前回复中说明情况，导致用户以为流程可以继续，但目标 Agent 实际没有收到任务。

截图中 Agent 自述两个原因：

1. delegation 完成条件允许“发送回传指令或在回复中明确说明”，Agent 选择了后者。
2. 当时 `send_message_to_thread` 不在可见工具列表中，Agent 没有继续用工具发现查找，也没有进入显式 handoff / blocked。

这不是单纯文案问题，而是 workflow runner / delegation 的完成条件不够硬。v0.12 的目标是补上“必须真实投递”的硬性规则。

## 产品判断

Workflow / delegation 中凡是目标是另一个 lane / Agent 的步骤，都不能把“在当前回复中说明”当作完成。该步骤只有三种合法结果：

1. **真实自动投递成功**：调用宿主标准线程工具成功，例如 Codex App 的 `send_message_to_thread`，再记录 `delivered_via_codex_thread_tool`。
2. **明确人工转交**：工具不可见、调用失败或宿主不支持时，输出 `manual_handoff_required` 和完整可复制消息，明确尚未自动送达。
3. **明确阻塞**：缺少目标 lane、目标 session、当前会话 ID、权限或必要确认时，进入 `blocked` / `unbound` / `needs_confirmation` 等状态，不能假装完成。

任何 workflow / delegation 指令中的“或在回复中说明”都不得覆盖上述规则。

## 术语

| 术语 | 定义 |
| --- | --- |
| 必须投递步骤 | 当前步骤的目标是另一个 lane / Agent / session，且用户期望 workflow 继续推进。 |
| 本地执行步骤 | 当前步骤由当前会话自己完成，不需要跨会话投递。 |
| 真实投递 | 成功调用宿主标准线程工具，目标会话实际收到消息。 |
| 人工转交 | 自动投递不可用，Agent 给出完整可复制消息，让用户手动粘贴到目标会话。 |
| 状态落账 | 在 `shared.md`、worklog 或 `multiagent request record` 中记录 delivery status。 |

## 必须真实投递的硬性规则

### 1. 判断步骤类型

Workflow Runner 或 delegation 执行前，必须先判断当前步骤是：

| 类型 | 条件 | 允许结果 |
| --- | --- | --- |
| 本地执行 | 目标 lane 就是当前会话，或用户明确要求当前会话执行 | 本地执行，不调用 `send_message_to_thread` |
| 必须投递 | 目标 lane 是其他已绑定会话 | 真实自动投递 / manual handoff / blocked |
| 不可执行 | 目标 lane 不存在、未绑定、当前会话 ID 不明、缺少确认 | blocked / unbound / needs_confirmation |

### 2. 必须投递步骤不能用当前回复替代

以下表达不得作为完成条件：

- “已在回复中说明。”
- “请用户自行通知。”
- “我已经准备好消息。”
- “我建议你转交给 development。”

除非同时进入 `manual_handoff_required`，并给出完整可复制消息、明确“尚未自动送达”。

### 3. delegation 文案中的完成条件必须收紧

Skill 或 workflow message 中不得再写：

```text
完成后请回报：发送回传指令或在回复中明确说明。
```

必须改为：

```text
完成后必须向来源 lane 回传。如果当前宿主能自动投递，调用标准线程工具投递；如果工具不可见或投递失败，输出 manual_handoff_required 和完整可复制回传消息，并明确尚未自动送达。不得只在当前回复中说明来替代跨 lane 回传。
```

### 4. 目标 lane 是当前会话时默认阻断

如果目标 lane 的 `current_session` 等于当前会话 ID，默认不得调用 `send_message_to_thread`。应说明：

```text
目标岗位绑定的是当前会话，直接发送会形成自我交接。
```

只有用户明确要求当前会话执行当前节点时，才进入本地执行模式。

## 工具不可见时的处理路径

当必须投递步骤需要 Codex App 标准线程工具，但当前工具列表中没有 `send_message_to_thread` 时，必须按顺序处理：

1. **工具发现**：调用可用的工具发现能力搜索 `send_message_to_thread` / Codex thread coordination 工具。
2. **发现成功**：使用发现到的标准工具投递消息。
3. **发现失败**：不得继续假装可投递，进入 `manual_handoff_required`。
4. **输出人工转交消息**：展示完整 `STARWORK:MULTIAGENT_MESSAGE v1`，包含 `from_lane`、`to_lane`、`source_thread_id`、request id、任务内容、return contract。
5. **状态记录**：未自动投递时，不得记录 `delivered_via_codex_thread_tool`。

如果连工具发现能力也不可见，直接进入 `manual_handoff_required`，说明缺少标准线程投递工具和工具发现能力。

## 状态写入顺序

状态写入必须遵守“事实先发生，状态后记录”。

### 自动投递成功

1. 读取 `multiagent status --target <path> --json`，确认目标 lane 和 session。
2. 确认当前会话 ID。
3. 组装 message。
4. 调用 `send_message_to_thread(threadId, prompt)`。
5. 只有工具调用成功返回后，才执行：

   ```bash
   starwork multiagent request record --host-delivery delivered_via_codex_thread_tool --delivery-tool send_message_to_thread ...
   ```

6. 回复用户：只能说“workflow 当前节点消息已送达，并已记录 StarWork request”，不得说目标任务已完成。

### 自动投递失败 / 工具不可见

1. 组装完整可复制 message。
2. 输出 `manual_handoff_required`。
3. 明确“尚未自动送达”。
4. 如需要落账，只能记录 `manual_handoff_required`、`delivery_tool_unavailable` 或 `recorded_only`，不得记录 `delivered_via_codex_thread_tool`。

### 阻塞

如果缺少目标 session、当前会话 ID、用户确认或 workflow definition：

1. 不投递。
2. 不记录 delivered。
3. 输出阻塞原因和下一步需要用户 / lane 提供的信息。

## 推荐状态

| 状态 | 使用场景 |
| --- | --- |
| `delivered_via_codex_thread_tool` | 已成功调用 Codex `send_message_to_thread` |
| `manual_handoff_required` | 自动投递不可用，需要用户复制消息 |
| `delivery_tool_unavailable` | 工具发现后确认缺少标准投递工具，可作为机器可读 warning 或 future status |
| `unbound` | 目标 lane 没有绑定 session |
| `needs_confirmation` | 用户尚未确认发送 / 写入 / 启动 |
| `blocked` | 缺少必要上下文或存在冲突，不能继续 |
| `recorded_only` | 用户已人工完成，StarWork 只补记事实，不代表自动投递 |

## Skill 文案要求

`starworkMultiagent` 必须增加一段“Workflow / Delegation 投递保证”：

- 必须投递步骤不能用“在当前回复中说明”替代。
- 工具不可见时先工具发现。
- 发现失败时输出 `manual_handoff_required` 和完整可复制消息。
- 未投递成功不得写 `delivered_via_codex_thread_tool`。
- 发送成功只代表消息送达，不代表目标任务完成。

## Development 验收建议

### 文本扫描

1. `product/skills-next/starworkMultiagent/SKILL.md` 必须命中：

   - `必须投递`
   - `不能用当前回复说明替代`
   - `工具发现`
   - `manual_handoff_required`
   - `尚未自动送达`
   - `delivered_via_codex_thread_tool`

2. 不得出现以下完成条件：

   - `发送回传指令或在回复中说明`
   - `发送回传指令或在回复中明确说明`
   - `或在回复中说明`

   如果作为反例出现，必须明确标注“禁止”。

### 回归测试

至少补两个测试：

1. **必须投递成功测试**
   - 给定 workflow / delegation 步骤目标为另一个 Codex lane。
   - Skill 文本必须要求调用 `send_message_to_thread`。
   - 成功后才能记录 `delivered_via_codex_thread_tool`。

2. **工具不可见测试**
   - 模拟 `send_message_to_thread` 不可见。
   - Skill 文本必须要求先工具发现。
   - 发现失败时必须输出 `manual_handoff_required` 和完整可复制消息。
   - 不得记录 `delivered_via_codex_thread_tool`。

### 真实或等价 smoke

完成后至少做一种：

- 真实 Codex App smoke：用 `send_message_to_thread` 向 development lane 投递测试消息，并确认目标 thread 收到。
- 等价 mock：在测试中验证状态写入顺序，确保 `request record` 在投递成功之后，失败时不会写 delivered。

## 关闭标准

1. `ISSUE-025` 中的两个根因都被覆盖：
   - delegation 完成条件不再允许“回复说明”替代投递。
   - 工具不可见时必须 discovery / handoff / blocked。
2. Workflow Runner / `starworkMultiagent` 文案落地投递保证。
3. 状态写入顺序有明确规则和测试保护。
4. 文档或 A 测指南不再让用户误以为“说明一下”就等于跨 lane 投递完成。
5. development 回传并通过 product-lead 复验。
