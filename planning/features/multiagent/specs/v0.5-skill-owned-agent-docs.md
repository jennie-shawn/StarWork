## 背景

`ISSUE-005` / `ISSUE-009` 已经修复了一个关键问题：MultiAgent 不应在非 StarWork 目录中绕过 `starworkInit` 做局部初始化。

但 `ISSUE-014` 暴露出第二层问题：当 MultiAgent onboarding 转入 `starworkInit` 后，流程仍可能执行完整命令：

```bash
starwork init --type project --pack general --language zh --adapter codex --target <existing-project> --yes
```

在已有代码仓库中，这会触发两类“安全副本”：

- `README.starwork-new.md`：`starwork init` 遇到已有 `README.md` 时，为避免覆盖而生成副本。
- `AGENTS.starwork.md`：Codex adapter 的规则入口是 `AGENTS.md`，遇到已有用户 `AGENTS.md` 时，为避免覆盖而生成 sidecar。

这两个机制在通用 CLI 写文件语境下是保护用户文件的安全策略，但在用户意图是“创建 MultiAgent / 绑定 lane”时，它们变成了未预期的工作区污染。

根因不是“副本文件名错了”，而是产品边界不清：

```text
CLI 不应直接决定最终 AI 入口文档。
Skill 应读取项目上下文，生成或整合最终 AI 入口文档。
```

## 一句话目标

StarWork CLI 只生成工作台结构、机器可验证状态和 AI 入口文档草稿；最终 `AGENTS.md`、`CLAUDE.md`、Cursor rules、Trae rules 等 AI 入口文档，必须由对应 Skill 驱动 AI 在读取项目上下文后生成、合并或确认写入。

## 产品原则

### P1. AI 入口文档是语义文档，不是机械模板

`AGENTS.md` 这类文件需要表达：

- 用户项目原有规则。
- StarWork 工作台边界。
- AI 写入范围。
- 已有 README / docs / package 配置透露出的项目事实。
- 当前宿主需要读取的入口和 Skill 目录。

代码模板无法可靠理解这些语义，因此 CLI 不应默认把模板写成最终文档。

### P2. CLI 负责结构，Skill 负责语义

CLI 可以直接写入：

- `.starwork/workspace.json`
- `.starwork/skills.json`
- `.starwork/adapters.json`
- `.starwork/agent-lanes/state.json`
- `_系统/` / `_system/` 协作和上下文结构
- Pack 目录、模板、机器可验证 manifest

Skill 负责最终写入或修改：

- `AGENTS.md`
- `CLAUDE.md`
- `.cursor/rules/starwork.mdc`
- `.trae/rules/starwork.md`
- README 中需要结合项目语义改写的部分

CLI 可以为这些文件生成草稿，但草稿不能冒充最终入口。

### P3. 已有非空项目默认不写根入口文档

在目标目录已存在且非空时，CLI 默认不得直接生成：

- `AGENTS.md`
- `AGENTS.starwork.md`
- `AGENTS.starwork-new.md`
- `README.starwork-new.md`
- `CLAUDE.starwork.md`
- 其他根入口 sidecar

若确实需要生成，应先进入 dry-run / draft 状态，明确告诉用户将产生哪些文件，并等待用户或 Skill 完成语义整合。

### P4. 用户确认的是整合结果，不是一条 CLI 命令

在已有项目中，`--yes` 只能表示用户确认写入结构文件和机器状态；不能表示用户已经同意最终 AI 入口文档内容。

## 新增概念

### Agent Docs Plan

CLI 在 init / adapt / multiagent onboarding 中生成结构化计划，用于告诉 Skill：

- 哪些 AI 入口文档需要创建或整合。
- 目标文件是否已存在。
- 建议加入哪些 StarWork 规则。
- 是否存在冲突或需要用户确认。
- 草稿文件路径。

建议 schema：

```json
{
  "schema": "starwork.agent_docs_plan.v0.1",
  "generated_at": "2026-06-04T00:00:00.000Z",
  "target": "/abs/path",
  "context": "init|adapt|multiagent-onboarding",
  "status": "draft_required",
  "entries": [
    {
      "kind": "agent_rules",
      "host": "codex",
      "target_path": "AGENTS.md",
      "target_exists": true,
      "draft_path": ".starwork/drafts/AGENTS.codex.proposed.md",
      "action": "merge_required",
      "reason": "Existing AGENTS.md must be preserved and semantically integrated.",
      "required_topics": [
        "StarWork read-first files",
        "workspace write boundaries",
        "project Skill directories",
        "MultiAgent lane workflow"
      ]
    }
  ]
}
```

### Draft paths

CLI 草稿统一放在：

```text
.starwork/drafts/
```

示例：

```text
.starwork/drafts/AGENTS.proposed.md
.starwork/drafts/README.proposed.md
.starwork/drafts/adapter.codex.proposed.md
.starwork/drafts/agent-docs-plan.json
```

草稿文件名必须包含 `proposed` 或 `draft`，避免用户误以为它已经是最终入口。

## CLI 行为要求

### 1. `starwork init`

新增或调整选项：

```bash
--agent-docs <draft|skip|write>
```

默认值：

| 场景 | 默认 |
| --- | --- |
| 目标目录不存在或为空 | `draft` |
| 目标目录已存在且非空 | `draft` |
| 用户明确只要机器结构 | `skip` |
| 用户明确要求 CLI 写最终文档 | `write`，但仅允许无冲突场景 |

要求：

- `draft`：写 `.starwork/drafts/*` 和 `agent-docs-plan.json`，不写根 `AGENTS.md` / `README.starwork-new.md`。
- `skip`：不写 AI 入口文档，也不写入口草稿；但输出提醒用户下一步用 `starworkInit` 生成入口。
- `write`：只允许目标入口不存在，或现有入口为空，或入口已有 StarWork marker 且可安全更新。已有用户内容时必须失败或降级为 `draft_required`，不能生成 sidecar。

`--yes` 不得绕过上述规则。

### 2. `starwork adapt <host>`

`adapt` 不再默认把 adapter 入口 sidecar 写到根目录。

要求：

- 若 host 入口文件不存在，可按 `--agent-docs` 策略写草稿或最终文件。
- 若 host 入口文件已存在且非空：
  - 默认生成 `.starwork/drafts/adapter.<host>.proposed.md`。
  - 写入 / 更新 `.starwork/adapters.json` 时，必须记录入口状态为 `draft_required` 或 `pending_merge`，而不是 `enabled: true` 冒充完成。
  - 不生成 `AGENTS.starwork.md`、`CLAUDE.starwork.md` 等根 sidecar。

建议 adapter state 增加字段：

```json
{
  "rules_entry": "AGENTS.md",
  "rules_entry_status": "pending_merge",
  "draft_entry": ".starwork/drafts/adapter.codex.proposed.md"
}
```

`doctor --host` 应能报告：

- `pending_merge`：adapter 已生成草稿，但最终入口还未由 Skill 合并。
- `active`：最终入口已存在且包含必要 StarWork 读取规则。
- `missing`：既无最终入口，也无草稿。

### 3. `starwork multiagent`

MultiAgent 写入类命令在非 StarWork 目标中仍必须拒绝，不得自动 init。

新增约束：

- `starworkMultiagent` 转入 `starworkInit` 后，不得建议一条完整 `starwork init --adapter codex --yes` 作为用户已确认的最终动作。
- `multiagent init/add/bind/launch` 只能在 `doctor` 判断目标是 StarWork 工作台，且 AI 入口状态不是 `pending_merge` 的情况下继续。
- 如果 `doctor --host` 报告 `rules_entry_status: pending_merge`，MultiAgent 应提示先完成入口文档整合。

### 4. `doctor`

`doctor` / `doctor --host` 应新增或强化检查：

| 检查 | 结果 |
| --- | --- |
| `.starwork/drafts/agent-docs-plan.json` 存在且未完成 | warn |
| adapter state 为 `pending_merge` | warn |
| 根目录存在 `AGENTS.starwork.md` / `AGENTS.starwork-new.md` / `README.starwork-new.md` | warn，提示这是旧流程或未确认副本 |
| 最终入口缺少 StarWork read-first 规则 | warn |

这些 warning 不应让 Core 结构检查失败，但必须阻止 Skill 把 MultiAgent 团队创建说成完成。

## Skill 行为要求

### 1. `starworkInit`

`starworkInit` 是最终 AI 入口文档的主要生产者。

在已有项目中，它必须：

1. 运行 `starwork doctor --target <path> --json`。
2. 执行 `starwork init --target <path> ... --agent-docs draft --dry-run`。
3. 读取现有项目入口：
   - `AGENTS.md`
   - `README.md`
   - `CLAUDE.md`
   - `.cursor/rules/*`
   - package / config / docs 中能帮助判断项目边界的文件
4. 读取 `.starwork/drafts/agent-docs-plan.json` 和相关草稿。
5. 生成整合方案，明确：
   - 保留哪些用户原规则。
   - 新增哪些 StarWork read-first / write-boundary 规则。
   - 哪些内容不会写入。
   - 将最终修改哪些文件。
6. 用户确认后，Skill 通过 AI 编辑工具写入最终 `AGENTS.md` 等入口。
7. 再运行 `starwork doctor --target <path> --host <host> --json` 验证。

不得直接把下面命令当成已有项目的完整接入方案：

```bash
starwork init --type project --pack general --language zh --adapter codex --target <path> --yes
```

### 2. `starworkMultiagent`

在已有非 StarWork 项目里，`starworkMultiagent` 只做路由：

```text
当前目录还不是 StarWork 工作台。请先使用 starworkInit 完成工作台接入和 AI 入口文档整合。完成后我再继续创建/绑定 lane。
```

它不得：

- 执行完整 init。
- 生成入口 sidecar。
- 在 `pending_merge` 时继续 `multiagent init/add/bind/launch`。

### 3. `starworkDoctor`

`starworkDoctor` 需要能解释：

- `pending_merge` 不是 Core 结构损坏。
- 它表示 AI 入口文档还需要 Skill 整合。
- 下一步应回到 `starworkInit` 或对应 adapter Skill 完成最终入口。

## 回归测试要求

### CLI 测试

新增测试场景：

1. 已有 `AGENTS.md` + `README.md` 的普通项目执行：

```bash
starwork init --type project --pack general --language zh --adapter codex --target <dir> --yes
```

期望：

- 不生成 `AGENTS.starwork.md`。
- 不生成 `AGENTS.starwork-new.md`。
- 不生成 `README.starwork-new.md`。
- 生成 `.starwork/drafts/agent-docs-plan.json`。
- 生成 `.starwork/drafts/AGENTS.proposed.md` 或 adapter 草稿。
- stdout 明确提示“AI 入口文档需要 Skill 整合后再生效”。

2. 已有 `AGENTS.md` 的 StarWork 工作台执行：

```bash
starwork adapt codex --target <dir> --yes
```

期望：

- 不生成 `AGENTS.starwork.md`。
- `.starwork/adapters.json` 中 codex adapter 为 `pending_merge` 或等价状态。
- `doctor --host codex --json` 报告 pending merge warning。

3. 健康 StarWork 工作台但 adapter 入口 pending merge 时执行 MultiAgent launch：

期望：

- 不应说团队创建完成。
- 输出 warning 或失败，要求先完成 AI 入口文档整合。

4. 空目录初始化：

期望：

- 默认也生成草稿而不是最终 `AGENTS.md`，或至少在测试中明确选择 `--agent-docs write` 才写最终入口。
- 若 development lane 选择分阶段落地，第一阶段可以保留空目录写最终入口，但必须在实现记录中标注为兼容过渡，并保证已有非空目录严格走 draft。

### Skill 文本测试

更新现有 Skill 文本测试：

- `starworkInit` 必须包含“已有非空项目不直接执行 --yes 写最终入口文档”。
- `starworkInit` 必须包含 `--agent-docs draft` 或等价流程。
- `starworkMultiagent` 必须包含 “pending_merge 时不继续创建 / 绑定 lane”。
- `starworkMultiagent` 不得包含 `starwork init --type project ... --adapter codex --yes` 作为非 StarWork 项目的直接下一步。

## 验收方式

### 产品复验场景 A：ISSUE-014 复现路径

准备已有普通项目：

```text
AGENTS.md
README.md
package.json 或任意项目文件
```

执行用户意图：

```text
帮我在这个项目里创建 MultiAgent，当前会话负责产品规划。
```

期望：

- `starworkMultiagent` 先发现非 StarWork，转入 `starworkInit`。
- `starworkInit` 不直接执行完整 `init --adapter codex --yes`。
- 未经用户确认最终整合结果前，不出现：
  - `AGENTS.starwork.md`
  - `AGENTS.starwork-new.md`
  - `README.starwork-new.md`
- 出现的是 `.starwork/drafts/agent-docs-plan.json` 和可读草稿。
- 用户确认整合结果后，最终 `AGENTS.md` 由 Skill 编辑生成或合并。
- `doctor --host codex` 可解释当前入口状态。

### 产品复验场景 B：已有 StarWork 工作台启用 Codex adapter

准备已有 StarWork 工作台，且根目录已有用户自写 `AGENTS.md`。

执行：

```bash
starwork adapt codex --target <dir> --yes
```

期望：

- 不生成根 sidecar。
- adapter state 不误报 fully enabled。
- doctor 提醒需要 Skill 合并入口。

### 产品复验场景 C：完成入口整合后创建 MultiAgent

在 `AGENTS.md` 已由 Skill 合并并通过 doctor 检查后，执行：

```bash
starwork multiagent init/add/bind/launch ...
```

期望：

- MultiAgent 可以继续。
- 不再生成额外入口副本。
- status / doctor 能说明当前 lane 与入口文档状态。

## ISSUE-014 关闭标准

`ISSUE-014` 只能在以下条件全部满足后关闭：

1. 已有普通项目按 MultiAgent onboarding 流程操作时，未确认前不生成 `AGENTS.starwork.md`、`AGENTS.starwork-new.md`、`README.starwork-new.md`。
2. CLI 对 AI 入口文档默认生成 draft / plan，不把草稿当最终入口。
3. `starworkInit` 明确接管最终 `AGENTS.md` 整合。
4. `starworkMultiagent` 在非 StarWork 或入口 pending merge 时不会继续创建 / 绑定 lane。
5. `doctor --host` 能解释 pending merge。
6. 自动测试覆盖已有 `AGENTS.md` / `README.md` 的非 StarWork 项目。
7. 在 GitHub Issue #3 回填修复说明和用户可理解的下一步。

## 非目标

本 SPEC 不要求：

- 一次性重写所有 Pack 文档。
- 立即实现复杂三方 merge 算法。
- 让 CLI 理解项目业务语义。
- 废除 CLI 的结构初始化能力。

本 SPEC 要求的是：CLI 不再把 AI 入口文档模板静默写成最终事实；已有项目的入口文档必须由 Skill 读取上下文后整合。
