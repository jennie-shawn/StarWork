# MultiAgent v0.6 Launch 会话控制能力与短标题修复 SPEC

## 1. 状态

- 日期：2026-06-06
- 状态：ready-for-development
- 所属功能：MultiAgent / Host Adapter / Skills
- 关联问题：
  - `product/planning/issues/ISSUE-015.md`
  - `product/planning/issues/ISSUE-017.md`
- 关联实测：`product/planning/features/multiagent/references/2026-06-07-codex-launch-surface-probe.md`
- 影响模块：`starwork multiagent launch`、`starwork multiagent instruct`、`starworkMultiagent` Skill、`.starwork/agent-lanes/state.json`

## 2. 背景

当前 MultiAgent 已经把跨宿主能力判断从 Skill 收敛到 CLI，但 ISSUE-017 暴露了一个更细的边界：

```text
同样是 Codex，会话来源不同，当前 Agent 可见的会话控制工具也可能不同。
```

2026-06-07 实测显示，`starwork multiagent launch` 当前通过 standalone `codex app-server` 创建 lane 会话。该会话可以完成 Launch Message 并承担 lane 工作，但不是 Codex Desktop App 当前会话那种可能暴露 thread coordination tools 的控制容器。

尤其是 `starwork multiagent launch` 创建出来的 lane 会话，它是被启动出来执行 lane 工作的 worker 会话，实测不具备 `tool_search`，也不具备 `create_thread`、`send_message_to_thread`、`set_thread_title`、`set_thread_pinned`、`set_thread_archived`、`read_thread` 等控制其它会话的工具。

2026-06-08 在新的 product-planning 会话中，当前 turn 已具备 Codex Desktop thread tools；但对 standalone launch 创建出的 thread 调用标准 `send_message_to_thread` 仍失败，错误为 `No AppServerManager registered for conversationId`。这说明 launch thread 可以被读取和列出，不代表它处在当前 Desktop App 可投递的 conversation manager 中。

同一轮实测还发现：如果 `launch` timeout 太短，thread 会被创建并改名，但 Launch Message turn 会变成 `interrupted`。这类结果不能绑定 lane。

同时 ISSUE-015 说明当前会话命名仍可能直接复用 lane purpose，导致标题混入使用场景和长描述。

## 3. 一句话目标

把 `launch` 创建出的 Codex 会话明确标记为 worker 会话和控制能力未知/缺失；所有依赖会话控制工具的后续动作必须保守降级。同时把会话标题固定为短职责名，不再拼接用途说明。

## 4. 产品判断

### 4.1 Host 名称不是能力证明

`host=codex` 只说明 session 属于 Codex，不说明当前 Agent turn 可见 Codex App 的线程控制工具。

CLI 不得仅凭以下信息判断可以自动控制会话：

- `codex:<thread-id>`
- `.starwork/adapters.json` 中 Codex 已启用
- Codex App Server 可启动
- `thread/start` / `turn/start` 等低层协议可用

### 4.2 Launch 创建的是 worker session

`multiagent launch` 的目标是创建独立 lane worker，让它接收 Launch Message 并承担职责内工作。

默认规则：

- launch 创建的 session 只有在 Launch Message turn completed 后，才可以绑定为 lane 的 `current_session`。
- launch 创建的 session 不应被视为 control session。
- launch 创建的 session 默认不能代表 StarWork 自动创建、投递、改名、pin 或 archive 其它会话。
- 如果 worker session 后续要向其它 lane 发指令，必须走 `manual_handoff_required`，除非当前 turn 显式证明具备标准会话控制工具。

### 4.3 Agent 可见工具不是 CLI 进程能力

`tool_search`、`send_message_to_thread` 这类能力是 Codex App 容器暴露给当前模型的工具，不是普通 npm CLI 进程可以直接调用的 shell API。

因此 v0.6 不再把“CLI 自己 probe 模型可见工具”作为必需实现。正确分层是：

```text
Skill / Agent：可观察当前 turn 的可见工具，但不解释宿主能力矩阵。
CLI：解释 StarWork 状态、构造消息、返回结构化动作和降级状态。
Skill / Agent：只执行 CLI 明确要求的宿主动作；工具不可见时按 CLI fallback 输出人工交付。
```

v0.6 的最低落地要求是保守：

- 没有明确工具证据时，所有跨会话自动投递都降级。
- launch worker session 一律记录为 `control_tools: assumed_absent`。

## 5. 状态模型变更

`multiagent launch` 成功绑定 lane 时，在 `.starwork/agent-lanes/state.json` 对应 lane 记录中增加运行时能力摘要：

```json
{
  "host": "codex",
  "current_session": "codex:<thread-id>",
  "created_by": "starwork multiagent launch",
  "runtime_capabilities": {
    "session_origin": "starwork_launch",
    "session_surface": "codex_app_server",
    "session_role": "worker",
    "model_visible_thread_tools": "absent_observed",
    "can_control_other_sessions": false,
    "send_message": "manual_handoff_required",
    "rename_session": "host_best_effort_only",
    "pin_session": "unsupported_or_unknown",
    "archive_session": "unsupported_or_unknown",
    "observed_at": "<iso-time>"
  }
}
```

要求：

- 字段缺失时，旧 state 仍可读。
- `runtime_capabilities` 是 StarWork 运行时观察，不替代 adapter profile。
- `session_role=worker` 只限制该 session 作为“发送方 / 控制方”的能力，不影响它作为 lane 工作会话被读取、绑定和记录。

## 6. `launch` 输出变更

`multiagent launch --json` 每个 launch result 增加：

```json
{
  "control_capability": {
    "session_origin": "starwork_launch",
    "session_surface": "codex_app_server",
    "session_role": "worker",
    "model_visible_thread_tools": "absent_observed",
    "can_control_other_sessions": false,
    "send_message": "manual_handoff_required",
    "warning": "Launch-created Codex sessions are not assumed to have Codex App thread control tools."
  }
}
```

非 JSON 输出也要在绑定成功后追加一句简短提示：

```text
注意：launch 创建的是 worker 会话，不默认具备跨会话控制工具；后续派活不可用时会提供手动交付消息。
```

## 7. `instruct` 路由变更

`multiagent instruct` 的能力判断要同时看目标 lane 和发送方上下文。

### 7.1 发送方为 launch worker

当满足以下任一条件时，视为当前发送方没有标准会话控制工具：

- `--from <lane>` 对应 state 中 `runtime_capabilities.session_origin = starwork_launch`。
- `--from <lane>` 对应 state 中 `runtime_capabilities.can_control_other_sessions = false`。
- CLI 未收到任何明确的 agent-visible tool 证据。

结果：

- 返回 `manual_handoff_required`。
- `warning` 说明原因是当前发送方会话缺少或未证明具备会话控制工具。
- 不得因为目标 lane 是 `codex:<id>` 而返回 `delivered`。

### 7.2 具备工具的普通 Codex 控制会话

如果未来要恢复自动投递，必须通过 Agent-mediated contract 实现，而不是 CLI 静默猜测：

1. CLI 返回 `host_action_required`，包含标准动作、目标 session、完整 message 和 manual fallback。
2. `starworkMultiagent` Skill 只按 CLI 返回执行指定宿主工具。
3. 如果当前 turn 不可见该工具，Skill 输出 CLI fallback 中的 `manual_handoff_required`。

v0.6 可以先不实现自动投递恢复，但不得误报自动完成。

## 8. 会话短标题规则

`buildLaneLaunchSessionName` 不得直接使用完整 `lane.purpose`。

新增短标题提取函数，例如：

```text
deriveLaneRoleName(lane)
```

规则：

1. 优先使用显式 `--session-name`，但仍要做危险字符和长度检查。
2. 若无显式名称，从 `lane.purpose` 提取短职责名。
3. 遇到 `:`、`：`、`。`、换行、逗号、顿号后的内容全部丢弃。
4. 去掉常见长描述前缀或句式，例如 `根据...`、`只负责...`、`用于...`、`负责...生成...`。
5. 若提取结果为空，使用 lane id 转可读名。
6. 最终格式固定为 `<短职责名> Agent`。
7. 默认标题不得包含 `:`、`：`、完整句子、任务目标、使用场景、项目路径或 UUID。

示例：

| lane purpose | session name |
| --- | --- |
| `数据复盘: 根据用户提供的每周数据...` | `数据复盘 Agent` |
| `素材准备：根据内容脚本准备封面方案` | `素材准备 Agent` |
| `内容写作。根据已确认选题生成文稿` | `内容写作 Agent` |
| `只负责登记自媒体选题、维护选题状态` | `选题管理 Agent` 或 lane id 对应短名 |

## 9. 开发任务

### Phase 1：补状态与输出

- `multiagent launch` 仅在 Launch Message turn completed 后绑定 lane。
- `multiagent launch` 成功绑定时写入 `runtime_capabilities`。
- `launch --json` 输出 `control_capability`。
- 非 JSON 输出增加 worker session 提示。
- 添加回归测试：launch 创建 Codex thread 后 state 中 `can_control_other_sessions=false`。
- 添加回归测试：未观测到 `turn/completed` 或目标 turn interrupted 时，保留 `created_thread_id` 但不绑定 lane。

### Phase 2：修正会话命名

- 新增短标题提取函数。
- 修改 `buildLaneLaunchSessionName`。
- 覆盖中文冒号、英文冒号、句号、长 purpose、`只负责...` 等用例。
- 确认 `session_name`、`state.lanes.<lane>.session_name` 和 fake Codex `thread/name/set` input 都是短标题。

### Phase 3：修正 instruct 保守路由

- `resolveHostRuntimeCapability` 读取 `--from` lane 的 runtime capabilities。
- 发送方为 launch worker 且未有明确工具证据时，返回 `manual_handoff_required`。
- warning 明确区分：
  - target host 不支持。
  - current sender session lacks thread control tools。
  - runtime tool evidence absent。

### Phase 4：Skill 解释同步

- `starworkMultiagent` Skill 增加解释：launch 创建的 Agent 是 lane worker，不代表它拥有跨线程控制台能力。
- Skill 仍不维护宿主能力矩阵；只解释 CLI 的结构化状态。

## 10. 验收标准

- ISSUE-017：
  - launch 创建出的 Codex lane 在 state 中被标记为 `session_role=worker`。
  - launch 创建出的 Codex lane 在 state / JSON 输出中被标记为 `can_control_other_sessions=false`。
  - 从 launch worker 作为 `--from` lane 发起 instruct 时，默认返回 `manual_handoff_required`。
  - 输出包含完整可复制 `STARWORK:MULTIAGENT_MESSAGE`。
  - 不再把 `host=codex` 直接解释成可自动投递。

- ISSUE-015：
  - 批量 launch 的会话名只保留短职责名。
  - 会话名不包含 `:`、`：` 后的长描述。
  - 会话名不包含“根据...”或“只负责...”等完整使用场景句子。

## 11. 不做范围

- 不用 `thread/resume + turn/start` 冒充跨会话 instruct。
- 不要求 CLI 直接调用模型可见的 `tool_search`。
- 不把 App Server 低层协议等同于 Codex App 当前 turn 的模型可见工具。
- 不改变 Cursor / Trae / Claude Code 的人工降级策略。
