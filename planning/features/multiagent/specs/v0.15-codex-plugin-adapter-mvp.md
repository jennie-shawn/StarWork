## 2. 背景

用户希望做一个 Codex plugin 版本，真实感受 StarWork MultiAgent workflow next 的安装和入口体验。

capability-research 已完成 Codex plugin 调研，product-lead 已接受核心判断：

```text
不建议全量 StarWork plugin 化。
建议先做实验性的 StarWork MultiAgent Codex Plugin Adapter。
```

plugin 的定位是 Codex 侧安装、发现、触发和可选 MCP 扩展层；它不替代 CLI、Core、项目事实源或 workflow run state。

用户进一步拍板：MVP 建议直接做 next workflow 版本，而不是 stable MultiAgent 版本。

product-lead 曾误将该方向直接写成正式 `product/planning/**` SPEC / ISSUE 并派发 development，后已撤回。本文按正确边界重新由 product-multiagent 先输出 lane workspace 草案。

## 3. 一句话目标

做一个实验性的 `StarWork MultiAgent Workflow Next Codex Plugin Adapter`：让用户在 Codex 中安装一个 plugin 后，能看到清晰的 StarWork MultiAgent Workflow Next 入口，显式触发设计 / 启动 workflow，且 bundled Skill + references 与现有 `product/skills-next/starworkMultiagent/**` 保持一致；同时不改变 StarWork CLI / Core / `.starwork` / `_系统/协作` 事实源。

## 4. MVP 最终效果

用户装完 plugin 后，在 Codex 里应看到：

1. 一个实验性 plugin：

   ```text
   StarWork MultiAgent Workflow Next
   ```

2. 一个清晰的入口说明：

   ```text
   Use StarWork MultiAgent Workflow Next to design or run AI lane workflows in a StarWork workspace.
   ```

3. 一个可复制的默认 prompt，例如：

   ```text
   Use $starworkMultiagentNext to check this StarWork workspace, then help me design a MultiAgent workflow. Do not start the workflow until I confirm.
   ```

4. bundled Skill 能引导两类 workflow next 入口：

   - 设计 workflow：进入 Workflow Builder，采访、预览、保存草案，不投递。
   - 启动 workflow：进入 Workflow Runner，读取 confirmed definition + run state，展示 route preflight，再投递或阻断。

5. 如果当前工作区不是 StarWork workspace，或 CLI / Skill / plugin channel 错配，Skill 应停止高风险操作，提示用户先安装 / 切换到正确版本。

6. 如果 Codex 标准线程工具不可见，仍按 v0.12 进入工具发现 / `manual_handoff_required`，不得说 plugin 自带投递能力。

用户体验上，MVP 不是“安装后后台自动跑 workflow”，而是：

```text
安装 plugin
  -> 在 Codex 里看到 StarWork MultiAgent Workflow Next
  -> 显式调用 plugin bundled Skill
  -> Skill 检查 StarWork workspace 与 @next CLI
  -> 用户选择设计 workflow 或启动已确认 workflow
  -> Runner 按 v0.14 run state / Step Router 展示下一步
```

## 5. 它和现有 CLI + Skill 的区别

### 5.1 Plugin 替代什么

Plugin MVP 只替代或改善 Codex 侧这些体验：

- Skill 安装入口：减少手动复制 `product/skills-next/starworkMultiagent/**` 的摩擦。
- Skill 发现入口：Codex Plugin Directory / plugin browser / marketplace 能展示名字、描述、默认 prompt。
- references 完整安装：bundled Skill 和 references 作为一个 plugin 包分发，降低漏装 references 风险。
- next workflow 试用入口：把 workflow next 作为明确 experimental plugin，不和 stable MultiAgent 混在一起。
- Codex 用户 onboarding：让用户更容易知道从“设计 workflow”还是“启动 workflow”开始。

### 5.2 Plugin 不替代什么

Plugin 不替代：

- `@jennie-shawn/starwork` CLI。
- StarWork Core 协议。
- `.starwork/` 状态。
- `_系统/协作/agent-lanes.md`、`shared.md`、lane worklog。
- `.starwork/workflows/runs/<run-id>.json` workflow run state。
- `starwork multiagent workflow ...` runtime state 命令。
- Codex App 标准线程工具。
- Cursor / Trae / Claude Code adapter。
- Pack / Kit / Capability 安装。
- 课程授权 / 付费分发系统。

### 5.3 事实源边界

Plugin 是 Codex 分发层，不是事实源。

| 对象 | 事实源 |
| --- | --- |
| StarWork workspace 是否有效 | CLI `doctor` / project files |
| lane / session binding | `_系统/协作/agent-lanes.md` + `.starwork/agent-lanes/state.json` |
| workflow run state | `.starwork/workflows/runs/<run-id>.json` |
| shared outputs / request records | `_系统/协作/shared.md` / CLI request record |
| Skill 行为规则 | bundled Skill + references |
| plugin 展示与安装入口 | `.codex-plugin/plugin.json` |

## 6. 为什么选 next workflow，而不是 stable MultiAgent

建议 MVP 直接做 next workflow plugin，理由：

1. 用户真实意图是“做一个版本感受 workflow next 安装和入口体验”，不是验证 stable lane 管理。
2. stable MultiAgent 主要解决职责位、会话绑定、跨 lane 消息；它的安装收益存在，但不如 workflow next 对 plugin 入口敏感。
3. workflow next 当前有更明显痛点：`skills-next`、references、CLI `@next`、run state、A 测口径都容易错配。
4. v0.11-v0.14 已经把 workflow next 的关键边界固化：Builder / Runner、delivery guarantee、Skill references、run state / self-delivery guard。适合用 plugin 打包体验。
5. 如果先做 stable plugin，短期无法验证用户最关心的“设计 / 启动 workflow”入口。

因此 MVP 应定位为：

```text
experimental / next workflow plugin
```

而不是：

```text
StarWork MultiAgent stable plugin
```

当前工作区没有可读取的 `codex-loop-engineering` 参考材料，因此本草案只从产品形态上抽象参考，不把它当作正式依据。

可以借鉴：

- bundled Skill + references 的分发方式。
- 如果对方有 MCP，只借鉴“可选扩展层”的产品位置。
- 对 loop / workflow 入口做显式 invocation，而不是靠用户记一串命令。

不能照搬：

- 后台 loop runtime。
- daemon / watcher / scheduler。
- hook 驱动的自动推进假设。
- 把插件当作 workflow state 事实源。
- 把 Codex plugin 当作跨宿主标准。
- 把插件能力宣传为自带 thread tools。

StarWork 的 workflow next 仍是：

```text
AI 辅助推进 + workflow run state + Step Router + 明确投递 / 阻断
```

不是完整 Loop Engineering 系统。

## 8. 产品边界

MVP 必须遵守：

- 不做 full StarWork plugin。
- 不替代 CLI。
- 不改变 `.starwork` / `_系统/协作` / workflow run state 事实源。
- 不承诺 plugin 自带 `create_thread` / `send_message_to_thread` / `read_thread`。
- 不用 MCP 重建 Codex 标准线程工具。
- 不做 hooks 驱动的自动 workflow。
- 不把 workflow next 描述成后台自动化或无监督自动流转。
- 不让普通 latest 用户通过 plugin 误用 workflow next。
- 不同时暴露 stable 和 next 两个同名 Skill。

## 10. MVP 是否需要 MCP / hooks / connector

MVP 不需要 MCP server、hooks 或 connector。

### 10.1 不需要 MCP server 的理由

第一轮要验证的是：

- plugin 是否能安装。
- bundled Skill 是否能出现。
- references 是否完整可读。
- next workflow 入口是否清楚。
- Skill 与 CLI / plugin channel 是否能校验。
- 同名 Skill 冲突是否可控。

MCP server 会增加：

- 启动配置。
- tool allowlist / approval mode。
- 本地路径和 Node/Python runtime。
- 新的安全边界。
- 是否读写项目状态的争议。

这些会掩盖 MVP 核心体验。

### 10.2 不需要 hooks 的理由

hooks 适合自动注入或生命周期动作，但本 MVP 不做后台 workflow，也不做自动启动 / 自动投递。调研也提示 hooks 虽有官方说明，但本地 plugin 校验与公开 schema 可能存在差异。第一版不依赖 hooks，降低实现风险。

### 10.3 不需要 connector 的理由

MultiAgent workflow next 当前不依赖 GitHub / Gmail / Lark / Drive connector。插件只需要 bundled Skill。未来如果 workflow 与外部系统集成，再单独设计 connector mapping。

### 10.4 第二阶段可选 MCP

若 MVP 通过，第二阶段可考虑只读 MCP：

- `starwork_status`
- `starwork_multiagent_status`
- `starwork_workflow_status`
- `starwork_version_check`

MCP 只能读状态或做版本检查；不重建 `send_message_to_thread`，不替代 CLI 事实源。

## 11. stable / next channel

MVP 是 next workflow plugin，因此必须清楚表达：

| 层 | 要求 |
| --- | --- |
| plugin name | `starwork-multiagent-workflow-next` |
| plugin display | `StarWork MultiAgent Workflow Next` |
| plugin version | `0.15.0-next.0` 或等价 experimental 版本 |
| bundled Skill name | `starworkMultiagentNext` |
| Skill metadata | 标注 `starwork_channel: next`、`starwork_multiagent: v0.15-codex-plugin-adapter` 或等价 |
| CLI requirement | `@jennie-shawn/starwork@next` |
| docs | 明确普通 latest 用户不使用该 plugin 测 workflow |

高风险操作前必须检查：

- 当前 StarWork CLI 是否为 next / 满足 v0.14 workflow run state 能力。
- bundled Skill references 是否包含 workflow builder / runner / run-state。
- plugin metadata 是否是 next workflow plugin。

错配时停止 workflow，不要降级成 stable lane 操作。

## 12. 同名 Skill 冲突处理

### 12.1 产品判断

MVP 不应依赖 Codex 对同名 Skill 的优先级规则。

原因：

- 用户可能已有全局 `~/.agents/skills/starworkMultiagent`。
- repo 可能有 `.agents/skills/starworkMultiagent`。
- plugin 也可能 bundled 一个同名 Skill。
- 如果 Codex implicit invocation 选错旧 Skill，workflow next 测试会变成假失败。

### 12.2 MVP 处理方式

建议 MVP bundled Skill 使用唯一名称：

```text
starworkMultiagentNext
```

并在 description / default prompt 中说明：

```text
This is the experimental plugin-bundled entry for StarWork MultiAgent Workflow Next.
```

MVP 验收时：

- 鼓励显式调用 `$starworkMultiagentNext`。
- 不依赖 implicit invocation。
- 不要求卸载用户级 / repo 级 `starworkMultiagent`。
- 如果用户调用旧 `$starworkMultiagent`，不能视为 plugin smoke 通过。

### 12.3 兼容提醒

plugin Skill 启动时应提示：

```text
如果你同时安装了用户级或仓库级 starworkMultiagent，MVP 请显式使用 $starworkMultiagentNext，以避免触发旧版本。
```

第二阶段再评估是否支持 alias / same-name takeover。

## 14. 安装与触发流程

### 14.1 安装 smoke

MVP 可优先支持：

- local plugin path；
- repo marketplace；
- git marketplace ref pin；
- workspace sharing 作为可选观察。

不把某一种 plugin 安装方式作为唯一正式发行路径。

### 14.2 触发流程

建议 onboarding：

```text
1. 安装 StarWork MultiAgent Workflow Next plugin。
2. 打开一个 StarWork workspace。
3. 确认 CLI 来自 @jennie-shawn/starwork@next。
4. 在 Codex 中显式输入：
   Use $starworkMultiagentNext to check this workspace and help me design a workflow.
5. Skill 先读取 AGENTS.md、_系统/协作/agent-lanes.md、shared.md 和必要 references。
6. 设计 workflow 时只保存草案。
7. 启动 workflow 时先读取 run state 并展示 route preflight。
```

### 14.3 用户可见失败口径

如果 CLI 不是 next：

```text
当前 plugin 是 workflow next 入口，但 StarWork CLI 不是 next 版本。我会停止 workflow 操作，避免 CLI / Skill / plugin 行为错配。
```

如果 references 缺失：

```text
当前 plugin bundled Skill 不完整，缺少 workflow references。我不会继续执行 workflow。
```

如果 Codex thread tools 不可见：

```text
当前 Codex 环境没有暴露标准线程投递工具。我会进入 manual_handoff_required，不会说已经自动送达。
```


### 15.3 References 验收

plugin bundled references 必须与 `product/skills-next/starworkMultiagent/references/**` 的关键文件一致，至少包括：

- `context-and-compatibility.md`

- `manual_confirmation_required`
- `self_step_recorded`
- `manual_handoff_required`
- `delivered_via_codex_thread_tool`

### 15.4 安装 smoke

必须验证至少一种安装路径：

- local plugin path；或
- repo marketplace；或
- git marketplace ref pin。

安装后：

- Codex App / CLI 能看到 plugin。
- 新线程能显式调用 `$starworkMultiagentNext`。
- Skill 能读取 references。
- 默认 prompt 可用。

### 15.5 Workflow 入口 smoke

在 StarWork workspace 中：

1. 显式调用 `$starworkMultiagentNext`。
2. 设计 workflow：应进入 Builder，只保存草案，不投递。
3. 启动 workflow：应读取 run state，展示 run id、current step、from lane、target lane、target session。
4. 目标不明确或自投递风险时，阻断。
5. 工具不可见时进入 `manual_handoff_required`。

### 15.6 文档验收

必须有 README 或 A 测说明，覆盖：

- 这是 experimental / next workflow plugin。
- 需要 StarWork CLI `@next`。
- 不替代 CLI / Core / `.starwork` / `_系统/协作`。
- 不承诺后台自动化。
- 不承诺自带 thread tools。
- 建议显式调用 `$starworkMultiagentNext`。
- 与用户级 / repo 级 `starworkMultiagent` 并存时的限制。

### 15.7 禁止项扫描

不得出现：

- “plugin 自带 send_message_to_thread”
- “后台自动跑完整 workflow”
- “无监督自动流转”
- “替代 StarWork CLI”
- “替代 .starwork run state”
- “full StarWork plugin”
- 恢复 `starwork multiagent instruct` / `launch` 作为 Codex 正常路径

如作为反例出现，必须明确标注“禁止”。

### 15.8 与 `skills-next` 一致性

必须验证：

- plugin bundled workflow references 与 `product/skills-next/starworkMultiagent/references/**` 关键规则一致。
- 差异只允许是 plugin entry 名称、display name、default prompt 和冲突提示。
- v0.14 run state / self-delivery guard 规则不能在 plugin 版缺失。
