## 2. 背景

v0.8 已经把 `starworkMultiagent` 的技术边界收紧：Codex App 中创建会话、发送消息、读取会话、改标题、置顶和归档，都由 Skill 直接调用标准线程工具；CLI 只记录 StarWork 项目事实源。

但运营 Agent 的体验审阅指出，当前 Skill 仍像工程助手：

- 第一屏暴露 `lane`、`write_scope`、`binding`、`thread`、`CLI` 等内部词。
- 说明步骤时更像“我要调用什么命令”，而不是“这一步帮用户避免什么风险”。
- 用户还没准备好项目时，切换到初始化流程显得突兀。
- 自动工具不可用时，容易被感知为失败，而不是清楚说明“我已经为你准备好人工交接消息”。
- 成功汇报没有稳定区分“岗位已创建”“会话已绑定”“消息已送达”“目标任务已完成”。

v0.9 不改变 v0.8 的调用边界，不新增默认岗位模板，不新增自动调度能力。本版只做用户体验层改造：让 Skill 在创建 AI 团队、绑定会话、跨岗位交接和失败降级时，用小白能理解的语言引导用户安全确认。

## 3. 一句话目标

让 `starworkMultiagent` 从“暴露内部命令的工程助手”升级为“耐心的多 AI 协作顾问”：先解释、再检查、再设计、先预览、确认后执行，最后明确告诉用户当前完成到哪一步和下一步可以怎么说。

## 4. 产品原则

### 4.1 用户看到的是 AI 岗位，不是内部 lane

默认用户语言：

| 内部词 | 用户可见说法 |
| --- | --- |
| lane | AI 岗位 / 职责位 |
| session / thread | AI 会话 / 当前会话 |
| write_scope | 可以整理或修改的范围 |
| binding | 把这个会话登记到某个岗位 |
| shared output | 共享给其他 AI 的成果 |
| handoff | 交接消息 |
| CLI | StarWork 命令工具 |
| host / adapter | 你正在使用的 AI 工具 |
| dry-run | 先预览，不真正写入 |

`lane`、`write_scope`、`binding`、`thread`、`CLI` 等词只在以下情况出现：

- 用户主动追问内部机制。
- 输出调试信息、验收记录或开发文档。
- 必须展示 `STARWORK:MULTIAGENT_MESSAGE` 协议正文。

### 4.2 不用命令解释流程，用用户收益解释流程

对用户说：

```text
我先检查这个项目是否准备好，这一步只读取信息，不会改文件。
```

不要先说：

```text
我会运行 starwork doctor --json。
```

Skill 可以在内部执行 CLI 或标准线程工具，但用户默认只需要知道：

- 这一步会不会改文件。
- 这一步是为了确认什么。
- 下一步是否需要用户确认。
- 当前结果意味着什么，不意味着什么。

### 4.3 写入前必须有预览承诺

所有 MultiAgent 写入动作前，Skill 必须让用户理解：

```text
下面是预览，还不会真正写入。
```

写入动作包括：

- 初始化多 AI 协作记录。
- 新增 AI 岗位。
- 绑定当前或新建 AI 会话。
- 登记共享成果。
- 记录跨岗位交接请求。

只读检查可以直接执行，但执行前仍应说明“只读取，不写入”。

### 4.4 不自动套模板

Skill 可以给少量示例帮助用户理解如何拆分 AI 岗位，但不得把内容创作、课程制作、产品开发、资料整理等示例做成默认模板或固定选择器。

正确方式：

```text
如果你还没想好怎么分工，我可以先举几个例子帮你找感觉。
这些只是参考，我会根据你当前项目重新设计，不会直接套模板。
```

错误方式：

```text
请选择模板：1. 内容创作 2. 课程制作 3. 产品开发 4. 资料整理
```

### 4.5 成功不等于完成任务

必须稳定区分：

| 状态 | 可以说 | 不可以说 |
| --- | --- | --- |
| 岗位已创建 | 已经创建了 AI 岗位 | Agent 已经开始工作 |
| 会话已绑定 | 这个岗位已经有对应 AI 会话 | 任务已经完成 |
| 消息已送达 | 交接消息已发送给目标会话 | 目标会话已经完成任务 |
| 目标已完成 | 目标会话已回报完成，或 worklog/shared output 有明确完成证据 | 只因消息已发送就说完成 |

## 5. 用户入口与首屏设计

### 5.1 创建 AI 团队

触发语义：

- 帮我创建多个 Agent。
- 开启 MultiAgent。
- 创建 AI 团队。
- 给这个项目拆几个智能体。
- 让产品、开发、验收几个 Agent 分工。

第一屏必须先解释用户能听懂的概念：

```text
可以。我会先帮你把这个项目拆成几个清楚的 AI 岗位。

每个岗位会有三件事：
1. 它负责什么；
2. 它可以整理或修改哪些内容；
3. 它完成后要怎么交接。

我会按这个顺序来：
1. 先检查当前项目是否准备好；
2. 再给你设计岗位方案；
3. 先预览要写入的协作记录；
4. 等你确认后再正式创建。

检查和预览阶段不会改你的项目文件。
```

第一屏不得出现：

```text
lane
write_scope
binding
thread
CLI
doctor
multiagent init
multiagent add
```

### 5.2 初始化多 AI 协作层

当用户明确说“初始化 multiagent / Agent Lanes / 多 Agent 协作层”时，仍然用用户语言复述：

```text
我会为这个项目建立一份多 AI 协作记录。它用来记录每个 AI 岗位负责什么、可以整理哪些内容、以及和其他岗位怎么交接。

我会先检查项目状态，再给你看预览。确认前不会写入。
```

如果用户使用了 `lane` 等内部词，Skill 可以沿用用户词，但仍要补一句用户语言解释。

### 5.3 绑定当前会话

触发语义：

- 把当前会话设成产品 Agent。
- 以后让这个会话负责验收。
- 这个会话绑定到 development。

用户说明：

```text
我可以把当前这个 AI 会话登记成一个长期岗位。以后你就可以说“让验收助手继续处理”，而不是每次从头解释。
```

如果拿不到当前会话 ID：

```text
我现在无法自动识别这个会话的标识。没关系，我们可以先创建岗位，稍后再绑定；也可以由你提供当前 AI 工具里的会话标识。
```

不得一上来问：

```text
请提供 codex:<thread-id>。
```

### 5.4 跨岗位交接

触发语义：

- 让开发 Agent 开始实现。
- 通知运营 Agent 写发布文案。
- 让验收助手检查这个输出。

用户说明：

```text
我会把这条任务整理成一段交接消息，发送给对应的 AI 岗位，并记录在项目协作记录里。

这表示消息送达了，不表示对方已经完成任务。需要的话，我可以接着帮你查看它的进展。
```

### 5.5 查看进展

触发语义：

- 看看开发 Agent 做到哪了。
- 运营 Agent 有没有回复。
- 那个岗位完成了吗？

用户说明：

```text
我会同时看两部分：这个 AI 会话最近的状态，以及项目协作记录里有没有正式进展。
```

不得只读 thread 后就把最近对话当作项目事实源。必须继续区分 worklog、shared output 和会话观察。

## 6. 信息采集方式

### 6.1 创建团队时只问自然问题

如果用户没有给出岗位方案，Skill 先问：

```text
这个项目主要想完成什么？
你希望哪些事情交给不同 AI 分开做？
有没有哪些文件或内容不希望 AI 主动修改？
```

不要问：

```text
lane id 是什么？
purpose 是什么？
write_scope 怎么填？
```

Skill 根据用户回答生成内部字段：

| 用户回答 | Skill 内部转换 |
| --- | --- |
| “帮我做产品规划” | 岗位名：产品规划助手；lane id 可派生为 `product-planning` |
| “不要改代码” | 写入范围排除 `product/cli/**`、`product/core/**` 等代码区 |
| “只负责文案” | 写入范围限于 docs、drafts 或用户指定文案目录 |

### 6.2 用户不知道怎么拆时给启发，不给模板选择器

如果用户说“不知道怎么分工”，Skill 可以说：

```text
没关系。我可以先按你的项目类型给一个初版。
你告诉我这是内容创作、课程制作、产品开发，还是资料整理项目？
```

随后给 2 到 4 个示例岗位，并明确：

```text
这些只是帮助你理解拆法，我会根据这个项目重新设计，不会直接套模板。
```

### 6.3 一次只追问必要信息

如果缺少多个信息，优先问最能决定方案的问题：

1. 项目目标。
2. AI 希望分担的工作类型。
3. 禁止主动修改的范围。

不要一次抛出内部字段表单。

## 7. 预览设计

### 7.1 岗位方案预览

创建或调整岗位前，Skill 必须用表格预览：

| AI 岗位 | 负责什么 | 可以整理或修改的范围 | 交接方式 |
| --- | --- | --- | --- |
| 调研助手 | 整理资料和用户痛点 | 调研笔记、资料区 | 共享调研摘要 |
| 写作助手 | 写初稿和改表达 | 草稿、文档区 | 提交草稿给检查助手 |
| 检查助手 | 检查事实和风险 | 检查记录 | 给出修改建议 |

表格后必须加确认句：

```text
如果这个方案没问题，我再创建这些协作记录。
```

### 7.2 写入影响预览

在执行写入前，用用户语言列出会写入什么：

```text
下面是预览，还不会真正写入。

准备写入：
- 多 AI 协作记录；
- 每个岗位的工作记录入口；
- 每个岗位的过程工作区。

不会改动：
- 你的业务代码；
- 现有正式文档内容；
- 其他未授权目录。
```

如果实际会修改正式文件，必须更明确：

```text
这一步会修改以下文件：
- <path>

修改目的：
- <purpose>

确认后我再继续。
```

### 7.3 只创建岗位但未创建独立会话

如果用户只确认创建岗位，或标准线程工具不可用，汇报必须说：

```text
我已经先把岗位方案记录好了，但还没有为每个岗位创建独立 AI 会话。

你可以选择：
1. 现在继续创建独立会话；
2. 先只保留岗位方案，等需要时再绑定具体会话。
```

## 8. 执行与汇报

### 8.1 创建成功汇报

完整创建并绑定后：

```text
已经创建好了。

现在这个项目里有 3 个 AI 岗位：
1. 调研助手：负责资料和用户痛点；
2. 写作助手：负责草稿和表达；
3. 检查助手：负责事实、风险和清晰度。

这些岗位已经记录到项目协作记录里；其中已成功创建独立会话的岗位，可以直接接收任务。

下一步你可以直接说：
“请让调研助手先整理这个主题的用户痛点。”
```

### 8.2 交接成功汇报

消息发送成功后：

```text
交接消息已经发送给写作助手，并且已记录在项目协作记录里。

这表示消息送达了，不表示写作助手已经完成任务。
我可以接着帮你查看它的进展。
```

### 8.3 查看进展汇报

查看结果必须分块：

```text
我看到三类信息：

1. AI 会话最近状态：<summary>
2. 岗位工作记录：<worklog summary>
3. 共享成果：<shared output summary>

目前可以确认的是：<confirmed facts>
还不能确认的是：<unknowns>
```

不要把“最近会话有回复”直接解释成“任务已完成”。

## 9. 降级与安全感

### 9.1 当前目录不是 StarWork 工作台

不要输出内部错误后停住。应说：

```text
我还不能确认这个目录已经适合开启多 AI 分工。

为了避免写错位置，我建议先完成项目接入检查。这个过程会先预览，不会直接改文件。
```

然后引导切换到 `starworkInit`，但要讲清楚这是安全接入，不是突然换任务。

### 9.2 AI 入口文档仍是待整合草稿

如果 doctor 显示 `pending_merge`：

```text
这个项目的 AI 入口文档还在待确认状态。为了避免不同 AI 读到不一致的规则，我建议先把入口文档整合好，再创建多 AI 分工。
```

然后转入 `starworkInit`。

### 9.3 自动线程工具不可用

不要说：

```text
send_message_to_thread 不可用，manual_handoff_required。
```

应说：

```text
当前这个 AI 工具暂时不能自动把消息送到另一个会话。

我会换成更稳妥的方式：生成一段交接消息，让你复制给目标 AI 会话。
这样项目记录仍然清楚，也不会误以为任务已经自动完成。
```

随后展示完整 `STARWORK:MULTIAGENT_MESSAGE`。

### 9.4 交接消息只生成未送达

必须明确：

```text
这段交接消息已经准备好，但还没有自动送达。
```

不得说：

```text
已通知目标 Agent。
```

## 10. 与 v0.8 调用边界的关系

v0.9 只改变用户交互层，不改变 v0.8 的工具边界。

继续保留：

- Codex App 创建会话：`create_thread`。
- Codex App 发送消息：`send_message_to_thread`。
- Codex App 读取会话：`read_thread` / `list_threads`。
- Codex App 改名、置顶、归档：`set_thread_title` / `set_thread_pinned` / `set_thread_archived`。
- StarWork 项目事实源：`multiagent status --target`、`multiagent add`、`multiagent bind`、`multiagent share`、`multiagent request record`。

继续禁止：

- 在 Codex App 正常路径中调用 `starwork multiagent instruct`。
- 在 Codex App 正常路径中调用 `starwork multiagent launch`。
- 为生成消息模板调用 `multiagent message instruct` / `multiagent message launch`。
- 用 CLI `read --host codex` / `status --host codex` 观察 Codex thread。
- 用 CLI 参数模拟改名、置顶或归档。

## 12. 验收标准

### 12.1 第一屏禁用内部词

对 `product/skills/starworkMultiagent/SKILL.md` 的“创建 AI 团队 / 初始化多 Agent”第一屏文本做测试或扫描，用户可见第一屏不得包含：

```text
lane
write_scope
binding
thread
CLI
doctor
multiagent init
multiagent add
```

允许这些词出现在后续“内部调用边界”“开发验收”“协议消息格式”段落，但不得出现在推荐给用户的第一屏话术中。

建议测试方式：

- 在测试中抽取第一屏代码块或第一屏段落。
- 对该段落执行 `doesNotMatch`。
- 同时确认包含 `AI 岗位`、`负责什么`、`整理或修改哪些内容`、`交接`、`先检查`、`先预览`、`确认后`。

### 12.2 用户语言映射必须存在

Skill 必须包含用户语言映射，至少覆盖：

```text
AI 岗位
当前 AI 会话
可以整理或修改的范围
把这个会话登记到某个岗位
共享给其他 AI 的成果
交接消息
先预览，不真正写入
```

这些词必须用于主流程说明，而不是只出现在附录。

### 12.3 创建团队追问不得索要内部字段


```text
这次只写入了协作记录，没有改你的业务内容。
```

如果涉及正式文件修改，必须要求先列出文件、目的并等用户确认。

### 12.6 非 StarWork 目录引导必须自然切换

当 `doctor` 判断目标不是 StarWork 工作台时，Skill 不得只展示内部错误或直接抛命令。必须说清：

- 还不能确认目录适合开启多 AI 分工。
- 为避免写错位置，建议先做项目接入检查。
- 接入检查先预览，不直接改文件。
- 后续交给 `starworkInit`。

### 12.7 自动工具不可用时不得像失败

当 `send_message_to_thread` / `create_thread` / `read_thread` 不可见或失败时，Skill 必须用用户语言说明：

```text
当前这个 AI 工具暂时不能自动完成这一步。
我会换成更稳妥的方式：生成一段交接消息，让你复制给目标 AI 会话。
```

同时必须展示完整可复制 `STARWORK:MULTIAGENT_MESSAGE`，并明确：

```text
这段交接消息已经准备好，但还没有自动送达。
```

不得说：

```text
已通知
已发送成功
目标已经开始处理
```

### 12.8 成功状态必须分层

Skill 必须明确区分：

- 岗位已创建。
- 会话已绑定。
- 消息已送达。
- 目标任务已完成。

测试可扫描以下关键句或等价表达：

```text
这表示消息送达了，不表示
不表示已经完成
可以接着帮你查看它的进展
```

### 12.9 第一次使用提示词必须存在

用户说“怎么用”或“安装后怎么开始”时，Skill 或用户文档必须给出可复制提示词：

```text
请帮我看看当前项目适不适合开启多 AI 分工。
先不要写入，只帮我设计 3 个岗位，并说明每个岗位负责什么、可以整理哪些内容、怎么交接。
```

不得优先展示一组 CLI 命令作为第一次使用入口。

### 12.10 不得内置固定岗位模板

Skill 可以包含示例：

- 内容创作：选题调研助手、初稿写作助手、审稿检查助手、发布整理助手。
- 课程制作：课程策划助手、案例整理助手、讲稿写作助手、学员视角检查助手。
- 产品开发：产品规划助手、开发实现助手、验收检查助手、发布说明助手。
- 资料整理：收集助手、分类整理助手、总结沉淀助手、复查助手。

但必须明确示例只用于启发，不作为固定模板。

禁止：

- “默认创建产品、开发、验收三个岗位”。
- “请选择模板编号”。
- 在用户未提供项目目标时直接创建固定岗位。

### 12.11 v0.8 禁止项仍必须通过

v0.9 完成后，v0.8 的禁止项扫描仍必须通过：

```bash
rg -n "starwork multiagent instruct|starwork multiagent launch|multiagent message instruct|multiagent message launch|multiagent read --host codex|multiagent status --host codex|--session-name|--pin" product/skills/starworkMultiagent/SKILL.md
```

不得有命中。

### 12.12 文档一致性验收

扫描：

```bash
rg -n "第一次|怎么用|创建 AI 团队|AI 岗位|交接消息|先预览" product/skills/starworkMultiagent/SKILL.md product/skills/starworkMultiagent-spec.md product/docs/multiagent-user-guide.md product/docs/alpha-test-guide.md product/docs/cli-skill-registry.html
```

必须能看到 v0.9 用户语言。

再扫描：

```bash
rg -n "直接运行 starwork multiagent instruct|直接运行 starwork multiagent launch|请输入 lane id|请输入 write_scope" product/skills product/docs product/planning/features/multiagent
```

用户指南、Skill 主流程和当前 planning 文档不得把这些作为推荐路径。

### 12.13 回归测试命令

## 13. 关闭标准

`ISSUE-021` 只有在以下全部满足后才能关闭：

1. `starworkMultiagent` 第一屏使用“AI 岗位 / 负责什么 / 可以整理或修改哪些内容 / 交接 / 先预览 / 确认后”这组用户语言。
2. 创建团队流程先自然采访项目目标和限制，不索要内部字段。
3. 创建或调整岗位前有表格预览和确认句。
4. 非 StarWork 目录和平滑转入 `starworkInit`，不抛内部错误。
5. 自动工具不可用时使用人工交接解释，不把能力差异说成失败。
6. 成功汇报明确区分岗位、会话、消息送达和任务完成。
7. 用户文档提供第一次使用提示词，不以 CLI 命令作为小白第一入口。
8. 不引入固定岗位模板或默认团队。
9. v0.8 Skill / CLI 最小边界扫描继续通过。
10. development lane 回报修改清单、测试命令和关键扫描结果，product-planning 复验通过。
