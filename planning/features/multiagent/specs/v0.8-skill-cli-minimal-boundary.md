- 日期：2026-06-13

- 关联问题：`product/planning/issues/ISSUE-020.md`
- 关联 GitHub Issue：<https://github.com/jennie-shawn/StarWork/issues/8>
- 影响模块：

## 2. 背景

`ISSUE-020` 暴露了一个产品边界问题：用户在 Codex App 中已经有目标 lane 绑定到 `codex:<threadId>`，但执行 `starwork multiagent instruct` 仍返回 `manual_handoff_required`。这不是单个 CLI bug，而是 Skill 与 CLI 边界还不够干净：

- CLI 是普通 Node 进程，不能调用 Codex App 当前会话暴露的 `send_message_to_thread`。
- Codex App Skill 可以调用标准线程工具，但当前 `starworkMultiagent` 的流程仍保留了“先用 CLI 生成 message / instruct，再由 CLI 降级”的惯性。
- 结果是明明宿主工具可用，用户却被带回手动复制粘贴。

奥卡姆剃刀下，本版只保留一条规则：

```text
CLI 只做 StarWork 项目内事实源账本。
Skill 直接做 Codex 宿主会话动作。
```

也就是说，CLI 不再参与 Codex thread 的创建、投递、读取、改名、置顶或归档；Skill 也不再为了生成消息模板而绕 CLI。

## 3. 一句话目标

让 `starworkMultiagent` 在 Codex App 正常路径中完全绕开不必要的 CLI 子命令，直接调用 Codex 标准线程工具；CLI 只在需要读写 StarWork 项目事实源时出现。

## 4. 核心原则

### 4.1 CLI 是账本，不是动作执行者

CLI 负责项目目录内的持久事实：

- 当前目录是不是 StarWork 工作台。
- 有哪些 lane。
- 每个 lane 的职责、写入范围、worklog、workspace。
- 每个 lane 绑定哪个宿主 session。
- 哪些输出被登记为 shared output。
- 哪些 cross-lane request 已记录，真实投递状态是什么。

CLI 不负责 Codex App 宿主动作：

- 不创建 Codex thread。
- 不向 Codex thread 发消息。
- 不读取 Codex thread。
- 不改 Codex thread 标题。
- 不置顶或归档 Codex thread。
- 不通过 app-server、turn/start、thread/resume 或其他低层方式模拟 Codex App 标准工具。

### 4.2 Skill 是 Codex 宿主动作执行者

在 Codex App 中，`starworkMultiagent` 必须直接调用：

| 宿主动作 | 标准工具 |
|---|---|
| 创建新 Agent 会话 | `create_thread` |
| 向已绑定 lane 投递指令 | `send_message_to_thread` |
| 读取目标 lane 会话 | `read_thread` |
| 查找或确认历史会话 | `list_threads` |
| 设置标题 | `set_thread_title` |
| 置顶 / 取消置顶 | `set_thread_pinned` |
| 归档 / 取消归档 | `set_thread_archived` |

这些动作不能通过 CLI 间接触发，也不能先让 CLI 产生 `manual_handoff_required` 后再由 Skill 补救。

### 4.3 Message 由 Skill 组装，CLI 模板只保留为兼容辅助

`STARWORK:MULTIAGENT_MESSAGE` 是协议格式，不必由 CLI 生成。

在 Codex App 正常路径中：

- Skill 直接根据 lane、from/to、request id、message body 和 write scope 组装 Launch / Instruction Message。
- Skill 发送成功后，用 CLI `request record` 记录真实投递状态。
- CLI `multiagent message launch` / `multiagent message instruct` 只保留为非 Codex 宿主、手动 handoff、测试 fixture 或 legacy 辅助，不再是 Skill 正常路径的一环。

## 5. CLI 使用白名单

`starworkMultiagent` Skill 中只允许把 CLI 用于以下场景。

### 5.1 `starwork doctor`

用途：

- 判断目标目录是不是 StarWork 工作台。
- 判断 AI 入口文档是否 `pending_merge`。
- 阻止在未接入或未完成入口整合的目录中创建 MultiAgent 状态。

允许示例：

```bash
starwork doctor --target <path> --json
starwork doctor --target <path> --host <host> --json
```

### 5.2 `starwork multiagent init`

用途：

- 创建 MultiAgent 协作层文件。
- 只在用户明确要初始化协作层或创建团队且协作层不存在时使用。

允许示例：

```bash
starwork multiagent init --target <path> --dry-run
starwork multiagent init --target <path> --yes
```

### 5.3 `starwork multiagent add`

用途：

- 创建或更新 lane 的稳定职责、写入范围、worklog 和 workspace 记录。
- 只处理项目内 lane 事实，不创建宿主会话。

允许示例：

```bash
starwork multiagent add <lane> --purpose "<purpose>" --write "<scope>" --target <path> --dry-run
starwork multiagent add <lane> --purpose "<purpose>" --write "<scope>" --target <path> --yes
```

### 5.4 `starwork multiagent bind`

用途：

- 在 `create_thread` 成功或用户提供现有 session 后，把 `codex:<threadId>` 写入 lane binding。
- 只记录绑定，不做改名、置顶或宿主动作。

允许示例：

```bash
starwork multiagent bind <lane> --session codex:<threadId> --target <path> --yes
```

禁止：

```bash
starwork multiagent bind <lane> --session-name "<name>"
starwork multiagent bind <lane> --pin
```

`--session-name` 和 `--pin` 这类宿主动作必须由 Skill 直接调用标准工具。

### 5.5 `starwork multiagent release`

用途：

- 从 StarWork lane state 中释放当前 binding。
- 如需归档 Codex thread，应先由 Skill 直接调用 `set_thread_archived`。

允许示例：

```bash
starwork multiagent release <lane> --target <path> --yes
```

### 5.6 `starwork multiagent status --json`

用途：

- 读取 StarWork lane binding、write scope、worklog、workspace、shared outputs 和 request 状态。
- 作为 Skill 调用宿主工具前的项目事实查询入口。

允许示例：

```bash
starwork multiagent status --target <path> --json
```

### 5.7 `starwork multiagent share`

用途：

- 把正式输出登记到 `shared.md`。
- 只写项目内共享索引，不向其他 thread 发送消息。

允许示例：

```bash
starwork multiagent share --from <lane> --title "<title>" --path "<path>" --audience <lane|all> --target <path> --yes
```

### 5.8 `starwork multiagent request record`

用途：

- 在 Skill 真实完成或失败一次跨 lane 投递后，记录投递状态。
- 这是 Codex App 正常投递路径中唯一必须保留的 CLI “收尾”命令。

允许示例：

```bash
starwork multiagent request record \
  --from <from-lane> \
  --to <to-lane> \
  --message "<user intent summary>" \
  --host-delivery delivered_via_codex_thread_tool \
  --delivery-tool send_message_to_thread \
  --target <path> \
  --yes
```

若 CLI 当前还不支持 `delivered_via_codex_thread_tool`，development lane 需要扩展允许状态；不要继续用含糊的 `delivered` 掩盖投递来源。

## 6. CLI 禁用清单

以下命令不得出现在 `starworkMultiagent` Skill 的 Codex App 正常路径中。

### 6.1 禁用：`starwork multiagent instruct`

原因：

- 它会让普通 CLI 进程尝试判断宿主投递能力。
- 在 Codex App 中这必然绕远，并容易返回 `manual_handoff_required`。
- Skill 已经有 `send_message_to_thread`，无需 CLI instruct。

替代：

```text
Skill 读取 status
-> Skill 组装 Instruction Message
-> send_message_to_thread(threadId, message)
-> starwork multiagent request record ...
```

### 6.2 禁用：`starwork multiagent launch`

原因：

- 创建 Codex thread 是宿主动作。
- Skill 必须直接调用 `create_thread`。

替代：

```text
Skill 创建 / 确认 lane
-> Skill 组装 Launch Message
-> create_thread(prompt = message)
-> set_thread_title / set_thread_pinned
-> starwork multiagent bind ...
```

### 6.3 禁用：`starwork multiagent message instruct`

原因：

- 生成 Instruction Message 不需要启动 CLI。
- 继续保留该命令会让 Skill 流程看起来仍依赖 CLI 投递链路，容易回到 ISSUE-020。

替代：

- Skill 内直接渲染 `STARWORK:MULTIAGENT_MESSAGE v1`。
- 渲染格式以本 SPEC 第 8 节为准。

### 6.4 禁用：`starwork multiagent message launch`

原因：

- 生成 Launch Message 不需要启动 CLI。
- `session_name` 可以由 Skill 根据 lane display name 生成，或从 lane state / user confirmation 得到。

替代：

- Skill 内直接渲染 Launch Message。
- 会话标题仍必须短标题：`<职责名> Agent`。

### 6.5 禁用：CLI 读取 Codex thread

禁用形式：

```bash
starwork multiagent read --host codex
starwork multiagent status --host codex
```

原因：

- Codex thread 观察是宿主动作。
- Skill 应直接调用 `read_thread` / `list_threads`。

说明：

- `multiagent status --json` 仍允许用于读取 StarWork binding。
- 禁止的是让 CLI 去观察 Codex thread。

### 6.6 禁用：CLI 触发宿主 UI 状态

禁用形式：

```bash
starwork multiagent bind --session-name ...
starwork multiagent bind --pin
starwork multiagent archive ...
```

替代：

- `set_thread_title`
- `set_thread_pinned`
- `set_thread_archived`
- 然后用 CLI 只记录 StarWork binding 或 release。

## 7. Codex App 正常流程

### 7.1 发送指令

用户说：

```text
让 development Agent 开始实现这个 spec
通知产品规划 Agent 复验
```

Skill 必须执行：

1. 用 CLI 读取 StarWork 状态：

```bash
starwork multiagent status --target <path> --json
```

2. 找到目标 lane 的 `codex:<threadId>`。
3. 直接组装 Instruction Message。
4. 调用：

```text
send_message_to_thread(threadId, message)
```

5. 发送成功后记录：

```bash
starwork multiagent request record \
  --from <from-lane> \
  --to <to-lane> \
  --message "<summary>" \
  --host-delivery delivered_via_codex_thread_tool \
  --delivery-tool send_message_to_thread \
  --target <path> \
  --yes
```

6. 对用户说：

```text
已投递到 <lane> 的 Codex 会话，并已记录 StarWork request。
```

不得说目标任务已完成。

### 7.2 创建 Agent 会话

用户说：

```text
创建 development Agent
帮我创建产品、开发、验收三个 Agent
```

Skill 必须执行：

1. `doctor` 确认工作台健康。
2. 必要时 `multiagent init` / `multiagent add` 写入 lane 事实。
3. 直接组装 Launch Message。
4. 调用 `create_thread(prompt = launchMessage)`。
5. 用 `set_thread_title(threadId, "<职责名> Agent")` 设置短标题。
6. 如需要置顶，用 `set_thread_pinned(threadId, true)`。
7. 用 `multiagent bind` 记录 `codex:<threadId>`。

只有 `create_thread` 成功且 `bind` 成功，才能说 Agent 已创建并绑定。

### 7.3 查看 Agent 状态

用户说：

```text
看看 development Agent 做到哪了
```

Skill 必须执行：

1. `multiagent status --json` 读取 lane binding。
2. 若是 `codex:<threadId>`，直接调用 `read_thread`。
3. 汇总 thread 状态、recent turns、lane worklog 和 shared outputs。

不得用 CLI Codex host read/status 路径替代 `read_thread`。

### 7.4 绑定当前会话

用户说：

```text
把当前会话绑定为 product-planning
```

Skill 必须执行：

1. 确认当前 thread id。
2. 如 lane 不存在，用 `multiagent add` 建 lane。
3. 如需改名，调用 `set_thread_title`。
4. 如需置顶，调用 `set_thread_pinned`。
5. 用 `multiagent bind` 记录 session。

CLI 不得负责改名或置顶。

### 7.5 归档或释放 Agent

用户说：

```text
归档这个 Agent
释放 development lane
```

Skill 必须执行：

1. 如需归档 Codex thread，调用 `set_thread_archived(threadId, true)`。
2. 如需释放 StarWork binding，用 `multiagent release`。

CLI 不得触发 Codex archive。

## 8. Skill-owned Message 格式

Skill 渲染消息时必须使用固定包裹格式：

```markdown
<!-- STARWORK:MULTIAGENT_MESSAGE v1 -->

# StarWork MultiAgent Instruction

message_type: instruction
request_id: <REQ-id>
from_lane: <from-lane>
to_lane: <to-lane>
created_at: <ISO timestamp>
recorded_in: _系统/协作/shared.md

## 消息内容

<用户要转交给目标 lane 的完整任务内容>

## 边界

- 只在你的 write_scope 内主动修改：<target lane write_scope>
- 如需修改 write_scope 之外的文件，先在 _系统/协作/shared.md 记录请求或在回复中说明需要授权。
- 不要修改与本任务无关的文件。
- 当前工作区：<absolute workspace path>

## 完成后请回报

1. 更新你的 lane worklog：<target lane worklog>
2. 如有正式输出，登记到 _系统/协作/shared.md 的 Shared Outputs。
3. 如需验收，向 <from-lane> 发送回传指令或在回复中明确说明。

<!-- /STARWORK:MULTIAGENT_MESSAGE -->
```

Launch Message 可使用同一外壳，但 `message_type` 为 `launch`，正文必须包含：

- lane id。
- lane purpose。
- write scope。
- worklog path。
- workspace path。
- 当前项目路径。
- 启动后先读的上下文文件。

Message 渲染可以由 Skill 文本模板维护，也可以由产品代码中的纯函数导出给测试使用；但 Codex App 正常路径不得为了渲染 message 调用 CLI。

## 9. CLI 状态扩展

### 9.1 `request record` 状态

需要支持或确认支持：

| 状态 | 含义 |
|---|---|
| `delivered_via_codex_thread_tool` | Skill 已调用 `send_message_to_thread` 并成功返回 |
| `recorded_only` | 只记录 request，未尝试宿主投递 |
| `manual_handoff_required` | 宿主工具不可用或调用失败，需要人工复制 |
| `failed` | 尝试投递但失败，且不能安全视为手动转交 |

旧状态 `delivered` 可以保留兼容，但 Codex App 正常路径必须使用更具体的 `delivered_via_codex_thread_tool`。

### 9.2 记录字段

`request record` 至少应记录：

- request id。
- from lane。
- to lane。
- user intent summary。
- host delivery status。
- delivery tool：`send_message_to_thread`。
- target session：`codex:<threadId>`。
- timestamp。

如果现有 CLI 不支持 target session 字段，本版可以先不强制 schema 扩展，但回报中要说明当前记录里如何追踪投递对象。

## 10. 失败与降级

### 10.1 目标 lane 未绑定

Skill 不得调用 `starwork multiagent instruct`。

应输出：

```text
目标 lane 还没有绑定可投递的会话。下一步可以绑定已有 Codex 会话，或创建新的 <lane> Agent。
```

然后根据用户选择走 bind 或 create_thread。

### 10.2 目标 session 不是 Codex

Skill 不得假装自动投递。

应按 Host Adapter 能力处理：

- Cursor / Trae / Claude Code 没有等价标准投递工具时，输出人工 handoff。
- 可以生成可复制 `STARWORK:MULTIAGENT_MESSAGE`，但不调用 CLI instruct。

### 10.3 Codex thread tool 不可见

Skill 应先用工具发现能力查找。

仍不可见时：

- 不调用 CLI instruct。
- 不调用 app-server 低层接口。
- 输出 `manual_handoff_required`。
- 展示完整可复制 message。
- 可用 CLI `request record` 记录 `manual_handoff_required`，但必须说明“未自动送达”。

### 10.4 `send_message_to_thread` 调用失败

Skill 应：

1. 不说已通知。
2. 输出错误摘要和手动复制消息。
3. 用 CLI `request record` 记录 `manual_handoff_required` 或 `failed`。

## 12. 验收标准

### 12.1 Skill 文本扫描：禁止项必须消失

对 `product/skills/starworkMultiagent/SKILL.md` 执行扫描。

以下命令不得有命中：

```bash
rg -n "starwork multiagent instruct|starwork multiagent launch|multiagent message instruct|multiagent message launch|multiagent read --host codex|multiagent status --host codex|--session-name|--pin" product/skills/starworkMultiagent/SKILL.md
```

允许命中仅限本 SPEC、测试文件或历史文档中明确标注为“禁用 / legacy / 不得使用”的段落；`product/skills/starworkMultiagent/SKILL.md` 中不允许出现这些命令字符串。

### 12.2 Skill 文本扫描：允许项必须存在

`product/skills/starworkMultiagent/SKILL.md` 必须明确出现以下能力或命令：

```bash
rg -n "send_message_to_thread|create_thread|read_thread|set_thread_title|set_thread_pinned|set_thread_archived|request record|multiagent status --target|multiagent bind|multiagent add|multiagent share" product/skills/starworkMultiagent/SKILL.md
```

每个关键项都要有命中，且语义必须是正常路径，不是只出现在禁止说明里。

### 12.3 Codex App instruct 正常路径验收

场景：

- 当前在 Codex App。
- `development` lane 已绑定 `codex:<threadId>`。
- `send_message_to_thread` 工具可用。

期望流程：

1. Skill 调用 `starwork multiagent status --target <path> --json` 读取绑定。
2. Skill 自己组装 Instruction Message。
3. Skill 调用 `send_message_to_thread(threadId, message)`。
4. Skill 调用 `starwork multiagent request record ... --host-delivery delivered_via_codex_thread_tool --delivery-tool send_message_to_thread`。
5. 用户看到“已投递到目标会话，并已记录 StarWork request”。

禁止：

- 不得调用 `starwork multiagent instruct`。
- 不得调用 `starwork multiagent message instruct`。
- 不得出现 `manual_handoff_required`。

验收方式：

- 使用真实 Codex thread smoke，或用可注入 mock 记录 Skill 计划中的工具调用序列。
- 如果当前测试框架无法自动观察 Skill 工具调用，至少补一条文档/Skill 扫描测试和一次真实人工 smoke 记录。

### 12.4 Codex App launch 正常路径验收

场景：

- 用户要求创建一个新 lane Agent。
- `create_thread` / `set_thread_title` 可用。

期望流程：

1. 必要时 CLI `doctor`、`multiagent init`、`multiagent add`。
2. Skill 自己组装 Launch Message。
3. Skill 调用 `create_thread`。
4. Skill 调用 `set_thread_title(threadId, "<职责名> Agent")`。
5. Skill 用 `multiagent bind` 记录 `codex:<threadId>`。

禁止：

- 不得调用 `starwork multiagent launch`。
- 不得调用 `starwork multiagent message launch`。
- 不得由 CLI 改名或置顶。

### 12.5 读取状态验收

场景：

- 用户问“看看 development Agent 做到哪了”。
- lane 绑定 `codex:<threadId>`。

期望流程：

1. Skill 调用 `multiagent status --json` 读取 binding。
2. Skill 调用 `read_thread(threadId)`。
3. 汇总 thread 状态、最近 turn、lane worklog 和 shared outputs。

- 不得调用 `multiagent read --host codex`。
- 不得调用 `multiagent status --host codex` 来观察 Codex thread。

### 12.6 失败降级验收

场景：

- `send_message_to_thread` 不可见或调用失败。

期望：

1. Skill 不调用 CLI instruct。
2. Skill 输出 `manual_handoff_required`。
3. Skill 展示完整 `STARWORK:MULTIAGENT_MESSAGE`。
4. Skill 可调用 `request record` 记录 `manual_handoff_required`。
5. 文案明确“尚未自动送达”，不得说“已通知”。

### 12.7 CLI 状态验收

`starwork multiagent request record` 必须接受：

```text
delivered_via_codex_thread_tool
recorded_only
manual_handoff_required
failed
```

至少补测试：

- `delivered_via_codex_thread_tool` 能写入 shared request / state。
- 非 JSON 输出或状态查询能看出该 request 是通过 `send_message_to_thread` 真实投递。
- 旧 `delivered` 如保留，不能作为 Codex App Skill 正常路径的推荐状态。

### 12.8 文档一致性验收

扫描：

```bash
rg -n "starwork multiagent instruct|starwork multiagent launch|multiagent message instruct|multiagent message launch" product/README.md product/docs product/skills product/planning/features/multiagent
```

验收要求：

- 在用户指南、Skill 正常流程和 README 中，不得把这些命令描述为 Codex App 自动投递 / 创建的推荐路径。
- 如果历史 SPEC 或兼容说明中保留这些字符串，必须明确标注为 legacy、manual fallback、CLI template helper 或禁止项。
- A 测指南必须告诉用户：在 Codex App 中应通过 `starworkMultiagent` Skill 通知 lane，而不是手动运行 `starwork multiagent instruct` 期待自动投递。

## 13. 关闭标准

`ISSUE-020` 只有在以下全部满足后才能关闭：

1. `starworkMultiagent` Skill 的 Codex App instruct 正常路径不再使用 CLI `instruct` 或 `message instruct`。
2. `starworkMultiagent` Skill 的 Codex App launch 正常路径不再使用 CLI `launch` 或 `message launch`。
3. Skill 文本扫描禁止项无命中。
4. CLI `request record` 能记录 `delivered_via_codex_thread_tool`。
5. 已绑定 Codex lane 的真实 smoke 或等价 mock 证明消息无需人工复制即可送达。
6. 宿主工具不可用时仍能安全输出 `manual_handoff_required` 和完整可复制消息。
7. 文档不再误导用户直接运行 CLI 完成 Codex App 自动投递。
8. development lane 回报修改清单、验证命令、真实 smoke / mock 证据后，product-planning 复验通过并更新 `ISSUE-020`。
