# Mainflow v0.1：Init / Doctor 面向 MultiAgent-only 用户的友好起步 SPEC

日期：2026-06-15
状态：accepted
来源请求：REQ-20260615-090828Z-product-mainflow
原始草案：`_系统/协作/lanes/product-mainflow/workspace/init-doctor-friendly-onboarding-spec-draft.md`
晋升 lane：product-lead
关联 issue：`product/planning/issues/ISSUE-023.md`

## 1. 背景

本轮 StarWork 发布以 MultiAgent Skill 为切入点，很多用户不是先完整理解 StarWork Core、Pack、Knowledge、Hub 等全套概念，而是因为“想创建多个 AI 分工协作”才安装：

- StarWork CLI
- `starworkMultiagent`
- `starworkInit`
- `starworkDoctor`

这意味着 `starworkInit` 和 `starworkDoctor` 不只是通用初始化 / 诊断工具，还承担了 MultiAgent 新用户的安全前置体验：

```text
用户想开启多 AI 协作
  ↓
先确认项目是否适合多个 AI 接手
  ↓
缺入口或边界时，用 Init / Doctor 最小补齐
  ↓
再回到 MultiAgent 设计 AI 岗位
```

当前 `starworkMultiagent` 已通过 v0.9 改成“AI 岗位”语言：先解释、再检查、再设计、先预览、确认后执行。Init / Doctor 也需要承接同一体验标准，避免用户在 MultiAgent 流程中被突然带回工程化的 `Core / Pack / Capability / workspace / blueprint / adapter` 语言。

## 2. 一句话目标

让 `starworkInit` 和 `starworkDoctor` 成为 MultiAgent 新用户的“安全接入顾问”：先告诉用户项目现在能不能开启多 AI 协作，再用最少提问补齐项目入口、当前任务和写入边界，且检查和预览阶段明确不改业务内容。

## 3. 产品原则

### 3.1 用户目标是开启多 AI 协作，不是理解 StarWork 全量架构

用户可见主线：

```text
我会帮你确认这个项目是否已经适合多个 AI 分工接手。
如果还差入口说明、当前任务或写入边界，我会先预览准备补哪些协作文件。
确认前不会改业务内容。
```

避免把用户带入：

- Core 是什么
- Pack 怎么选
- Capability 如何安装
- workspace schema 是什么
- blueprint / adapter profile 怎么配置

这些内部概念可以保留为实现能力，但默认不作为小白用户第一层语言。

### 3.2 检查、预览、写入必须分清

| 阶段 | 用户理解 | 文件影响 |
|---|---|---|
| 检查 | 看项目现在是否适合多 AI 接手 | 只读，不改文件 |
| 预览 | 展示准备补哪些协作入口和边界 | 不写入 |
| 写入 | 用户确认后补齐 StarWork 协作文件 | 只写 StarWork 可控文件，不改业务内容 |
| 整合 | 已有 AI 规则文件时，生成并合并待确认草稿 | 用户确认前不覆盖入口规则 |
| 复查 | 确认 AI 后续能读到入口和边界 | 只读检查 |

Skill 每次进入阶段前，都要先说清楚是否会写文件。

### 3.3 成功状态必须分层

MultiAgent v0.9 已区分“岗位创建、会话绑定、消息送达、任务完成”。Init / Doctor 也要区分：

| 状态 | 可以说 | 不可以说 |
|---|---|---|
| 检查完成 | 已看过项目当前入口和边界 | 项目已经接入完成 |
| 工作台骨架已写入 | 已补齐 StarWork 协作文件 | 多 AI 协作已经可用 |
| AI 入口待整合 | 已生成待确认草稿，需要合并 | AI 工具已经会读到最终规则 |
| AI 入口已生效 | 入口规则已写入最终位置并复查通过 | 所有宿主能力都自动可用 |
| MultiAgent preflight 通过 | 适合继续设计 AI 岗位 | 已创建 AI 岗位 |

### 3.4 不内置场景模板

可以用“产品开发 / 内容创作 / 资料整理”等例子帮用户理解，但不得做固定模板选择器。

正确：

```text
如果你还没想好怎么分工，我可以举几个例子帮你找感觉。
这些只是参考，我会根据当前项目重新设计，不会直接套模板。
```

错误：

```text
请选择模板：1. 产品开发 2. 内容创作 3. 资料整理
```

## 4. 用户语言映射

| 内部词 | 用户可见说法 |
|---|---|
| workspace | 项目工作台 / 这个项目的 AI 协作入口 |
| Core | StarWork 工作台规则 |
| Pack | 附加工作结构 / 默认项目结构 |
| Capability | 可选能力 |
| blueprint | 初始化方案 / 升级方案 / 目录方案 |
| adapter / host | 你正在使用的 AI 工具 |
| agent docs | AI 入口说明 |
| pending_merge | 待整合草稿 |
| dry-run | 先预览，不真正写入 |
| strict | 严格检查 |
| checks | 检查项 |
| write_scope | AI 可以整理或修改的范围 |
| lane | AI 岗位 |

内部词只在用户主动追问机制、开发验收、调试输出或文件路径本身必须展示时出现。

## 5. starworkInit 改造要求

### 5.1 新增 MultiAgent-only 入口第一屏

触发场景：

- 用户从 `starworkMultiagent` 回流：当前目录不是 StarWork 工作台。
- 用户说“我要开启多 Agent / 多 AI 分工，但这个项目还没接入”。
- 用户只安装了 MultiAgent 相关 Skill，需要先补齐项目入口。
- `doctor` 发现 AI 入口待整合，MultiAgent 暂停写入。

推荐第一屏：

```text
我先把你带回安全接入这一步。

不是要打断你创建多 AI 分工，而是多个 AI 开始协作前，需要先确认三件事：
1. 这个项目是什么；
2. 当前正在推进什么；
3. 不同 AI 哪些内容能整理，哪些内容不能随便改。

我会先做一份写入预览，只告诉你准备补哪些协作入口和边界。
确认前不会改业务内容，也不会覆盖已有 AI 规则文件。
```

然后只问一个问题：

```text
你现在是想把当前已有项目接入 StarWork，还是新建一个空项目工作台试用？
```

### 5.2 每一步提问前说明目的

Init 现有流程可以保留，但每一步要先说明“为什么问”：

| 步骤 | 目的说明 |
|---|---|
| 新建还是已有项目 | 因为已有项目要保护原文件，新建项目可以直接生成推荐结构 |
| 项目还是项目中心 | 因为单项目和多个项目管理的入口不同 |
| 语言 | 因为目录名和 AI 规则说明会跟着语言变化 |
| 目标路径 | 因为写入前必须确认具体位置，避免改错目录 |
| 是否定制 | 因为默认结构适合快速起步，定制结构适合已有稳定习惯 |
| AI 工具 | 因为 Codex、Claude、Cursor 等工具读取规则的位置不同 |

示例：

```text
现在我先确认目标路径，因为下一步预览会按这个路径计算准备新增或修改哪些文件。
确认前我不会写入。
```

### 5.3 MultiAgent 快速起步默认只做最小必要提问

如果用户目标是“先开启多 AI 协作”，Init 默认不主动展开完整定制采访。

最小必要信息：

1. 目标目录。
2. 新建还是已有项目。
3. 工作台语言。
4. 主要使用的 AI 工具，不确定可跳过。
5. 如已有项目，读取现有入口和生成待整合草稿。

默认不主动询问：

- 知识库。
- 场景 Pack。
- 复杂目录定制。
- 项目中心。
- 多个宿主同时适配。

用户主动要求定制时再进入完整 `starworkInit` 定制流程。

### 5.4 已有项目安全预告强化

已有项目场景，在运行 dry-run 前必须先说明：

```text
我检测到这是已有项目时，会按更保守的方式处理：
- 保留你的业务代码和现有资料；
- 不直接覆盖已有 AGENTS.md、README.md、CLAUDE.md 或其他 AI 规则入口；
- 先生成待整合草稿；
- 让你确认后再合并入口说明。
```

dry-run 复述必须包含：

```text
这是预览，还没有写入文件。

准备新增：
- ...

准备更新：
- ...

不会改动：
- 你的业务代码
- 已有非空 AI 规则文件

需要你确认：
- 目标路径是否正确
- 是否接受这些 StarWork 协作入口
- 是否继续合并待整合草稿
```

### 5.5 AI 入口待整合闭环

已有非空项目或已有 AI 规则文件时，`init --yes` 不是最终完成。Skill 必须继续：

1. 读取 `.starwork/drafts/agent-docs-plan.json`。
2. 读取 proposed 草稿。
3. 读取现有入口规则，例如 `AGENTS.md` / `CLAUDE.md` / Cursor rules。
4. 用人话解释：
   - 现有规则会保留什么；
   - StarWork 建议补什么；
   - 是否有冲突或重复；
   - 合并后哪个 AI 工具会读到哪里。
5. 让用户确认后再写入最终入口。
6. 重新运行 `starwork doctor --host <host>` 或普通 doctor。

用户语言：

```text
工作台骨架已经写入，但 AI 入口还没有最终生效。
因为你的项目已有规则文件，我只生成了待整合草稿，没有直接覆盖。

下一步我会把现有规则和 StarWork 建议放在一起，让你确认后再合并。
```

### 5.6 AI 工具入口适配语言

把“宿主适配”默认表达为：

```text
让你使用的 AI 工具进项目时能先读到 StarWork 规则。
```

推荐话术：

```text
你主要会用哪个 AI 工具打开这个项目？
我只会为你选择的工具准备入口，不会一次性改所有工具的规则。
如果不确定，可以先跳过，之后再补。
```

适配结果分层：

| 状态 | 用户语言 |
|---|---|
| 未选择工具 | 先生成通用工作台，稍后再适配具体 AI 工具 |
| 已生成入口草稿 | 已准备好入口草稿，等待你确认合并 |
| 已写入入口 | 该 AI 工具已经能读到 StarWork 规则 |
| 工具能力有限 | 这个工具需要人工复制交接消息或手动打开目录，不是 StarWork 故障 |

## 6. starworkDoctor 改造要求

### 6.1 新增 MultiAgent preflight 模式

触发场景：

- 用户说“这个项目适不适合开启多 Agent / 多 AI 分工？”
- `starworkMultiagent` 在写入前调用 doctor。
- Init 完成后准备继续创建 AI 岗位。
- 用户只想先检查，不想升级或修复。

Doctor 首屏必须先回答三个问题：

```text
## 多 AI 协作准备度

结论：现在是否适合继续创建 AI 岗位。
文件影响：这次只是检查，不会改项目文件。
下一步：可以继续设计岗位 / 需要先补入口说明 / 需要先确认写入边界。
```

### 6.2 Preflight 检查维度

Doctor 在 MultiAgent preflight 中至少判断：

| 维度 | 用户问题 | 缺失时用户影响 |
|---|---|---|
| 项目背景 | 另一个 AI 能不能看懂这个项目是做什么的？ | 其他 AI 接手时可能要你重新解释项目目标 |
| 当前任务 | 另一个 AI 能不能知道现在正在推进什么？ | 分工后容易不知道先接哪一步 |
| AI 入口 | AI 进来先读哪里？ | 不同 AI 可能读到不一致规则 |
| 草稿 / 正式内容边界 | 哪些是草稿，哪些是确认版？ | AI 可能误改正式成果，或把草稿当最终版 |
| 写入边界 | 哪些内容能整理，哪些要先问？ | 多个 AI 可能互相抢改或改到不该改的文件 |
| 交接位置 | 工作记录和共享成果放哪里？ | 一个 AI 做完后，另一个 AI 不知道看哪里 |
| 宿主入口 | Codex / Claude / Cursor 等是否能读到规则？ | 用户以为已适配，但工具实际读不到入口 |

### 6.3 诊断结论层

Doctor 输出在现有“我看到的事实 / 我推测的角色 / Core 逻辑贴近程度”之前，增加用户一眼看懂的结论层：

```text
## 诊断结论

多 AI 协作准备度：可以继续 / 需要先补入口 / 需要先确认边界 / 不建议继续。

这次是否会改文件：不会，这只是检查。

下一步建议：
- 如果你要创建 AI 岗位：先补齐 ...
- 如果你只是想了解现状：目前主要缺 ...
```

### 6.4 缺失项翻译成用户影响

Doctor 不应只说：

```text
缺少 current-work file。
缺少 workspace state。
缺少 business_work_area。
```

应翻译为：

```text
现在缺少“当前任务入口”。这不代表项目有问题，但另一个 AI 接手时可能不知道你现在要它接哪一步。
```

```text
现在还没有 StarWork 工作台身份证。CLI 还不能稳定判断这个目录的类型和写入边界，所以不建议直接创建多个 AI 岗位。
```

```text
现在草稿和确认版边界还不够清楚。多个 AI 同时协作时，可能把草稿当成最终成果，或误改已经确认的内容。
```

### 6.5 Doctor 不直接修复

MultiAgent preflight 下，Doctor 默认只检查和建议，不生成 upgrade blueprint，不执行修复。

如果用户明确说“帮我补齐 / 修复 / 接入”，再转到：

- `starworkInit`：新建或接入工作台。
- `starworkDoctor` upgrade flow：旧目录升级。
- 后续 repair / upgrade 命令：仅在有明确 dry-run 和用户确认时。

推荐话术：

```text
这一步只是检查，不会改文件。
如果你确认要补齐，我下一步会先展示准备新增或修改哪些 StarWork 协作文件，再等你确认。
```

## 7. CLI / JSON 建议

### 7.1 doctor JSON 可新增 MultiAgent preflight 结构

建议在 `doctor --json` 中增加可选结构，供 Skill 做稳定解释：

```json
{
  "multiagent_preflight": {
    "status": "ready | needs_init | needs_agent_docs_merge | needs_boundaries | blocked",
    "checks": [
      {
        "id": "project_context",
        "status": "ok | warn | missing",
        "user_impact": "另一个 AI 能否看懂项目目标"
      },
      {
        "id": "current_work",
        "status": "ok | warn | missing",
        "user_impact": "另一个 AI 能否知道现在该接哪一步"
      },
      {
        "id": "content_boundaries",
        "status": "ok | warn | missing",
        "user_impact": "草稿和确认版是否分得清"
      },
      {
        "id": "write_boundaries",
        "status": "ok | warn | missing",
        "user_impact": "不同 AI 是否知道哪些内容能改"
      },
      {
        "id": "agent_entry",
        "status": "ok | pending_merge | missing",
        "user_impact": "AI 进项目时是否能读到一致规则"
      }
    ],
    "next_step": "continue_multiagent | run_init | merge_agent_docs | clarify_boundaries | run_doctor_upgrade"
  }
}
```

这不是要求 CLI 做复杂语义判断；CLI 可以先暴露事实和基础状态，Skill 负责最终解释。字段命名可由 development 按现有代码风格调整。

### 7.2 init dry-run JSON 可复用 user_summary

`starwork init --dry-run --json` 已有或建议保留面向 Skill 的 `user_summary`：

```json
{
  "user_summary": {
    "mode": "preview_no_write",
    "target_kind": "existing_project",
    "will_create": [],
    "will_update": [],
    "will_not_touch": [],
    "needs_confirmation": []
  }
}
```

MultiAgent-only 入口下，Skill 必须优先用 `user_summary` 复述，不直接把底层 action 列表原样丢给用户。

## 8. Skill 文案验收

### 8.1 starworkInit 验收

必须满足：

- 有 MultiAgent-only 回流第一屏，说明“为了开启多 AI 协作，先补齐项目入口和边界”。
- 每一步提问前说明目的。
- 预览前明确“不写入”。
- 已有项目说明不覆盖业务代码和已有 AI 规则文件。
- 有 AI 入口待整合状态口径。
- 默认不主动询问知识库、Pack、Capability、复杂定制和多个宿主。

用户可见第一屏和预览话术不得出现：

```text
Core
Pack
Capability
workspace schema
adapter profile
host_native_dirs
rules_entry_status
```

允许文件名中出现 `AGENTS.md`、`CLAUDE.md`、`.starwork/drafts/`，但必须配用户解释。

### 8.2 starworkDoctor 验收

必须满足：

- 有 MultiAgent preflight 输出结构。
- 首屏先回答能否继续开启多 AI 协作、是否改文件、下一步是什么。
- 检查阶段明确只读。
- 缺失项必须翻译成用户影响。
- 不把缺失项说成“项目不合格”。
- 不在用户未确认前生成或执行修复 / upgrade。

### 8.3 文本扫描建议

可在 `product/cli/test/init.test.js` 增加 Skill 文本扫描：

- `starworkInit` 包含：
  - `多 AI 协作`
  - `先预览`
  - `不会改业务内容`
  - `待整合草稿`
  - `AI 入口`

- `starworkDoctor` 包含：
  - `多 AI 协作准备度`
  - `这次只是检查`
  - `不会改项目文件`
  - `另一个 AI`
  - `草稿和确认版`

- 推荐用户第一屏不得出现：
  - `adapter profile`
  - `host_native_dirs`
  - `rules_entry_status`

## 9. 建议开发拆分

### Step 1：Skill 文案层

先改：

- `product/skills/starworkInit/SKILL.md`
- `product/skills/starworkDoctor/SKILL.md`
- `product/skills/starworkInit-spec.md`
- `product/skills/starworkDoctor-spec.md`

目标：不改 CLI 行为，也能明显提升小白路径。

### Step 2：CLI JSON 支撑

如 development 判断需要，再补：

- `doctor --json` 的 `multiagent_preflight` 或等价结构。
- `init --dry-run --json` 的 MultiAgent 起步摘要字段。

### Step 3：文档同步

同步：

- A 测指南。
- MultiAgent 用户指南。
- CLI / Skill 注册表。

## 10. 非目标

本 SPEC 不要求：

- 新增内置业务场景模板。
- 改变 MultiAgent v0.8 / v0.9 的 Skill / CLI 边界。
- 默认安装全套 StarWork Skills。
- 把 Knowledge、Hub、Pack 作为 MultiAgent 起步必选项。
- 自动修复或自动迁移用户项目。
- 在用户未确认前覆盖已有入口规则。

## 11. 开放问题

1. `doctor --json` 是否应该由 CLI 输出 `multiagent_preflight`，还是只增强现有 checks，由 Skill 聚合？
2. MultiAgent-only 起步是否需要一个独立 CLI flag，例如 `starwork doctor --multiagent-preflight`？
3. Init 生成待整合草稿后，是否需要 CLI 提供专门的 merge preview 命令，还是继续由 Skill 读取草稿和现有入口自行合并？
4. Cursor / Trae 等人工宿主限制，是否放入 Init / Doctor 统一话术，还是继续由 MultiAgent Skill 在投递阶段解释？
