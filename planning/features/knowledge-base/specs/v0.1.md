# M2.11 Knowledge Capability SPEC

## 背景

StarWork 早期结构里曾出现 `知识/` 或 `knowledge/`，但它们的产品边界不够清楚：有时像资料夹，有时像共享知识入口，有时又像项目自己的长期记忆。

本轮需求要把知识库重新定义清楚：

> 参考资料是输入，输出是成果，知识库是 Agent 持续维护的长期理解层。

知识库不是基础目录，也不是普通资料堆放区。它是一种可选能力：用户需要长期沉淀理解时，再为项目工作台开启。

## 目标

1. 把知识库定义为可插拔能力，而不是 Project Kit 默认目录。
2. 明确知识库和 `参考资料/`、`输出/`、项目中心共享知识的边界。
3. 明确知识库目录结构，尤其是 `schema.md`、`pages/`、`synthesis/` 的作用和产生机制。
4. 明确 CLI 和 Skill 如何配合创建、检查、整理知识库。
5. 规划 `starworkKnowledge` skill 的一期能力。
6. 规划 CLI、doctor、upgrade、init 和文档需要配合调整的地方。

## 不做什么

本轮暂不做这些事：

- 不做“把项目知识提交到项目中心共享知识库”的流程。
- 不做项目中心共享知识库的审核、合并和分发机制。
- 不强制迁移用户已有的 `知识/` 或 `knowledge/`。
- 不把知识库能力默认装进所有项目。
- 不把知识库当成 Pack 的普通业务目录。
- 不把所有 knowledge 相关业务 Skill 默认装进全局 Agent 环境。

## 进入开发前的收口口径

本 SPEC 进入开发时，按以下口径执行，避免开发过程中继续摇摆。

| 问题 | v0.1 决策 |
|---|---|
| 新知识库路径 | 中文使用 `知识库/`，英文使用 `knowledge-base/`。 |
| 主入口 | 已有项目和新项目都以 `starwork knowledge init` 作为知识库开启主入口。 |
| `init` 关系 | `init --knowledge` 只作为后续便捷入口；v0.1 不要求改造交互式 `init` 主流程。 |
| 全局 Skill | `starworkKnowledge` 是全局入口 Skill，可通过 `npx skills add ...` 单独安装。 |
| 项目内业务 Skill | v0.1 先提供一个项目内业务 Skill：`starworkKnowledgeProject`；后续再按需要拆成 ingest / synthesis / lint 等多个 Skill。 |
| 业务 Skill 安装时机 | 只有项目执行 `starwork knowledge init` 并成功开启知识库后，CLI 才把项目内业务 Skill 装入当前项目。 |
| 旧 `知识/knowledge` | 只识别和暴露事实，不自动迁移、不自动删除、不自动改名。 |
| 项目中心共享知识 | 本轮不做；项目知识提交项目中心另开需求。 |

## 关键风险和防线

| 风险 | 防线 |
|---|---|
| Agent 把原始资料直接塞进知识库 | `schema.md`、`README.md` 和项目内业务 Skill 都必须明确：原始资料留在 Pack 的参考资料区。 |
| CLI 生成内容判断 | CLI 只创建结构、模板、配置和 Skill，不生成主题页正文或综合判断。 |
| Skill 绕过 CLI 手写目录 | `starworkKnowledge` 必须要求 Agent 调用 `starwork knowledge init/apply` 创建结构。 |
| 旧目录被误迁移 | `status` 和 `doctor` 只暴露旧目录信号；迁移必须走 blueprint + 用户确认。 |
| 全局 Skill 过载 | 全局只装入口 Skill；业务 Skill 在项目开启能力后进入当前项目。 |
| `init` 变复杂 | v0.1 不把知识库问题塞进默认 `init` 采访链路。 |

## 核心产品判断

### 判断 1：知识库是能力，不是基础骨架

Project Kit 只应该提供项目工作台的最小骨架，例如 Agent 入口、系统状态、运行配置和 skill 挂载位置。

知识库是否存在，取决于用户是否需要长期积累和复用理解。因此：

```text
项目工作台
+ 知识库能力
= 带长期知识沉淀的项目工作台
```

而不是：

```text
Project Kit 默认包含 知识/
```

### 判断 2：知识库不是参考资料

`参考资料/` 是用户提供的原始材料，例如 PDF、网页、访谈记录、截图、会议纪要、案例库。

知识库是 Agent 整理后的长期理解，例如概念、主题、方法、关系、判断、阶段性总结。

简单区别：

| 目录 | 作用 | 是否需要整理 |
|---|---|---|
| `参考资料/` | 原始输入 | 不一定 |
| `输出/` | 当前项目成果 | 按任务交付整理 |
| `知识库/` | 长期可复用理解 | 必须由 Agent 持续整理 |

### 判断 3：知识库不是项目中心共享知识

项目知识库服务当前项目。

项目中心共享知识服务多个项目。

本轮只设计“项目知识库”。项目知识是否能进入项目中心共享知识，后续另开需求设计。

### 判断 4：知识库要有维护机制

如果只是建一个目录让 Agent 随便写，它很快会变成新的资料堆。

所以知识库必须同时定义：

- 什么内容值得进入知识库。
- 新资料如何吸收。
- 主题页如何更新。
- 综合判断如何形成。
- 索引和维护日志如何更新。
- 哪些内容不能进入知识库。

## 用户侧表达

对用户不要说复杂术语。

推荐表达：

- “开启项目知识库”
- “整理项目知识库”
- “让 AI 把长期有用的内容沉淀下来”
- “检查知识库是否混乱”

避免表达：

- “启用 knowledge capability”
- “执行 ingest / synthesis pipeline”
- “更新知识 schema”

内部文档和代码可以使用 `knowledge capability`，但用户文案应尽量说人话。

## 标准目录结构

中文项目工作台开启知识库后：

```text
知识库/
├── README.md
├── index.md
├── schema.md
├── log.md
├── inbox/
├── sources/
├── pages/
└── synthesis/
```

英文项目工作台开启知识库后：

```text
knowledge-base/
├── README.md
├── index.md
├── schema.md
├── log.md
├── inbox/
├── sources/
├── pages/
└── synthesis/
```

### 为什么不用 `知识/` 和 `knowledge/`

`知识/`、`knowledge/` 在旧结构中含义过多：

- 可能是项目本地知识。
- 可能是项目中心共享知识。
- 可能是历史模板留下的资料目录。
- 可能是只读链接。

新能力建议使用更明确的路径：

| 语言 | 新路径 | 含义 |
|---|---|---|
| 中文 | `知识库/` | 当前项目自己的长期知识库 |
| 英文 | `knowledge-base/` | Current project knowledge base |

旧路径由 `doctor` 和 `upgrade` 识别，但不作为新项目标准路径。

## 文件和文件夹职责

### `README.md`

给人类和 Agent 的入口说明。

它应该说明：

- 这个目录是项目知识库，不是原始资料区。
- 原始资料应放在 Pack 定义的参考资料区。
- 重要知识应进入 `pages/` 或 `synthesis/`。
- 更新知识库前应先读 `schema.md` 和 `index.md`。

### `index.md`

知识地图。

它负责告诉 Agent：

- 当前知识库有哪些主题。
- 哪些页面最重要。
- 哪些综合判断已经形成。
- 相关页面之间大概如何连接。

`index.md` 不应变成所有内容的正文集合。它是导航，不是知识正文。

### `schema.md`

知识库的整理说明书。

它不是放知识的地方，而是告诉 Agent 应该怎么维护这个知识库。

必须包含：

- 什么内容值得进入知识库。
- 什么内容只应留在参考资料或输出中。
- `pages/` 的写作规则。
- `synthesis/` 的写作规则。
- 命名规则。
- 引用来源规则。
- 更新 `index.md` 和 `log.md` 的规则。
- 不要生成空泛总结、不要堆砌未验证判断。

一句话：

> `schema.md` 管“怎么整理知识”。

### `log.md`

维护记录。

它记录知识库发生过哪些重要变化，例如：

- 新增了哪些主题页。
- 合并了哪些重复主题。
- 根据哪批资料更新了哪些页面。
- 形成了哪些综合判断。
- 哪些内容仍待整理。

`log.md` 不是工作日志，不记录普通任务过程，只记录知识库维护动作。

### `inbox/`

待整理入口。

适合放：

- 用户要求 Agent 后续整理的知识候选。
- 从参考资料里摘出的待判断片段。
- 尚未确定该进入哪个主题页的内容。

`inbox/` 不能长期堆积。skill 应提醒 Agent 定期清理。

### `sources/`

来源索引。

它不复制所有原始资料，而是记录知识库引用过哪些来源。

可以包含：

- 来源文件清单。
- 来源摘要。
- 关键出处链接。
- 原始资料在 `参考资料/` 中的位置。

### `pages/`

稳定主题页。

它记录一个个可长期更新的主题、概念、对象或方法。

例子：

```text
pages/
├── 用户画像.md
├── 标题结构.md
├── 发布节奏.md
├── 账号定位.md
└── 竞品账号.md
```

它回答：

- 这个东西是什么？
- 目前我们知道什么？
- 有哪些规律、例子和反例？
- 和哪些主题有关？
- 这些知识来自哪里？

一句话：

> `pages/` 管“一个个长期主题”。

### `synthesis/`

综合判断和阶段性理解。

它把多个主题页、来源和项目经验组合起来，形成更高一层的判断。

例子：

```text
synthesis/
├── 30天账号冷启动策略.md
├── 内容增长方法论.md
├── 选题到发布工作流.md
└── 账号定位调整建议.md
```

它回答：

- 基于已有知识，现在应该怎么理解？
- 多个主题之间有什么关系？
- 当前阶段应该怎么做？
- 某个阶段有什么趋势？
- 哪些知识可以组成一套方法？

一句话：

> `synthesis/` 管“基于多个主题形成的判断和洞察”。

## `pages/` 和 `synthesis/` 的区别

最简单的判断：

```text
pages/      = 知识卡片
synthesis/  = 思考成果
```

更具体一点：

| 对比项 | `pages/` | `synthesis/` |
|---|---|---|
| 关注对象 | 单个主题、概念、对象、方法 | 多个主题组合后的判断 |
| 典型标题 | 用户画像、标题结构、竞品账号 | 冷启动策略、增长复盘、定位调整建议 |
| 主要来源 | 新资料、新观察、新经验 | 用户问题、策略判断、阶段复盘 |
| 更新频率 | 较高 | 较低 |
| 作用 | 让知识库记得住 | 让知识库想得明白 |

## 产生机制

### `pages/`：资料触发

`pages/` 通常由新资料、新观察、新经验触发。

```text
新资料 / 新对话 / 新复盘
        ↓
Agent 判断是否有长期有用的主题
        ↓
如果是新主题：创建 page
如果是旧主题：更新已有 page
        ↓
更新 index.md 和 log.md
```

例子：

用户给了一批小红书爆款案例。Agent 发现里面反复出现“标题结构”这个主题。

- 如果已有 `pages/标题结构.md`，就补充进去。
- 如果没有，就新建 `pages/标题结构.md`。

`pages/` 不是为了完成一次交付而写，而是为了长期积累主题知识。

### `synthesis/`：问题触发

`synthesis/` 通常由复杂问题、策略判断、阶段复盘触发。

```text
用户提出复杂问题
        ↓
Agent 读取 index.md 和相关 pages
        ↓
整合、比较、判断
        ↓
生成或更新 synthesis
        ↓
必要时反向更新 pages
        ↓
更新 index.md 和 log.md
```

例子：

用户问：

```text
我这个账号接下来 30 天应该怎么做？
```

Agent 可能读取：

```text
pages/用户画像.md
pages/账号定位.md
pages/标题结构.md
pages/发布节奏.md
pages/竞品账号.md
```

然后生成：

```text
synthesis/30天账号冷启动策略.md
```

`synthesis/` 不是资料一来就生成，而是在需要形成判断时生成。

## 不应进入知识库的内容

以下内容默认不进入知识库：

- 原始 PDF、截图、网页全文。
- 临时草稿。
- 用户还没有确认的正式成果。
- 单次任务过程。
- 没有长期复用价值的聊天记录。
- 没有来源、没有上下文的空泛总结。

这些内容应留在 Pack 定义的参考资料区、草稿区、成果区或事项工作区。

## CLI 和 Skill 的分工

知识库能力不能只靠 CLI，也不能只靠 Skill。

CLI 适合做稳定、可重复、可测试的动作。Skill 适合做人类访谈、理解项目、判断内容该怎么整理。

| 层级 | 负责什么 | 不负责什么 |
|---|---|---|
| CLI | 创建标准目录、写入模板、更新配置、输出结构诊断、按 blueprint 执行变更。 | 判断哪些内容值得沉淀、总结资料、生成主题页和综合判断。 |
| `starworkKnowledge` Skill | 采访用户、理解项目、判断知识库是否需要开启、生成或更新知识页、维护索引和日志。 | 绕过 CLI 随意创建结构、把原始资料整包搬进知识库、自动提交项目中心。 |

核心原则：

```text
CLI 负责“把骨架搭对”
Skill 负责“把知识整理对”
```

## Skill 层级和安装时机

知识库相关 Skill 分三层，不能混在一起。

| 层级 | 示例 | 安装位置 | 安装时机 | 作用 |
|---|---|---|---|---|
| 全局入口 Skill | `starworkKnowledge` | 用户全局 Agent Skill 环境 | 用户可通过 `npx skills add ...` 单独安装 | 让 Agent 学会如何引导用户开启和维护 StarWork 知识库。 |
| 知识库能力自带 Skill | `starworkKnowledgeProject` | 当前项目 `.agents/skills/`，必要时同步到 `.claude/skills/` | 当前项目成功开启 knowledge 能力后，由 CLI 自动装入 | 服务当前项目的知识库吸收、整理、检查和维护。 |
| 场景扩展 Skill | 内容创作者知识整理、研究资料卡片化等 | 当前项目 skill 目录 | Pack 推荐，用户确认后安装 | 针对具体业务场景扩展知识库能力。 |

### `starworkKnowledge` 的定位

`starworkKnowledge` 是全局入口 Skill，不是每个项目默认自带的业务 Skill。

它应该允许用户单独安装：

```bash
npx skills add <starworkKnowledge>
```

该命令的准确包名或路径以后由发布文档给出。产品判断是：用户不需要重新初始化项目，也可以先让 Agent 学会如何处理 StarWork 知识库。

`starworkKnowledge` 负责：

- 向用户解释知识库不是资料夹。
- 判断当前项目是否适合开启知识库。
- 引导已有 StarWork 项目开启知识库。
- 调用 `starwork knowledge init` 或生成 blueprint。
- 指导 Agent 后续如何维护知识库。

它不负责：

- 默认复制进所有项目。
- 代替 CLI 创建结构。
- 把 knowledge 的全部业务 Skill 装到全局环境。

### 知识库能力自带 Skill 的定位

当某个项目真正开启知识库能力后，才需要项目内的知识库业务 Skill。

这些 Skill 服务的是当前项目的知识库，不应默认进入全局环境，也不应在用户尚未开启知识库前出现。

它们应该由 CLI 在 `starwork knowledge init` 成功后自动装入当前项目：

```text
.agents/skills/
└── starworkKnowledgeProject/
```

v0.1 先合并为一个项目内业务 Skill，降低安装、体检和更新复杂度。后续如果知识库维护动作变复杂，再拆成：

```text
starworkKnowledgeIngest/
starworkKnowledgeSynthesis/
starworkKnowledgeLint/
```

本 SPEC 先确定原则：

> 全局只装入口和引导，项目开启能力后才装业务 Skill。

建议源码位置：

```text
product/core/capabilities/knowledge/skills/starworkKnowledgeProject/
```

这样它跟 knowledge capability 绑定，不会被全局系统 Skill 安装命令误装。

### 为什么不能绑死 `init`

很多用户已经有 StarWork 项目，不能要求他们重新执行 `starwork init`。

所以知识库能力必须有独立入口：

```bash
starwork knowledge init
```

`init --knowledge` 只能作为新项目创建时的快捷方式，不能成为唯一入口。

## 创建知识库的用户流程

### 流程 A：用户只想快速开启

用户表达：

```text
给这个项目开一个知识库
```

推荐执行：

1. 如果 Agent 尚未安装 `starworkKnowledge`，用户可以先通过 `npx skills add ...` 单独安装。
2. Agent 使用 `starworkKnowledge` skill。
3. Skill 判断当前目录是否是 StarWork 项目工作台。
4. Skill 询问用户：是否现在开启项目知识库。
5. 用户确认后，Skill 调用 CLI：

```bash
starwork knowledge init
```

6. CLI 创建标准结构，并把知识库能力自带业务 Skill 安装到当前项目。
7. Skill 根据项目情况补充 `schema.md`、`index.md` 和 AGENTS 规则。

### 流程 B：用户正在创建新项目

`starwork init` 默认不创建知识库，也不在 v0.1 默认采访链路里询问知识库。

推荐流程是：

1. 用户先用 `starwork init` 创建项目工作台和 Pack。
2. 如果用户随后需要知识库，再运行：

```bash
starwork knowledge init
```

3. 最终结果与已有项目后安装知识库保持一致。

原因：

- 知识库不是基础工作台必需能力。
- `init` 已经承担工作台类型、语言、Pack 等选择，不应继续变重。
- 已有项目和新项目使用同一个知识库开启入口，开发和文档都更稳定。

后续可以考虑增加：

```bash
starwork init --knowledge
```

但它只是快捷入口，必须复用 `starwork knowledge init`，不能另写一套结构。

### 流程 C：用户有旧资料或旧 `知识/knowledge`

用户表达：

```text
我这个项目以前有一些知识材料，帮我整理成 StarWork 知识库
```

推荐执行：

1. Agent 使用 `starworkDoctor` 或 `starworkKnowledge`。
2. CLI 输出结构和文件信号。
3. Skill 判断旧目录更像参考资料、知识草稿、旧知识库，还是共享链接。
4. Skill 生成知识库整理 blueprint。
5. 用户确认。
6. CLI 只负责创建结构和执行安全的文件操作。
7. Skill 负责提炼、合并、更新 `pages/` 和 `synthesis/`。

## `starwork knowledge` 命令组

建议新增一个明确的命令组：

```bash
starwork knowledge <command>
```

一期命令建议如下。

### `starwork knowledge init`

创建项目本地知识库标准结构。

示例：

```bash
starwork knowledge init
starwork knowledge init --language zh
starwork knowledge init --path 知识库
starwork knowledge init --dry-run
```

职责：

- 判断当前工作台语言。
- 创建 `知识库/` 或 `knowledge-base/`。
- 写入 `README.md`、`index.md`、`schema.md`、`log.md`。
- 创建 `inbox/`、`sources/`、`pages/`、`synthesis/`。
- 更新 `.starwork/workspace.json`，声明已开启知识库能力。
- 安装知识库能力自带业务 Skill 到当前项目 skill 目录。
- 可选更新 AGENTS 规则中的知识库读取说明。
- 支持 `--dry-run`。
- 如果目录已存在，不覆盖用户内容，只报告已有状态。

不做：

- 不读取和总结用户资料。
- 不自动创建主题页。
- 不迁移旧 `知识/knowledge`。
- 不连接项目中心共享知识库。
- 不安装全局入口 Skill。

### `starwork knowledge status --json`

输出当前项目知识库状态，供 Skill 判断。

示例：

```bash
starwork knowledge status --json
```

建议输出：

```json
{
  "ok": true,
  "enabled": true,
  "language": "zh",
  "root": "知识库",
  "structure": {
    "readme": true,
    "index": true,
    "schema": true,
    "log": true,
    "inbox": true,
    "sources": true,
    "pages": true,
    "synthesis": true
  },
  "counts": {
    "pages": 4,
    "synthesis": 1,
    "inbox": 2,
    "sources": 6
  },
  "skills": {
    "project_skill_installed": true,
    "project_skill_ids": ["starworkKnowledgeProject"]
  },
  "legacy_candidates": ["知识"],
  "warnings": []
}
```

注意：

- 输出只描述事实，不给“下一步建议”。
- 避免影响 Skill 的独立判断。
- 应包含当前项目已安装的 knowledge 业务 Skill 状态；但只陈述事实，不判断是否应该安装更多 Skill。

### `starwork knowledge check`

只检查结构完整性，不判断内容质量。

示例：

```bash
starwork knowledge check
starwork knowledge check --json
```

检查项：

- 标准文件是否存在。
- 标准目录是否存在。
- `index.md` 是否为空。
- `schema.md` 是否为空。
- `log.md` 是否存在。
- `pages/` 和 `synthesis/` 是否可读写。

内容是否空泛、主题是否重复、判断是否可靠，由 Skill 做。

### `starwork knowledge apply --blueprint <file>`

按 blueprint 执行结构性变更。

示例：

```bash
starwork knowledge apply --blueprint knowledge-blueprint.json
starwork knowledge apply --blueprint knowledge-blueprint.json --dry-run
```

适用：

- 从旧 `知识/` 整理出新 `知识库/`。
- 创建标准结构。
- 安全移动或复制经过用户确认的文件。
- 更新 AGENTS 规则。
- 安装或修复项目内 knowledge 业务 Skill。

不适用：

- 生成知识正文。
- 总结资料。
- 判断内容价值。

这些仍由 Skill 完成。

## Knowledge Blueprint

当涉及旧目录整理、用户定制路径或 AGENTS 更新时，Skill 应先生成 blueprint，再由 CLI 执行。

建议格式：

```json
{
  "version": "0.1",
  "type": "starwork.knowledge",
  "language": "zh",
  "root": "知识库",
  "actions": [
    {
      "type": "create_knowledge_base",
      "path": "知识库"
    },
    {
      "type": "create_dir",
      "path": "知识库/pages"
    },
    {
      "type": "write_template",
      "path": "知识库/schema.md",
      "template": "knowledge.schema.zh"
    },
    {
      "type": "append_agents_rule",
      "path": "AGENTS.md",
      "section": "知识库"
    }
  ],
  "preserve": [
    "知识/",
    "参考资料/"
  ],
  "notes": [
    "旧 知识/ 暂不迁移，等待用户确认其真实用途。"
  ]
}
```

Blueprint 约束：

- 必须声明语言和目标根目录。
- 不能包含删除动作。
- 移动文件必须有明确来源、目标和用户确认。
- 不能要求 CLI 生成知识正文。
- 不能默认提交到项目中心。
- 不能安装全局 `starworkKnowledge`。

v0.1 允许的 action 类型：

| action | 说明 |
|---|---|
| `create_knowledge_base` | 创建知识库根目录和标准结构。 |
| `create_dir` | 创建标准子目录。 |
| `write_template` | 写入 README / index / schema / log 模板；已存在时不覆盖，除非 blueprint 明确允许。 |
| `append_agents_rule` | 向 AGENTS 添加知识库读取规则；必须避免重复写入。 |
| `install_project_skill` | 安装或修复项目内 `starworkKnowledgeProject`。 |
| `copy_preserved_file` | 复制用户确认过的旧文件到知识库 inbox 或 sources；默认保留原文件。 |
| `record_workspace_capability` | 更新 `.starwork/workspace.json` 的 knowledge 能力声明。 |

v0.1 禁止的 action 类型：

- `delete`
- `rename_without_preserve`
- `summarize_source`
- `generate_page_content`
- `promote_to_project_center`

## `starworkKnowledge` skill 一期能力

一期只做项目本地知识库，不做项目中心提交。

### 能力 1：引导创建知识库

适用场景：

用户说“给这个项目开一个知识库”“我想让 AI 长期整理这个项目的知识”。

Agent 应做：

1. 判断当前工作台语言。
2. 向用户解释：知识库不是资料夹，是长期理解层。
3. 询问是否现在开启。
4. 如果是新建空知识库，调用 `starwork knowledge init`。
5. 如果涉及旧目录、定制路径或 AGENTS 规则调整，先生成 blueprint，再调用 `starwork knowledge apply`。
6. 根据项目情况微调 `schema.md` 和 `index.md`。
7. 不移动用户已有资料，除非用户明确确认。

如果当前项目尚未安装知识库业务 Skill，不应由 Agent 手动复制；应通过 `starwork knowledge init` 或 `starwork knowledge apply` 让 CLI 统一安装。

### 能力 2：吸收资料

适用场景：

用户给了新资料，要求“整理到知识库里”。

Agent 应做：

1. 先读 `schema.md` 和 `index.md`。
2. 判断资料中是否有长期复用价值。
3. 更新或创建相关 `pages/`。
4. 必要时记录来源到 `sources/`。
5. 更新 `index.md`。
6. 更新 `log.md`。

### 能力 3：回答并沉淀

适用场景：

用户询问和项目长期知识相关的问题。

Agent 应做：

1. 先读 `index.md`。
2. 再读相关 `pages/` 和 `synthesis/`。
3. 回答用户问题。
4. 如果产生了可长期复用的新判断，经用户确认后更新知识库。

### 能力 4：形成综合判断

适用场景：

用户要求策略、复盘、阶段判断、方法论整理。

Agent 应做：

1. 读取相关 `pages/`。
2. 读取必要来源和历史 `synthesis/`。
3. 生成或更新一份 `synthesis/`。
4. 必要时把新概念反向沉淀到 `pages/`。
5. 更新 `index.md` 和 `log.md`。

### 能力 5：健康检查

适用场景：

用户说“检查一下知识库是否混乱”“整理一下知识库”。

Agent 应检查：

- `index.md` 是否能导航到主要页面。
- `pages/` 是否有重复主题。
- `synthesis/` 是否缺少引用的主题页。
- `inbox/` 是否长期堆积。
- `sources/` 是否能说明关键知识来源。
- 是否有空泛、无来源、无法复用的内容。

### 能力 6：生成知识库整理 Blueprint

适用场景：

用户已有旧 `知识/`、`knowledge/`、`资料库/` 或其他类似目录，希望整理成新知识库。

Agent 应做：

1. 读取 `starwork knowledge status --json` 或 `doctor --json`。
2. 判断旧目录更像什么角色。
3. 和用户确认是否开启新知识库。
4. 生成 `starwork.knowledge` blueprint。
5. 交给 CLI 执行结构性动作。
6. 再由 Skill 完成内容提炼和知识整理。

### 暂不做能力：提交到项目中心

旧备忘里提过 Promote，即把项目知识提交到项目中心共享知识库。

本轮暂不做。

原因：

- 项目知识库和项目中心共享知识的边界还需要单独设计。
- 审核、候选、合并、分发机制会显著增加复杂度。
- 当前优先级是先让单个项目里的知识库真正有用。

## CLI 配合调整

### `starwork init`

默认不创建知识库。

v0.1 不要求改造交互式 `init`。

后续可以增加可选项：

```bash
starwork init --knowledge
```

如果未来支持该选项，它必须复用 `starwork knowledge init` 的创建逻辑，而不是单独写一套结构。

`init --knowledge` 只是便捷入口，不是知识库能力的主入口。已有 StarWork 项目开启知识库，主入口仍然是：

```bash
starwork knowledge init
```

### `starwork doctor`

`doctor` 不应把缺少 `知识库/` 或 `knowledge-base/` 当成问题。

它应该识别：

- 当前项目是否开启了知识库能力。
- 旧 `知识/` 或 `knowledge/` 更像资料夹、旧知识目录，还是项目中心链接。
- 如果存在 `知识库/`，检查基础结构是否完整。
- 如果存在多个类似知识目录，只暴露事实和风险，不直接建议合并。

### `starwork upgrade`

`upgrade` 不应自动把旧 `知识/` 迁移成新 `知识库/`。

合理策略：

1. 先由 `doctor` 暴露目录结构和内容信号。
2. 由 `starworkDoctor` 或后续知识库 skill 判断旧目录性质。
3. 如果用户确认要开启知识库，再生成升级蓝图。
4. `upgrade` 只按蓝图执行，不自行判断。

知识库相关升级动作应优先走：

```bash
starwork knowledge apply --blueprint <file>
```

而不是塞进通用 `upgrade` 的硬编码判断里。

### `starwork spawn`

项目中心创建项目工作台时，默认不强行挂载共享知识库为项目知识库。

后续如项目中心支持共享知识库，应另行设计：

- 项目本地知识库。
- 项目中心共享知识库。
- 二者之间是否只读、候选、审核和同步。

## Core 配合调整

后续实现时，建议新增：

```text
product/core/capabilities/knowledge/
├── capability.md
├── templates/zh/
└── templates/en/
```

该 capability 只描述项目本地知识库能力，不描述项目中心共享知识。

Project Kit 不应直接包含 `知识库/` 或 `knowledge-base/`。

`.starwork/workspace.json` 可增加能力声明：

```json
{
  "capabilities": {
    "knowledge": {
      "enabled": true,
      "root": "知识库",
      "language": "zh",
      "mode": "local",
      "version": "0.1",
      "project_skill_ids": ["starworkKnowledgeProject"]
    }
  }
}
```

该声明只表示当前项目开启了本地知识库，不表示连接项目中心共享知识。

## AGENTS 规则配合

开启知识库能力后，应在项目 AGENTS 中增加简短规则：

中文示例：

```markdown
## 知识库

如果任务需要复用本项目的长期知识，先读 `知识库/index.md`。

不要把原始资料、临时草稿或单次任务过程直接塞进知识库。新资料需要整理成稳定主题页，放入 `知识库/pages/`；跨主题的策略、复盘和综合判断放入 `知识库/synthesis/`。
```

英文示例：

```markdown
## Knowledge Base

When a task depends on long-term project knowledge, read `knowledge-base/index.md` first.

Do not dump raw sources, temporary drafts, or one-off task notes into the knowledge base. Stable topics belong in `knowledge-base/pages/`; cross-topic strategy, reviews, and synthesized judgment belong in `knowledge-base/synthesis/`.
```

## 与 Pack 的关系

Pack 可以声明自己推荐开启知识库，但不应直接把知识库当作普通业务目录。

例如内容创作者 Pack 后续可以推荐：

```text
内容创作项目
+ General Pack
+ Knowledge Capability
```

但知识库仍由 Knowledge Capability 定义结构和维护规则。

## 与旧结构的关系

旧项目可能存在：

- `知识/`
- `knowledge/`
- `资料库/`
- `参考资料/知识/`
- Hub 软链接形式的 `knowledge/`

处理原则：

1. 不直接删除。
2. 不自动改名。
3. 不假设它就是新知识库。
4. 通过 `doctor --json` 暴露结构、文件数量、README 内容、是否软链接等信号。
5. 由 skill 结合用户确认生成整理建议。

## 实施拆分和验收标准

本需求进入开发时按以下 phase 推进。每个 phase 都应该能独立验收；后一个 phase 不应依赖尚未验收的隐藏假设。

### Phase 1：Core Capability 和模板冻结

目标：

- 冻结 knowledge capability 的标准结构。
- 提供中文和英文模板。
- 明确项目内业务 Skill 的源码位置。

开发内容：

1. 完善 `product/core/capabilities/knowledge/capability.md`。
2. 完善模板：

```text
product/core/capabilities/knowledge/templates/zh/
product/core/capabilities/knowledge/templates/en/
```

3. 新增项目内业务 Skill 源码位置：

```text
product/core/capabilities/knowledge/skills/starworkKnowledgeProject/
```

4. 模板至少包含：

```text
README.md
index.md
schema.md
log.md
```

5. `schema.md` 必须写清：

- `pages/` 和 `synthesis/` 的区别。
- 原始资料不进入知识库。
- 新资料如何进入 `pages/`。
- 复杂问题如何生成 `synthesis/`。
- 更新 `index.md` 和 `log.md` 的规则。

验收标准：

1. 中文模板生成路径为 `知识库/`，英文模板生成路径为 `knowledge-base/`。
2. 模板中不出现“提交到项目中心”的默认流程。
3. `schema.md` 能让 Agent 明确知道：原始资料留在参考资料区，稳定主题进 `pages/`，综合判断进 `synthesis/`。
4. `starworkKnowledgeProject` 不在全局 `product/skills/` 下，避免被全局安装命令误装。
5. Project Kit 不因为本 phase 重新默认包含 `知识库/` 或 `knowledge-base/`。

### Phase 2：CLI 基础命令

目标：

- 实现已有项目开启知识库的主入口。
- CLI 负责创建结构、记录能力、安装项目内业务 Skill。

开发内容：

1. 新增命令组：

```bash
starwork knowledge init
starwork knowledge status --json
starwork knowledge check
```

2. `starwork knowledge init` 支持：

```bash
starwork knowledge init
starwork knowledge init --language zh
starwork knowledge init --language en
starwork knowledge init --path 知识库
starwork knowledge init --dry-run
```

3. `init` 成功后写入或更新：

```json
{
  "capabilities": {
    "knowledge": {
      "enabled": true,
      "root": "知识库",
      "language": "zh",
      "mode": "local",
      "version": "0.1",
      "project_skill_ids": ["starworkKnowledgeProject"]
    }
  }
}
```

4. `init` 成功后安装项目内业务 Skill：

```text
.agents/skills/starworkKnowledgeProject/
```

必要时可同步：

```text
.claude/skills/starworkKnowledgeProject/
```

5. `status --json` 只输出事实，不输出下一步建议。

验收标准：

1. 在一个已有中文 StarWork 项目中运行 `starwork knowledge init --dry-run`，只展示计划，不写入文件。
2. 在一个已有中文 StarWork 项目中运行 `starwork knowledge init` 后，出现：

```text
知识库/README.md
知识库/index.md
知识库/schema.md
知识库/log.md
知识库/inbox/
知识库/sources/
知识库/pages/
知识库/synthesis/
.agents/skills/starworkKnowledgeProject/
```

3. 在英文项目中运行后，根路径为 `knowledge-base/`。
4. 重复运行 `starwork knowledge init` 不覆盖用户已修改的知识库文件。
5. `starwork knowledge status --json` 包含 `enabled`、`root`、`language`、`structure`、`counts`、`skills`、`legacy_candidates`，且没有建议性字段。
6. `starwork knowledge check --json` 能指出缺失的标准文件或目录。
7. 普通 `starwork init` 不因为本 phase 默认创建知识库。

### Phase 3：Blueprint 和旧目录安全处理

目标：

- 支持旧目录整理的安全执行框架。
- 让 Skill 能先生成 blueprint，再由 CLI 执行确定性动作。

开发内容：

1. 新增：

```bash
starwork knowledge apply --blueprint <file>
starwork knowledge apply --blueprint <file> --dry-run
```

2. 支持 v0.1 action：

| action | 是否必须支持 |
|---|---|
| `create_knowledge_base` | 是 |
| `create_dir` | 是 |
| `write_template` | 是 |
| `append_agents_rule` | 是 |
| `install_project_skill` | 是 |
| `copy_preserved_file` | 是 |
| `record_workspace_capability` | 是 |

3. 拒绝危险 action：

```text
delete
rename_without_preserve
summarize_source
generate_page_content
promote_to_project_center
```

4. 对旧 `知识/`、`knowledge/`、`资料库/` 只做识别和保留，不自动迁移。

验收标准：

1. 合法 blueprint 在 `--dry-run` 下展示完整计划，不写文件。
2. 合法 blueprint 执行后，只执行声明过的结构动作。
3. blueprint 中出现 `delete` 或 `promote_to_project_center` 时，CLI 拒绝执行并给出清楚错误。
4. `copy_preserved_file` 默认复制，不移动原文件。
5. 旧 `知识/knowledge` 存在时，`status --json` 能列入 `legacy_candidates`，但不会自动迁移。

### Phase 4：全局入口 Skill `starworkKnowledge`

目标：

- 让 Agent 能通过全局入口 Skill 引导用户开启和维护知识库。
- Skill 必须调用 CLI，而不是自己手写结构。

开发内容：

1. 完善：

```text
product/skills/starworkKnowledge/SKILL.md
```

2. Skill 必须覆盖：

- 向用户解释知识库不是资料夹。
- 判断当前目录是否是 StarWork 项目。
- 引导已有项目运行 `starwork knowledge init`。
- 遇到旧目录时生成 blueprint。
- 吸收资料时更新 `pages/`、`sources/`、`index.md`、`log.md`。
- 复杂问题触发 `synthesis/`。
- 健康检查知识库。

3. Skill 必须声明：

- 不提交到项目中心。
- 不手动复制项目内业务 Skill。
- 不把原始资料整包搬进知识库。
- 创建结构时必须优先调用 CLI。

验收标准：

1. `starworkKnowledge` 可以作为全局入口 Skill 单独安装。
2. Skill 文案不把 `starworkKnowledgeProject` 当成全局 Skill。
3. Skill 中创建知识库的流程明确调用 `starwork knowledge init` 或 `starwork knowledge apply`。
4. Skill 中不出现自动提交项目中心的默认流程。
5. Skill 能清楚解释 `pages/` 是资料触发，`synthesis/` 是问题触发。

### Phase 5：doctor / upgrade / init 配合

目标：

- 让现有 StarWork 体检和升级链路能识别知识库能力，但不越权判断。

开发内容：

1. `doctor` 增加知识库事实探测：

- 是否开启 knowledge capability。
- 标准结构是否完整。
- 项目内业务 Skill 是否存在。
- 是否存在旧 `知识/knowledge/资料库` 候选目录。

2. `doctor` 不把缺少知识库当成错误。
3. `doctor --json` 不输出下一步建议。
4. `upgrade` 不硬编码迁移旧知识目录，只执行用户确认后的 blueprint。
5. `init` 不默认创建知识库；`init --knowledge` 如实现，必须复用 `starwork knowledge init`。

验收标准：

1. 没有知识库的普通项目运行 `doctor` 不报错。
2. 已开启知识库的项目运行 `doctor --json` 能识别 knowledge capability。
3. 缺失 `schema.md` 或项目内业务 Skill 时，`doctor` 能暴露事实。
4. 存在旧 `知识/` 的项目，`doctor --json` 只报告 legacy signal，不建议自动迁移。
5. `upgrade` 不在没有 blueprint 的情况下创建、删除或迁移知识库目录。
6. 普通 `starwork init` 回归测试通过，不出现知识库默认目录。

### Phase 6：文档、测试和发布材料

目标：

- 让用户、Agent 和开发者都能理解如何开启、使用和测试知识库能力。

开发内容：

1. 更新用户文档：

- CLI 能力说明。
- Skill 安装说明。
- 已有项目如何开启知识库。
- 知识库不是参考资料的解释。

2. 更新 Agent 文档：

- 什么时候安装 `starworkKnowledge`。
- 如何调用 `starwork knowledge init`。
- 如何处理旧目录。

3. 更新开发/验收文档：

- CLI 测试用例。
- Skill 验收脚本或人工测试步骤。
- A 测反馈记录入口。

4. 更新相关索引：

- `product/planning/features/knowledge-base/README.md`
- `product/planning/features/knowledge-base/specs/index.md`
- 必要时更新 docs 总索引。

验收标准：

1. README 能回答：已有 StarWork 项目如何开启知识库。
2. 文档明确：`starworkKnowledge` 是全局入口 Skill，`starworkKnowledgeProject` 是项目内业务 Skill。
3. 文档明确：业务 Skill 在 `starwork knowledge init` 后自动进入项目，不是全局默认安装。
4. 文档中没有把 `知识库/` 描述成原始资料目录。
5. `npm test` 通过。
6. `npm pack --dry-run` 通过。

## 总体验收标准

全部 phase 完成后，必须满足：

1. 新建普通项目时，不默认出现 `知识库/` 或 `knowledge-base/`。
2. 已有 StarWork 项目可以通过 `starwork knowledge init` 开启知识库。
3. 开启知识库能力后生成标准结构，并安装项目内 `starworkKnowledgeProject`。
4. `schema.md` 能明确告诉 Agent 如何维护知识库。
5. `pages/` 和 `synthesis/` 的区别在文档和 Skill 中表达清楚。
6. `doctor` 不把缺少知识库当成结构错误。
7. 旧 `知识/knowledge` 不被自动迁移、删除或改名。
8. Skill 一期不出现“提交到项目中心”的默认动作。
9. 用户文案避免使用内部术语。
10. `starwork knowledge init --dry-run` 能展示将创建的结构和将安装的项目内业务 Skill。
11. `starwork knowledge status --json` 只暴露事实，不输出下一步建议。
12. `starworkKnowledge` 创建知识库时优先调用 CLI，不手写一套不一致结构。
13. 涉及旧目录整理时，必须先生成 blueprint 并让用户确认。
14. `starworkKnowledge` 可以通过 `npx skills add ...` 作为全局入口 Skill 单独安装。
15. knowledge 业务 Skill 不默认进入全局 Skill 环境，只在项目开启知识库能力后装入当前项目 skill 目录。

## 后续另开需求

以下内容不阻塞 v0.1 开发：

1. 项目知识提交到项目中心共享知识库。
2. 项目中心共享知识库的审核、合并和分发。
3. 内容创作者 Pack 是否默认推荐开启知识库。
4. 是否把 `starworkKnowledgeProject` 拆成 ingest / synthesis / lint 多个项目内业务 Skill。
5. 是否在交互式 `init` 中增加知识库问题。
