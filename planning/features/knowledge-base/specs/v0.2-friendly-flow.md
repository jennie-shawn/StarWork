# Knowledge Base v0.2：友好的资料分类与写入确认流程

状态：accepted

负责人：product-lead

关联 Issue：`ISSUE-029`

## 背景

Knowledge v0.1 已经确定核心边界：

- 知识库不是原始资料夹。
- 知识库不是草稿区。
- 知识库是当前项目里长期可复用的稳定理解层。
- CLI 负责创建结构和检查事实，Skill 负责判断、采访和整理。

当前体验缺口在于：当用户说“帮我记住”“给这些资料建知识库”“这一堆材料整理一下”时，Agent 容易过早进入写入动作，缺少一个小白可理解的“先分类、再预览、再确认写入”流程。

同时，项目内业务 Skill `starworkKnowledgeProject` 当前过短、偏英文和内部规则，不像一个普通用户可直接使用的项目内知识助手。

## 目标

让用户给资料或说“帮我记住”时，Agent 先帮用户判断这些内容适不适合进入长期知识库，并用预览表说明准备保存什么、为什么保存、放到哪里、哪些需要确认；用户确认前不得写入正式知识文件。

## 非目标

- 不新增 CLI 命令。
- 不改变知识库目录结构。
- 不把 `starworkKnowledgeProject` 装入全局系统 Skill。
- 不自动提交到项目中心共享知识库。
- 不默认把知识库塞进 `starworkInit` 主采访链路。
- 不做 references 拆分，除非 development 发现主 Skill 超过本 SPEC 行数上限且必须拆分。

## 第一屏体验

`starworkKnowledge` 在用户给资料、说“帮我记住”、要求“整理成知识库”时，应先输出用户友好的第一屏。推荐口径：

```text
我会先帮你判断这些材料哪些适合进入长期知识库。

知识库不是把所有资料搬进去的文件夹，也不是草稿区。它只保存以后会反复用到、已经比较稳定的理解，例如项目规则、术语解释、客户背景、长期策略、阶段复盘结论。

接下来我会先做三件事：
1. 把你给的材料分成长期知识、临时资料、草稿、参考来源和待确认事实；
2. 预览我建议写入知识库的条目、来源、保存理由和位置；
3. 等你确认后，再写入正式知识文件。

在你确认前，我不会把整批资料直接搬进知识库，也不会改动已有知识文件。
```

如果项目尚未开启知识库，仍按 v0.1 流程先运行 `starwork knowledge status --json`，再用 `starwork knowledge init --dry-run` 预览结构；不能绕过 CLI 手写知识库结构。

## Incoming Material Classification

当用户给出材料时，`starworkKnowledge` 和 `starworkKnowledgeProject` 都应先分类，再判断是否写入。

| 分类 | 用户可见解释 | 默认处理 | 能否进入知识库 |
| --- | --- | --- | --- |
| 长期知识 | 以后会反复用到、已经比较稳定的项目理解 | 候选写入 `pages/` 或 `synthesis/` | 可以，但仍需预览确认 |
| 临时资料 | 这次任务可能有用，但不一定长期复用 | 留在参考资料、任务上下文或用户指定位置 | 默认不进入 |
| 草稿 | 还在写、还没定稿、可能会大改的内容 | 留在草稿或输出流程 | 不进入，除非转化为已确认结论 |
| 参考来源 | 支撑知识判断的原始出处、链接、文件、访谈记录 | 记录到 `sources/` 或引用已有来源位置 | 可记录来源，不复制全文 |
| 待确认事实 | 看起来重要，但来源、真实性或稳定性不足 | 放入候选清单，向用户追问 | 用户确认前不写正式知识 |

判断规则：

- 一段材料可以同时包含多个分类。
- 来源不是知识正文；网页、PDF、会议纪要、聊天记录可以作为来源，但不能整包搬进 `pages/` 或 `synthesis/`。
- 草稿只有在用户确认某个判断已经稳定后，才能转成长期知识。
- 待确认事实不能伪装成确定结论；最多放入待确认清单或 `inbox/`，并写清楚为什么待确认。

## 写入前预览表

在任何正式写入 `pages/`、`synthesis/`、`sources/`、`index.md` 或 `log.md` 前，必须先给用户看预览表。

预览表至少包含：

| 知识条目 | 来源 | 为什么值得长期保存 | 建议放入位置 | 是否需要用户确认 |
| --- | --- | --- | --- | --- |

预览后必须列出本次不建议写入知识库的内容，例如：

```text
这次我不建议写入知识库的内容：
- 原始资料全文：只作为来源保留。
- 尚未定稿的段落：仍按草稿处理。
- 来源不明确的判断：先列为待确认事实。
```

确认语必须具体：

```text
请确认：是否按上表写入这些知识条目？
如果你只想保存其中几条，也可以告诉我编号。
```

不得用“我继续整理了”“我会帮你处理好”这类模糊授权替代确认。

## `starworkKnowledgeProject` 友好化

`starworkKnowledgeProject` 是项目开启知识库后自动进入当前项目的维护助手。它应改为中文友好的项目内知识助手表达，隐藏内部术语，只保留必要文件路径。

推荐定位：

```text
你是当前项目的知识库助手。

你的任务不是保存所有资料，而是帮用户把长期有用、已经比较稳定的项目理解整理进知识库。每次写入前，你都要先分类、预览、等待确认。
```

推荐流程：

1. 先确认当前项目已经开启知识库：运行或查看 `starwork knowledge status --json`。
2. 先读 `schema.md` 和 `index.md`，理解当前知识库规则和已有地图。
3. 对用户给的新材料做分类：长期知识、临时资料、草稿、参考来源、待确认事实。
4. 给出写入前预览表。
5. 用户确认后再更新 `pages/`、`synthesis/`、`sources/`、`index.md` 和 `log.md`。
6. 写入后简短说明写了哪里、没有写什么、哪些仍待确认。

安全边界：

- 不把原始文件、会议转写、网页全文、命令输出整包写入知识库。
- 不把草稿当成长期知识。
- 不把单次任务过程写成知识。
- 不把未确认事实写成确定结论。
- 不移动、删除或重命名旧 `知识/`、`knowledge/` 或类似目录。
- 不提交到项目中心共享知识库。
- 不在用户确认前写入正式知识文件。

`inbox/` 只用于暂存待整理片段或待确认事实，不能变成新的资料堆。每次放入 `inbox/` 都要说明原因和后续确认问题。

## 用户可见边界

普通用户不需要理解 `starworkKnowledge` 和 `starworkKnowledgeProject` 的内部差异。Skill 应用用户语言表达阶段：

| 用户场景 | 用户理解 | 背后使用 |
| --- | --- | --- |
| 还没开知识库，想让项目有长期记忆 | 创建项目知识库 | `starworkKnowledge` 引导 + `starwork knowledge init --dry-run/--yes` |
| 已有一堆资料，不知道是否适合保存 | 先帮我分类和预览 | `starworkKnowledge` 或项目内 `starworkKnowledgeProject` |
| 当前项目已经有知识库，要持续维护 | 维护当前项目知识 | `starworkKnowledgeProject` |
| 问某个长期规则、背景或策略 | 从当前项目知识库查和答 | 优先读 `index.md`、相关 `pages/` / `synthesis/` |

用户可见话术：

```text
如果这个项目还没有知识库，我会先带你创建结构。
如果已经有知识库，我会直接按当前项目的知识库规则帮你维护。
你不需要区分内部 Skill 名字，只要确认哪些内容值得长期保存。
```

## 验收标准

### 必须做到

- 用户给资料时，第一步是分类和解释，不是直接写入。
- 必须出现五类分类：长期知识、临时资料、草稿、参考来源、待确认事实。
- 必须出现写入前预览表字段：知识条目、来源、为什么值得长期保存、建议放入位置、是否需要用户确认。
- 用户确认前不得写入正式知识文件。
- 不得批量搬运旧材料或原始资料全文。
- 不得把草稿当长期知识。
- 不得把未确认事实写成确定结论。
- `starworkKnowledgeProject` 必须是中文友好的项目内知识助手表达。
- `starworkKnowledgeProject` 必须说明安全边界和确认流程。
- stable / next `starworkKnowledge` 不得出现相互矛盾的用户流程。

### 文本扫描建议

必须命中：

- `长期知识`
- `临时资料`
- `草稿`
- `参考来源`
- `待确认事实`
- `写入前预览`
- `知识条目`
- `为什么值得长期保存`
- `建议放入位置`
- `用户确认`

禁止出现会引导直接搬运的口径：

- `把所有资料写入知识库`
- `直接导入全部资料`
- `不需要确认`
