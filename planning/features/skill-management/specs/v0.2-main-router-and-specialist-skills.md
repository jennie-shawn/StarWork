# StarWork Skill Management v0.2：主 Skill 路由与专家 Skill 分层

## 状态

- 版本：v0.2 draft
- 日期：2026-06-09
- 所属模块：StarWork Skills / Skill Management / CLI 分发 / 用户入口文档
- 相关源码：`product/skills/`、`product/kit-skills/`、`product/core/capabilities/*/skills/`
- 相关文档：`product/README.md`、`product/docs/agent-install-guide.md`、`product/docs/cli-skill-registry.html`、`product/core/skill-management-spec.md`

## 背景

StarWork 当前已经有多个系统级 Skill：

- `starworkInit`
- `starworkDoctor`
- `starworkKnowledge`
- `starworkMultiagent`

这些 Skill 都有明确价值，但在用户第一次接触 StarWork 时会产生三个问题：

1. **入口太散**：用户不知道应该先调用哪个 Skill。
2. **触发重叠**：多个 Skill 都带有“StarWork 工作台”“初始化”“诊断”“协作”等泛化词，容易抢同一个模糊请求。
3. **产品解释重复**：每个 Skill 都在第一屏解释自己的一部分产品概念，导致 StarWork 的总入口不稳定。

但反过来，不能把所有能力都压进一个大 Skill。`starworkMultiagent`、`starworkKnowledge`、`starworkDoctor` 这些能力有明确场景、复杂流程、专门安全边界和宿主差异，应该继续支持直接触发。

因此 v0.2 采用：

```text
主 Skill 路由 + 专家 Skill 直接触发
```

不是“只有一个大 Skill”，也不是“所有 Skill 平铺”。

## 目标

1. 新增 `starwork` 主 Skill，作为 StarWork 的统一产品入口和模糊意图路由层。
2. 保留 `starworkInit`、`starworkDoctor`、`starworkKnowledge`、`starworkMultiagent` 等专家 Skill 的独立触发能力。
3. 明确四层 Skill 层级：系统主 Skill、系统专家 Skill、Kit 自带 Skill、Capability 项目内 Skill。
4. 收窄专家 Skill 的触发描述，避免它们抢“StarWork 是什么 / 怎么开始”这类泛化请求。
5. README 和 Agent 安装指南默认只引导用户使用 `starwork` 主入口；进阶文档再列出专家 Skill。
6. 保持跨宿主兼容：不要依赖“Skill 调 Skill”这种不稳定能力；主 Skill 可以指示用户或 Agent 切换到专家 Skill，也可以按专家 Skill 的公开流程继续执行。

## 非目标

1. 不取消 `starworkMultiagent` 等专家 Skill。
2. 不把所有专家 Skill 内容复制进 `starwork` 主 Skill。
3. 不要求所有宿主支持自动 Skill-to-Skill 调用。
4. 不改变 CLI 的职责边界：Skill 负责判断和生成方案，CLI 负责确定性执行和校验。
5. 不把 Kit 自带 Skill 全局化安装。
6. 不在 v0.2 设计通用 Skill 市场、云端 Skill registry 或自动推荐系统。

## Skill 层级

### L0：主入口 Skill

| Skill | 安装位置 | 是否全局安装 | 作用 |
|---|---|---:|---|
| `starwork` | `product/skills/starwork/` | 是 | 统一入口、产品解释、安装引导、意图判断、能力路由 |

`starwork` 是用户最应该记住的入口。它回答：

- StarWork 是什么？
- 我现在该怎么开始？
- 当前请求应该走初始化、诊断、知识库、多智能体，还是安装？
- 当前目录是否需要先变成 StarWork 工作台？

主 Skill 不负责深度执行所有专家流程。它只负责把用户带到正确能力，并在必要时读取最小的路由说明。

### L1：系统专家 Skill

| Skill | 安装位置 | 是否全局安装 | 直接触发场景 |
|---|---|---:|---|
| `starworkInit` | `product/skills/starworkInit/` | 是 | 创建、接入、初始化项目工作台或项目中心 |
| `starworkDoctor` | `product/skills/starworkDoctor/` | 是 | 诊断旧目录、解释 doctor 结果、设计 upgrade blueprint |
| `starworkKnowledge` | `product/skills/starworkKnowledge/` | 是 | 开启、检查、维护项目知识库 |
| `starworkMultiagent` | `product/skills/starworkMultiagent/` | 是 | 多 Agent 分工、lane、跨会话消息、Codex 标准会话工具 |

这些 Skill 继续保留直接触发，因为它们是用户会明确点名的专家能力。

但它们不再承担“StarWork 总入口”职责。用户问“StarWork 能做什么 / 怎么开始 / 我应该用哪个能力”时，应触发 `starwork` 主 Skill。

### L2：Kit 自带 Skill

| Skill | 源码位置 | 分发方式 | 触发场景 |
|---|---|---|---|
| `starworkSpawn` | `product/kit-skills/starworkSpawn/` | 项目中心 Kit 写入工作台 | 从项目中心创建项目工作台 |
| `starworkAudit` | `product/kit-skills/starworkAudit/` | 项目中心 Kit 写入工作台 | 巡检项目中心管理的项目 |
| `neat-freak` | `product/kit-skills/neat-freak/` | 项目 Kit 写入工作台 | 阶段收尾、整理、归档 |

Kit Skill 不是全局系统 Skill。它们跟具体工作台形态绑定。

主 Skill 可以识别这些场景，但不应把它们全局安装：

- 用户在普通项目里说“从项目中心创建项目”：主 Skill 提醒需要在项目中心工作台执行。
- 用户在项目中心里说“创建项目”：可以路由到 `starworkSpawn` 或按 `hub-spawn` 流程执行。
- 用户说“收尾整理”：如果当前工作台安装了 `neat-freak`，优先使用它；否则主 Skill 给轻量收尾建议，不假装项目内 Skill 存在。

### L3：Capability 项目内 Skill

| Skill | 源码位置 | 分发方式 | 触发场景 |
|---|---|---|---|
| `starworkKnowledgeProject` | `product/core/capabilities/knowledge/skills/starworkKnowledgeProject/` | `starwork knowledge init` 写入当前项目 | 项目知识库开启后的长期维护 |

Capability Skill 只在能力开启后出现在具体项目里。不要全局安装，也不要让 README 面向小白用户直接介绍。

主 Skill 和 `starworkKnowledge` 只需要知道：

- 开启知识库前：使用 `starworkKnowledge`。
- 开启知识库后：项目内维护可以使用 `starworkKnowledgeProject`。

## 主 Skill 职责

`starwork` 主 Skill 的 `SKILL.md` 应保持短小，建议不超过 250 行。

它只包含：

1. StarWork 一句话解释。
2. 安全承诺：先说明、先预览、用户确认后写入。
3. 路由矩阵。
4. 模糊请求处理流程。
5. 不确定时的最少提问规则。
6. 对专家 Skill 的切换指引。

### 主 Skill 第一屏

当用户第一次说“帮我用 StarWork”“这个项目接入 StarWork”“StarWork 怎么开始”时，主 Skill 应先回复：

```text
StarWork 是给 AI 协作准备的项目工作台。

它会把项目说明、当前任务、协作规则、交接记录和健康检查入口放到固定位置，让 AI 每次进入项目时不用从零猜上下文。

我会先判断你现在是哪种情况，再带你走对应流程。整个过程会先预览，不会直接改业务代码，也不会直接覆盖已有 AI 规则文件。
```

然后只问一个问题：

```text
你现在是想：
1. 安装 StarWork；
2. 创建或接入一个项目工作台；
3. 诊断一个旧目录；
4. 开启知识库；
5. 创建多个 Agent 分工；
6. 管理项目中心？
```

如果用户已经表达清楚意图，不要再问这道题，直接路由。

## 路由规则

| 用户意图 | 主 Skill 动作 | 专家 Skill |
|---|---|---|
| “StarWork 是什么 / 能做什么 / 怎么开始” | 解释产品，判断下一步 | `starwork` |
| “安装 StarWork / 让 AI 会用 StarWork” | 引导安装 CLI + Skills | `starwork` |
| “创建工作台 / 接入当前项目 / 初始化项目” | 切到初始化流程 | `starworkInit` |
| “旧项目能不能升级 / 目录乱了 / doctor 结果怎么看” | 切到诊断升级流程 | `starworkDoctor` |
| “开启知识库 / 让 AI 记住项目知识” | 切到知识库流程 | `starworkKnowledge` |
| “多智能体 / 多 Agent / lane / 跨会话指令 / 让开发 Agent 修” | 切到多智能体流程 | `starworkMultiagent` |
| “从项目中心创建项目” | 在项目中心内使用项目创建流程 | `starworkSpawn` 或主 Skill 项目中心流程 |
| “巡检项目中心 / 修复登记项目” | 在项目中心内使用巡检流程 | `starworkAudit` 或主 Skill 项目中心流程 |
| “收尾 / 整理 / 阶段结束” | 优先使用项目内整理 Skill | `neat-freak` |

## 专家 Skill 职责调整

### 共同调整

所有 L1 专家 Skill 都要做三类收窄：

1. **description 收窄**：保留明确场景词，减少泛化入口词。
2. **第一屏收窄**：解释本能力，不重复完整 StarWork 总介绍。
3. **主入口提示**：当用户请求过于模糊时，专家 Skill 应提示回到 `starwork` 主入口。

### `starworkInit`

保留直接触发：

- “创建 StarWork 工作台”
- “初始化当前项目”
- “接入已有项目”
- “创建项目中心”
- “init dry-run / init blueprint”

不再主动覆盖：

- “StarWork 是什么”
- “我该怎么用 StarWork”
- “帮我规划 StarWork 能力”

第一屏可以保留“工作台是什么”的短解释，但不要重复安装、知识库、多智能体等完整能力介绍。

### `starworkDoctor`

保留直接触发：

- “诊断这个目录”
- “doctor 结果怎么看”
- “旧模板升级”
- “生成 upgrade blueprint”

不再主动覆盖：

- 普通“开始使用 StarWork”
- 普通“项目初始化”

如果 doctor 发现目录不是 StarWork 工作台，下一步应明确交给 `starworkInit`，不要自己补初始化流程。

### `starworkKnowledge`

保留直接触发：

- “开启知识库”
- “初始化项目知识库”
- “整理长期知识”
- “knowledge status / check”

不再主动覆盖：

- 普通资料整理
- 普通 README 文档整理
- 阶段收尾整理

阶段收尾整理优先属于 `neat-freak`；长期稳定知识沉淀才属于 `starworkKnowledge`。

### `starworkMultiagent`

保留强直接触发。以下场景应直接触发，不必先经过主 Skill：

- 多 Agent 分工
- Agent Lanes
- 创建 / 绑定 / 读取 / 指令发送给其他 Agent
- Codex thread 创建、读写、命名、置顶、归档
- 跨会话交接消息

`starworkMultiagent` 是专家 Skill，不应降级为 reference。原因：

- 它要处理宿主能力差异。
- Codex 场景必须使用标准会话控制工具。
- 它涉及跨会话写入和用户授权边界。
- 用户经常会明确点名“开发 Agent / 产品 Agent / 验收 Agent”。

## 主 Skill 与专家 Skill 的关系

跨宿主不能假设存在稳定的“Skill 调 Skill”机制。因此 v0.2 采用文本级路由契约：

1. 主 Skill 判断出明确专家场景后，应在回复中点名建议使用的专家能力。
2. 如果当前宿主支持自动加载对应 Skill，可以加载并继续。
3. 如果当前宿主不支持自动 Skill 切换，主 Skill 仍可按专家 Skill 的公开规则继续执行，但不得复制维护另一套完整逻辑。
4. 专家 Skill 的详细流程仍以各自 `SKILL.md` 和 SPEC 为事实源。

推荐主 Skill 路由话术：

```text
这属于 StarWork 的多 Agent 分工场景，接下来应按 `starworkMultiagent` 流程处理。

我会先确认当前目录是不是 StarWork 工作台，再设计 lane 职责和写入范围；涉及 Codex 会话时，会直接使用 Codex 标准会话工具。
```

## 文件结构设计

新增：

```text
product/skills/starwork/
  SKILL.md
  references/
    routing.md
    install.md
```

说明：

- `SKILL.md`：主入口说明和核心路由。
- `references/routing.md`：完整路由矩阵、模糊意图判断、冲突处理。
- `references/install.md`：安装 CLI + Skills 的最小流程。

不建议把 `init.md`、`knowledge.md`、`multiagent.md` 全部复制成 reference。专家 Skill 已经是事实源，主 Skill 不应维护第二份流程。

调整：

```text
product/skills/starworkInit/SKILL.md
product/skills/starworkDoctor/SKILL.md
product/skills/starworkKnowledge/SKILL.md
product/skills/starworkMultiagent/SKILL.md
```

仅调整 description、第一屏边界和主入口回退提示；不要重写完整流程。

保持：

```text
product/kit-skills/starworkSpawn/
product/kit-skills/starworkAudit/
product/kit-skills/neat-freak/
product/core/capabilities/knowledge/skills/starworkKnowledgeProject/
```

这些不进入全局系统安装清单。

## 安装与分发

### v0.2 全局安装清单

`npx skills add jennie-shawn/StarWork -g -a codex -y` 应安装：

- `starwork`
- `starworkInit`
- `starworkDoctor`
- `starworkKnowledge`
- `starworkMultiagent`

不要安装：

- `starworkSpawn`
- `starworkAudit`
- `neat-freak`
- `starworkKnowledgeProject`

### 为什么不只安装 `starwork`

v0.2 不只安装 `starwork`，原因是：

1. 专家 Skill 有明确直接触发场景。
2. `starworkMultiagent` 等能力过复杂，不适合靠主入口转述。
3. 用户和 Agent 可能已经形成直接点名专家 Skill 的习惯。
4. 分阶段迁移更安全，避免一次性改变触发行为。

未来可以在 v0.3 评估：

- 是否把 `starworkInit`、`starworkDoctor` 等降级为主 Skill references。
- 是否只保留 `starworkMultiagent` 这类复杂专家 Skill。
- 是否让安装命令支持 “basic / advanced” 两种安装集。

## 验收标准

### 触发与路由

1. 用户说“StarWork 是什么 / 怎么开始 / 帮我用 StarWork”，应触发 `starwork` 主 Skill。
2. 用户说“安装 StarWork / 让这个 AI 会用 StarWork”，应触发 `starwork` 主 Skill。
3. 用户说“初始化 / 接入当前项目 / 创建项目工作台”，应触发 `starworkInit`，或由 `starwork` 立即路由到 `starworkInit`。
4. 用户说“诊断旧目录 / doctor 结果 / 升级旧模板”，应触发 `starworkDoctor`，或由 `starwork` 立即路由到 `starworkDoctor`。
5. 用户说“开启知识库 / 维护项目知识库”，应触发 `starworkKnowledge`，或由 `starwork` 立即路由到 `starworkKnowledge`。
6. 用户说“多 Agent / 多智能体 / lane / 跨会话消息 / 开发 Agent”，应直接触发 `starworkMultiagent`。
7. 用户说“从项目中心创建项目 / 巡检项目中心 / 收尾整理”，不得错误全局安装 Kit Skill；应根据当前工作台是否具备对应 Kit Skill 决定下一步。

### 层级与分发

1. `product/skills/` 中只放全局系统 Skill：`starwork` 和 L1 专家 Skill。
2. `product/kit-skills/` 继续只放 Kit 自带 Skill。
3. `product/core/capabilities/*/skills/` 继续只放 Capability 项目内 Skill。
4. 全局安装命令不得把 `starworkSpawn`、`starworkAudit`、`neat-freak`、`starworkKnowledgeProject` 装到全局。
5. `product/skills/README.md` 能解释 L0/L1/L2/L3 四层。

### 内容去重

1. 主 Skill 不复制 `starworkMultiagent` 的 Codex 标准会话工具细节。
2. 主 Skill 不复制 `starworkKnowledge` 的知识库 pages/synthesis 维护规则。
3. 主 Skill 不复制 `starworkDoctor` 的 upgrade blueprint 细节。
4. 专家 Skill 不再各自维护完整 StarWork 产品总介绍。
5. README 不平铺所有专家 Skill 的内部工作流，只给用户可理解的能力入口。

### 文档一致性

1. README、Agent 安装指南、`product/skills/README.md`、Skill 注册表对全局 Skill 清单说法一致。
2. README 仍面向 C 端用户，不退回技术部署说明。
3. Agent 安装指南仍只做 CLI + Skills 安装，不要求初始化工作台。
4. `rg -n "starworkSpawn|starworkAudit|neat-freak|starworkKnowledgeProject" product/skills product/docs/agent-install-guide.md product/README.md` 不应出现“全局安装这些 Skill”的说法。
5. `rg -n "StarWork 是什么|怎么开始|安装 StarWork" product/skills/starworkInit product/skills/starworkDoctor product/skills/starworkKnowledge product/skills/starworkMultiagent` 不应显示这些专家 Skill 抢主入口触发。

## 风险与应对

### 风险 1：主 Skill 和专家 Skill 同时触发

应对：

- 主 Skill 覆盖模糊入口。
- 专家 Skill 覆盖明确能力。
- description 中避免所有 Skill 都写“帮助用户使用 StarWork”。

### 风险 2：主 Skill 变成第二套巨型 Skill

应对：

- 主 Skill 只保留路由、安装和产品解释。
- 专家流程仍在专家 Skill。
- references 只放 routing 和 install，不复制所有专家文档。

### 风险 3：跨宿主不支持自动调用子 Skill

应对：

- 设计为“文本级路由契约”，不依赖自动 Skill 调 Skill。
- 主 Skill 可以继续执行高层确认，但复杂流程要提示进入专家能力。

### 风险 4：Kit Skill 被误装到全局

应对：

- 不移动 Kit Skill 源码。
- 文档和安装指南明确只安装系统 Skill。
- 验收扫描全局安装清单和 skill source 目录。
