## 〇、本文结论速览

1. **记忆要分三层**：用户级归宿主、项目级归工作台、跨项目级归 Hub。身份降级为"桥"能力；教训保留但收紧为项目教训，并改为"晋升式"使用契约。
2. **生存战略一条原则**：凡是宿主能原生做的，StarWork 不重新实现，而是编排它；StarWork 只拥有一样东西——宿主中立的项目事实。`adapt` 应升格为战略中心（provider 模式），宿主每次迭代变成 StarWork 的发版节奏。
3. **`_系统/` 骨架正确，需四个外科手术**：去掉重复的"下一步"（快慢分层）、压平目录、用"一文件一问题"表重写定义、补归档出口。
4. **上下文文件价值框架**："相关时再读"的文件几乎永远不会被读；文件只有两种可行使用方式——小到每次必读，或晋升为规则。
5. **worklog 冲突用一条协议定义消解**：`当前工作.md` 就是默认 lane 的 worklog；开启协作时 CLI 做一次性转换（内容迁移 + 降级为机器汇总看板 + write_scope 保护）。概念数量不增反减。
6. **"从真实工作流推导结构"应升格为核心产品叙事**：文件夹结构 = 工作循环的物化；目录是工位、lane 是岗位、Pack 是预制循环、init 采访是定制循环。配两条铁律压住风险。

## 一、记忆分层：身份/教训争论的最终结论

### 1.1 问题背景

总体评审报告曾提出"身份/教训放在单项目 Kit 里错位"。创始人指出：产品定位是帮普通人零配置结构化使用 AI，做记忆/教训功能时宿主（Codex、Claude Code）尚无记忆能力。经讨论，结论修正如下——**反对的不是记忆功能，是记忆没有分层**。

### 1.2 记忆的三层归属

"记忆"不是一种东西，至少有三种，归属完全不同：

| 记忆类型 | 例子 | 应该归谁 | 宿主会不会做 |
|---|---|---|---|
| 用户级 | 我是谁、沟通偏好、表达习惯、领域背景 | 跟人走，跨项目 | **正在做**（Claude Code memory、ChatGPT memory），且会越做越好 |
| 项目级 | 项目状态、决策、"这个客户讨厌 X"、"这个流程在 Y 步会出错" | 跟项目走，进 git | **不会做好**——宿主记忆是工具私有、不可移植、不可审计的 |
| 跨项目级 | 多项目复用的方法论、通用教训 | 跟组织/Hub 走 | 不会做 |

### 1.3 对现有 Kit 的结论

- **`_系统/教训/` 大部分是对的**（修正总体报告的说法）。"这个项目踩过的坑"是纯项目级资产，必须留在项目、进 git、换工具不丢——恰恰是宿主记忆做不到的。需要的改动：定义收紧为**项目教训**（只记这个项目的坑），通用教训上浮到 Hub。
- **`_系统/身份/` 是真正错位的**。用户偏好是用户级记忆，每个项目复制一份必然漂移，且这是宿主原生记忆的主场。在宿主必赢的地盘上并行维护两套，将来不一致用户会把账算在 StarWork 头上。

### 1.4 身份改为"桥"模式

具体方案：

- **宿主有原生用户级记忆时**：`_系统/身份/` 不存正文，只存一句指引（"用户级偏好由宿主记忆维护"）；`adapt` 负责往宿主记忆里种一条指路条目。一份事实源，零漂移。
- **宿主没有记忆时**（或多宿主混用）：StarWork 身份文件作为降级方案继续工作——复用已有的"能力探测 + 降级"框架。
- **反向晋升流**：宿主记忆里自动捕获的内容，经用户确认后晋升为项目事实（doctor 或 skill 提示"宿主最近记了这几条，要不要沉淀进项目教训？"）。"捕获在宿主、确认归 StarWork"与已有的"草稿晋升正式事实源"是同一产品语法。

### 1.5 协议修订项

Core 协议补一节**"记忆分层"**：用户级归宿主、项目级归工作台、跨项目归 Hub。这一节同时是对"Claude Code 都有记忆了还要 StarWork 干嘛"的标准答案——A 测用户必然会问，提前写进协议比临场解释强。

## 二、宿主生存战略：事实归你，功能租宿主的

### 2.1 核心原则

> **凡是宿主能原生做的，StarWork 不重新实现，而是去编排它；StarWork 自己只拥有一样东西——宿主中立的项目事实。**

### 2.2 三层模型

```text
┌─────────────────────────────────────────────┐
│ 事实层（StarWork 拥有）                        │
│ 项目状态 / 当前工作 / 决策 / 项目教训 /          │
│ lane 分工 / 知识库 —— 纯文件、人可读、进 git     │
├─────────────────────────────────────────────┤
│ 注入层（StarWork 编排，宿主提供）                │
│ adapt 把事实接进每个宿主的原生机制：              │
│ CLAUDE.md / memory / AGENTS.md / hooks /      │
│ skills / subagents……                         │
├─────────────────────────────────────────────┤
│ 行为层（最薄，随宿主迭代随时重写）                │
│ Skill prompt、降级策略、引导话术                 │
└─────────────────────────────────────────────┘
```

- **事实层吃不掉的原因**：宿主的商业利益决定其记忆永远是工具私有的——Claude Code 不会帮用户把记忆带去 Codex；而项目事实必须比工具活得久。"你的项目记忆属于你，写成你看得懂的文件，存在你的 git 里"——这个位置宿主结构性地做不了。
- **注入层让 StarWork 顺着宿主变强**：宿主每发布一个新能力，不是威胁，是一个新的注入目标。实例：
  - 宿主出原生 memory → adapt 把宿主 memory 的索引指向 StarWork 项目事实文件，或种一条"项目级事实读 `_系统/`"的指路记忆。
  - 宿主出 hooks → adapt 注册"会话结束提醒更新当前工作"的 hook（执行回路正是靠宿主新功能才做得成）。
  - 宿主出原生 subagents / 多会话 → lane 的 charter 和 write_scope 投影成宿主 subagent 配置，不与之竞争。

  宿主越强，注入层能接的插座越多，同一份事实在每个宿主里的表达越原生——宿主在替 StarWork 打工。

### 2.3 `adapt` 升格为战略中心（provider 模式）

当前产品的明星是 `init`（一生用一次），但持续创造价值的是 `adapt`（注入层执行者）。建议改造为按宿主版本演进的 **provider 模式**：

- 每个宿主一个适配包，声明"该宿主当前版本有哪些插座（rules 文件 / memory / hooks / skills / subagents），StarWork 的哪个事实角色接到哪个插座"。
- 宿主发新版 → StarWork 发 adapter 更新 → 用户跑 `starwork adapt --refresh`。
- **宿主的迭代节奏直接变成 StarWork 的发版节奏**——这是"吃宿主红利"的产品化形态。

### 2.4 判断什么不该做

凡是在自建"宿主迟早原生提供"的运行时能力（跨会话投递、会话管理、自动记忆捕获），标记为**过渡能力**：做薄，随时准备换成宿主原生版。

### 2.5 第二重护城河：普通人

所有宿主的产品基因都面向开发者：英文目录、终端心智、配置文件文化。StarWork 定位"普通人不需要配置就能结构化用 AI"：中文目录、工作台隐喻、课程陪跑、dry-run 确认。这不是本地化差异，是**用户群的结构性错位**——宿主再迭代记忆和 subagent，不会为不懂终端的内容创作者设计"项目状态 / 当前工作 / 交接"的工作语义。

防御纵深因此是双重的：架构上事实层宿主中立（需持续跟跑宿主迭代来维持）；用户上服务被 AI 能力溢出覆盖的普通工作者（宿主基因不会掉头来打，**更硬**）。这反过来印证：Content Creator Pack 和课程渠道不是商业化附属品，是护城河本体的一部分。

## 三、`_系统/` 结构审计与修订建议

### 3.1 总判断

骨架正确，该有的角色都有，不缺东西；问题出在**重复、层级和命名**。需要四个外科手术，全部是 profile 和模板层改动，协议不动——这恰好证明角色抽象的价值。

### 3.2 缺陷与修法

**缺陷 1：两个文件都有"下一步"，模板自己违反单一事实源原则。**
`当前项目.md` 和 `当前工作.md` 模板都有"下一步"段，两个文件同时声明拥有未来，漂移必然。
修法：用**变化速度**切分。`当前项目.md` 只放慢变内容（目标、阶段、事实源、风险）；"下一步""近期重点"全部归 `当前工作.md`。快慢分层后 AI 也容易判断该更新哪个：会话级变化写当前工作，里程碑级变化才动当前项目。

**缺陷 2：目录层级为不存在的文件付费。**
现状：`上下文/` 一个文件、`任务/` 一个文件、`身份/` 和 `教训/` 各一个 README.md。其中 `身份/README.md`、`教训/README.md` 里装的是正文不是目录说明——人和 AI 对 README 的预期都是"这个目录干嘛的"，语义错位。
修法：**压平**。

```text
_系统/
├── 当前项目.md      # 慢变：这个项目是什么、做到哪个阶段
├── 当前工作.md      # 快变：现在干什么、下一步、下次会话从哪接
├── 决策.md          # 定了就不反悔的事（decisions 能力，建议默认开）
├── 教训.md          # 这个项目踩过的坑
└── 协作/            # 开启多 Agent 后才出现（lanes、shared）
```

五个条目、一眼到底。压平只是改 zh profile 路径映射。等某个角色真的长出多个文件（如决策按年归档）再升格成目录，由 doctor 引导。

**缺陷 3：教训 / 决策 / 知识库的分拣规则没写成用户语言。**
普通用户每次沉淀都要三选一，认知负担真实存在。
修法：用**"每个文件回答一个问题"**重写 `_系统/` 定义，直接放进 AGENTS.md：

| 文件 | 它回答的唯一问题 | 写入时机 |
|---|---|---|
| 当前项目.md | 这个项目是什么？做到哪了？ | 阶段变化时 |
| 当前工作.md | 现在在干什么？下个会话从哪接？ | 每个会话 |
| 决策.md | 我们定过什么不再反悔的事？ | 用户拍板时 |
| 教训.md | 这个项目里踩过什么坑？ | 踩坑之后 |
| 知识库（可选） | 这个领域/客户的长期知识是什么？ | 知识复用第二次时 |

这张表本身就是结构的自我解释。**一个结构如果不能用"一文件一问题"说清楚，就是设计错了**——建议作为后续所有结构设计（Pack、Lane Workbench）的验收标准。

**缺陷 4：只有写入，没有排出——结构缺少生命周期。**
当前工作和教训持续累积，最小 Kit 没有归档机制。修法：模板加"已归档"指引 + doctor 体积提醒，归档目录按需创建。

## 四、上下文文件的价值框架与逐文件结论

### 4.1 三个测试

一个给 AI 读的文件，价值取决于三个测试：

1. **读取测试**：AI 读了之后，行为会不会真的不同？
2. **写入测试**：有没有清晰的时机让 AI 知道"现在该写它"？没有触发时机的文件必然变质。
3. **替代测试**：这个信息是否有更便宜的载体（git 历史、宿主记忆、内容本身）？

### 4.2 一条关键经验规律

> **"相关时再读"的文件，实际上几乎永远不会被读。** AI 不知道自己不知道什么——它不会在高风险操作前想起来"该去查教训"。

因此文件只有两种可行使用方式：**小到每次会话必读**（进必读路径），或**晋升成规则**（写进 AGENTS.md）。"放在那里供查阅"是给人设计的模式，对 AI 基本失效。

### 4.3 逐文件结论

| 文件 | 读取测试 | 写入测试 | 替代测试 | 结论 |
|---|---|---|---|---|
| 当前项目.md | 满分：每会话开局定向 | 偏弱但慢变、伤害小 | 无替代 | **保留**，去掉"下一步" |
| 当前工作.md | 满分：交接核心 | 时机清晰但靠自觉（需 hook 闭环） | 宿主 resume 仅覆盖同工具内续接 | **保留**，协作模式下重定义所有权（第五节） |
| 身份/ | 语气沟通——宿主原生主场 | 几乎无触发时机（init 填一次永不更新） | 被宿主记忆替代 | **降级为桥能力**（唯一动存废的） |
| 教训/ | 读取契约（"相关时读"）不会被履行 | 候选/已确认设计良好 | 无替代 | **保留但换使用契约**（4.4） |

### 4.4 教训重新定义为"规则的苗圃"

```text
踩坑 → 候选教训（教训.md）→ 已确认教训 → 足够重要的，晋升为 AGENTS.md 里的一行规则
```

两条硬约束：

1. 教训.md 进入每次会话必读路径，因此**活跃教训设上限**（建议 ≤10 条），超限必须晋升、合并或归档。
2. 真正改变行为的最终形态不是"教训"，是"规则"——AGENTS.md 的"避免"清单是教训的毕业去向。教训文件永远小而锋利。

### 4.5 调整后的必读路径

AGENTS.md → 当前项目.md → 当前工作.md + 教训.md，共三个小文件。每次会话上下文开销克制，这本身就是对普通用户的承诺："**工作台不会越用越重**"。

## 五、协作模式下 `当前工作.md` 与 lane worklog 的统一

### 5.1 冲突本质

开启协作后，"现在在干什么"有 N+1 个声明者：每条 lane 的 worklog + 全局当前工作.md。三种坏结局：所有 lane 都写（争抢+重复）、没人写（变质误导）、部分 lane 写（信息偏科）。

### 5.2 解法：一条协议定义，不加新机制

> **`当前工作.md` 就是"默认 lane"的 worklog。单 Agent 工作台本质上是只有一条隐式 lane 的多 Agent 工作台。**

**单 Agent 模式**：一切照旧，无冲突。

**开启 agent-lanes 时**，由 CLI 在 `multiagent init` 执行一次性转换：

1. **内容迁移**：当前工作.md 的存量内容迁入第一条 lane（通常 product-planning 或用户指定主 lane）的 worklog。内容不丢，只是搬到该在的位置。
2. **降级为看板**：当前工作.md 变为每条 lane 一行（lane 名、当前焦点、阻塞、最后更新时间），细节在各自 worklog。文件顶部写明"本文件由机制维护，请写自己 lane 的 worklog"。
3. **write_scope 保护**：转换后当前工作.md 移出所有普通 lane 的写入范围——write_scope 本来就是干这个的，只是此前未把全局文件纳入管辖。

### 5.3 看板由机器汇总（推荐）

- worklog 规定固定头部块（**当前焦点 / 下一步 / 阻塞 / 更新时间**四字段）。
- `starwork multiagent status` 或 doctor 从各 worklog 头部提取、重新生成看板。零争抢、永不偏科。
- "worklog 更新了但看板没刷新"成为 doctor 可机检的漂移项。
- 协调 lane 人工维护可作为机器汇总之上的批注层，不作为基础机制（避免回到"靠自觉"和 CEO lane 单点）。

### 5.4 其他全局文件在协作模式下的所有权

| 文件 | 协作模式下的所有权 |
|---|---|
| 当前项目.md | 仍是单一事实源，慢变；任何 lane 可提议，经用户或协调 lane 确认（现有"需要确认"规则已覆盖） |
| 决策.md | 任何 lane 可提议，用户拍板后写入（现有规则已覆盖） |
| 教训.md | 任何 lane 可直接追加**候选教训**（追加式写入，争抢概率低），晋升仍需确认 |
| shared.md | 不变。与看板分工：看板答"谁在干什么"，shared 答"谁产出了什么给谁用"，不重叠 |

### 5.5 额外收益：协议被简化

此前"单 Agent 的当前工作"和"多 Agent 的 worklog"是两套并列机制；统一后协议里只有一个概念（lane worklog），单 Agent 是 N=1 的退化情形。**概念数量减一**，且"从一个人用到一个团队用"的升级路径变成平滑连续谱——与"普通人零配置起步、需要时长出多 Agent"的产品叙事严丝合缝。

## 六、工作循环：把"从真实工作流推导结构"升格为核心叙事

### 6.1 产品定义

创始人提出：init 可以根据用户的实际工作内容和流程，梳理出合理的工作区结构，配合多 Agent 机制（"Loop Engineering"方向）。顾问判断：**这是产品最值钱的一句产品定义**——它把 StarWork 从"模板"彻底区分开。不管这个词最终流行成什么样，背后的实质成立：

> **好的工作区结构不是资料分类学，而是一条循环的工位图。**

普通人的真实工作是不断重复的循环：

```text
输入进来 → 加工 → 评审/确认 → 成果出去 → 复盘 → 回到输入
```

Content Creator Pack 的"灵感→选题→大纲→正文→发布→复盘"就是一条循环。

### 6.2 统一心智模型（同时解决概念过载）

| 现有概念 | 循环视角下的本质 |
|---|---|
| 目录 | 循环上的**工位** |
| Lane | 工位上的**岗位**（write_scope 即工位边界） |
| Pack | **预制好的循环**（场景验证过的循环直接装） |
| init 采访 / blueprint | **定制循环**（从用户真实循环推导工位图） |

对外只讲一个心智模型："**StarWork 把你的工作循环变成 AI 团队的流水线**"。Pack、blueprint、lane 都是这句话的不同侧面——概念过载问题被同一个动作顺手缓解。

### 6.3 实现路径（顺势升级，非新造系统）

- `starworkInit` 采访问题从分类学问法（"你有哪些资料、想要哪些目录"）改为**循环问法**："你的工作一轮怎么转：什么进来、经过几道工序、谁确认、什么出去、多久复盘一次。"
- blueprint schema 加 **`loop` 段**（工位、输入输出、确认关卡、岗位配置），成为贯通 init、multiagent、pack 的统一产物。
- 现有 `starworkInit` 采访 + `spawn --blueprint` 骨架已在。

### 6.4 战略意义

宿主可以一键生成 CLAUDE.md，但**不会采访一个不懂终端的普通人"你的业务一轮怎么转"，再设计工位图和岗位分工**——这是咨询能力的软件化，直接接进课程和陪跑。

### 6.5 两条铁律压住风险

**铁律 1：路径可定制，角色不可变。**
若每个工作区都 bespoke，doctor 检查不了、Demo 不可迁移、Pack 装不进——产品退化回"AI 帮你建了一堆文件夹"。采访产出的任何定制结构都必须表达为 blueprint 里的**角色映射**，doctor 永远按角色检查、不按路径检查。init 越聪明，这条越要硬。

**铁律 2：先通用，后演化。**
采访得来的循环是用户"以为的"工作方式，与真实方式常常不同；按错误循环生成的定制结构比通用结构更糟。正确节奏：

```text
General Pack 通用循环开工 → AI 陪用户真实跑两三轮 →
doctor/skill 基于实际使用提出结构演化建议 → 用户确认后调整
```

"结构跟随使用而演化"是比"一次生成"更高级的叙事——工作区本身也在循环里迭代。可作为 v0.2 候选能力（`starwork evolve` 或 doctor 结构建议）；当前先做采访问法和 blueprint loop 段。

另：**不要在 Golden Demo 做出来之前对外营销这个词**——"从工作流推导结构"的主张需要 Demo 证明，否则只是话术。
