## 一、总体判断（TLDR）

产品思考密度高，规划纪律好（issue 台账、SPEC、验收、roadmap 真实在用），方向踩在真实痛点上。但有三个比产品设计更紧迫的问题：

1. **没有外部用户证据。** 全部 17 个 issue 来自创始人和内部测试。没有真实 A 测用户的"A 测稳定化"是在真空里打磨。
2. **概念数量远超用户承受力。** Core、Kit、Pack、Capability、Preset、Profile、Skill、Adapter、Lane、Hub、Blueprint、Workbench——需要主动收敛，而不只是承认。
3. **工程底座与产品承诺不匹配。** CLI 是约 1 万行的单文件（`cli/src/cli.js`），测试只覆盖 init；而产品核心承诺恰恰是"保守、不破坏用户文件"，doctor / upgrade / spawn / multiagent 等高风险写入路径没有回归保护。

贯穿性结构问题：**协议的可信度完全取决于执行机制。当前 90% 的力气花在"定义什么是对的"，只有 10% 花在"保证它持续是对的"。** 一个三周没更新的 `当前工作.md` 比没有更糟——它会主动误导 AI。

另：顾问简报本身已经路径漂移（写的是 `satellite-starwork/product/` 结构，当前仓库根目录即 product 仓库）。一个以防漂移为卖点的产品，引导文档先漂移了——说明"文档漂移检查"应该机制化。

## 二、产品定位与叙事

- "AI 工作系统套件"是内部语言。README 里"把项目变成一个 AI 看得懂、你也放心的工作台"更好。
- 建议一句话卖点方向：**"StarWork 把你的项目文件夹变成 AI 团队的办公室——背景、规则、分工、交接都有固定位置，换会话、换工具都不断档。"** "办公室 / 工位 / 员工手册"的类比天然解释多 Agent 和交接。
- 核心卖点应明示：**"你的项目记忆以文件协议存在，属于你，不绑定任何一家 AI 工具。"** 各宿主都在自建记忆能力，StarWork 的防御位是宿主中立，这一点目前是隐含的，应该说出来。

### 必须正视的竞争位置

宿主（Claude Code 的 CLAUDE.md + memory、Codex 的 AGENTS.md 原生支持）正在蚕食"给 AI 项目上下文"这个单点价值，这个点会被宿主白嫖掉。StarWork 必须站住宿主因商业利益不会做的三件事：

1. **跨宿主中立**（Claude Code 不会帮你把上下文带去 Codex）。
2. **多 Agent 职责协作协议**（lane / write_scope / handoff；宿主只关心自己的会话）。
3. **多项目组合管理**（Hub；宿主边界是单个项目目录）。

产品叙事、roadmap 资源、协议演进都应向这三点倾斜。凡是宿主下个季度就可能原生做掉的功能，标记为"过渡能力"，不投重注。

## 三、Core 协议设计评价

### 做对了的（坚持）

1. **角色抽象（`core/baseline/roles.md`）是全产品最值钱的设计。** 角色→profile 路径映射让已有项目无损接入和多语言成为可能，是 StarWork 区别于"文件夹模板"的真正依据。不允许任何 Pack / Skill 绕过角色写死路径。
2. **"一个工作区只能有一个项目状态事实源" + "过程材料必须明确晋升才能进正式事实源"**：对多份过时状态互相打架这一最常见溃败模式的正确防御。
3. **Kit 只是 preset 组装产物、不是协议事实源**：避免模板腐烂反噬协议。
4. **Project Kit 的 `AGENTS.md` 模板是质量最高的单一产出物**（短、分层、动作明确），这是用户实际买到的东西。

### 有问题的

1. **五层管线为不存在的多样性买单。** `baseline + profiles + capabilities + presets → kit` 五层抽象，真实变体只有 2 preset × 2 语言。建议**冻结**：v0.2 前不给任何一层加新机制；第三个真实 preset 出现时再检验管线是否值得，若 profiles 和 presets 总是一起变就合并。
2. **"协议"目前是散文，不是协议。** 机器可验证的事实只存在于 doctor 的检查逻辑里，而 doctor 没有测试。建议把协议事实源收敛为：`workspace.json` schema（含 role→path 映射）+ doctor 检查项清单；散文文档降级为解释。"符合 Core 协议"必须是可判定命题，这是"开源协议形成传播"叙事成立的前提。
3. **身份/教训放在单项目 Kit 里错位。** 它们本质是用户级资产，单项目用户每个项目复制一份必然漂移；且宿主正在原生解决用户级记忆。建议：单项目 Kit 默认不带身份/教训（降为 capability），协议明确"用户级记忆交给宿主、项目级事实归 StarWork"。
4. **`.obsidian/` 不该出现在 Kit 里。** 个人工作流泄漏进产品，应降为可选 capability 或移除。

## 四、工作台结构设计评价

### 结构本身

- `_系统/` 下划线置顶 + 中文目录名对目标用户正确，但**中文目录名有跨平台税**：在宣传跨宿主之前，必须在 Windows 上完整跑通 init → doctor。
- M2.10 把通用工作目录移交 General Pack 的边界清理方向正确：**Kit 越小，协议越可信**。
- **Hub Kit 是最明显的过度设计区。** `.incoming/` 五类收件箱、`.internal/` twin-bot 回写协议、`coordination/messages/` 四态消息队列，是为创始人本人"几十个项目 + 分身 bot"设计的机制，alpha 用户无人需要。建议对外 Hub 砍到三件事：**项目注册表、共享技能、巡检（audit/repair）**；消息队列与回写协议保留为 power-user 自用配置，不进公开 Kit 和文档。

### 结构性缺口：协议没有执行回路（本报告最重要的一条）

当前体系隐含假设"AI 会自觉遵守 AGENTS.md 的维护规则"（会话结束更新当前工作、登记决策、登记 shared 输出），但 prompt 遵循是概率性的，没有机制保证状态文件保持新鲜。

**工作台的价值不等于结构完整度，等于状态文件的新鲜度。** 结构完美但状态过期的工作台，对下一个 AI 会话是负资产。

建议三步闭环：

1. **doctor 增加新鲜度检查（一级检查项）**：`当前工作.md` 等入口文件的更新时间显著落后于项目其他文件时，提示"状态可能过期，接手前先核对"；git 仓库可用 commit 历史做更准判断。
2. **宿主 hook 闭合回路**：`starwork adapt` 生成适配文件时注册"会话结束前提醒更新当前工作和 worklog"的 hook（Claude Code 有 Stop/SessionEnd hooks，Codex 有对应机制）。这是"协议靠自觉"到"协议有执行"的关键一步，属于 Adapter 层，符合现有架构，也是竞品最难抄的部分。
3. **git 作为审计层**：`init` 默认 `git init`（用户可拒绝），doctor 检查未提交变更。这同时解决"AI 写坏文件如何回滚"——比 dry-run 更根本地回应新用户"不放心"。

### 上下文经济学缺失

入口文件（当前项目、当前工作、worklog）会随时间膨胀，而它们是每个会话的必读项。协议应定义**文件预算**：每个入口角色有建议行数上限，超限时 doctor 提醒归档。可作为差异化卖点："StarWork 的工作台不会越用越重"。

## 五、Skill / CLI / Pack / MultiAgent 边界

- **主入口 + 专家 Skill 分层方向正确**；`starworkMultiagent` 保持强直接触发合理（涉及宿主工具调用，多一层路由多一分出错面）。
- **README 只暴露主入口 + multiagent**，其余专家能力放"继续了解"。新用户第一个决策应是"装不装"，不是"装哪几个"。
- **SKILL.md 过长**（starworkInit 538 行、starworkDoctor 435 行），跨宿主模型遵循率会不稳定。alpha 期间做一次"砍半"练习：流程性内容下沉给 CLI 输出承载（CLI 输出确定，prompt 遵循是概率）。
- **MultiAgent 壁垒成色要打折**：自动化只在 Codex 成立，Claude Code 降级、Cursor 只读、Trae 人工。对外叙事相对真实能力超售。建议文档放一张诚实的**宿主能力矩阵**；叙事重心放在文件协作协议（任何宿主、包括人工降级时都成立），自动投递讲成"在支持的宿主上的加速器"。
- **`.starwork/` 边界判断规则（"脱离 StarWork 仍有独立业务价值就不进"）非常好**，但目前只是文档约定。让 doctor 做边界漂移检查：`.starwork/` 出现 .md 正文、worklog、超阈值文本即 warning。便宜且高价值。

## 六、Lane Workbench：值得做，但简报方案会重蹈覆辙

"AI 不会主动使用空 workspace"的观察准确，但"预生成 active/drafts/notes/evidence/handoff 五目录 + 按岗位差异化 scaffold"会制造更多空目录。空目录不被使用的原因不是不够多，而是没有行为驱动。

最小可行设计：

1. 每个 lane 只生成两个文件：`worklog.md`（已有）+ `charter.md`（岗位说明：职责、写入范围、产出物去哪、交接给谁）。charter 是给 AI 读的行为指令，不是给文件住的目录。
2. 目录按需懒创建，由 Skill 规则驱动（"产出证据时放进 `workspace/evidence/`，没有就建"）。AI 对"有指令的懒创建"的遵循率远高于"看见空目录就用"。
3. 暂不做 `promote` / `review` / `archive` 命令；先用 doctor 加"workspace 陈旧度检查"，观察真实使用模式两个月再决定哪些操作值得命令化。
4. 岗位差异化 scaffold 放 v0.2，且作为 Pack 能力而非 Core 机制——岗位结构本质是场景知识。

## 七、工程层面

- **cli.js 万行单文件**：alpha 可忍，邀请外部贡献者或加新命令前必须按命令拆模块。
- **测试只有 init 一条线**：最低限度补——doctor 对固定 fixture 工作台的输出快照测试、`upgrade --blueprint` 的"用户文件不被覆盖"测试、multiagent 状态机（`manual_handoff_required` 等）单元测试。"保守写入"承诺目前靠人肉验收。
- **release checklist 脚本化**为 `npm run release-check`：版本号一致性、latest 检查、文档与 CLI help 的命令名 grep 比对。文档漂移是反复出现的问题类别，值得机制化。

## 八、商业化（CEO 视角）

### 生意的形状

这是**创始人即渠道**的生意：真实护城河不是协议（会被抄、会被宿主蚕食），而是 GFM 课程沉淀的受众信任 + 创始人重度使用产生的方法论。商业设计应顺着这个形状，而不是按"开源工具公司"标准剧本。

**单靠开源不会传播。** 传播的不是协议，是看得见的结果——"学员的 AI 团队真的在干活"的截图和录屏。建议做 `starwork showcase`：把工作台脱敏导出成一页可分享 HTML（项目状态、lane 分工、worklog 摘要、协作时间线），让每个学员的工作台变成获客素材，产品自带分发。

### 收入阶梯（四层）

| 层 | 内容 | 角色 | 时间 |
|---|---|---|---|
| 免费 | Core + CLI + General Pack + 文档 | 信任资产、教具、获客 | 现在 |
| 课程 | GFM 课程 + Content Creator Pack + Demo 工作台 + 社群 | **现金流主体** | 现在到 v1.0 |
| 陪跑 | 把学员真实业务搬上 StarWork 的高客单服务 | 利润 + 最深的用户研究 | alpha 后即可 |
| 团队版 | 共享 Hub、权限、同步、审计（需服务端） | 真正可订阅的形态 | v1.0 之后再评估 |

关键判断：

- **Pack 不单独定价。** Pack 是课程章节的物化，捆在课程里价值感知高一个量级，省掉支付/license/盗版全部 plumbing。v0.2 前不投入任何商业化管道。
- **陪跑被低估**：每一单陪跑都是付费的用户研究。建议 alpha 期间开 2-3 个名额、定高价，目的是学习不是收入。
- **团队版才是订阅制成立的地方**（个人工具在中国市场收订阅极难），但需要服务端，是 v1.0 之后的事。现在唯一要做的：协议层不做"假设永远单机单用户"的不可逆决策（当前 workspace.json 和 Hub registry 的设计没有此问题，保持）。

## 九、发展方向与迭代节奏

### 当前最重要的转向：从"完善产品"到"获取证据"

建议 alpha 退出标准定义为用户行为指标：

> 10 个非本人/非学员的外部用户，仅凭公开文档完成 init → doctor，其中 5 个第二周仍回来使用；记录每一个卡住的位置。

### 北极星指标建议

- 每周运行过 doctor 的工作台数（活跃）——**留存住在 doctor 里**：init 一生用一次，doctor 一生用一千次。
- 状态文件新鲜度中位数（健康）。
- 开启多 lane 的工作台比例（深度）。

### 迭代节奏：两周一周期

每周期纪律：
1. 一个用户可见的成果（不是内部重构）。
2. 至少 2 次真实用户使用观察（学员录屏亦可）。
3. 周期末跑 release-check + 用 doctor 自检本仓库（包括顾问简报等文档的漂移）。

### 6 个月主线

```text
现在    内容创作者 Golden Demo（合并 M2.13 + M3 启动：Demo 直接做成内容创作者工作台）
        + 5-10 个外部用户跑通安装链路，记录卡点
1-2 月  按卡点收敛概念和文档；Lane charter 最小版；doctor 新鲜度 + 边界检查
2-4 月  Content Creator Pack v0.1 正式化；会话结束 hook；CLI 拆模块 + 核心路径测试
4-6 月  v0.1 正式发布；课程渠道第一波传播；再评估团队版可行性
```

合并 M2.13 与 M3 的理由：种子用户是内容创作者学员，general pack 的 demo 对他们没有代入感；Demo 本身就是营销素材；串行排法会把真实场景验证再推迟一两个月，而当前最缺的就是外部反馈。

## 十、四档分桶汇总

### 必须现在改

- 更新顾问简报及相关文档的路径漂移（仓库结构已变）。
- 定义带用户行为指标的 alpha 退出标准，开始找外部用户。
- 文档补诚实的宿主能力矩阵，停止隐性超售跨宿主自动化。
- release checklist 脚本化（先覆盖版本号一致性）。

### Alpha 期间改

- 用户可见概念收敛到 3 个以内（工作台 / 功能 / Agent 分工），其余降为内部词。
- Golden Demo 直接做成内容创作者工作台（合并 M2.13 与 M3 启动）。
- doctor 三项升级：新鲜度检查、`.starwork/` 边界漂移检查、workspace 陈旧度检查。
- `init` 默认 git init（可拒绝）+ doctor 检查未提交变更。
- Lane `charter.md` 最小版（不做目录 scaffold）。
- starworkInit / starworkDoctor 的 SKILL.md 砍半，流程下沉给 CLI 输出。
- doctor / upgrade / multiagent 回归测试。
- README 第一屏分流"使用者 / 开发者"；只暴露主入口 + multiagent。
- 对外 Hub 砍到注册表 + 技能 + 巡检；Kit 移除 `.obsidian/`；身份/教训降为 capability。
- Windows 上完整验证 init → doctor（中文目录名跨平台税）。
- 陪跑开 2-3 个高价名额（目的是用户研究）。

### v0.2 再考虑

- 岗位差异化 workbench scaffold（作为 Pack 能力）。
- `promote` / `review` / `archive` 命令（等真实使用模式出现）。
- cli.js 模块化拆分（若外部贡献者出现则提前）。
- npm 包瘦身（files 当前含 core/schemas/adapters 全量研发资产）。
- `starwork showcase` 工作台脱敏导出（若传播需求提前则提前）。
- 协议事实源收敛为 workspace.json schema + doctor 检查项清单。
- 入口文件"文件预算"与归档规则。
- 会话结束 hook 的全宿主覆盖。

### 不建议做

- 继续扩张 Core 协议或新增宿主自动化（现有判断正确，坚持）。
- 预生成多层空目录的 Lane Workbench 方案。
- 拿到外部用户证据前启动第二个场景 Pack。
- 任何付费 / license 基础设施。
- Pack 单独定价。
- v1.0 前投入团队版服务端。
