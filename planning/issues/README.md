# StarWork Issue 反馈与跟踪机制

日期：2026-06-01

## 定位

`product/planning/issues/` 用来收集和跟踪 StarWork 的真实问题闭环，包括 bug、A 测反馈、体验问题、验收阻塞、文档偏差和需要进一步判断的产品反馈。

它和需求、SPEC 的区别：

- Issue 记录“发现了什么问题、影响谁、证据是什么、现在处理到哪一步”。
- SPEC 记录“确认要怎么改、由谁实现、怎么验收”。
- GitHub Issue 适合公开协作或外部用户跟踪；本地 issue 是产品规划事实源，两者需要互链，不互相替代。

## 文件职责

| 文件 | 职责 | 属性 |
| --- | --- | --- |
| `product/planning/issues/index.md` | Issue 跟踪唯一入口，记录状态、优先级、负责人、来源、下一步和关联文档。 | 持续更新 / issue 事实源 |
| `product/planning/issues/template.md` | 新 issue 的记录模板。 | 模板 |
| `product/planning/issues/ISSUE-XXX-*.md` | 信息量较大的 issue 详情文件。 | 可选 |

## Issue 单填写要求

每个 issue 必须同时有两层记录：

1. `index.md` 上方表格里有一行摘要，方便扫描状态和下一步。
2. 同一个文件里有对应的 `## ISSUE-XXX：标题` 详情段；信息量很大时拆成独立 Markdown 文件，并从 index 链接过去。

新 issue 必须至少写清：

| 必填项 | 要求 |
| --- | --- |
| 标题 | 用用户能理解的问题命名，不写成内部任务名。 |
| 类型 | 从 `cli`、`core`、`skill`、`kit-pack`、`docs`、`release`、`product`、`workflow` 中选择。 |
| 优先级 | 用 P0-P3 标记影响程度。 |
| 状态 | 初始为 `new`，分流后改为 `triaged`、`planned` 等。 |
| 来源 | 写清来自用户反馈、A 测、验收、真实项目、自动测试还是开发验证。 |
| 现象 | 区分用户可见表现、期望表现和实际表现。 |
| 证据 | 至少给出一个文件、命令、日志、截图、复现描述或验收报告。 |
| 影响范围 | 说明影响 CLI、Core、Skill、Kit / Pack、文档、发布还是用户工作区安全。 |
| 下一步 | 写清需要谁处理，以及是补信息、转 SPEC、开发修复、GitHub 同步还是用户验收。 |
| 验收方式 | 写清如何判断这个 issue 可以关闭。 |

如果必填项暂时无法补齐，也可以先登记，但状态必须保持 `new` 或 `needs_user`，并在“下一步”里写明缺什么信息。

## Issue 状态

| 状态 | 含义 |
| --- | --- |
| `new` | 已记录，但尚未分流。 |
| `triaged` | 已确认类型、优先级和下一步。 |
| `planned` | 已进入路线图、SPEC 或开发计划，等待实现。 |
| `in_progress` | 对应 lane 正在处理。 |
| `needs_user` | 需要用户复现、确认或补充信息。 |
| `resolved` | 已解决，等待必要验收或已完成验收。 |
| `closed` | 已关闭，不再跟进。 |

## Issue 类型

| 类型 | 说明 |
| --- | --- |
| `cli` | CLI 命令、参数、输出、幂等性、安装和发布问题。 |
| `core` | Core 协议、Capability、结构约束和事实源问题。 |
| `skill` | 系统级 Skill、Kit 自带 Skill、Capability Skill 的行为和安装范围问题。 |
| `kit-pack` | Kit / Pack 结构、路径、默认内容和生成规则问题。 |
| `docs` | README、安装指南、用户文档、Agent 文档和 HTML 阅读稿问题。 |
| `release` | npm、版本号、发布包、安装命令和本地更新问题。 |
| `product` | 产品定位、命名、体验、边界和路线图问题。 |
| `workflow` | lane 协作、验收、产物归属和工作流污染问题。 |

## 优先级

| 优先级 | 判断标准 |
| --- | --- |
| `P0` | 阻断 A 测主链路、造成用户工作区损坏、数据丢失或发布包不可用。 |
| `P1` | 明显影响真实用户使用、升级安全、Agent 信任或阶段验收。 |
| `P2` | 影响体验或维护质量，但有可接受绕行方式。 |
| `P3` | 文案、整理、低风险优化或未来可做的改进。 |

## 处理流程

1. 收到反馈后，先分配下一个 `ISSUE-*` 编号。
2. 在 `index.md` 的表格里新增摘要行，至少填标题、类型、优先级、状态、来源和下一步。
3. 按 `template.md` 补完整 issue 单；信息量很大时拆成独立文件，并从 index 摘要行链接过去。
4. 先记录事实：来源、复现方式、影响范围、证据文件、用户可见表现。
5. 分流判断：
   - 如果是实现缺陷，交给 optimization / development lane。
   - 如果是产品边界问题，沉淀到对应 feature 的 SPEC 或 decisions。
   - 如果需要公开协作，创建或关联 GitHub Issue。
   - 如果是文档问题，关联 `product/docs/` 或对应功能档案。
6. 解决后更新 issue 状态、处理结果和验证方式。
7. 已转成 SPEC 的 issue，不要在 issue 表里继续扩写完整方案；方案沉淀到对应事实源，issue 只保留链接和状态。

## 记录原则

- 不把 issue 表写成第二个需求池。
- 不把 issue 表写成开发日志。
- 不把同一个问题散落在聊天、验收报告、SPEC 和 GitHub 里而没有互链。
- 用户真实反馈优先于 dry-run 结论。
- 涉及发布、升级、工作区结构和 Agent 规则污染的问题，必须进入 issue 跟踪，不能只留在聊天里。
