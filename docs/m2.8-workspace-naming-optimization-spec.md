# M2.8 工作台命名体系优化 SPEC

## 背景

本 SPEC 来自 StarWork 产品规划会话对 `satellite`、`hub`、`kit`、`project` 等概念的重新梳理。

当前产品事实已经逐渐清楚：

- StarWork 面向用户不应该暴露三四种工作台类型。
- `Satellite` 不应作为独立产品类型存在。
- `Kit` 是内部结构模板，不适合作为普通用户理解产品时的核心词。
- `Hub / 中枢` 对普通用户来说偏工程化，不够生活化。

因此需要统一 StarWork 的命名体系，让用户只需要理解两个一目了然的对象：

1. 项目工作台
2. 项目中心

## 目标

本轮优化目标是统一产品语言、内部协议字段和文档表达，降低用户理解成本。

最终用户应该能用一句话理解 StarWork：

> 你可以创建一个项目工作台；如果你有很多项目，可以创建一个项目中心，用它统一管理多个项目工作台、共享资料、常用 Skill 和跨项目协作记录。

## 核心决策

### 决策 1：正式对外名称使用“项目中心”

`Hub` 的用户侧表达统一改为：

```text
项目中心
```

原因：

- 比“中枢”更生活化。
- 比“主库”更不技术化。
- 比“多项目管理中枢”更短。
- 和“项目工作台”天然成对。

内部协议字段仍可保留：

```text
hub
```

但对外文档、CLI 文案、Skill 交互应优先说“项目中心”。

### 决策 2：StarWork 对外只讲两种工作台

正式对外概念：

| 用户看到的名称 | 含义 | 内部字段 |
|---|---|---|
| 项目工作台 | 一个具体项目的日常工作区 | `workspace_type: project` |
| 项目中心 | 管理多个项目工作台的共享管理区 | `workspace_type: hub` |

不要再把以下内容作为对外工作台类型：

- Satellite
- 卫星项目
- starter
- local starter
- matter kit
- satellite starter

### 决策 3：Satellite 只是关系，不是类型

原来的 `Satellite` 应改为关系描述：

```text
项目中心里的项目工作台
```

或更短：

```text
中心管理的项目工作台
```

产品解释：

```text
项目工作台可以独立存在，也可以加入项目中心。
加入项目中心后，它仍然是项目工作台，只是多了项目中心同步关系。
```

内部表达可以是：

```text
Project Workspace + Hub Binding = Hub-managed Project Workspace
```

中文产品表达：

```text
项目工作台 + 加入项目中心 = 中心管理的项目工作台
```

### 决策 4：Kit 是内部模板，不作为用户主概念

用户不需要理解 `Kit`。

对外应使用：

- 创建项目工作台
- 创建项目中心
- 从项目中心创建项目工作台
- 安装场景能力
- 自定义工作台结构

内部仍可使用：

- `kit: project`
- `kit: hub`
- `pack: general`
- `hub binding`
- `hub sync overlay`

文档中如必须出现 Kit，应解释为：

```text
Kit 是 StarWork 内部用来生成工作台基础结构的模板。普通用户通常不需要直接理解或选择 Kit。
```

## 用户流程文案

### init 选择工作台类型

推荐文案：

```text
你想创建哪种工作台？

1. 项目工作台
   适合一个具体项目。比如写作项目、产品项目、客户交付、资料整理。

2. 项目中心
   适合同时管理多个项目。它会保存共享资料、项目清单、常用 Skill 和跨项目协作记录。
```

默认推荐：

```text
如果你只是开始一个具体项目，建议先选“项目工作台”。
```

不要再说：

```text
单事务项目
多事务项目
卫星项目
多项目中枢
starter
```

### spawn 说明

推荐文案：

```text
从项目中心创建一个新的项目工作台。
创建后，项目中心会记录这个项目的位置、名称和协作信息。
```

不要说：

```text
生成卫星项目
创建 satellite starter
spawn starter
```

CLI 命令名 `spawn` 可暂时保留，因为它已经是内部和高级用户命令。但文档中要解释为：

```text
spawn = 从项目中心创建项目工作台
```

### doctor / audit 说明

对项目工作台：

```text
检查这个项目工作台的结构是否清楚，AI 是否知道项目状态、当前工作、资料区和成果区在哪里。
```

对项目中心：

```text
检查项目中心是否能正确管理项目清单、共享资料、常用 Skill 和跨项目协作记录。
```

对中心管理的项目工作台：

```text
检查这个项目工作台是否正确连接到项目中心。
```

不要让普通用户先理解：

```text
Hub-like
Satellite
Binding
Overlay
Preset
```

这些词可以留在 JSON 或开发 SPEC 中。

## 产品结构调整

### 正式工作台类型

正式保留：

```text
project
hub
```

对应用户表达：

```text
project = 项目工作台
hub = 项目中心
```

### 中心管理项目的判断方式

不再通过 `kit` 或 `workspace_type` 判断是否为 Satellite。

判断逻辑：

```text
workspace_type: project
+ .starwork/workspace.json 中存在 hub/project center 连接信息
= 中心管理的项目工作台
```

推荐内部字段逐步统一为：

```json
{
  "workspace_type": "project",
  "kit": "project",
  "project_center": {
    "path": "/path/to/project-center",
    "project_id": "example-project"
  }
}
```

兼容期可以继续读取旧字段：

```json
{
  "hub": {
    "path": "/path/to/hub",
    "project_id": "example-project"
  }
}
```

但用户侧文案不展示 `hub`。

### `satellite-starter` 处理

产品判断：

```text
satellite-starter 不应作为正式 Kit 继续维护。
```

原因：

- 它会让用户误以为 StarWork 有第三种工作台。
- 它与 `project` Kit 大量重复。
- 中心管理关系应该由 `project + project_center binding` 表达，而不是由另一个 Kit 表达。

调整方向：

1. 保留 `project` Kit 作为唯一项目工作台基础模板。
2. `spawn` 使用 `project` Kit 创建项目工作台。
3. `spawn` 额外叠加项目中心同步层。
4. `satellite-starter` 目录从正式 Core Kit 中移除或降级为 legacy fixture。
5. 文档中不再把 `satellite-starter` 作为用户可选结构。

## 不做的事

本 SPEC 不要求立刻改 CLI 命令名。

暂不改：

```text
starwork spawn
starwork audit
starwork repair
workspace_type: hub
kit: hub
```

原因：

- 命令名和内部字段已有测试和实现依赖。
- 当前优先级是用户理解和文案一致。
- 等产品语言稳定后，再考虑是否新增更生活化的命令别名。

可以未来讨论：

```text
starwork center create
starwork project create
starwork center add-project
```

但 v0.1 不引入。

## 实施计划

### Phase 1：产品语言事实源

1. 新增本 SPEC。
2. 在 `product/docs/README.md` 登记本 SPEC。
3. 在产品方向文档中写入两类工作台命名。

验收：

- 有一个清晰文档能解释“项目中心 / 项目工作台 / 中心管理的项目工作台”。
- 文档明确 `Satellite` 不再是正式类型。

### Phase 2：文档清理

1. 清理 README 和 roadmap 中的旧五类 Kit 说法。
2. 清理 HTML 文档标题和导航中的 Hub/Satellite 用户侧表达。
3. 将 `hub-management.html` 改名或标题改为“项目中心管理”。
4. alpha 测试文档改成“创建项目中心 / 从项目中心创建项目工作台”。

验收：

- 用户从 README 到 alpha test guide 不需要理解 Satellite。
- 不再出现 `local-starter`、`local-matter`、`satellite-matter` 作为当前正式结构。

### Phase 3：Skill 交互文案

1. `starworkInit` 改用“项目工作台 / 项目中心”。
2. `starworkSpawn` 改用“从项目中心创建项目工作台”。
3. `starworkDoctor` 改用用户可理解的诊断语言。

验收：

- Skill 描述和输出不再要求用户理解 Hub/Satellite/Kit。

### Phase 4：CLI 文案和状态模型

1. `init --help` 和 dry-run 文案改为“项目工作台 / 项目中心”。
2. `spawn --help` 和 dry-run 文案改为“从项目中心创建项目工作台”。
3. `doctor` / `audit` 的人类可读输出减少内部术语。
4. 新建中心管理项目时，在 workspace state 中增加 `project_center` 字段。
5. 继续兼容旧 `hub` 字段。

验收：

- CLI 输出可以给非技术用户直接看。
- JSON 仍保留机器可读内部字段，不破坏旧测试。
- 新 workspace state 能表达“加入项目中心”关系。

### Phase 5：Kit 结构收敛

1. 将 `satellite-starter` 从正式 Core Kit 体系中移除或移到 legacy/fixtures。
2. `spawn` 改为始终基于 `project` Kit。
3. 项目中心同步说明作为 overlay 生成。
4. 清理 `product/core/presets/satellite-starter.yaml`。

验收：

- Core 正式 Kit 只剩 `project` 和 `hub`。
- `spawn` 生成的是 `project` Kit + 项目中心连接。
- `doctor` 能识别旧 `satellite-starter`，但不推荐新建。

## 风险

### 风险 1：内部字段和用户文案不一致

短期内内部仍会保留 `hub` 字段，用户文案使用“项目中心”。

应对：

- 文档明确 `hub` 是内部字段。
- CLI JSON 保留内部字段，人类可读输出使用用户词。

### 风险 2：旧文档残留造成二次混乱

项目里历史文档很多，容易出现 `satellite-starter`、`卫星项目`、`中枢` 残留。

应对：

- 用 `rg` 建立术语清理清单。
- 先清用户入口文档，再清内部 SPEC。
- 内部历史判断文档可以保留旧词，但必须标注“旧称”。

### 风险 3：过早改 CLI 命令名

如果现在直接改 `spawn`，会影响测试、README、用户命令和已发布包。

应对：

- v0.1 只改文案，不改命令名。
- 未来如需更生活化命令，新增别名，不删除旧命令。
